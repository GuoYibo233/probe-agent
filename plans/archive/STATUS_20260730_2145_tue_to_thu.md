## 先把代号讲清楚

后面所有节都要用到这些词，先在这里一次讲完。

**三个环境。** 探针不是训一个通用的，而是在三个互不相干的测试场景里各训一个。第一个叫 bfcl，一个公开的工具调用评测集，用的是它里面多轮对话那一类题：用户来回说几轮话，agent 得在中间调用函数；它的工具种类少、参数格式固定。第二个叫 appworld，一个模拟的手机应用世界，agent 在里面完成订票、发消息这类任务，工具多、参数复杂。第三个叫 tales，一批文字冒险游戏，agent 用文字指令去玩，它能说出来的话几乎没有边界，账上把这一点叫开放动作空间，意思是没有一份固定的动作清单可选。

**三代训练。** 探针一共训了三代，代号 v2、v2fix、v3。v2 是第一代，浮点格式设错了，模型几乎没学动，整批作废、不能引用。v2fix 是把浮点格式改对之后重训的一代。v3 是又补了一批轨迹、样本量翻倍之后重训的一代。还有一个 v3_1，是在 v3 的基础上把 bfcl 的另一种模型轨迹并进去之后的数据集。

**产生轨迹的模型，跟探针不是一回事。** 轨迹是 agent 做完一个任务的完整记录，用来当探针的训练数据。产生轨迹的模型有两种：阿里的 Qwen 系模型（账上写 qwen），和 OpenAI 放出权重的 gpt-oss-120b（账上写 gpt-oss）。探针自己是另一个模型，ModernBERT-base，它只做分类、不做生成。

**C1 到 C4 是论文的四个部分。** C1 是动机部分，用公开的多跳问答数据集 HotpotQA 做注入实验，说明提前拿到工具结果值钱、而且什么时候拿有讲究。C2 是探针本体，也就是能不能从思考文本里提前看出工具调用，又分两半：C2-2t 是离线的，把存好的轨迹重读一遍模拟判断；C2-3 是把探针接进真跑的 agent，账上管这件事叫闭环。C3 是一个新的测评基准，把速度和准确率两条学习曲线画在一张图里。C4 是会师，把自己的探针当成一个参赛选手放到 C3 的基准上跑，产论文的旗舰图。

**T 后面跟数字的是任务编号。** `plans/2026-07-30-task-plan.md` 把要干的事编成 T0 到 T16，就是待办清单的行号。

**判定探针合格的三条标准**，在开跑之前就定死了：触发时的预测准确率要到 95%（也就是探针决定触发的那些事件里，猜对工具的比例）；触发比例不能太低（也就是全部事件里探针触发的比例不能接近零）；还要高过先验基线（先验基线的意思是不动脑子，永远猜训练集里出现最多的那个工具，这么做能猜对的比例）。三条同时满足叫**达标**，差一条就叫**不达标**。

## 第二节 · 每个实验详解

### 线 1 · 探针主线（C2-2t，9 条记录，全部跑完）

**问的是什么。** agent 在调用工具之前会先写一段思考文本。问题是：能不能在它还没写完的时候，就从这段半成品文本里看出它接下来要调哪个工具，而且准到敢替它先把这个工具调出去。

**怎么做的。** 把 agent 做任务留下的轨迹切成样本。一个事件是轨迹里的一次工具调用，连同它前面那段思考；把这段思考按句子边界切开，每切一次就得到一条样本，样本的内容是任务描述加上历史加上思考的前缀，标签是这次实际调用的工具名。样本按任务实例分成四堆：七成拿去训练，一成叫拟温度堆，用来拟合温度（一个把模型输出的分数拉成可信概率的参数），一成叫扫门槛堆，用来找触发门槛，最后一成叫测试堆，留出来不参与训练。

训练完之后跑回放。回放的意思是把测试堆那一堆轨迹按原顺序重读一遍，每个事件从思考的第一句开始一句一句送进探针，探针的置信度第一次超过触发门槛的那一刻，就记下它此刻猜的工具，跟这个事件真实调用的工具对一下。门槛调高，探针触发就少但准；门槛调低，触发多但错得多。所以要在门槛上扫一遍，找有没有一个门槛能同时满足前面说的三条标准。

**为什么这么设计才算数。** 三条标准里最硬的是 95% 这条，理由是投机执行猜错要付真代价——提前发出去的调用如果是错的，要么白花钱，要么把 agent 的状态搞坏。高过先验基线这条是防止把照猜当成学到：tales 里最常见的那个工具本身就占 67.2%（v2fix 那一代的数），一个什么都不学的模型照猜也有 67.2% 的准确率，所以探针的成绩必须明显高过这个数，否则分不清它是学到了东西还是在照猜。触发比例不能太低这条防的是另一种情况：把门槛调到 0.999，准确率能到 100%，但一万个事件里只触发三次，工程上用不上。

这个设计覆盖不到的地方：回放是离线模拟，探针给出的判断没有真的去执行，所以它算出来的省 token 是估算，不是实测。实测要等闭环那条线。

**看一条真的。** 下面这条是 `envs/bert_data/v3/bfcl/train.jsonl` 的第 1 条记录，一条真实的训练样本。`text` 字段装的是喂给探针的全部文字，原文照贴、不翻译：

```

[HISTORY]
(start)
[THINKING]
The user wants to move a file called 'final_report.pdf' from the 'document' directory to a 'temp' directory within the 'document' directory.
```

这条样本的标签（`label` 字段，装的是这个事件真实调用的工具名）是 `cd`。也就是说，agent 想搬文件，但它下一步实际发出的调用是切换目录。这条样本是这个事件切出来的第一条（`sent_idx` 字段为 0，装的是这是思考的第几句；`n_sents` 字段为 24，装的是这个事件的思考一共切出 24 条），`depth` 字段为 0.1863，装的是这一条落在整段思考的百分之多少处。产生这条轨迹的模型是 `qwen3.5-27b`（`model` 字段）。

### 线 2 · 因果探针（T8，1 条记录，跑完）

**问的是什么。** ModernBERT 每探一次要把整段前缀重读一遍，思考越长、探得越勤，总开销涨得越快。问题是：换成一个只能从左往右读的语言模型当底座，读过的部分缓存下来不重读，成绩掉多少、开销省多少。

**怎么做的。** 两个底座各训一遍：Qwen3-0.6B-Base 和 LFM2.5-350M-Base。做法是把整段文本一次前向送进去，在每个句子边界的位置放一个分类监督，训完的评测走跟 ModernBERT 完全一样的回放协议，所以两边的数字可以并排。

**为什么这么设计才算数。** 评测协议一致是这条线成立的前提。如果因果探针换了评测方式，它跟 ModernBERT 的成绩差就分不清是模型造成的还是评测方式造成的。另外开训之前强制过一道对齐检查：同一段文本，整段一次前向，和按分块增量前向的方式送进去，末位置输出的分数必须逐位一致才许开训。这一步是因为混合架构的模型在缓存非空又一次喂多个 token 的时候有过静默算错的前例，算错了不会报错，只会训出一个看起来正常、其实算错了的模型。

**看一条真的。** 这条线和线 1 用的是同一批样本，样本长什么样见线 1 那一条。它的输出格式也和线 1 一样，下面是 `envs/bert_runs/appworld_v3_causal_qwen/REPLAY_REPORT.json` 里冻结测试堆那一节的原始内容：风险 0.05 档门槛 0.975、事件数 791、触发比例 0.3338、触发时的预测准确率 0.9621、提前量 0.356、错误投机率 0.0126。

**实验结果。** 风险 0.05 档（要求 95% 准确率）的数字，两个底座各一套，都来自 `envs/bert_runs/<环境>_v3_causal_<底座>/REPLAY_REPORT.json`：

| 环境 | Qwen3-0.6B 准确率 / 触发比例 | LFM2.5-350M 准确率 / 触发比例 |
|---|---|---|
| bfcl | 0.9779 / 0.8009 | 0.9515 / 0.9115 |
| appworld | 0.9621 / 0.3338 | 0.9513 / 0.4412 |
| tales | 0.9077 / 0.6373 | 0.9225 / 0.6324 |

`ops/runs.jsonl` 里只汇总了 Qwen3-0.6B 这一套的三个准确率和 appworld 的触发比例，上表其余六个数只在硬盘上，没有进账。

探测开销比（原始字段名 `cost_ratio`，装的是 ModernBERT 探完一条轨迹的计算量除以因果探针探完同一条轨迹的计算量）：bfcl 19.8、appworld 26.4、tales 34.1。tales 这一条在风险 0.1 档上，从扫门槛堆选出来的门槛搬到测试堆之后没能维持住准确率。

把 tales 的窗口从 4096 个 token 放宽到 8192 个的对照（Qwen3-0.6B 底座）：准确率从 0.9077 变成 0.9385，触发比例两边都是 0.6373。账上给这次对照的结论字段写的是"噪声级收益，窗口非瓶颈"。

**值得注意的设置细节。**

LFM2.5 这个底座在 transformers 5.14.1 上，按分块增量前向的方式喂数据仍然会静默算错。所以对齐检查的结论是：这个底座只能整段一次前向、或者一个 token 一个 token 喂，禁止分块。

对齐检查的判定口径改过一次。8192 窗口下 fp32 的舍入误差绝对值顶到 1.1e-4，超过原来定的 1e-4 门槛，但相对误差只有 1.7e-6。所以判定从看绝对差改成看相对差，并加了一个命令行参数 `--align-tol` 用来调这个门槛，默认值仍是 1e-4。

LFM2.5 的许可不是 Apache。论文里要如实标注。

### 线 3 · 三个对照实验（T5 消融 / T6 跨模型 / T7 抽取头，4 条记录，都在跑）

**问的是什么。** 三件事：一，探针的本事到底来自思考文本还是来自历史（消融）；二，用一种 agent 模型的轨迹训出来的探针，换到另一种模型上还灵不灵（跨模型）；三，除了猜对工具名，能不能把参数的值也提前定位出来（抽取头）。

**怎么做的。** 消融的做法是给训练脚本加一个输入模式开关，把样本里的 `[THINKING]` 段整段切掉训一遍，再把 `[HISTORY]` 段整段切掉训一遍，其他一切不动，跟完整输入的成绩比。跨模型的做法是按样本的 `model` 字段把轨迹分成 qwen 侧和 gpt-oss 侧，训练侧乘测试侧凑成四格，每格报两种校准：一种是拟温度堆和扫门槛堆都用训练侧的数据（账上叫冷迁移，意思是换了模型之后什么都不重新调），一种是只把这两堆换成测试侧的数据、模型权重不动（下面叫只换校准）。三个环境各做一套这样的四格。抽取头的做法是在探针上加第二个输出头，输入里拼上"工具名点参数名"指明要找哪个参数，输出这个参数的值在文本里的起止位置，而且必须支持输出"抽不到"。

**为什么这么设计才算数。** 消融只砍一段、其他全不动，掉下来的成绩才归得到被砍的那一段头上。跨模型做双向而不是单向，是因为只做一个方向没法区分"探针不通用"和"某一侧数据本身更好"。抽取头必须能说"抽不到"，是因为触发的时候参数的值常常还没写出来——任务清单里引用的一个先行试点数据是：提前 25 个 token 的时候，参数的字面串只有 33.8% 已经出现在文本里。这个先行试点没有对应的实验记录落在这个窗口内，账上查不到它的出处；不给这个模型一个说"抽不到"的选项，它只能硬指一个位置。

**看一条真的。** 消融砍的就是线 1 那条样本里 `[THINKING]` 和 `[HISTORY]` 这两个标记后面的内容。以线 1 那条样本为例，砍掉思考段之后剩下的是任务描述加上一个空历史；砍掉历史段之后剩下的是任务描述加上那句思考。

**实验结果。** 账上这四条记录的 `status` 字段都还是 `running`，`ops/runs.jsonl` 里没有它们的收尾记录（一条实验跑完要追加一条带结论和数字的记录，缺了它这条实验在账上就永远是在跑），所以**账上没有结果**。

硬盘上已经有 4 份消融的回放报告落地了（`envs/bert_runs/*_v3_no*/REPLAY_REPORT.json`），风险 0.05 档的数字是：bfcl 砍历史 准确率 0.9817、触发比例 0.4823；bfcl 砍思考 准确率 0.9412、触发比例 0.0752；appworld 砍思考 准确率 0.8889、触发比例 0.1252；tales 砍思考 准确率 1.0、触发比例 0.0294。这四个数没有进 `ops/runs.jsonl`。

**值得注意的设置细节。**

消融里砍思考那一档改了评测方式：一个事件的所有样本合并成一条，原来按样本分配的权重按条数摊平，报的是普通准确率，因为思考被砍掉之后回放协议退化成每个事件只读一次，没有"一句一句喂"这个过程了。所以砍思考的触发比例和完整输入的触发比例**不是一个口径**。

GPU 台账里有一处不一致：`ops/jobs.json` 的 `active` 字段（装的是当前登记为在跑的任务，每条带机器名、卡号、tmux 会话名和日志路径）里，消融这个任务登记占用 tokyo106 这台机器的 0 到 3 号卡，bfcl 混训那个任务也登记占用 tokyo106 的 3 号卡。同一张卡挂着两个任务名。硬盘上 bfcl 砍历史的报告已经生成，说明 3 号卡上原来那条已经跑完，但台账没有把它从在跑名单里划掉。

### 线 4 · 采集轨迹并合进数据集（T1 + T3，1 条记录，跑完）

**问的是什么。** bfcl 这个环境原来的轨迹全是 qwen 系模型产生的，缺另一种模型的。跨模型那条线要是缺 bfcl 这一列，"换 agent 模型探针还能不能用"这个结论就只有两个环境的证据。

**怎么做的。** 用 gpt-oss-120b 跑 bfcl 的 200 个任务，收 200 条轨迹，然后合进数据集——账上把"合进数据集"这个动作叫建库，指的是把散在各处的轨迹文件重新解析、切成样本、按四堆分好，产出一个新版本号的数据集目录。收的时候卡两条判据：思考文本非空、发出的调用能被解析出来。

**为什么这么设计才算数。** 两条判据缺一不可。思考非空是因为探针读的就是思考，思考是空的轨迹对训练没有任何用；调用能解析是因为标签就是从调用里抽的，解析不出来这条轨迹没有标签。

**看一条真的。** 账上记的是 `n_traj=200`（收到的轨迹条数）和 `think_nonempty=200`（其中思考非空的条数），两个数相等，说明 200 条全过。

**实验结果。** 200 条轨迹全部落盘，两条判据全过。并入数据集之后，bfcl 的事件数从 2265 涨到 3325（`bfcl_events_v3_1` 字段，装的是合并成 v3_1 版本之后 bfcl 这个环境的事件总条数）。重新建库两次，产物逐字节一致。

v3 数据集三个环境的训练样本条数：tales 142621、appworld 71002、bfcl 25061（这三个数记在 `20260730_0056_bert_probe_v3` 这条记录的参数字段里，是 v3 这个版本的数，不是并入 gpt-oss 轨迹之后那个 v3_1 版本的数）。

**值得注意的设置细节。**

合进数据集的脚本修过一个排序问题。原来它用递归通配符去找文件，返回的顺序是不定的，又按 id 去重，两次重建出来的事件数会在 2265 和 2267 之间飘。修完之后才建的 v3_1，验收的时候做了两次重建逐字节对比。

### 线 5 · C1 收尾（T11，1 条记录，跑完）

**问的是什么。** C1 这一块的主张是"提前拿到工具结果值钱，而且什么时候拿有讲究"。这条实验补的是两个边界：多跳问题的两种类型分开报，以及换随机种子重跑，看结论稳不稳。

**怎么做的。** 用 HotpotQA 的题，模型是 Qwen3-8B。做法是在模型生成到不同位置的时候，把工具的返回结果直接插进它的上文里（账上把这个动作叫注入），看答对率和花的 token 怎么变。两种题型分开：一种是两跳互相独立（问两个东西然后比较），一种是两跳有依赖（第二跳要用第一跳的答案）。温度设 0.6，换三个生成种子（1、2、3）各跑一遍，每种题型 40 题，分 8 片并行。

**为什么这么设计才算数。** 温度不为零的时候模型每次答的不一样，单跑一遍得出的结论可能只是运气。三个种子跑出来的结论如果一致，才敢说是真的。两种题型分开报是因为混在一起会被问"这个效应是不是只在其中一类上成立"。

**看一条真的。** 下面是 `hotpot_inject/results_t11/hp8b_T06_s1_shard0of8.jsonl` 的第 1 条记录，字段照抄：

题目编号 `5adbf0a255429947ff17385a`，题型 comparison（两跳独立），条件 baseline（不注入，当对照），温度 0.6，生成种子 1。模型答出来的话是：

```
No, the Laleli Mosque is located in the Laleli district of Fatih, while the Esma Sultan Mansion is in the Ortaköy neighborhood of Beşiktaş
```

这条判对（`em` 字段为 True，装的是答案和标准答案是否完全一致）。它调了 2 次工具（`n_calls` 字段），两次调用分别在第 157 和第 211 个 token 的位置发出（`call_toks` 字段），整题生成了 403 个 token（`gen_tokens` 字段），花了 16.5 秒（`wall_s` 字段）。

**实验结果。** 一共 1338 条记录（`n_records` 字段，装的是这一批落盘的结果条数），3 个种子。账上没有记 1338 这个数是怎么由题数、种子数、注入位置数乘出来的。两个数：两跳独立那一类，注入得太早会掉 0.18 的宽松判对率（`comp_early_soft_drop` 字段；宽松判对指的是不要求答案和标准答案完全一致，账上没有记它具体用的是哪种匹配规则）；两跳有依赖那一类，存在一个区间，在那里注入既不省 token 也不帮忙，账上记的是 -153 个 token（`bridge_deadzone_dtok` 字段）。账上的结论字段写的是三条主线结论跨三个种子都稳，但只列出了上面这两个数，第三条是什么没有记。

**值得注意的设置细节。**

两跳有依赖那一类的第二跳子集样本量小，账上已经标注了这一点。

### 线 6 · C3 基准装配（T12，5 条记录，4 条跑完 1 条在跑）

这条线有五个互相独立的零件，下面分开讲。

#### 6a · 存解法全矩阵（周二跑的那条）

**问的是什么。** 让 agent 把做过的题的解法存下来、下次做题之前放进提示里，跟什么都不存、每道题从零开始做相比，要处理的文字总量是变多还是变少。

**怎么做的。** 环境是 ALFWorld，一个用纯文字描述的家务模拟器：模型读到一段描述房间的文字，然后一条一条发出动作指令，系统再把这条指令的结果用文字回给它。从模型接到一条任务指令到系统判定成败，这一整个过程叫一轮。模型是 Qwen3-8B，解码时每一步都取概率最高的那个词。

两种条件各完整连做十轮，不是两种条件分掉十轮。存解法这一边，每做完一轮，如果这一轮做成了，就把这道题的原文和做成功的那串动作指令存下来；下一轮开始之前取最近五轮，这五轮里做成了的才放进提示、整段放在最前面，所以提示里的解法最多五条，最近五轮有几轮没做成就不足五条。不存解法这一边，每一轮都从零开始。

题目按"下一轮和前面做过的有多像"分三档。完全一样的题是同一道题原封不动重复十轮。几乎一样的题是任务要求的文字相同、换一个房间布置。同类但换了东西的题是任务模板相同、都是把某个物品放到某个容器上，但要放的物品和目标容器换成别的种类。三档乘两种条件乘五个随机种子（编号 0 到 4）等于三十次"连做十轮"，一共三百轮。

**为什么这么设计才算数。** 两种条件之间只差一样东西：一轮做完之后解法存不存、放不放进下一轮的提示。题目、模型、解码方式、出题顺序全都一样，随机种子逐轮对齐，所以差别只能来自存不存解法。

判定标准在开跑之前就定死：把发给模型的 token 和模型写出来的 token 加在一起算总量。定这个标准的理由是，存下来的解法要整段放进提示、模型每一步都要重读一遍，所以存解法一定会让发进去的 token 变多，换来的是模型少发几条指令。如果换成只统计模型写出来的 token，存解法那一边就不可能输，因为它多花的那部分根本没被算进去。

分三档而不是只跑一档，是为了看出结论在哪一档反转。只在完全一样的题上测会得出"存解法有用"，只在换了东西的题上测会得出"存解法有害"。

这个设计覆盖不到两件事。第一，做成的轮数在两种条件下三档完全相同：几乎一样的那档五十轮全做成，完全一样的那档五十轮里做成三十轮，同类但换了东西的那档做成四十二轮。也就是说这批题上，存不存解法对做成多少题没有产生任何差别。第二，只存做成功的解法，所以模型本来就做不成的题攒不下任何能用的东西。

**看一条真的。** 下面这些来自 `fig1_pilot/results/8bfull_L1_mem_s0.jsonl`（几乎一样的题这一档、存解法那一边、种子 0），取前四轮。

第 0 轮的任务原文（`task` 字段，装的是环境给模型的那句任务指令）：

```
put a toiletpaper in toiletpaperhanger.
```

模型在第 0 轮实际发出的五条指令（`actions` 字段，装的是这一轮按顺序发出的全部指令）：

```
go to toilet 1 → go to countertop 1 → take toiletpaper 2 from countertop 1 → go to toiletpaperhanger 1 → move toiletpaper 2 to toiletpaperhanger 1
```

第 2 轮开跑的时候，提示最前面多出来的那段解法长这样。这段文字是按代码里拼接解法的逻辑、用第 0 轮和第 1 轮的记录重建出来的；原始文件里没有存下这段完整字符串：

```
=== experience from earlier similar tasks ===
Task: put a toiletpaper in toiletpaperhanger.
Successful actions: go to toilet 1 -> go to countertop 1 -> take toiletpaper 2 from countertop 1 -> go to toiletpaperhanger 1 -> move toiletpaper 2 to toiletpaperhanger 1

Task: put some toiletpaper on toiletpaperhanger.
Successful actions: go to drawer 1 -> open drawer 1 -> go to toilet 1 -> take toiletpaper 1 from toilet 1 -> go to toiletpaperhanger 1 -> move toiletpaper 1 to toiletpaperhanger 1
```

存解法存的就是这个东西：一行任务原文，一行做成功的指令序列。没做成的不存，房间里看到的陈设不存。

前四轮的数字，两种条件并排。"步数"是这一轮发出的指令条数（`steps` 字段），"读进"是这一轮里每一步发给模型的提示 token 数加总（`tokens_in` 字段），"写出"是这一轮里模型生成的 token 数加总（`tokens_out` 字段）：

| 轮 | 任务原文 | 存解法 步数/读进/写出 | 不存解法 步数/读进/写出 |
|---|---|---|---|
| 0 | put a toiletpaper in toiletpaperhanger. | 5 / 2901 / 3765 | 5 / 2901 / 3765 |
| 1 | put some toiletpaper on toiletpaperhanger. | 6 / 3226 / 4620 | 5 / 2268 / 4367 |
| 2 | put a toiletpaper in toiletpaperhanger. | 4 / 2669 / 1184 | 4 / 2115 / 3594 |
| 3 | put a toiletpaper in toiletpaperhanger. | 4 / 2873 / 2407 | 4 / 2057 / 2646 |

第 0 轮两边三个数完全一样。第 0 轮的时候还没有任何解法可放，两边的提示逐字相同。

**实验结果。** 下面所有百分比的算法统一是：存解法那一边的数减去不存解法那一边的数，再除以不存解法那一边的数。分母一律是不存解法那一边，正号表示存解法花得更多，负号表示花得更少。总量是这一档五十轮的数字全部加起来的合计，不是平均。

| 档 | 存解法 总量 | 不存解法 总量 | 差 | 存解法 做成 | 不存解法 做成 |
|---|---|---|---|---|---|
| 完全一样的题 | 1005290 | 1112570 | −9.6% | 30 / 50 轮 | 30 / 50 轮 |
| 几乎一样的题 | 417666 | 357630 | +16.8% | 50 / 50 轮 | 50 / 50 轮 |
| 同类但换了东西的题 | 1094894 | 915116 | +19.6% | 42 / 50 轮 | 42 / 50 轮 |

只看种子 0 这一个种子（也就是十轮的合计）：完全一样的题 存解法 52143、不存解法 38500、差 +35.4%；几乎一样的题 存解法 68688、不存解法 71526、差 −4.0%；同类但换了东西的题 存解法 248818、不存解法 237368、差 +4.8%。

**值得注意的设置细节。**

相似度档的编号有两套，取值正好颠倒。写实验脚本的时候，代码里给这三档的标签是 `L0`、`L1`、`L2`：`L0` 是完全一样的题、`L1` 是几乎一样的题、`L2` 是同类但换了东西的题。后来定下来的正式编号反过来数：完全一样的题是 `L2`、几乎一样的题是 `L2⁻`、同类但换了东西的题是 `L1`。两套编号里 `L1` 和 `L2` 这两个符号都存在，指的却不是同一档。原始数据的文件名用的是代码那一套，写进正式文档的数字用的是正式那一套。引用的时候不先查清楚手上这个数字属于哪一套编号，就会把"同类但换了东西的题上存解法净亏"写成"完全一样的题上存解法净亏"，两个档一个是省一个是亏，正好说反。

耗时没有进报告。存解法那一边的耗时比不存解法那一边低 7% 到 12%，这个区间是三档各自算出来的三个数的范围。但这三十次"连做十轮"不是全在同一型号的显卡上跑的，不同型号跑同样的计算花的时间本来就不一样，所以耗时之间不能比。出报告的时候把耗时这一整列删掉了。

完全一样的题这一档、不存解法那一边，**在同一个种子内部**十轮的数字逐字相同：这一档的十轮是同一道题、同一套房间布置，解码时每一步又都取概率最高的那个词，所以模型每一轮的行为完全重复。但**五个种子之间差别极大**，因为每个种子抽到的是不同的题。逐种子从原始文件里直接数出来的每轮写出 token 数是：种子 0 是 1191、种子 1 是 4538、种子 2 是 13778、种子 3 是 2670、种子 4 是 12195。聚合报告里那个 6874，是这五个数的平均，不是任何一轮的实际值。

这一档做成的三十轮也不是平均摊在五个种子上：种子 0、1、3 十轮全做成，种子 2 和种子 4 十轮全没做成。两种条件做成的轮数在这一档完全相同，就是因为不存解法那一边每个种子的行为固定，做得成做不成由抽到哪道题决定。

"连做十轮"和"取最近五轮"这两个数是当初定下来就没再动过的，账上没有记为什么定这两个数。另外，这条记录的结论字段里写着"8B 红利小于 4B"，意思是同一套做法在一个 4B 模型上先跑过一次、省得比 8B 多；那次先跑的实验记录不在这个窗口内，本文档查不到它的数字。另外两档为什么两种条件做成的轮数也恰好相同，原始记录里没有留下说明。

#### 6b · 完美复用上限

**问的是什么。** 假设复用做到完美无损——凡是之前做过的题，这次一个字都不用重新生成，直接把上次的答案搬过来——最多能省多少。这个数是给上面那条实验的真实成绩定一个上限。

**怎么做的。** 不重新跑模型，直接在上面那条实验里"不存解法"那一边已经存好的记录上算：对每一轮，看它是不是跟前面某一轮完全同一道题，是就假设它零成本，不是就照原样计费。

**为什么这么设计才算数。** 这个上限只算逐字复用，所以它管不住任何靠泛化省下来的部分。也就是说，真实成绩如果超过这个上限，多出来的部分一定不是靠照搬来的。

**看一条真的。** `benchmark_design/ORACLE_CEILING_8bfull.md` 里同类但换了东西的题那一档，十行逐轮的数字全是"+0.0%"，可替换集占比全是"0/5"——这一档十轮里没有任何一轮和前面某一轮是同一道题，所以逐字复用在这一档没有定义，上限等于不存解法本身。表里"可替换集占比"这一列的分母 5 是这一档的五个随机种子，分子是其中有多少条能找到可以照搬的前轮。

**实验结果。** 完全一样的题这一档，上限是省 21.0%、23.4%。前一个数是把十轮的成本加总之后算的，后一个数是每一轮各算一次省了多少再取平均。另外两档都是 0%。符号约定跟 6a 一致：这里说"省 21.0%"，写进第三节的对照表时记作 −21.0%。

**值得注意的设置细节。** 这条实验是纯 CPU 后处理，没有占显卡。它跑在那批带有两套编号问题的数据上，账上记的字段名 `ceiling_L2_total` 用的是正式编号，指的是完全一样的题那一档。

#### 6c · 真实负载相似度（周一跑的那条）

**问的是什么。** 上面那些实验都假设"相似的任务会反复出现"。这条实验查的是这个假设在真实负载里成不成立。

**怎么做的。** 拿一批真实的编程 agent 使用记录来算：357000 次交互、4265 个会话，其中可用的 3594 个（账上没有记判定一个会话可用的标准是什么）。这里的"次交互"跟 6a 定义的"一轮"不是一个东西，6a 的一轮指做完一道题，这里的一次交互指一来一回。两个会话之间的相似度，算的是它们各自调用工具的次数向量的余弦相似度。

**为什么这么设计才算数。** 这批记录的内容已经脱敏，所以只能测出"调用的工具构成有多像"，测不出"任务内容有多像"。这是这条实验管不住的地方，论文里已经声明了这条边界。

**看一条真的。** `tracelab_analysis/RESULTS_v0.md` 里的原文写法是"相邻 session 相似度:p50=0.93"，意思是把每个会话和它前一个会话算相似度，这些数排序之后中位数是 0.93。

**实验结果。** 相邻会话的相似度中位数 0.93；大于 0.8 的占 68.4%，0.3 到 0.8 的占 17.2%，小于 0.3 的占 14.5%。96.1% 的会话在往前数 50 个的窗口里能找到一个相似度大于 0.8 的前驱，这个距离的中位数是 1、九成位数是 4。相似度大于 0.8 的那些配对里，10.8% 分属不同的项目。

**值得注意的设置细节。** 相似度只按工具调用次数算，不看内容。这批数据是外部记录，不是自己跑出来的。

#### 6d · 六个记忆系统冒烟

**问的是什么。** C3 这个基准需要一批对照选手。这条实验验的是：六个别人做的记忆系统，接进自己的评测流程之后能不能跑通。

**怎么做的。** 模型统一换成 Qwen2.5-7B-Instruct，六个系统各跑 15 道题，走完整链条：拼提示、跑一轮、抽答案、抽答案、评分、把结果回填进记忆。评分的代码同时实现了完全一致和词重叠两种算法，但这次冒烟的判定只用了完全一致这一种。

**为什么这么设计才算数。** 冒烟指的是只验"整条链子能不能从头跑到尾、中间报不报错"的一次小规模试跑，不看成绩。所以这次的判定标准是跑通不报错，不是分数高。这批题是闭卷的两跳题，分数低本来就在预期内，所以这条实验不拿分数做任何判断。

**看一条真的。** 下面是 `benchmark_design/l3_2wiki_items.jsonl` 的第 1 条题目，字段照抄：

题号 `2wiki/train/l3_two_hop/000000`，题目：

```
What is the date of birth of the director of film Amateur Crook?
```

标准答案 `July 7, 1901`。这道题的推理链（`chain` 字段）是两跳：先从电影 `Amateur Crook` 查到导演 `Sam Katzman`，再从 `Sam Katzman` 查到出生日期 `July 7, 1901`。中间那个人名 `Sam Katzman` 是两跳的接头（`junction_entity` 字段）。造这道题用的随机种子是 20260729（`rng_seed` 字段）。

**实验结果。** 六个系统全部跑通，报错 0 次。六个系统在 15 道题上的完全一致答对率：两个自家写的检索基线各 0.2，另外四个引用别人方法的系统都是 0.0。每道题调用模型的次数不等：ReMem 在 15 道题上共调 58 次；DC-Cu 和 DC-RS 各在 15 道题上共调 30 次，也就是每题 2 次；剩下三个每题 1 次。

**值得注意的设置细节。**

这次冒烟暴露了两个可以分开修的问题：其中四个系统的答案抽取没有处理长句，以及判定只用了完全一致、没有用词重叠。账上这条记录的结论字段把这两条列为"正式跑分前处理"。

六个系统里有四个是照别人的方法重建的，这四个另有一份保真度核对记录（`benchmark_design/FIDELITY_T12C.md`）。核对表逐个点名给了判语：ReMem 在多轮设定下忠实、单轮设定下简化但方向一致；DC-Cu 标"失真需声明"；DC-RS 也标"失真需声明"，而且原方法里"先检索再整理再作答"这个用来区分它和 DC-Cu 的机制在重建版里没有实现；AWM 在单轮设定下机制完全缺失，核对表建议不报这个系统。剩下两个 ExpRAG 和 ExpRecent 是自家写的检索基线，不在核对范围内。

账上这条记录的结论字段还写了一条：每道题调用模型的次数不等这件事计入 token 账，否则不同系统之间的成本不可比。

#### 6e · 全历史塞上下文第三臂（在跑）

**问的是什么。** 6a 那条实验只有两种条件：存解法和不存解法。这条实验加第三种，把之前所有轮的完整记录全塞进提示，超出预算就从最旧的开始丢。账上把每一种条件叫一条臂，所以这条新加的叫第三臂，前两条臂就是 6a 的存解法和不存解法。它的作用是给存解法那一条臂当参照上界。

**怎么做的。** 三档各占一张卡，同一张卡上先跑不存解法再跑第三臂，这样两边的耗时可以比。种子沿用 0 到 4，跟前面那条实验逐轮配对。预算 24576 个 token。

**为什么这么设计才算数。** 同卡先后跑是为了让耗时可比——前面那条实验就是因为跨型号显卡跑而丢掉了整列耗时数据。改代码的时候做了逐字节对比：存解法和不存解法两条臂的产物跟改之前完全一致，25 项单元测试全过，所以第三臂的加入没有污染原来两臂。

**实验结果。** 账上 `status` 字段是 `running`，没有 finish 记录，**账上没有结果**。

**值得注意的设置细节。** 预算截断的规则是：以整轮为单位丢，最旧的那一轮先丢；丢到只剩最后一轮还超预算时，保留这一轮的开头、从中间按对话来回次数切断。

### 线 7 · 闭环（T9 + T10，0 条实验记录）

**问的是什么。** 前面所有数字都是离线回放算出来的估算。闭环要回答的是：把探针接进真跑的 agent，真发调用、真掐表，省下来的 token 和时间是多少。

**怎么做的。** 计划里是三个环境乘五种跑法（账上管这五种叫五个口径，为了不和前面"这两个数不是一个口径"里的口径混起来，本文档一律叫跑法）。基线是不带探针原样跑。截断是探针一触发就停止生成思考、直接提交预测的调用。预取是只读的调用先在后台执行，等 agent 自己发同一个调用的时候，把后台执行的结果和 agent 想发的调用核对一遍，一致就把结果直接交给 agent，省掉这次真实调用的等待。影子记录是探针只记下"此刻会提交什么"但不执行，事后和真实调用对账。fork 对照是在探针触发那一刻把进程的完整状态复制一份，让副本走投机路线跑到任务结束，和原来那条线对比 token 账和成败。

**为什么这么设计才算数。** 五种跑法各回答一个不同的问题，缺一个就有一处没法验证。影子记录是零风险的，全程开着，它的作用是验证离线回放的估算准不准。fork 对照是唯一能给出因果对照的口径——同一个事件，一个副本走投机、一个走原路，两边的 token 账直接相减。fork 有一条硬规定：每个事件只在第一次过门槛的地方复制一次，副本里面探针关掉，不许嵌套，否则会无限递归。

**看一条真的。** 账上没有实验记录可捞。已经落地的是代码：探针服务、流式生成、记账、bfcl 的四种口径处理器、appworld 和 tales 的运行器。

**实验结果。** `ops/runs.jsonl` 里这条线一条记录都没有。**实验一次没跑。**

**值得注意的设置细节。**

探针服务的性能修过三次，每次都是同一类问题：第一次，服务原来是每来一个请求就开一个线程，每个线程都要重新初始化一次矩阵运算库的上下文，每请求 760 毫秒；改成单线程复用同一个上下文之后降到 14 毫秒（提交 `e9c7a7a`）。第二次，模型每遇到一个没见过的输入长度就重新编译一次计算图，长度一变就付 400 到 560 毫秒；关掉这个自动重编译之后稳定在 8 到 10 毫秒（提交 `b17f1c9`）。第三次，注意力的某个后端每遇到一个新的序列长度要先算一遍执行方案，大约 770 毫秒；换掉这个后端之后任意长度稳定在 11 到 15 毫秒（提交 `715e4bc`）。这四组数字来自这三次提交的说明，不是实验记录里的字段。中间有一次归因错了：先归到重编译上，后来用性能分析器确认是注意力后端的问题。

tales 这个环境的游戏引擎能不能存档还没查清楚。任务清单把这一条标为这条线已知的工程风险。fork 对照需要现场可复制，bfcl 和 appworld 的模拟状态可以复制，tales 不确定。

# 下半 · 解读

**以下全是我的判断，可以吵。上半那些数字不需要你同意，它们就是那么大。**

**探针这条路在 bfcl 上成了，在另两个环境上没成，而且原因不一样。** bfcl 两代都达标，v3 上准确率 0.9925、触发比例 0.5929，换一次数据切分重测之后置信区间仍互相覆盖，我认为 bfcl 这一个环境可以写进论文当正面结果。appworld 的准确率两代都停在 0.93 上下——v2fix 是 0.931（风险 0.05 档），v3 是 0.933（风险 0.1 档，0.05 档找不到可用门槛），这两个数不是一个口径，但都离 95% 差两个点上下。数据翻倍没把它抬起来，我判断这是信号本身的上限，不是数据量问题。tales 更明确：先验基线本来就 0.556，探针的准确率 0.85 离 95% 差 10 个点，账上把原因归到开放动作空间（原话见线 1 表格下面那句），我同意——没有固定动作清单，分类头要在一个不封闭的集合上做选择。

**因果探针这条线的结果比主线更值得注意，因为 appworld 这个环境只有它做到了 95%。** ModernBERT 在 appworld 上找不到可用门槛，换成 Qwen3-0.6B 底座之后准确率 0.9621、触发比例 0.3338，同时探测开销降到二十几分之一。tales 也从 0.85 升到 0.9077，虽然还不到 95%。我的判断是：部署形态这个问题已经有答案了，应该用因果探针，而不是把它当成 ModernBERT 的一个备选。这条结论动了原来"ModernBERT 是主线、因果探针是对照"的框架，`TIMELINE.md` 该补一条。

**消融那四个数支撑了论文的核心主张，但也暴露一个口径问题。** bfcl 砍掉思考之后触发比例从 0.5929 掉到 0.0752，掉了将近九成，砍掉历史只掉到 0.4823。所以思考文本确实带着主要的增量信号，这条主张有消融支撑了。但砍思考那一档换了评测方式，触发比例的口径和完整输入不一致，直接把 0.0752 和 0.5929 并排写进论文，审稿人会指出这两个数不可比。我建议在表里把这一档单独标注，或者补一次同口径的评测。

**存解法全矩阵那条实验的结论是负的。** 账上还提到同一套做法在一个 4B 模型上先跑过一次、省得比 8B 多，但那次的数字不在这个窗口内，我没法把两次放在一起比，所以下面只谈 8B 这一次。 三个档里只有完全一样的题省了 9.6%，另两档分别亏 16.8% 和 19.6%。完美复用上限那条实验又说明：完全一样的题这一档最多只能省 21.0%，另两档上限是 0——也就是说另两档想省，靠照搬是不可能的，必须靠泛化。把这两条放在一起看，我认为 C3 这个基准的立论反而更稳了：直接把过去的解法放进提示这种做法，在诚实的相似度档上已经净亏，这正好支持"需要一个会学习的系统，而不是把历史原样放进提示"这个说法。

**真实负载相似度那条数据是这批实验里对论文最有用的一条，但它的边界很紧。** 相邻会话相似度大于 0.8 的占 68.4%，说明重复相似任务是真实负载的主体，不是造出来的假设。但它只测了工具调用构成的相似度，没测任务内容，所以它能支撑"任务会重复出现"，支撑不了"重复的任务能复用同一个解法"。同样地，把这三个相似度区间和 6a 那三个任务相似度档对应起来是有诱惑力的，但两边的相似度定义不是一回事——一个是工具调用次数向量的余弦，一个是题目内容像不像，我认为不能直接换算，论文里要么补一次同定义的测量，要么只把它当定性证据。

**六个记忆系统那条线我判断有问题。** 保真度核对说四个重建的系统里有两个失真、还有一个的机制在单轮设定下根本不存在。拿一个失真的实现去比，赢了也没有说服力。我建议按核对记录的建议办：机制不存在的那个直接不报，失真的两个在论文里明确声明失真在哪。

**闭环这条线是现在最大的问题，因为它一次没跑。** 前面所有省 token 的数字都是离线估算，审稿只认真实计时。代码已经写完、探针服务的三处性能问题也修完了（三处各自的修法和数字见线 7），但端到端演示都还没跑过一次。tales 的现场能不能复制还没查清楚。任务清单的依赖图写的是闭环正式跑分和 C3 正式跑分两条都汇进 C4，所以闭环晚一天，C4 那张关键图就晚一天；清单自己也把闭环标成全项目日程上最卡的一环。
