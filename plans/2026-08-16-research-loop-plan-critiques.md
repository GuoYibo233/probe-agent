# 三个 subagent 对 2026-08-16 计划的审读原文（opus，未经主会话裁决）

三份都是对 `plans/2026-08-16-research-loop-next-steps.md` 重写版的审读，主会话没有改动一个字。哪条采纳、哪条顶回，记在计划文件里，不记在这里。

## 一、研究迭代视角（博士生：快、多次、代码不严密）

1. 写权白名单把 new1 每天必改的文件（run.py、MAP.md、ops/）全关在门外；「不设过渡期旧路径清单」等于禁止改一切老代码。建议黑名单式只拦 loop/、notes/、review/。
2. 小实验快车道整个消失了。spec §2.6「快试一下」通道免工单免报告，定稿没交代是裁了还是漏了。改一个 batch size 也要走全链。
3. 改主意的成本没人算：决定改版后在办单子只打标不处理；废弃想法要给每张废单编卡住理由开 issue 才能销号。建议自动标待复核、加「弃单」命令。
4. 部署报告是转状态硬门槛，改三行也要写两层。建议按 diff 规模分档。
5. run 分步计时成本超过被测实验，sonnet 读代码列步骤会漏，乘 N 张单。建议只对长任务要求，短任务标 rough。
6. 决定必须带来源、空列表拒收：「昨天 loss 曲线不对试试换 warmup」既不是旧决定也不是 notes 文件。建议加自由文本来源类型。
7. 口径账把探索性分析禁掉了。建议拆探索级（analysis 自算、不进 review、不被决定引用）和正式级。
8. 下游发现 typo 只能开 issue 绕全链。建议小修口子：改动不超过若干行、强制留痕。
9. init 全量搬代码能吃掉一周（jobs.json、RUNMETA、软链、注册表全钉着旧路径）。建议第一版只给按需搬。
10. reviewer 不读部署报告逐条对研究代码会刷出一清单假问题（硬编码路径、magic number 都是有意的）。建议只审「决定里明说的那几条有没有被执行」，每条必须引到决定编号版本。

附注：一个会话一个角色，一条链要开四个 session，没有「gyb 一个人从头跑到尾」的路径。

## 二、机制落地视角（写过 Claude Code 插件的工程师）

1. 没加载角色的会话完全不受写权管；同一会话加载两个角色的行为未定义（叠加还是覆盖）。建议兜底钩子进项目 settings.json，默认拒写受管目录、按 sessions 账放行；补验证。
2. 角色身份没有不可伪造的来源，「只有 X 能写」全是自报，`rl grants add --role gyb` 就能自授权。spec §5 原话「防呆不是防伪」，定稿升格成「硬拦」口径不一致。建议挑明防呆不防伪；或钩子拦 rl 命令注入角色（要验钩子能不能改写 tool_input）。
3. 钩子按路径拦得住 Write/Edit，拦不住 Bash 和子进程：产物根是训练进程写的、loop/ 可以 echo >>、NotebookEdit 没在名单里。建议硬拦缩到 Write/Edit/NotebookEdit，产物根和 loop/ 改事后对账（行哈希链、RUNMETA 孤儿）。
4. 状态机五处说不清谁能写：打回写开干和「开干下游写」打架；回 issue 捞回开干常是上游写；收回是第六个状态；派活单有没有版本没定义；发射单验收人是 deploy 但 deploy 可能已经结束；retire 别人角色的决定谁有权。建议做成显式转移表（起、止、谁、前置条件）。
5. 跨账复合写入不是原子的（卡住=两账互引），编号「取最大加一」同角色多会话会撞；spec §5 的写序和半状态扫描这一版丢了；`_lib.py` 的 alloc_id 注释写明「caller holds the lock」。建议搬回写序、编号分配和追加同一把锁、加并发测试。
6. 销号靠模型自觉会被 subagent 静默绕过（上下文满、报错、被中断）。建议挂 SessionEnd/SubagentStop 钩子；补两条验证；rl status 要能判会话活没活。
7. deploy 写权只有 experiments/，和 new1「改代码必挂 run.py 注册表同一 commit」冲突。建议文件粒度白名单或注册表分表。
8. 读纪律两处一定破：部署报告和代码同目录，reviewer ls 一次就看见；idea 每条决定要引 notes/ 文件又不许读文献。建议报告挪出 experiments/、经 rl 命令取；idea 只读 gyb 点名的 notes 文件。
9. 看门狗只有一个判据且是外推值，GPU 步不线性。建议卡死看进展停没停、超时才用预估乘系数（spec 原本就是双判据）；跑完回填真实耗时。
10. 通知没有落地通道：rl 跑在 subagent 的 Bash 里，输出只有它看见。建议定清落点（loop/inbox + SessionStart 播报 / 系统通知）；rl status 单列「改派给 gyb 超过 N 小时没动」。

## 三、日常负担视角（gyb 替身）

一条顺利的链 gyb 亲手动作 16 个、开 3 到 4 个会话、硬卡点 9 处（谈想法多轮、报来源、谈工程细节、答自动接还是手动接、issue 改派、答统计什么、批口径、销号裁单子、审 review 清单）。

1. 不加载角色的会话什么都不受管，绕过流程成本为零。建议承认裸会话是逃生门并给边界（最小钩子记路径、reviewer 标「未经流程」）。
2. 看到图前卡两次人工批准、一行一个指标，探索性多画一张也要补批。建议按组批、探索期先画后追认。
3. 销号靠人敲，一周账本被僵尸单塞满，rl status 变噪声。建议单子加心跳超时自动标卡住。
4. 验收这一步没写 gyb 在不在场。建议 idea 自主验收、只在打回时通知 gyb 并附报告上半。
5. 一条链开三到四个会话。建议自动接单是唯一默认，手动接只在 gyb 当场点名。
6. 一个 OOM 走两跳单据，gyb 会直接进 tmux 改完不回账。建议 run 环境类失败就地重试一次只留一行记录。
7. 过版检查每次上线全量弹；改版后在跑单子无规则。建议只在引用真被读到时提示一次；默认在跑的跑完、验收时复核。
8. 每张发射单都做分步计时，N 遍。建议允许手填上界跳过；同代码第一次跑才做完整分步。
9. 来源空列表拒收，「学习率就 3e-4」填不出来源。建议加「gyb 当场口头」类型带会话 id 和时间；只对方向性决定压来源。
10. 要人手动开的 reviewer 不会被开；反常结果预警没定阈值和收件人。建议 reviewer 挂验收自动跑一次只报硬冲突；预警定阈值先发 analysis/deploy。
