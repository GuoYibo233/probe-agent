下面是我的解读

速度提升的来源是前缀共享：旧训练器给一个事件的每个切点（平均 45 个）各算一遍前缀，新训练器只算一遍。六个对照点高出 23 到 67 倍，对旧稳态是 16 倍；末尾窗口掉到 145 是那一段事件每行 token 多（按补齐 token 算吞吐 12.9k 对中段 16.9k token/s 同量级），不是尾组更新或评估造成的（助手 2 在 CPU 上复现了同一份抽样验证）。预算 24576 比 16384 慢的原因没有量（16384 那一档的补齐占比在速度档样本上是 28%，24576 那一档没有算）；16384 又快又稳，定为默认。上限 8192 不用退档：最长事件 31.4 GB，训练峰值余量 39%。ctool 撤掉截断之后每批 4 个事件在 8192 上限下训练第一批就装不下 H100（那一批四个事件的长度没有记录），每批 2 个累积 4 次保持 8 个事件一次更新，峰值 55.5 GiB；48G 卡装不下 ctool 0.6B 全参不带梯度检查点，排卡时只能上 H100 / H200。按每秒 185 行算，train 集 186,479 行的训练部分约 17 分钟一个 epoch，加上四次全量评估和加载；这个数还没有全量实跑验证。

下面是我的解读

最终代码的速度和对齐结果与冒烟一致，六个对照数没有退步。探针改动是有效的（两档各抬高 3.3 与 1.4 GB）但没有追平训练峰值：探针按「token 数最多的块」选，而显存最大的块可能是行数多、损失位多的那一块（损失位的 logits 随目标 token 数涨），这是猜测没有量。决定 25：这一轮不再改探针，把它定为带实测偏差的下界估计，排卡时探针最满块的数加 10% 再判余量（助手 1 算过：两档偏差 7.5% 与 5.8%，54.38 × 1.1 = 59.81 高于 58.47，76.47 × 1.1 = 84.12 高于 80.91；这 10% 只盖已分配峰值之间的差，reserved 碎片的折是另一层，stage-commands 里写成两条分开的规则）；「按真实训练循环连做两个小批」的退路列进需要 gyb 拍板的事。

遗留与已知问题

  • ctool 读取位置规则让训练与离线评测和「全文一次分词」的 token 边界一致；活跑时模型自己生成的 token 边界可能不同（比如先出 ."\n 再出 \n），那是另一个坑，没有解决，回写里明确没有写成「活跑错位已修」。
  • 评审留下的小问题（都记在各工单的 Comments 里）：工单 05 的新测试与既有 LoRA 测试大段重复（wave3 评审 minor N1，sdd/2026-08-28-wave3/T05-report.md）；工单 04 报告里一个 commit sha 写错（wave4 评审 minor N1）；stage-commands §3.1 的峰值表把两条单格数据塞进三格同批次形态的表（工单 04 实现者 concern）。
  • 全量测试里 test_splice_replay 那 1 个 error 是仓库记忆里的老毛病；实现者报的 test_no_env_reads_default_preset 失败在 HEAD 上复现不了（助手 1 核过，系统 python3 全量 356 个测试只剩那 1 个 error），与本轮无关。
  • 速度档的 epoch 末 val_ce 是 450 个事件子集上的数，不能和 np821 比；新口径的全量训练一次都还没跑。
  • H100 上 ctool 冒烟那两次的显存只有 nvidia-smi 采样（当时它自己不记）；工单 06 之后 ctool 的 step / eval 事件带 peak_mem_gb，终验里第一次自记到 47.34 GB（H200，已分配）。
  • 终审的 16 条观察里值得记的：「补到 16 的倍数」在 share_data 与训练器各写了一份；「按事件分组取全文」三处各一份；packed_len_max 写的是补齐后的长度；--readonly-env 下 READONLY.json 审计的分母口径与旧脚本不同；驱动器的 smoke 门只查 ctool 的 PASS，cgen/cparam 的对齐门靠训练器自己 exit 2 兜着。
