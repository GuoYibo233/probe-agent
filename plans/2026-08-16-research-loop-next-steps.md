# research-loop 插件开发计划（2026-08-16 定稿，同日夜间按两轮模拟走查修订）

这份文档是 research-loop 插件在 2026-08-16 六轮讨论之后的设计现状：上午一轮逐步确认锁了六个裁决和五块架构，下午一轮语音打磨，晚上一轮按 gyb 的真实用法从 init 走到 reviewer 做了纸上走查，第四轮拿三个 subagent 的审读意见（原文在 `plans/2026-08-16-research-loop-plan-critiques.md`）逐条裁了八个题目，第五轮拿十一个 subagent 对五个使用场景的模拟结果（原文在 `plans/2026-08-16-research-loop-simulation-round1.md`）抽出八条设计原则并按原则改了正文，第六轮拿十六个 subagent 对十七个场景的第二次模拟结果（原文在 `plans/2026-08-16-research-loop-simulation-round2.md`，只有模拟没有核实，见那份文件开头的说明）把八条原则补成十一条、再按十一条把正文审了一遍。六轮的结论全部合并写在这里，往后施工以这份为准，和 `.scratch/research-loop/redesign.md` 冲突的地方以这份为准。第五轮、第六轮各改了哪些地方、为什么改，列在最后两节。

两份文档的分工（原则 8）：这份写「做成什么样」和「为什么」，字段名、状态转移表、命令表、阈值、测试清单这些可枚举的东西只在 `plans/2026-08-16-research-loop-build-plan.md`（下面叫「施工计划」）里写一遍，这份只指过去，不抄一遍。施工计划第一节的裁决优先于这份正文。

## 目标与总验收

这套东西服务的是研究：想法要快速、多次迭代，代码风格不要求严密，能出数字就行。设计里每一条手续都要拿这两点去衡量。第二轮模拟数出来的手续量摆在最后一节，gyb 看着定哪几条要再砍。

先把共同底座和交流用的 json 落进插件，落完之后才写五个角色的 SKILL.md。总验收由 gyb 定：每个角色配一个对应的任务，两个 agent 一个加载角色 skill、一个不加载，各做一遍，产出摆在一起由 gyb 自己看，不预先定判分办法。

## 十一条设计原则（第一轮抽出八条，第二轮补成十一条）

第一轮模拟报了 59 条摩擦，归并之后根子只有八个。第二轮模拟按八条改过的文档再走十七个场景，报了 234 条（未核实），归并之后：八条原则本身没有一条被推翻，但是有五条只写了正面一句、没把推论写出来，模拟者在推论上各猜各的；另外有三个根子八条里没有。下面十一条是根子的正面写法，带着推论；正文里每一处规矩都要能对回其中一条，施工时遇到文档没写到的岔路也按这十一条推。

1. 谁在打命令和会话装了什么角色是两回事。每次写账都有一个 actor：要么是五个角色之一，要么是 gyb。gyb 是超级用户，钩子、入账校验里的「谁能调」和转移表的「谁能写」对 gyb 一律不生效，gyb 在任何终端、任何角色会话里都能行使自己的权。账行如实记 actor 和会话两样。第二轮补的推论：rl 只认会话，不认手指。rl 能看到的只有「这条命令从哪个会话发出来」，看不到键盘前面坐的是 gyb 还是模型，所以一切身份规矩只按会话定：裸终端（session_id 是 `cli`）发出的命令 actor 就是 gyb，不用旗子也不用原话；角色会话里发出的命令默认 actor 是那个角色，加 `--as-gyb` 才以 gyb 身份写，而且不论是谁敲的都要带 `--quote`（gyb 本人敲就引自己刚说的那句），这个 quote 是留给 reviewer 的痕迹，缺了 rl 拒收。gyb 的豁免只豁免权限（谁能调、谁能写），不豁免账行的完整性：必填字段、路径存在、引用存在这些数据校验对 gyb 同样生效，gyb 要硬写就加 `--force --reason`，rl 照写并把 reason 记进账行。授权（grants）只收裸终端写的行，角色会话里替 gyb 批授权没有意义。
2. 约束分三层，各管各的。钩子只管 Write 和 Edit 两个工具、只按研究仓库内的相对路径判、只拦两类离谱事：写别的角色的目录，直接写 loop/。入账校验管九本账的每一行，是硬的。其余一切（Bash 写出来的文件、宿主发射器的台账、读什么、怎么读）靠 SKILL.md 的纪律加 reviewer 事后查。第二轮补的推论：读一律不设权。九本账的查询命令谁都能调，角色 json 的 reads 栏是纪律不是门禁；机器检查只查 SKILL.md 里的写命令在不在 ledger_writes 里。
3. 每张派活单有 owner 和 holder。owner 是开单的角色，负责单子从开到关：拉起下游、验收、收回。holder 是当前正在干这张单子的会话。第二轮补的推论：holder 非空当且仅当单子在开干。任何离开开干的转移（交活、卡住、打回、收回、交回、回收）都清空 holder，上一个 holder 另记一栏；开干只能从空 holder 进；销号只查开干的单子。owner 是角色不是会话，owner 角色当下没有活着的会话时单子由 gyb 拉起，`rl status` 单列这一类。开单时可以标「gyb 手动接」，标了 owner 就不起 subagent。
4. 九本账全是事件流。全部只增不改、全部带版本号，「改」永远等于追加一版；一个字段必不必填看这一版的状态，不看全局。第二轮补的推论：九本账每本都有 status 字段，校验按 status 查，runs 和 sessions 也不例外；改单子内容（换命令、补报告路径、补引用）也是追加一版，允许改的状态写在转移表里；前提查在交付那一刻，不查在开单那一刻，开单只查「单子说得清自己是什么」，交付才查「东西齐不齐」。
5. 权限从动作倒推。每个角色的读、写、能调的命令，从它的 use case 表逐条倒推出来，写进角色 json；不是先写 json 再找活对。第二轮补的推论：gyb 也有一张 use case 表（开工第一眼、批、验收、拉起、回收、修账），`rl status` 的段落和各 list 命令的过滤维度从这张表倒推，不是从五个角色的表推。
6. 进出对称，等人的事有收件箱。每本账能写进去就能查出来。第二轮补的推论：收件箱有两个，gyb 的叫 `rl status`，角色的叫 `rl inbox`。任何一版把某一行送进「等某人」的状态（等 gyb 批、等 owner 验收、等 assignee 回、等 owner 拉起、等谁读通知），那一行必须出现在那个人的收件箱里；桌面通知只是 gyb 收件箱里几段的推送，哪几段推送写成一张表。角色上线第一个动作是 `rl inbox`。
7. 快车道有明确的进和出，进出都是账上的一行。进是 gyb 点名后 `rl ql open`（分配标签、建 worktree、记杂账），出是 `rl ql close`（合回或放弃，各一行）；中间的一切都在 worktree 和杂账里。快车道不是 deploy 专属：analysis 想先画一张图给 gyb 看也走同一条。
8. 文档只有一处为准，后裁的赢。施工计划第一节的裁决优先于设计文档正文；每条推翻正文某一行的裁决，要回来把那一行改掉并标日期，不留两个值。工程内的规矩优先于机器全局规矩，例外要明写。第二轮补的推论：可枚举的东西只在施工计划写一遍，设计文档指过去不抄；两份文档里同一件事说了两遍的地方，第二轮找出来的全部并成一处。
9. 每张单、每条 run 都有一条回到决定的显式链（第二轮新增）。发射单和分析单都记父单，开单时从父单继承决定引用和 batch；发射单上就带 run_id、track、config，run 只抄不猜；`rl trace` 一条命令从任何一个编号打出 run 到发射单到工单到决定各版本的整条链。决定树上每条决定记根决定，两条研究线并行时按根决定切开看。
10. 发射单是多次尝试的容器（第二轮新增）。一张发射单可以跑几次：smoke 失败、发射失败、跑挂、修完再来，每一次是单子上的一个 attempt，各带自己的命令、分步表、预计时长和 run 行；预计时长只算最新一次尝试；数字账默认只列每张单最新一次退出状态为 ok 的行；真实耗时由 `rl run finish` 从时间戳算出来，不管退出状态是什么都记。
11. 派活不占终端（第二轮新增，取代原则 3 里「subagent 接单默认同步」那一句）。上游开完单后台起 subagent 接走，上游会话继续可用，subagent 回来时上游验收；上游会话先结束了，单子照常在账上等 owner 下次上线或 gyb 验收。GPU 任务本体在 tmux 里跑、不跟会话走：run 会话死了单子交回待干，下一个 run 会话接单时发现最新一次尝试已经发射还没收尾就认领它（不重新 smoke、不重新发射，只接管看门狗和收尾）。等几个小时的事只发生在 tmux 里，不发生在任何会话里。

## gyb 自己做的事

这套系统里有几件事只有 gyb 亲自做，任何角色都不代劳。

文献变成想法这件事由 gyb 亲自做。gyb 自己做文献调查，把调查报告写成 md 放进 notes/，notes/ 只有 gyb 写，谁都能读。这一版不加文献线，也没有角色去查「这个想法别人做过没有」，要加文献账是另一件事；notes/ 就是文献进入这套系统的唯一入口。idea 角色要经 gyb 允许才有读文献的权限：`rl init` 的时候问 gyb 一次要不要当场给 idea 发 `read:notes`，发了就不再走申请；没发的话 idea 开一条 issue 给 gyb（kind 是 request），gyb 在裸终端写一条 grant，idea 之后才读 notes/。读权不上钩子，grant 是给 reviewer 事后查的凭据，doctor 有一项扫描「决定的来源指向 notes/ 但 grants 里查不到这个 actor 的 read:notes」。

分析什么、画什么图由 gyb 亲自说。口径账每一行都是 gyb 说、analysis 记、gyb 批，任何角色都不许自己写新的要分析的东西，analysis 不许自作主张画图，只把 gyb 说要看的数算出来。批可以一句话批一组：`rl eval approve` 收多个编号一个 quote。

另外五件：写 grants 账（授权只有 gyb 能写，只收裸终端）、裁 feedback 账（谁都能提、只有 gyb 能裁）、手动结束会话（可以指定别的会话）、手动开 reviewer、定期跑回收命令收拾很久没动的会话和单子（有定时提醒叫他）。

gyb 的身份按原则 1：裸终端就是 gyb；角色会话里 `--as-gyb` 加 `--quote`，不论谁敲；gyb 直接写的决定落 `decisions.gyb.jsonl`（第六个决定文件），这个文件只收裸终端写的行，角色会话里替 gyb 记的决定落那个角色自己那本、actor 记 gyb、带 quote。reviewer 的审查基准是「actor 是 gyb 或 idea 的决定行」，不看落在哪个文件里。

## 五个角色

idea 和 gyb 交流想法，出工单派给 deploy。deploy 写代码，把探索性概念转成清晰可发布的实现，把怎么运行交给 run。run 看服务器、运行实验、主要负责长时间的任务，出问题回报。analysis 分析实验结果，按 gyb 说的算数、画图。reviewer 审查整条链有没有照定好的执行。

每个角色由两份文件定义：一份 SKILL.md，一份 json。json 里的东西从 SKILL.md 的 use case 表倒推（原则 5）：每个 use case 写清读哪些账和目录、写哪个目录、调哪些 rl 写命令，json 的 reads、writes、ledger_writes、dispatches_to 四栏是这张表的并集，model 另记。五份 json 合起来就是分权表本体，钩子按角色读自己那份。一个会话只加载一个角色。测试里有一条机器检查：SKILL.md 正文出现的每条 rl 写命令都要在这个角色 json 的 ledger_writes 里，查询命令不查（原则 2 推论）。SKILL.md 不抄公共母版的条文，只写一句「按 common/ 执行」，测试同样查抄没抄。

角色上线第一个动作是 `rl inbox`（原则 6）：列本角色名下 open 的 issue、owner 是本角色而没有 holder 的单子、本角色持有或拥有的单子里过版的决定引用、发给本角色的通知（收回、孤儿、feedback 裁决）。run 的 inbox 不查过版，发射单不引决定。

### idea

idea 和 gyb 谈想法，谈定的东西写进 idea 的决定账。gyb 会参与到影响实验结果的工程细节里，这些细节同样写进决定账，reviewer 的审查基准只有这些 gyb 定下的决定。gyb 在场定的那一版和 idea 自决的那一版账上要分得出来：actor 是 gyb（带 quote）还是 idea（不带 quote）。

每条决定必须带来源。来源是一个列表，每一项是三类之一：旧决定的编号加版本、仓库里的文件路径（可以是任何仓库内路径：notes/ 里 gyb 的调查报告、analysis/ 里的图和 notebook、experiments/ 里的部署报告、review/ 里的清单、experiments/ 里的代码文件；可选一个锚点指到小节或行号区间）、runs 账里的一个 run_id。三类可以混着放；至少一项，空列表入账脚本拒收。跑完实验才知道的结论（比如「学习率太低，换高一点再跑」）就是这么进账的：来源指那次跑的 run_id 和 analysis 的图，成为原决定的新一版或者一条新决定。不设「口头」这一类来源，每条决定都要能追到一个文件或一个数字；一条决定链的第一条决定，来源指现有代码文件或 notes/ 里的一行，两样都没有就先让 gyb 在 notes/ 写一行。新一版还是新一条的判据：改的是同一个问题的答案（同一件事换个做法、换个参数、停掉）就追加一版；换了要回答的问题就开新条；跨角色改别人的决定一律在自己那本开新条，来源指原决定的编号加版本。看过一批结果之后确认「继续、设定不变」也要留痕：`rl decision confirm` 追加一版正文不变、只加来源。追加一版的时候来源默认继承上一版；决定改版或废除的那一刻 rl 当场列出引着旧版而没到终态的单子和它们的 holder。每条决定记根决定（新开的决定根是自己，追加一版继承，合并时指定保留哪个根），`rl status --group-by line` 按根决定切。

idea 把决定拆成工单派给 deploy。工单里不能只甩决定编号，还要附一段 idea 自己写的解释，把那条决定里的东西讲明白，解释权在 idea。怎么测试、什么算成功，也要 idea 自己想明白，只是不预写成单子上的字段。deploy 干完之后由 idea 验收，验收的办法见「交接」一节的部署报告。idea 是工单的 owner（原则 3），工单被打回、被回收、下游销号之后回到待干，都由 idea 重新拉起下游；开单可以带 `--no-dispatch`（只定计划不现在开跑）或 `--manual`（gyb 亲自接）。

idea 也可以给 analysis 开单。单子上引的口径可以还是 proposed，交活的时候必须全部 approved（原则 4 推论）。单个 run 的原始指标 idea 可以直接从 runs 账念给 gyb 听，任何跨 run 的对比、聚合、画图一律走 analysis 的分析单和口径账。

idea 读的东西：九本账全部、notes/（要 grant）、analysis/ 的产物、experiments/ 下的部署报告目录（验收要读）、review/（reviewer 的清单是 idea 下一轮的输入）。

### deploy

deploy 写代码，写权只有 experiments/，写的是研究代码，不要求严密的工程风格。干完写部署报告，分两份：一份像论文里那样只讲做法、用了什么技术、数据怎么被处理，不带任何文件；另一份带上文件和处理细节、这次改了哪些文件的清单（含 experiments/ 外的宿主文件）、这张单子上关联的 issue 编号和结论。两份放 experiments/ 下这张工单自己的目录里，提「干完等待验收」的时候派活单记两份报告路径和代码路径清单。不带文件的那一份必须原样抄一遍这张工单引的决定编号加版本，reviewer 拿它当锚审「代码和决定是不是一回事」。发射单验收完之后 deploy 把 run_id 和关键指标补进带文件的那一份，再提工单的「干完等待验收」。

deploy 给 run 开发射单（原则 9）：父单填工单，决定引用和 batch 自动继承；单子上带命令、参数、工作目录、track（宿主发射器要的方向名，从被派的工单继承或 deploy 填）、config 字典（模型名、参数量、数据集、划分、关键超参，给 analysis 分组用），run_id 由 rl 按单号加尝试号分配。deploy 不跑 smoke、不估时长，这两样都是 run 的活。deploy 是发射单的 owner：后台起 run 的 subagent 接单（原则 11），回来之后验收发射单，再拿数字接着干工单；发射单被打回或者 run 会话销号交回待干，都由 deploy 重新起 run。发射单卡住（smoke 失败、发射失败、跑挂）的 issue 回到 deploy 手上：deploy 改代码，改完 `rl handoff amend` 给发射单追加一次新的尝试（新命令、新工作目录都在这一版里），回 issue，`rl handoff resume` 把单子交回待干，再起 run。一次开 N 张同 batch 的发射单时只起一个 run 会话接整个 batch，见 run 一节。

deploy 自决的粒度：改变实验结果的选择（取第几层、用哪个划分、超参取值）算自决，进 `decisions.deploy.jsonl`，来源默认填改动的文件路径；纯写法的选择不算。gyb 坐在 deploy 会话里当场拍板的参数按原则 1 落 `decisions.deploy.jsonl`、actor 记 gyb、带 quote，不算 deploy 自决。

deploy 改到 experiments/ 外的宿主文件（仓库根 run.py 的注册表、MAP.md、ops/ 里的东西）钩子不拦（原则 2，见「分权与钩子」），纪律是三条：改动列进部署报告带文件的那一份；在 `decisions.deploy.jsonl` 留一条来源指向那个文件；宿主仓库自己对这些文件的规矩照守（new1 是 CLAUDE.md 里的 probe-pipeline skill 和 run.py 注册表三件套）。老代码要不要搬进 experiments/ 由 gyb 手动定，deploy 只提醒。

### 快车道（原则 7，deploy 和 analysis 共用）

进快车道由 gyb 点名，口头就行，不设别的判据；典型情形是决定不动只微调代码，或者一个想法还没成型先跑一把看看，或者 gyb 想先看一眼图再定要不要正式算。进的动作是 `rl ql open`：rl 在锁里分配标签（形如 `ql-20260816-01`）、在配置里的 `quick_lane.worktree_root` 下建 worktree 和同名分支（analysis 的快车道不建 worktree，产物放 analysis/scratch/<标签>/）、往杂账写开张的一行；`--from ho-ID` 可以把一张待干的工单转进快车道。中间：deploy 在 worktree 上改，自己小规模跑；GPU 照旧走宿主发射器（快车道里 deploy 可以派 gpu-runner，这是 deploy 唯一能派 run 之外的对象），run_id 用快车道标签，track 沿用被微调的那个实验的方向，宿主的台账照登记、record finish 的结论栏写 quick_lane 加标签；数字追加进杂账，不进 runs 账；不开发射单、不叫 run、不做分步计时、不写决定账。出快车道两条路，各是杂账上的一行：`rl ql close --merged --handoff ID` 或 `rl ql close --dropped --reason`。合回的时候 gyb 亲自 merge 主分支，deploy 补一张标了 quick_lane 的工单：from_role 和 to_role 都是 deploy、验收人固定是 gyb、允许新建直接进「干完等待验收」、只要一份不带文件的简报（带文件的那一份用杂账里的记录顶替）、解释栏由 deploy 写并抄 gyb 点名的原话、同时补一条 decisions.deploy 记这次改动。主分支上永远只有走过工单的代码；合回之后要正式数字按正常路再开发射单跑一遍，那张发射单的父单就是这张快车道工单，doctor 会报「快车道工单已验收但没有关联发射单」。没关掉的快车道出现在 `rl status` 里，reclaim 把超期的快车道也列进来。

### run

run 要小要快；模型 2026-08-16 晚 gyb 改裁为 opus（原来写 sonnet，那一句作废）。一张卡一个 run，多卡跑一个任务的例外。deploy 一次开 N 张同 batch 的发射单时，一个 run 会话用 `rl handoff start --batch` 一次接下整个 batch：smoke 做一次、分步表填一次（其余单子按规模系数复制）、探卡挑卡一次、按宿主发射器自己的分片规矩发射 N 份、落 N 条 run 行，不再一个 workflow 起 N 个 run 各自探卡抢同一张卡。

run 接单先看最新一次尝试有没有已经发射还没收尾的 run 行，有就认领（原则 11），没有才走 smoke。预计时长不许模型自己猜，也不许拿一题时间乘题数：run 先读代码列出每一步都干了什么，smoke 的时候给每一步计时，GPU 步按规模外推（装载一次大模型这类一次性开销也是 GPU 步，只算一次），CPU 步很短可以忽略，加总填进这次尝试的时长字段，分步表附在这次尝试上。smoke 的标准输出一律落到产物根下 smoke/ 目录的文件里，开 issue 时 `--log-tail` 指它。看门狗判两件事，分开判：卡死看进展停没停（日志多久没新行、产物目录多久没新文件、显卡利用率是不是掉到零），和预计时长无关；超时才用预计时长乘一个宽松系数。看门狗是独立进程，只判、只写自己的状态文件，不写九本账；run 会话每轮读它，杀进程和写账一律由 run 会话做。看门狗每轮采样顺带查一次本单状态，见到被收回或被回收就走中断流程。真实耗时由 `rl run finish` 从开始和结束时间算出来回填，退出状态是什么都记，几次之后就知道外推偏多少。

产物根只有 run 的任务能写，数字账只有 run 的脚本能写（gyb 例外，原则 1）。数字账一张单子一次尝试两版：发射成功那一刻落发射版（run_id、发射单、尝试号、commit、命令、机器、卡、产物目录、日志路径、tmux session 名、监控命令、开始时间，config 从发射单抄），跑完落收尾版（结束时间、退出状态、指标、真实耗时）。退出状态是 ok 才能把发射单提到「干完等待验收」；失败或被杀，发射单标卡住并开 issue 给 deploy，kind 是 failed 并注明是 smoke、launch 还是 crash 哪一段。反常结果预警不做常驻进程，就在落收尾版的时候同一个进程里查阈值，超阈值当场开一条 issue（kind 是 anomaly，actor 记 run，归 gyb）。`rl run finish` 同时调宿主发射器的收尾命令（new1 是 `run.py record finish`），ok 和失败都调，两本账一次落。出问题一律开 issue 回给 deploy：smoke 失败、发射失败、跑挂、结果反常四种，附日志末 40 行和 traceback，run 不修代码不重试。smoke 就失败的时候分步表和预计时长还没有，单子直接标卡住，这两样不是卡住的前提。中断（被收回、被回收）只做 `rl run finish --exit killed` 加收尾，不再改单子状态，状态由收回或回收那一步改。

### analysis

analysis 写权只有 analysis/，读 runs 账、写统计代码和 notebook，把 gyb 说要看的数算出来。先问 gyb 要统计什么，问完再出推荐口径给 gyb 批。画什么图 gyb 自己定、自己说，analysis 只按 gyb 说的画，不许擅自替 gyb 主张画什么图。analysis 的上游是 idea，gyb 直接开 analysis session 的时候上游填 gyb。gyb 只想先看一眼图的时候走快车道，图落 analysis/scratch/，要引用或复用的时候再补口径和分析单。

口径账一行一条口径，分两类：指标（kind 是 metric）和图（kind 是 figure）。指标行写清这个数从哪来：直接取 runs 账 metrics 里的哪个键（不重算），或者由 analysis 按 code_path 现算的派生量，两者必居其一。图行写清分组维度、横轴纵轴、用哪几条指标口径；分组维度和横纵轴的取值只能是 runs 行的顶层字段、config 里的键、或已批准的指标口径编号。code_path 提的时候可以还不存在、代码可以先写，批的时候必须存在，出数才要 approved。gyb 可以打回一条口径（附原因），analysis 改了再提一版；已经 approved 的口径再改一版就回到 proposed，要 gyb 重新批。历史 run 的 config 里缺这次要用的分组键时 analysis 开 issue 给 gyb（kind 是 cannot），由 gyb 定补跑、换口径、还是走 code_path 从产物目录现算。

analysis 读的东西：runs 账、口径账、派给自己的分析单、`decisions.idea` 和 `decisions.gyb`（分组的时候要知道哪些 run 属于同一条决定），加 handoffs（沿原则 9 的链从决定走到 run_id）。分析单交活的时候在单子上记 notebook 路径和图路径，路径存在、引的口径全部 approved 才能提「干完等待验收」。小图和 notebook 进仓库 analysis/，大文件进配置里的分析产物根并在口径行里记路径。

### reviewer

reviewer 由 gyb 手动开，审整条链，产出只写 review/ 里的问题清单，不开 issue、不派活，动不动由 gyb 看完之后定（施工计划公共规矩第 6 条里 reviewer 那半句按这一句改）。清单不进 notebook。清单一次审查一个文件，文件名 `review/<日期>-<审的决定编号>.md`，头部写审的是哪个 run_id、哪个 commit（按 runs 账里那个 commit 审，不审当前工作树），一条问题五栏：决定编号加版本、代码或记录的位置、对不上在哪、建议动作、决定账里没写但代码里做了的选择。`rl status` 列出最近的清单，idea 读 review/。reviewer 开工时 `rl session focus --decision ID` 记一下在审什么，`rl status` 的活着会话那一段带出来。

reviewer 审的是「gyb 和 idea 层谈定的东西有没有被好好执行」，具体三样：代码写得对不对、实验运行得对不对、analysis 写的分析代码和 notebook 是不是 gyb 要的。它审分析代码，不碰数据统计本身，统计是 analysis 的活。要审的代码清单从工单交活时记的代码路径栏来。

reviewer 什么都能读（2026-08-16 晚 gyb 裁，原来的「默认不读 deploy 的想法和部署报告」作废）。对抗性只体现在读的顺序：先读 gyb 和 idea 的决定和最终的代码，形成自己的判断，再读运行记录和分析代码，最后才读 deploy 的决定账和部署报告核对；这个顺序写进 SKILL.md，靠纪律。reviewer 的审查基准只有决定账里 actor 是 gyb 或 idea 的行，不拿文献当基准、不猜 gyb 的意思。

## 账本

账本一共九本，全放 loop/，一行一条 json（不用 markdown），只经 bin/rl 命令进出，只增不改（原则 4）：九本全部带版本号和 status，任何「改」都是追加一版，默认查询每个主键只取最新版；每一版哪些字段必填由这一版的 status 决定，入账校验按 status 查。多个会话会同时追加同一本账，所以 bin/rl 加文件锁，而且「扫号、分配编号、追加」三步放在同一把锁里，不许扫完号再排队写，否则同角色两个会话会撞号；快车道标签和 run_id 也在锁里分。跨两本账的写入（比如标卡住要同时开 issue 互相引用）定死写序：先写 issue 拿到编号，再写单子那一行引它，中间崩了顶多多一条没人引的 issue，doctor 命令扫得出来。九本账的行格式、每本的 status 取值、必填规则在施工计划第三节。

每本账都配写和查两头的命令（原则 6）：能 add 就有 show 和 list，sessions 和 runs 也不例外；`rl trace` 从任何编号打整条链（原则 9）。

1. decisions，决定账，按五个角色加 gyb 拆成六个文件，并行各写各的不撞车；`decisions.gyb.jsonl` 只收裸终端写的行。
2. issues，问题条：干不了、不归我干、被钩子拦了、跑失败（smoke、发射、跑挂三段）、结果反常、申请、通知（收回、孤儿、fyi），开一条等 assignee 回。每条带「归谁」字段，run 开给 deploy，deploy 解决不了改派给 gyb。assignee 是 gyb 的那一版（含首次开单）触发桌面通知，其余进角色的 `rl inbox`。回复只有 assignee 或 gyb 能写；关闭由开单的 actor 或 gyb 做，验收一张单子时它关联的已回复 issue 自动关，通知类 issue 被 `rl inbox` 读过即关。
3. handoffs，派活单：工单、分析单、发射单同一本账，用 work_type 区分。每张单子记 owner（开单角色）、holder（当前在干的会话，接单时写、离开开干时清空）、上一个 holder、父单、可选的 batch 标签、派发方式（自动起 subagent、gyb 手动接、暂不派）、可选的「接替哪张单」。工单带解释、部署报告路径、代码路径清单，发射单带尝试列表（每次尝试自己的命令、参数、工作目录、track、config、run_id、分步表、预计时长），分析单带口径引用和交活的 notebook 与图路径。交回待干那一版必填一段进度说明（干到哪、产物在哪、脏改动放在哪个分支）。
4. runs，数字账，一个 schema，只有 run 角色的脚本能写（gyb 例外），一次尝试两版（发射版、收尾版）。
5. grants，授权，只有 gyb 在裸终端能写。
6. feedback，反馈账，谁都能提、只有 gyb 能裁；谁都能读，提的人在 `rl inbox` 里看得到裁决。裁成采纳的那一版写清改了哪几个文件（列表，母版和文档都算）；母版改动在下次加载角色时生效，正在跑的会话不追、不通知，按现行母版干到底。母版带一个 rules_version，会话开始版记下它，采纳时 rl 列出还活着的会话让 gyb 挑要不要收；母版改动单独一个 commit。
7. evaluations，口径账，一行一条口径（指标或图），gyb 说、analysis 记、gyb 批准后才生效，gyb 也可以打回；引用带版本。
8. sessions，会话账：哪个会话、什么角色、什么模型（钩子从钩子输入里取真实模型标识，取不到记 unknown）、怎么起的（手动、subagent、workflow）、几点开始、几点销号，两版（开始版、结束版）；「最后一次写账几点」不落在这本账上，rl 查询时从九本账里该会话的最大 `ts` 现算。
9. scratch，杂账：快车道的开张、数字、关张，只有快车道写，格式松、只校验骨架和快车道标签，analysis 和 reviewer 默认不读。快车道的东西一旦要进正账拿来复用，它就不是快车道了，得按正常路重跑。

行格式的公共骨架：主键、版本、状态、时间、写这行的 actor（五个角色或 gyb）、写入会话的 session_id（裸终端写的记 `cli`）、schema_version，加一个可选的 fix_for（doctor 修账时记是修哪一项）。

决定账的结构是一棵引用树：
- 编号带角色前缀（dec-idea-0007、dec-gyb-0002），更新不换编号、版本号加一，谁写的记在 actor 里，编号前缀只说这条决定开在哪本账。默认读取对每个编号只取最新版，历史全在文件里但默认读不到，要旧版本用 `--version` 或历史命令。废除等于追加一版标 retired，来源默认继承上一版，停一条方向的时候鼓励再加上那次 run 和那张图。
- 两个旧决定可以合成一个新决定：新决定拿新编号，来源列表自动含全部被合并的旧决定，旧的各追加一版标 retired。
- 跨层引用带版本（「依据 dec-idea-0007 第 2 版」）。引用记的版本比账里最新版小就是过时，查询命令当场标出「上层依据已从第 2 版更新到第 3 版，复核这条还成不成立」。过版的单子进 `rl status` 和相关角色的 `rl inbox`。
- 决定改了一版，不影响已经派出去的单子：单子按派出时引的那一版继续做，rl 只标过时，不自动打回、不自动标待复核、不自动停。停不停由 gyb 点名，停就用收回；改版之后要重派的用 `rl handoff reissue`，一条命令收旧单、开新单、记接替关系。retired 决定名下还有活单的进 `rl status` 和 doctor。

## 交接与会话生命周期

派活单的状态（原则 3）：待干（开单时写，也是一切失去 holder 之后的落点）、开干（下游接活时写，holder 记这个会话，只能从空 holder 进）、卡住（下游写，必须连带开 issue 互相引用，holder 清空）、干完等待验收（下游写，交付物齐才收，holder 清空）、验收完成（owner 或 gyb 写）、打回（owner 或 gyb 写，必须附原因，之后单子回待干、owner 重新拉起）、收回（owner 或 gyb 写，单子关闭；收回一张有 holder 的单子时 rl 顺带开一条通知给 holder 的角色和 owner）。卡住的 issue 被回复之后由回 issue 的角色 `rl handoff resume` 把单子交回待干，to_role 的任何一个会话都能接，默认还是 owner 再起一个下游。这些状态和转移不写成散句，写成一张显式的转移表（施工计划第四节），一行是一次状态变化：从哪个状态、到哪个状态、谁能写、要满足什么前提、之后谁负责拉起下游、对应哪条子命令。入账脚本读这张表校验。改单子内容（补一次尝试、补报告路径、补引用）也是表里的行，写清允许在哪些状态上做。

交付物按单子类型定：工单是两份部署报告的路径加代码路径清单；发射单是数字账里退出状态为 ok 的那一版；分析单是 notebook 和图的路径加口径全部 approved。三样都是「路径存在或行存在」这种机器可查的前提，缺了不收「干完等待验收」；开单的时候不查这些（原则 4 推论）。

接单（原则 11）：默认是上游开完单后台起一个 subagent 接走，上游会话继续可用，subagent 回来时上游验收；开单带 `--manual` 的上游只开单，gyb 自己开 session 去接；带 `--no-dispatch` 的停在待干等 gyb 说开跑。subagent 加载角色 skill 那一刻和普通 session 一样登记进 sessions 账。下游 subagent 没走到交活或卡住就返回的（报错、上下文满），上游当场 `rl handoff release` 交回待干并决定重起还是开 issue 给 gyb。

验收不预写标准，验收产物是部署报告。理由：要验的是「代码和想法是不是一回事」，这个判断在代码写出来之前写不成条目，写得成条目的（跑得通、快不快）不是要验的东西。所以 deploy 提「干完等待验收」必须附报告路径，路径为空入账脚本不收这个状态。验收人是 owner，gyb 随时可以自己验（原则 1）：先读不带文件的那一份看做法对不对，再读带文件的那一份看写出来的东西和说的是不是一回事，打回要写明原因。gyb 越过 owner 验收或打回时 rl 给 owner 发一条 fyi 通知。

交接由程序盯着，不许有去无回（原则 6）：`rl status` 是 gyb 的收件箱，段落从 gyb 的 use case 表倒推，具体几段、每段列什么、哪几段推送桌面通知，只在施工计划第六节写；可以按 batch 或根决定归组，`--json` 的行结构写死。`rl inbox` 是角色的收件箱。owner 可以收回：对派出去还没干完的单子追加一版标收回，单子关闭；收回带 cascade 时 rl 代 owner 连它派生的下游单子一起收，下游单的账行 actor 记发起人；收回要带 gyb 原话或 owner 的理由。

会话生命周期：加载 skill 把角色分配给会话的那一刻算开始，钩子看得见这次加载，自动登记进 sessions 账（钩子代角色写，actor 填角色）。销号也由钩子自动做，挂在 SessionEnd 和 SubagentStop 上，不指望模型自觉调结束命令；gyb 也可以手动结束，可以指定别的会话。销号时程序当场检查这个会话作为 holder 有没有还挂在开干的单子（只查开干，原则 3 推论），有就不许悄悄下线：钩子调的销号默认把单子交回待干并写进度说明「会话销号，holder 是 X」、给 owner 发孤儿通知，experiments/ 里的脏改动打一个 wip/<单号> 分支记进说明。钩子漏掉的，`rl status` 有一段「holder 会话超过 N 分钟没写任何账的开干单子」先露头，gyb 或 owner 当场 release；再没人管的由 `rl reclaim` 兜底：列出很久没动的会话和单子，gyb 定期手动收，可以逐条挑或跳过；回收对开干的发射单先走中断收尾（杀进程、释放显存、宿主销号、runs 落 killed）再交回待干，对卡住的单子只清 holder 状态保持卡住并把 issue 改派给 owner，对等验收和待干的只列出附现成命令不动手；回收完自动跑一遍 doctor。定时提醒定期叫 gyb 跑回收、看 feedback 账、跑 doctor、把采纳的 feedback 落进母版并单独 commit。

## 分权与钩子

约束分三层（原则 2）。

第一层是钩子，硬拦，宽宽的：只挂 Write 和 Edit 两个工具，只按研究仓库内的相对路径判，仓库外的路径（git worktree、产物根、/tmp）一律放行；只拦两类事：写别的角色的目录（experiments/ 只有 deploy 能写，analysis/ 只有 analysis 能写，review/ 只有 reviewer 能写，notes/ 只有 gyb 能写），和直接 Write/Edit loop/。其余路径（仓库根的 run.py、MAP.md、ops/、docs 之类）钩子放行，纪律管（见 deploy 一节）。Bash 写出来的文件钩子不看，所以宿主发射器 `run.py launch` 写 ops/jobs.json、ops/runs.jsonl、RUNMETA.json 这些照旧，不算越权。硬拦只管加载了角色的会话；gyb 的裸终端和 `--as-gyb` 不受钩子约束。

第二层是入账校验，硬的：九本账只能经 bin/rl，每本账内部谁能追加哪种行、哪一版哪些字段必填、转移表允许哪些变化，都由入账脚本按施工计划校验，违反的拒收并说明下一步。gyb 只豁免「谁能调」和「谁能写」，完整性校验对 gyb 同样生效，`--force --reason` 硬写留痕（原则 1 推论）。

第三层是纪律，写在 SKILL.md 里：读什么、怎么读、Bash 里能写什么、什么时候该开 issue、什么时候该停下来问 gyb。读权一律不硬拦，查询命令谁都能调。reviewer 事后审的就是这一层。

没加载角色的裸会话身上没有钩子，什么都能写，这一点不用兜底钩子去堵：init 往研究仓库的 CLAUDE.md 里写一节，内容有三句：「没有 gyb 允许，experiments/、analysis/、review/、loop/ 只能在加载了对应角色的会话里改」；「加载了 run 角色的会话以 run 的 SKILL.md 为准，它是 gpu-run 的超集，宿主 GPU 铁律里的『唯一入口』对 run 会话读作 run skill」；「loop/*.jsonl 和 loop/.lock 不算脏树」（new1 的发射门禁白名单要加这两样，宿主 CLAUDE.md 那一行由 gyb 改）。裸会话和读权一样靠纪律。

钩子跟角色绑定，先有角色才有钩子：钩子写在角色 SKILL.md 的头部，加载角色的那一刻装上，不存在「用钩子去认角色」这回事（机制 2026-08-16 已实测：加载前不拦、加载后拦、拦的时候模型收到钩子写进标准错误的原话）。

钩子的回话要指路：拦下越权用 deny，同时告诉模型你是谁、为什么拦、去开 issue 的命令是什么。读失败之类的场合同样要返回合理的下一步建议（换个办法、还是发给哪个角色），学 Claude Code 工具调用失败时的回话方式。

读的纪律写进每个角色 SKILL.md 的读法栏，公共母版里的原话方向：读文件先想清楚要回答什么问题，再挑最小的读法。读进来的每个字都留在上下文里挤占后面的判断，所以大文件禁止整读，抽查实验输出就是抽几条看文字形态，日志用 grep 和头尾定位。读记忆一律经 rl 的查询命令、只读自己需要的那部分、默认最新版，不直接开 loop/ 下的文件；`rl inbox` 和 `rl decision stale` 都只列和本会话手上单子有关的，不列全库。对污染上下文大的读操作特别警惕。

## 入口 skill 与代码迁移

入口 skill 只干三件事：init、迁移提醒、领路，明写「本 skill 不干别的」。只许 gyb 手动调用，永远不许模型或其他东西调用（候选机制是 skill 头部声明禁止模型调用，待验证）。领路是几条常见路线图，头几条是：「一批结果出来之后先开 analysis 出数再开 idea 落决定」「新想法先开 idea 落决定再派工单」「结果不对先开 reviewer」「只想先跑一把看数、不打算留决定和报告的，gyb 直接点快车道；其余走正常路」「收到定期提醒：rl status、rl reclaim 看列表、--apply、按 owner 逐个拉起、rl doctor」，加载角色的动作是 gyb 在终端里 `/`加角色 skill 名。

迁移是搬文件，不是登记指向。理由：文件不搬，写权钩子按路径拦这一条就只覆盖新写的代码，老代码全在钩子外面。new1 的老代码由 gyb 手动按需搬（2026-08-16 晚裁，全量搬的 workflow 作废），入口 skill 只在 deploy 报告里列出「这次改了哪些 experiments/ 外的文件」时提醒 gyb 搬。研究仓库代码量小，搬得动。

- 原则 1 补「rl 只认会话不认手指」。归进来的：`--as-gyb` 缺 quote 设计文档说靠纪律、施工计划说拒收（8 个场景各报一次）；gyb 本人坐在角色会话里分不出是谁敲的；gyb 定的决定落 gyb 那本还是角色那本两种读法；grants 可以自提自批；gyb 的豁免包不包括转移表的前提栏和 runs 的 actor 限制；手动会话 model 从哪来；sessions 分不出手动还是 subagent。改了「gyb 自己做的事」的身份段、idea 一节 actor 判据、deploy 一节 gyb 拍板句、账本一节 grants 和 sessions、分权第二层的豁免范围。
- 原则 2 补「读不设权」。归进来的：grant list 只有 gyb 能调、feedback 只能写不能读、机器检查把查询命令也算进 ledger_writes、run 上线跑 decision stale 越出自己的 reads。改了「五个角色」总段、账本 feedback 一条、分权第三层。
- 原则 3 补「holder 非空当且仅当开干」。归进来的：销号扫哪些状态两份文档不一样（11 个场景各报一次）；交活和卡住不清 holder 于是销不了号；stuck→todo 两行前提打架；withdrawn 那一行没写清 holder；两个会话先后 start 同一张单；owner 角色没有活会话时谁拉起；gyb 手动接单没法表达；等验收的单子 holder 指着死会话。改了「交接」一节的状态段、接单段、会话生命周期段，idea 一节的开单旗子。
- 原则 4 补「每本账有 status、前提查在交付」。归进来的：runs 和 sessions 没有 status 字段校验器无从查；分析单和口径互为前提（5 个场景）；口径引用不带版本；approved 的口径能不能再改；改单子内容没有路（换命令、补报告路径、补 handoff 引用）。改了账本一节开头、analysis 一节的口径段、idea 一节的分析单句、交接一节的交付物段。
- 原则 5 补「gyb 也有 use case 表」。归进来的：两条线并行时 status 混排、每条要两跳才认线、list 没有按 owner 或 holder 过滤、--mine 没定义、status --json 结构没写、rl status 七段和八段两处不一样、doctor 的修法命令没写、reclaim 不能逐条挑。改了「交接」一节的收件箱段（列什么只在施工计划写一遍）。
- 原则 6 补「两个收件箱、推送有表」。归进来的：feedback 提了没人叫 gyb、角色名下的 issue 没有推送、withdrawn 通知没人关、retired 决定名下还有活单没人扫、doctor 结果没有落点、issue 从 answered 到 closed 谁打、首次开给 gyb 的 issue 通知两处说法不一、reviewer 干活期间收件箱里没痕迹、决定改版那一刻不列受影响的单子、监控入口到不了 gyb 眼前。改了「五个角色」总段的上线第一动作、账本一节 issues 和 feedback、决定树的改版句、reviewer 一节。
- 原则 7 补「进出都是账上的一行、不是 deploy 专属」。归进来的：scratch 只有 add 没有关张、快车道补单 deploy 开给自己自己验收、补单要两份报告把免掉的手续搬到出口、快车道要不要写决定账、宿主台账登不登记、track 填 quick_lane 对不上 TIMELINE、worktree 建在哪、标签谁分、派 gpu-runner 算不算越权、已开出的工单能不能转快车道、analysis 没有轻路。deploy 一节的快车道段拆成独立小节重写。
- 原则 8 补「可枚举的只写一遍」。归进来的：status 段落、销号规则、通知触发、quote 规则、机器检查范围各在两份文档里各有一句且不一样。这一版设计文档不再抄施工计划的表，改成指过去。
- 原则 9（新）显式链。归进来的：handoffs 没有父单字段（12 个场景各报一次）；发射单不引决定所以 stale 看不见正在烧卡的单；run_id、track、config 谁定；batch 被当两种粒度用；根决定没定义；重开的单和被收回的单看不出是同一件事；顺不回决定要五条命令。改了 deploy 一节的发射单段、idea 一节的根决定句、账本一节 handoffs 和 runs、决定树的 reissue 句。
- 原则 10（新）多次尝试。归进来的：修完代码发射单上的命令还是旧的、分步表跨轮累加、崩掉的那次没地方记耗时、killed 和 ok 的 run 混在一起、跑失败填哪个 kind、smoke 没有日志文件、看门狗判死之后谁杀、宿主账在失败分支没收尾、run 上线跑过版检查空转。改了 run 一节、deploy 一节的卡住段、账本一节 issues 的种类。
