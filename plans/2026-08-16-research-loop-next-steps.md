# research-loop 插件开发计划（2026-08-16 定稿）

这份文档是 research-loop 插件在 2026-08-16 四轮讨论之后的设计现状：上午一轮逐步确认锁了六个裁决和五块架构，下午一轮语音打磨，晚上一轮按 gyb 的真实用法从 init 走到 reviewer 做了纸上走查，最后一轮拿三个 subagent 的审读意见（原文在 `plans/2026-08-16-research-loop-plan-critiques.md`）逐条裁了八个题目。四轮的结论全部合并写在这里，往后施工以这份为准，和 `.scratch/research-loop/redesign.md` 冲突的地方以这份为准。

## 目标与总验收

这套东西服务的是研究：想法要快速、多次迭代，代码风格不要求严密，能出数字就行。设计里每一条手续都要拿这两点去衡量。

先把共同底座和交流用的 json 落进插件，落完之后才写五个角色的 SKILL.md。总验收由 gyb 定：每个角色配一个对应的任务，两个 agent 一个加载角色 skill、一个不加载，各做一遍，产出摆在一起由 gyb 自己看，不预先定判分办法。

## gyb 自己做的事

这套系统里有几件事只有 gyb 亲自做，任何角色都不代劳。

文献变成想法这件事由 gyb 亲自做。gyb 自己做文献调查，把调查报告写成 md 放进 notes/，notes/ 只有 gyb 写，谁都能读。这一版不加文献线，也没有角色去查「这个想法别人做过没有」，要加文献账是另一件事；notes/ 就是文献进入这套系统的唯一入口。idea 角色要经 gyb 允许才有读文献的权限。

分析什么、画什么图由 gyb 亲自说。口径账每一行都是 gyb 说、analysis 记、gyb 批，任何角色都不许自己写新的要分析的东西，analysis 不许自作主张画图，只把 gyb 说要看的数算出来。

另外五件：写 grants 账（授权只有 gyb 能写）、裁 feedback 账（谁都能提、只有 gyb 能裁）、手动结束会话、手动开 reviewer、定期跑回收命令收拾很久没动的会话和单子（有定时提醒叫他）。

## 五个角色

idea 和 gyb 交流想法，出工单派给 deploy。deploy 写代码，把探索性概念转成清晰可发布的实现，把怎么运行交给 run。run 看服务器、运行实验、主要负责长时间的任务，出问题回报。analysis 分析实验结果，按 gyb 说的算数、画图。reviewer 审查整条链有没有照定好的执行。

每个角色由两份文件定义：一份 SKILL.md，一份 json。json 里四样：能读哪些记忆、能干什么事、能给谁派活、用哪个模型。五份 json 合起来就是分权表本体，钩子按角色读自己那份。一个会话只加载一个角色。

### idea

idea 和 gyb 谈想法，谈定的东西写进 idea 的决定账。gyb 会参与到影响实验结果的工程细节里，这些细节同样写进决定账，reviewer 的审查基准只有这些 gyb 定下的决定。

每条决定必须带来源。来源是一个列表，每一项是三类之一：旧决定的编号加版本、仓库里的文件路径（notes/ 里 gyb 写的调查报告，或者 analysis/ 里 analysis 按 gyb 要求算出来的图和 notebook）、runs 账里的一个 run_id。三类可以混着放；至少一项，空列表入账脚本拒收。跑完实验才知道的结论（比如「学习率太低，换高一点再跑」）就是这么进账的：这种结论 gyb 可以得出，模型也可以得出，来源都指那次跑的 run_id 和 analysis 的图，成为原决定的新一版或者一条新决定。不设「口头」这一类来源，每条决定都要能追到一个文件或一个数字。

idea 把决定拆成工单派给 deploy。工单里不能只甩决定编号，还要附一段 idea 自己写的解释，把那条决定里的东西讲明白，解释权在 idea。怎么测试、什么算成功，也要 idea 自己想明白，只是不预写成单子上的字段。deploy 干完之后由 idea 验收，验收的办法见「交接」一节的部署报告。

idea 也可以给 analysis 开单，但是单子里只能引已经批准的口径行。

### deploy

deploy 写代码，写权只有 experiments/，写的是研究代码，不要求严密的工程风格。干完写部署报告，分两份：一份像论文里那样只讲做法、用了什么技术、数据怎么被处理，不带任何文件；另一份带上文件和处理细节。两份放 experiments/ 下这张工单自己的目录里，提「干完等待验收」的时候派活单记报告路径。

deploy 给 run 开发射单，附命令和参数。deploy 不跑 smoke、不估时长，这两样都是 run 的活。

deploy 有一个快车道模式，不是新角色。触发条件是「决定不动、只微调代码」。deploy 在一棵独立的 git worktree 上改，自己小规模跑（GPU 照旧走 gpu-run，只是不开发射单、不叫 run、不做分步计时、不写两层部署报告）。快车道的产物文件留在 worktree 目录里，跑出来的数字不进 runs 账，进一本专门的杂账（见「账本」第 9 本）；gyb 看着行就合回主分支，合回那一刻补一张正常工单引上决定，主分支上永远只有走过工单的代码，合回之后要正式数字按正常路再跑一遍。

### run

run 要小要快，模型用 sonnet。一张卡一个 run，多卡跑一个任务的例外。deploy 一次开 N 张发射单，一个 workflow 起 N 个 run subagent 各接一张。

run 接单先跑 smoke。预计时长不许模型自己猜，也不许拿一题时间乘题数：run 先读代码列出每一步都干了什么，smoke 的时候给每一步计时，GPU 步按规模外推（装载一次大模型这类一次性开销也是 GPU 步，只算一次），CPU 步很短可以忽略，加总填进发射单的时长字段，分步表附在单子里。看门狗判两件事，分开判：卡死看进展停没停（日志多久没新行、产物目录多久没新文件、显卡利用率是不是掉到零），和预计时长无关；超时才用预计时长乘一个宽松系数。跑完之后 run 把真实耗时回填到发射单上，几次之后就知道外推偏多少。

产物根只有 run 的任务能写，数字账只有 run 的脚本能写。出问题开 issue 回给 deploy。

### analysis

analysis 写权只有 analysis/，读 runs 账、写统计代码和 notebook，把 gyb 说要看的数算出来。先问 gyb 要统计什么，问完再出推荐口径给 gyb 批。画什么图 gyb 自己定、自己说，analysis 只按 gyb 说的画，不许擅自替 gyb 主张画什么图。analysis 的上游是 idea，gyb 直接开 analysis session 的时候上游填 gyb。

### reviewer

reviewer 由 gyb 手动开，审整条链，产出只写 review/ 里的问题清单，不开 issue、不派活，动不动由 gyb 看完之后定。清单不进 notebook。

reviewer 审的是「gyb 和 idea 层谈定的东西有没有被好好执行」，具体三样：代码写得对不对、实验运行得对不对、analysis 写的分析代码和 notebook 是不是 gyb 要的。它审分析代码，不碰数据统计本身，统计是 analysis 的活。

对抗性隔离：reviewer 默认不读 deploy 的想法和部署报告，只读 idea 的决定和最终的代码，从不知道实现者怎么想的位置对抗着查。gyb 口头点名让读才读，不走 grants。这条靠纪律写进 SKILL.md，不上钩子（gyb 裁定「读权一律不硬拦」无例外）。reviewer 永远不读文献、不猜 gyb 的意思。

## 账本

账本一共九本，全放 loop/，一行一条 json（不用 markdown），只经 bin/rl 命令进出，只增不改。多个会话会同时追加同一本账（比如 N 个 run 同时写数字账），所以 bin/rl 加文件锁，而且「扫号、分配编号、追加」三步放在同一把锁里，不许扫完号再排队写，否则同角色两个会话会撞号。跨两本账的写入（比如标卡住要同时开 issue 互相引用）定死写序：先写 issue 拿到编号，再写单子那一行引它，中间崩了顶多多一条没人引的 issue，doctor 命令扫得出来。

1. decisions，决定账，按五个角色拆成五个文件，五个 session 并行各写各的不撞车。
2. issues，问题条：干不了、不归我干、被钩子拦了，开一条等上游或 gyb 回。每条带「归谁」字段，run 开给 deploy，deploy 解决不了改派给 gyb。只有改派到 gyb 名下的时候 bin/rl 才给 gyb 发通知，其余不发。通知是桌面弹窗（机制待验证）；gyb 问「有什么 issue 没处理」的时候 rl status 列出来，就这两层。
3. handoffs，派活单：工单和发射单同一本账，用 work_type 区分。工单带解释和部署报告路径，发射单带命令、参数、时长字段和分步表。
4. runs，数字账，一个 schema，只有 run 角色的脚本能写。
5. grants，授权，只有 gyb 能写。
6. feedback，反馈账，谁都能提、只有 gyb 能裁。
7. evaluations，口径账，一行一个指标，gyb 说、analysis 记、gyb 批准后才生效。
8. sessions，会话账：哪个会话、什么角色、几点开始、几点销号。
9. scratch，杂账：deploy 快车道模式跑出来的数字，只有快车道写，格式松、不校验，analysis 和 reviewer 默认不读。快车道的东西一旦要进正账拿来复用，它就不是快车道了，得按正常路重跑。

行格式的公共骨架五样：主键、时间、写这行的角色、内容字段、schema_version。每一版另记写入会话的 session_id。

决定账的结构是一棵引用树：
- 编号带角色前缀（dec-idea-0007），更新不换编号、版本号加一。默认读取对每个编号只取最新版，历史全在文件里但默认读不到，要旧版本用专门的历史命令。废除等于追加一版标 retired。
- 两个旧决定可以合成一个新决定：新决定拿新编号，来源列表指多条旧决定，旧的各追加一版标 retired。
- 跨层引用带版本（「依据 dec-idea-0007 第 2 版」）。引用记的版本比账里最新版小就是过时，查询命令当场标出「上层依据已从第 2 版更新到第 3 版，复核这条还成不成立」。角色上线第一个动作跑过版检查。
- 决定改了一版，不影响已经派出去的单子：单子按派出时引的那一版继续做，rl 只标过时，不自动打回、不自动标待复核、不自动停。停不停由 gyb 点名，停就用收回。

## 交接与会话生命周期

派活单的状态：待干（上游开单时写）、开干（下游接活时写）、卡住（下游写，必须连带开 issue 互相引用，谁回了 issue 谁捞回开干）、干完等待验收（下游写）、验收完成（只有上游写，验收人必须是派活的人）、打回（上游写，必须附原因，打回之后下游重新开干）、收回（上游写，单子关闭）。这些状态和转移不写成散句，写成一张显式的转移表，一行是一次状态变化：从哪个状态、到哪个状态、谁能写、要满足什么前提。入账脚本读这张表校验，文档里就不会再出现两句互相打架的话。

接单分两种。默认是上游开完单直接起一个 subagent 接走，比如 deploy 起 run 的 subagent 去跑；gyb 想手动跑的时候，上游只开单，gyb 自己开 session 去接。subagent 加载角色 skill 那一刻和普通 session 一样登记进 sessions 账。

验收不预写标准，验收产物是部署报告。理由：要验的是「代码和想法是不是一回事」，这个判断在代码写出来之前写不成条目，写得成条目的（跑得通、快不快）不是要验的东西。所以 deploy 提「干完等待验收」必须附报告路径，路径为空入账脚本不收这个状态。验收人（默认 idea，gyb 点名的时候是 gyb 自己）先读不带文件的那一份看做法对不对，再读带文件的那一份看写出来的东西和说的是不是一回事，打回要写明原因。

交接由程序盯着，不许有去无回：rl status 现场汇出所有没走到验收完成的单子，谁手上、卡在哪个状态、挂了多久，另外单列「改派给 gyb、超过 N 小时没动的 issue」。上游可以收回：对派出去还没干完的单子追加一版标收回，单子关闭。

会话生命周期：加载 skill 把角色分配给会话的那一刻算开始，钩子看得见这次加载，自动登记进 sessions 账。销号也由钩子自动做，挂在 SessionEnd 和 SubagentStop 上，不指望模型自觉调结束命令（subagent 上下文满、报错、被中断的时候结束命令不会跑）；gyb 也可以手动结束。销号时程序当场检查这个会话名下有没有还挂在开干的单子，有就不许悄悄下线，要么交回待干让别人接，要么标卡住开 issue。钩子漏掉的，rl 有一条回收命令列出很久没动的会话和单子，gyb 定期手动收；定时提醒定期叫 gyb 跑回收、看 feedback 账、迭代框架本身，框架要随着用一起改。

## 分权与钩子

写权硬拦，按路径判：experiments/ 只有 deploy 能写，analysis/ 只有 analysis 能写，review/ 只有 reviewer 能写，notes/ 只有 gyb 能写，产物根只有 run 的任务能写，loop/ 谁都不许直接 Write/Edit，九本账只能经 bin/rl。没搬进 experiments/ 或 analysis/ 的老代码不在任何角色的写权里，不设过渡期旧路径清单，也不给仓库根的 run.py、MAP.md、ops/ 这类文件开白名单：deploy 或 run 撞到这类文件，钩子拦下并提醒 gyb「把这个文件搬进 experiments/ 再改」，搬不搬 gyb 手动定。每本账内部谁能追加哪种行，由入账脚本按上面两节的规矩校验。读权一律不硬拦，靠纪律。

硬拦只管加载了角色的会话。没加载角色的裸会话身上没有钩子，什么都能写，这一点不用兜底钩子去堵：init 往研究仓库的 CLAUDE.md 里写一句「没有 gyb 允许，experiments/、analysis/、review/、loop/ 只能在加载了对应角色的会话里改」，裸会话和读权一样靠纪律。

钩子跟角色绑定，先有角色才有钩子：钩子写在角色 SKILL.md 的头部，加载角色的那一刻装上，不存在「用钩子去认角色」这回事（机制 2026-08-16 已实测：加载前不拦、加载后拦、拦的时候模型收到钩子写进标准错误的原话）。

钩子的回话要指路：拦下越权用 deny，同时告诉模型你是谁、为什么拦、去开 issue 的命令是什么。读失败之类的场合同样要返回合理的下一步建议（换个办法、还是发给哪个角色），学 Claude Code 工具调用失败时的回话方式。

读的纪律写进每个角色 SKILL.md 的读法栏，公共母版里的原话方向：读文件先想清楚要回答什么问题，再挑最小的读法。读进来的每个字都留在上下文里挤占后面的判断，所以大文件禁止整读，抽查实验输出就是抽几条看文字形态，日志用 grep 和头尾定位。读记忆只读自己需要的那部分、默认最新版。对污染上下文大的读操作特别警惕。

## 两棵树

init 在研究仓库里建的（六样加一句）：research-loop.json 配置（各账路径、产物根、本仓库跑法）、loop/ 九本账、experiments/ 运行实验的代码、analysis/ 统计代码和 notebook（公共统计件由 init 播模板，notebook 由 analysis 干活时新建）、review/ reviewer 的产出、notes/ gyb 自己写的文档；另外往仓库的 CLAUDE.md 里写上一节裸会话的纪律。原始数据不新建目录，走配置里的产物根，在 new1 指到 net 盘。

插件本体：skills/ 六个（入口加五个角色）、common/ 公共母版（通例九条、词表、五栏规格）、tables/ 和 schemas/（九本账的表结构和行格式、派活单的状态转移表）、scripts/ 入账与查询的实现、bin/rl 命令入口（含 status、回收、doctor）、hooks/ 钩子脚本本体（五个角色共用一个脚本、参数报角色名，落不落得下见待验证；登记和销号的钩子也在这里）、monitors/ 两个（发射看门狗只在 run 上线时起、反常结果预警盯数字账）、tests/。

## 入口 skill 与代码迁移

入口 skill 只干三件事：init、迁移、领路，明写「本 skill 不干别的」。只许 gyb 手动调用，永远不许模型或其他东西调用（候选机制是 skill 头部声明禁止模型调用，待验证）。

迁移是搬文件，不是登记指向。理由：文件不搬，写权钩子按路径拦这一条就只覆盖新写的代码，老代码全在钩子外面。归类要读代码做判断，所以由模型做。首次加载 init 问 gyb 一句：全量搬还是按需搬。全量搬发一个 workflow，subagent 分头搬并修 import 和注册表；按需搬就先登记，之后每次要改一个老文件先搬那一个。研究仓库代码量小，搬得动。

## 待验证清单（gyb 裁定：讨论全部收口之前一律不测）

1. Bash 环境里有没有现成的会话 id 变量；没有就用 SessionStart 钩子写状态文件。
2. skill 头部声明钩子能不能给命令带参数（五个角色共用一个钩子脚本靠它）。
3. monitor 的 when: "on-skill-invoke:run" 写法实测行不行。
4. skill 头部禁止模型调用的声明，能不能把入口 skill 锁成只许 gyb 手动调用。
5. SessionEnd 和 SubagentStop 钩子在 subagent 结束的时候会不会触发、拿不拿得到和启动时同一个会话 id。
6. 桌面弹窗通知用什么机制能到 gyb 桌面（Claude Code 自带的推送通知，还是这台机器上的系统通知命令）。
7. 定时提醒用什么机制（cron 还是 Claude Code 的 schedule）。

## 施工步骤

施工之前 gyb 先自己打磨这份设计文档。之后写架构文档（一个文件一行）、施工第一段共同底座、第二段交流用的 json、三个 session 并行写 SKILL.md、装上跑通最小一条路、总验收对比。

## 审读意见里没采纳的

三个 subagent 的三十条意见里，八个题目已经裁进上文。剩下九条只出现一次、这一版不采纳，一行一条写为什么：

1. 部署报告按改动大小分档：小改动走快车道，快车道不写报告，分档没必要。
2. 分步计时只对长任务做：同上，小任务走快车道，正常路的发射单一律做。
3. 下游发现 typo 的小修口子：写权按角色不开例外，run 或 analysis 发现代码问题开 issue 给 deploy。
4. 第一版只给按需搬不给全量搬：全量搬保留，走 workflow，是不是吃一周由 gyb 首次加载时自己选。

6. 口径按组批不按行批：analysis 不许自作主张，要看什么 gyb 一条条说，按行批就是这个意思。
7. 验收那一步 gyb 在不在场：默认 idea 验收，gyb 点名的时候 gyb 自己读，已经写在「交接」一节。
8. 环境类失败 run 就地重试一次不开 issue：run 出问题一律开 issue 给 deploy，不给自行重试的口子。
