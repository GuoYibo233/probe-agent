## 第二节 · 每组实验详解

### 实验一 · 注意力内核验证

这个实验问的是：把一个事件的前缀和全部目标段打包成一条序列一次前向（设计文档叫形态 A），在真实显卡上会落到哪个注意力内核，最长的事件要多少显存，逐行 loss 和逐行训练器差多少。

怎么做的：在 tokyo108 的一张 H100 上跑一个验证脚本，脚本从 val 堆里挑出全文不超过 8192 个 token 的最长事件（64 行，前缀 8,167 个 token，打包后 9,381 个 token），按顺序做九步：问 torch 四种内核对真实形状的掩码各自接不接；强制用省显存的 mem-efficient 内核做一次前向加反向记峰值和内核名；不指定内核再做一次看默认落到哪个；在一个 2,048 个 token 的短事件上量 math 内核的峰值；换四种掩码写法（布尔或 bf16 加性，长度补不补到 16 的倍数）各记峰值；在同一批 5 个短事件 34 行上把打包前向和逐行训练器的逐行 loss 逐行相减；开梯度检查点再量一次最长事件；挂 LoRA 再量一次。脚本一共发射三次，前两次分别在 math 那一步和对齐那一步崩掉、改脚本后第三次九步全过。

为什么这么设计才算数：变的只有前向的形态和内核，模型权重、事件、精度设置全部相同，所以 loss 的差只能来自形态和内核。开跑前定的判据（设计文档第五节）是 fp32 下逐行 loss 最大差不超过 1e-5、逐 token 不超过 1e-4，超过就说明掩码或位置编号错了；显存的判据是最长事件的峰值对 H100 的 93.10 GiB 余量不低于 10%。这个设计管不住的是多事件同批的显存，那要等冒烟。

看一条真的：结果文件 `pipeline/runs/smoke/kvshare_gpu_kernel_check/gpu_result.json`（NFS）里强制 mem-efficient 那一步的原始记录是

```
"forced_efficient": {"L": 9381, "mask": "bool", "backends": ["EFFICIENT_ATTENTION"],
  "peak_alloc_GiB": 31.08, "delta_GiB": 28.86, "seconds": 2.96,
  "kernels": [..., "fmha_cutlassB_bf16_aligned_128x128_k128_sm80(...)", "fmha_cutlassF_bf16_...", ...]}
```

同一个文件里 fp32 对齐那一步的原始记录是 `"row_new_vs_old_batched": {"n": 34, "max_abs": 4.410743713378906e-06, "mean_abs": 1.65e-06, "p90_abs": 3.06e-06, "max_rel": 3.10e-06}`。这次运行的 commit 是 024b34f，机器是 tokyo108 GPU 0（H100 NVL 93.10 GiB），torch 2.11.0+cu128，写在同一个 JSON 的 `torch` 与 `gpu` 字段和目录里的 `RUNMETA.json`。

实验结果（数字都出自 `gpu_result.json`，`ops/runs.jsonl` 的 finish 记录抄的是同一份）：

- 内核资格：带掩码的时候 flash 内核拒绝，mem-efficient 和 cuDNN 都接受；fp32 的 query 配 fp32 掩码时 cuDNN 拒绝；不带掩码并且 K/V 只有 8 个头的时候 mem-efficient 拒绝。
- 强制 mem-efficient：最长事件峰值 31.08 GiB，内核名是 cutlass 的 fmha 前向与反向。不指定内核：峰值 31.11 GiB，内核名是 cuDNN 的 sdpa 前向与反向，64 行 loss 的平均值 3.2500 对 mem-efficient 的 3.2452。
- math 内核在 2,552 个 token 的序列上峰值 22.55 GiB，同一输入 mem-efficient 10.37 GiB。
- 四种掩码写法里，bf16 加性并且长度补到 16 的倍数的那一种峰值 26.65 GiB，另外三种 31.11 到 31.20 GiB，四种的 64 行 loss 平均值都是 3.2452。
- fp32 对齐（5 个事件 34 行 505 个目标 token）：打包前向对逐行训练器整批的逐行最大差 4.41e-6、逐 token 最大差 3.05e-5；逐行训练器自己「单行不补齐」对「整批补齐」的基线差是逐行 5.01e-6、逐 token 6.91e-5。bf16 下逐行平均差 9.31e-3、最大 3.07e-2。
- 梯度检查点把最长事件的峰值压到 6.34 GiB；挂 LoRA 是 31.18 GiB。

值得注意的设置细节：第二次发射对齐那一步报「没有可用内核」，原因是逐行训练器的「单行不补齐」批没有掩码，HF 会让 K/V 保持 8 个头走分组查询，而 mem-efficient 内核不支持分组查询；修法是只给打包前向的路径套内核上下文，参照路径用默认内核。所以上面的基线差里，「单行」那一批走的内核和「整批」不同，基线差比新旧之差还大，这一点是按资格表推断的，没有 profiler 实测。另外这个脚本里没有优化器状态，训练时要再加 AdamW 两份状态。

索引：run_id `kvshare_gpu_kernel_check`；脚本 `.scratch/kvshare-train/verify/gpu_kernel_check.py`；判读在 `.scratch/kvshare-train/design-attention.md` 第七节；决定 17、18 在 `.scratch/kvshare-train/decisions.md`。

### 实验二 · 三个格的第一次冒烟加 ctool 的显存补测

这个实验问的是：缓存复用训练器（cgen 与 cparam 两个格）和改过丢弃规则、上限、读取位置的 ctool 训练器，在真实数据的小样本上能不能从头跑到尾，对齐检查过不过；以及 ctool 撤掉截断、上限翻到 8192 之后在 H100 上装不装得下。

怎么做的：三个格各跑一次冒烟档（缓存复用训练器的冒烟档取全文 token 数最短的 40 个训练事件和 16 个评估事件跑 1 个 epoch；ctool 的冒烟档取 200 个训练事件和 80 个评估事件跑 25 次更新），在 tokyo108 的三张 H200 上并行。冒烟档前面先做对齐检查：缓存复用训练器抽 6 个全文不超过 2,048 个 token 的 val 事件，同一份临时文件同时喂给缓存复用训练器和逐行训练器，fp32 关 TF32 逐行比 loss；ctool 的对齐检查是整段一次前向对逐 token 增量前向，比末位隐状态和分类头 logits 的最大绝对差。ctool 的显存补测另外在一张 H100 上发两次，外面包一层每 2 秒记一次 nvidia-smi 的脚本：第一次用当时的默认值每批 4 个事件累积 2 次，第二次改成每批 2 个事件累积 4 次。

为什么这么设计才算数：冒烟档只验「能跑、能存、日志齐、对齐检查过」，不验数字好坏；对齐检查的门槛是开跑前定的（逐行 2e-5、逐 token 3e-4，决定 18，按实验一的 4.41e-6 放 3 倍余量），过了才说明打包前向算的 loss 和逐行训练器是同一个函数。ctool 的两次显存补测只差每批事件数一个变量，一次更新都是 8 个事件，所以峰值的差只能归到每批事件数。这个设计管不住的是冒烟档只取最短事件，显存和速度的数都不代表全量。

看一条真的：缓存复用训练器看到的一个真实事件。val 堆文件 `pipeline/data/nyapass_aw_v1/gptoss/val.jsonl`（NFS）第 3726 到 3728 行是事件 `appworld_gptoss/appworld_0d8a4ee_2_r3|s7` 的三行（行号从 0 数），三行的 `label_call` 字段（标准答案，也就是被探测模型接下来真的发出的调用串）都是

```
apis.api_docs.show_api_doc(app_name=phone, api_name=login)
```

事件全文（`sent_idx` 最大那一行的 `text` 字段，2,028 个字符）开头是任务原文和已经执行过的历史：

```
Task: Send the following phone message to my siblings and roommates, who do not have a venmo account, "Get on venmo please!".
[HISTORY]
# Try logging in to the phone app using the supervisor's phone number as the username
...
Exception: Response status code is 401:
{"message":"Invalid credentials"}
...
```

全文末尾是被探测模型的思考文本，三行各在一个句子边界截断：

```
[THINKING]
We are seeing that phone.login is maybe expecting email as username, but the API docs for login were not retrieved earlier. Let's retrieve phone.login doc.


We need to get API documentation for phone.login to understand parameters.
```

用 Qwen3-0.6B-Base 的分词器现算（和 `share_data.py` 的公共前缀规则同一个算法）：事件全文是 500 个 token；第 0 行（`sent_idx` 0，文本到 `retrieved earlier. ` 为止，1,920 个字符）加分隔串 `\n[CALL] ` 之后是 485 个 token，和全文的公共前缀 480 个，尾巴是 5 个 token `['ĠĊ', '[', 'CALL', ']', 'Ġ']`；第 1 行 491 个 token、公共前缀 486 个、尾巴 5 个（第一个 token 是 `.ĊĊĊĊ`，句号和四个换行并成了一个）；第 2 行 504 个 token、公共前缀 499 个、尾巴 5 个；三行的目标串各 17 个 token（调用串 16 个加结束符 `<|endoftext|>`）。所以这个事件打包之后的序列是 500 个前缀 token 加三段各 22 个 token，一共 566 个 token，三行的 `w` 字段（样本权重）都是 1.0。这个样例只说明一条数据长什么样，不是证据。

实验结果（出自各 run 目录的 `train_log.jsonl`、`ALIGN_CHECK.json`、两份 nvidia-smi 采样文件，`ops/runs.jsonl` 的 finish 记录抄的是同一份）：

- ctool 冒烟档（H200 gpu3）：第一次发射被代码默认容差 1e-4 拦下（最长 val 事件 8,167 个 token，隐状态最大绝对差 1.03e-4，相对差 1.46e-6），默认改成 3e-4 之后补射通过；25 次更新，事件级丢弃 train 1 个、val 3 个，找不到读取位置的切点 0 个，校准集加权准确率（日志字段 `calA_weighted_acc`，ctool 在校准堆上按权重算的判对比例）0.408。
- ctool 显存补测（H100 gpu0，上限 8192，200 个训练事件）：每批 4 个事件累积 2 次，对齐检查过了之后训练第一批前向就爆显存，报错原文 `Tried to allocate 154.00 MiB. ### 实验三 · 速度档

这个实验问的是：缓存复用训练器在 H100 上每秒处理多少行，对逐行训练器同机同行数的速度快多少；token 预算取 16384 还是 24576；分配器的 `expandable_segments` 开关有没有用。

怎么做的：三个 run 都是 b06 的 cgen 格，从 train 堆里按种子 42 随机取 450 个事件（20,641 行，57 次更新），每 3 次更新写一条 step 日志，epoch 中间不评估，开显存探针；三个 run 只差 token 预算（16384 或 24576）和分配器开关，在 tokyo108 的三张 H100 上并行。速度的对照数取自逐行训练器 np821b06 的 cgen 在同一台机器同一张卡型上的日志：累计每秒行数在 1,600 / 9,600 / 19,200 行处是 2.76 / 3.26 / 3.97，三个窗口（0 到 1,600、8,000 到 9,600、17,600 到 19,200 行）的每秒行数是 2.77 / 3.94 / 6.24。缓存复用训练器的数用 step 日志里的累计行数和训练秒数夹住对照行数做线性插值。

为什么这么设计才算数：按相同累计行数比而不按更新次数比，是因为 tokyo108 上每个 run 头 2,000 步有爬升段，只比第 50 次更新会把爬升当成加速（决定 9）；三个 run 种子相同、事件顺序相同，所以每个窗口里的行数逐条相同，差异只能归到预算和开关。开跑前定的判据（spec 第 1 节）是六个对照数全部高于逐行训练器，整程峰值对卡容量的余量 10% 以上。这个设计管不住的是 450 个事件只是 train 堆 4,127 个事件的 11%，末尾窗口的速度受那一段事件的长度影响。

### 实验五 · 第二轮冒烟：三个新配置加两个新开关

这个实验问的是：b17、l17、l4 三个配置在缓存复用训练器上能不能跑通、对齐差多大、显存探针量到多少（给学习率扫描排卡用）；b06 上新加的挑块方式 cost 和 loop、生成式评估、梯度检查点这几条代码路径走不走得通。

怎么做的：七个 run 都是 cgen 格的冒烟档（最短 40 个训练事件、16 个评估事件），都开显存探针和 200 行的生成式评估。b17（不开梯度检查点）和 l17（LoRA，不开）上 H200，挑块方式 tokens；l4（LoRA，开梯度检查点）上 H100，挑块方式 tokens；b06 三次都在 H100：smoke2 用 cost、smoke3 用 loop、smoke4 开梯度检查点用 tokens。l4 第一次在显存探针的第一次反向崩掉，修代码后重发（smoke2）。挑块方式 tokens 的意思是从 train 全集里挑 token 数最多的两块（最满块和最长事件），cost 是枚举本次 run 第一个 epoch 的全部物理块、按 token 数、损失位数、两者归一化之和各挑一块，loop 是对 cost 挑出的三块各按真实训练循环跑一组更新。

## 第六节 · 我的判断

这一周真正立住的东西只有一件：缓存复用训练器可以替代逐行训练器。理由是第三节的对齐表和速度表，逐行 loss 的差在 5.007e-6 到 1.5378e-5 之间、随底座单调涨、同卡型逐位可复现，而速度在同一张 H100 上是逐行训练器的 46 到 67 倍（累计三点 185.6 / 189.5 / 184.1 对 2.76 / 3.26 / 3.97）。这个结论的边界是 b06 的 cgen 格和 450 个事件的样本，cparam 只有冒烟档，ctool 走的是另一条代码路径，两者的全量数字一个都没有。

学习率扫描回答了扫描要回答的问题，但答案对代码默认值只动了一半。全参两个配置的最低点都是 1e-5，和默认值相同，两侧 2e-6 和 5e-5 都高（b06 0.2157 / 0.1730 / 0.1857，b17 0.2046 / 0.1636 / 0.1750）；LoRA 两个配置的最低点都是 5e-4，比默认值 2e-4 高 2.5 倍，两侧 1e-4 和 2e-3 都高。所以「要不要改默认值」这个决定实际上只关 LoRA：全参改不改结果一样。这个决定卡着新口径的正式训练，因为批次前缀和 invariants 都要跟着定。l4 在 2e-3 上 loss 第 70 次升到 4.2674 又回到 0.5433，说明网格上端对 4B 已经过线，这一档不必再往上试。

显存的账已经算平了。cost 挑块方式的显存探针对四个配置的整程峰值只低 0.001 到 0.422 GB，1.1 倍的折是按第一轮显存探针 7.5% 的偏差定的，对 cost 可以降到 1.05，但这只是排卡余量的事，不影响任何结论。

第二节和第五节里有两处窟窿要点出来。第一，`WORKPLAN.md` 已经落后两段，按规矩由 gyb 改。第二，np821 十二格是唯一评测过的探针，而这十二格是旧口径；新口径下连 b06 的三格全量都没有跑，第五节 5.3 那 99 GB 的扫描权重是 1 个 epoch 的 cgen，没有评测过。要拿新口径的探针去做任何下游的事（活跑注入、矩阵对比），先要决定学习率，再跑三格全量，再评测；按实验七的墙钟，cgen 格 1 个 epoch 的一个 run，b06 在 Ada 上 3494.7 到 3678.9 秒，b17 在 H200 上 2299.3 到 2830.4 秒，l4 在 H100 上 7081.2 到 7284.8 秒。

第六节以下没有别的判断。文档末尾的「已知没处理的地方」等阶段 4.5 的检查员报回来之后补。
