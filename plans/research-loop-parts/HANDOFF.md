## 二、每份 part 的固定结构（part session 改的时候要保持）

```
# 标题
> 覆盖什么、不覆盖什么；源：设计文档哪几节、施工计划哪几节
## 正文（若干小节）
## 和别的 part 的接口
## 源文档没写清的（留给 gyb）
## 第二轮模拟里归到这一份的摩擦（原样，未核实）
```

part session 定稿之后会多两节：

```
## 裁决记录（日期）
## 要同步到别处的
```

「裁决记录」一行一条带日期，是 gyb 说的原话或原意；「要同步到别处的」一行一条，写清目标文件名和要改成什么。摩擦那一节永远原样保留。

## 三、统筹 session 和 part session 怎么通话

统筹 session 的名字由 gyb 定（当值的叫 `rl-hub-v6`），part session 的名字是 `rl-part-<编号>`（比如 `rl-part-10`），名字定了两边才找得到对方。同一台机器上的 Claude Code 会话互相能看见：用 `ListAgents` 列出来，用 `SendMessage` 按名字发消息（收件人名字照 `ListAgents` 那一行原样抄）。part session 有事回报就 `SendMessage` 给当值统筹；统筹有话交代就 `SendMessage` 给 `rl-part-<编号>`。

消息发不出去（对方还没开、`ListAgents` 里没有）就走文件邮箱：往 `plans/research-loop-parts/sync-inbox.md` 末尾追加一段，格式固定：

```
## <日期 时间> 来自 <会话名> 关于 <part 文件名>
- 事项：<一句话>
- 裁决原文：<gyb 说的>
- 要改的地方：<目标文件名>：<哪一句改成什么>
- 状态：待处理
```

统筹每次开工先读 `sync-inbox.md`，处理完把那段的状态改成「已处理 <日期>」。消息和邮箱两条路的内容一样，邮箱是兜底，不是可选的第二份：发了消息也要往邮箱补一段，这样会话崩了记录还在。

part session 要回报的三种事：（1）一条裁决动到了别的 part 里的东西（字段、状态、命令、接口一节列的），把裁决原文和要改的目标句子报上去，自己不去改；（2）自己这份里的一句和别的 part 打架，两边原文报上去等裁，不自己定；（3）这份过完了，报一句「`<文件名>` 定稿，commit `<hash>`」。回报之后不等回音接着往下过；统筹有回话（比如「这条别处已经裁成另一个值」）再照回话改。

统筹要交代给 part session 的两种事：（1）它手上那份 part 里的某一句，因为别的 part 先裁了，现在要改成什么，附来源 part 的裁决原文；（2）它报上来的打架 gyb 裁了，结果是什么。

## 三点五、part session 怎么开（2026-08-21 起：fork 母体开法）

gyb 先开一个母体 session 把公共材料读好，再从它 fork 出各个 part 的分支，分支继承母体读过的东西。两段贴话如下。

贴给母体 session 的话：

> 读 `plans/research-loop-parts/HANDOFF.md` 第二、三、四点五节：第二节是每份 part 的固定结构，第三节是和统筹 session 怎么通话（当轮统筹叫 `rl-hub-v6`，文件信箱是 `plans/research-loop-parts/sync-inbox.md`），四点五节是每样东西的定义处和引用处。这些是 research-loop 插件设计拆分文档定稿流程的公共背景。读好之后什么都不要改、什么都不要问，回一句读好了就停下；我会 fork 这个会话，每个分支各领一份 part。

贴给 fork 出的分支的话（`<编号>`、`<文件名>` gyb 换成那一份的）：

> 先 `/rename rl-part-<编号>`。全文读 `plans/research-loop-parts/<文件名>`。这份是 research-loop 插件设计的一个部分，我要把它逐条定稿。规矩：只在这一个文件里改，别的 part 和两份源文档不动（`03`、`04`、`05` 已冻结，动到它们的只报不改）；文件末尾「第二轮模拟里归到这一份的摩擦」那一节原样保留不改；十一条设计原则在 `00-overview.md` 第二节，改任何一条规矩都要能对回其中一条。先读文末「裁决记录」，传播进来的行别再问一遍。然后从「源文档没写清的」那一节开始问我要裁决，正文里标了「两处原文不一致」的地方同样问（裁决记录里已收口的除外）。问法：一次问三个问题；每个问题只讲逻辑，给白话场景和选项，不带文件名、行号、命令名、字段名；每个选项写清利和弊；利大于弊的选项标「推荐」，利巨大弊很小的标「强烈推荐」，拿不准哪个好就一个都不标，直接问我的意见。问完等我答。答案先攒着，全部问完再一次性改正文、删「没写清」里已裁的条、把每条裁决追加到文件末尾「裁决记录（日期）」一节，一行一条带日期。一切默认英语，看到语言相关的约束直接去掉，不用问我。改动牵连别的 part 的（字段名、命令、状态、接口一节里列的东西），不去改那边：在文末「要同步到别处的」一节里列一条，整份过完之后一次性按 HANDOFF 第三节 `SendMessage` 报给 `rl-hub-v6` 并往 `sync-inbox.md` 追加一段。收到 `rl-hub-v6` 的消息照它说的改。全部过完之后把「和别的 part 的接口」一节按定稿重写一遍，commit（前缀 `research-loop parts:`），再报 `rl-hub-v6` 一句定稿。

角色五份 `10` 到 `14` 的分支多贴一句：「json 副本已按 `06` 定稿重抄过，五栏骨架句和派活起法句是统筹传进来的，别改回去；要改 json 栏或 agent 定义相关的，报 `rl-hub-v6` 回 `06`。」

同开的错法：`10` 到 `14` 彼此基本不互引，可以同开；`20`/`21`/`25` 互引、`23` 引 `21`/`22`，同开时错开；角色 part 和它对应的角色对 part（`10` 对 `20`/`22`/`25`、`11` 对 `20`/`21`/`24`、`12` 对 `21`/`23`、`13` 对 `22`/`23`/`24`、`14` 对 `25`）别同时开。建议顺序：先角色五份（它们是 use case 表的定义处，角色对六份都引它们），再角色对六份。

## 四、统筹 session 干什么

统筹常驻，干四件事：

1. 记谁在干什么。维护 `README.md` 进度表里每份的状态（未开、在 `rl-part-NN` 手上、已定稿 commit 几号），part session 报定稿就更新。
2. 收回报、传播。收到 part session 的消息或 `sync-inbox.md` 里的待处理段，先按第四点五节的表判定义处：定义处在别的 part，就把裁决搬回定义处那一份（改它的正文并补进它的「裁决记录」，注明来自哪份），再从定义处往所有引用处传。两份源文档不回写。目标 part 正在某个 `rl-part-NN` 手上的，不直接改它的文件，`SendMessage` 交代给那个 session 去改，它不在了才自己改；已定稿不冻结的八份统筹直接改。动到冻结三份的不改，攒问题标「等最后一期」（见第五节）。传播完把来源 part 里那条标「已同步 <日期>」，把邮箱那段标「已处理」，README 改状态，commit 前缀 `research-loop sync:`。
3. 攒问题等 gyb。传播时发现目标 part 已经有相反的裁决，或者 part session 报上来的打架，不自己裁：把两边裁决原文并排记进 `sync-inbox.md` 一段（状态「等 gyb」），按下面的问法规矩问，裁了再改并回话给相关的 part session、补进两份 part 的「裁决记录」。
4. 补漏。空下来的时候做第一节说的覆盖检查。

统筹开工时先做四件事：`ListAgents`；读这份文档全文；`git log --oneline -20` 加 `git status`；读 `sync-inbox.md` 有没有待处理的。铁律和 part session 一样：只搬运不发明；改任何规矩都要能对回十一条原则（`00-overview.md` 第二节）；两处不一致不自己裁；摩擦那一节永远不动；每份的固定结构不动；gyb 不在场时不猜他的意思，把问题攒着等他。

问 gyb 的规矩三条：（1）选择题式裁决一次问三个，每个选项写利弊，利大于弊的标「推荐」，利巨大弊很小的标「强烈推荐」，拿不准哪个好就一个都不标、直接问 gyb 的意见（2026-08-21 gyb 原话「一次问我三个问题，每个问题提出利弊。问题的选项之后利大于弊的标上推荐，如果利巨大弊很小就是强烈推荐，如果不确定选项的话就不要推荐，问我的意见」）；开放讨论一轮一个。（2）只讲逻辑：场景加白话选项，不带文件名、行号、命令名、字段名，落到哪些文件是统筹自己查的事。（3）讨论期间不开 Monitor（gyb 说吵），落地和空闲时再开，开的话盯 `sync-inbox.md` 的变化即可。

传播的干法：一份定稿牵连五到十五处，统筹自己改就行；十几处以上考虑 workflow——把引用处按文件组切成互不相交的几份交 opus 各干各的（不 commit），每组接一路 opus 审（missed / wrong / invented / contradiction / record_missing），末尾一路全局 grep 漏网，统筹逐条裁、亲自补，再一笔 commit。施工者的规矩：只改名下文件、摩擦一节不动、「没写清」被答掉的条目按清单说销就销否则加「已裁」标注、每份文末裁决记录一问题一行、拿不准的报 undecided 不猜。用量教训：subagent 一次派六个以内（派过 22 个撞月度上限）。
