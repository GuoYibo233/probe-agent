事实到此为止，下面是我的解读。

这个做法成立，三路评审（原则、可实施性、反方）的裁定都是「成立，措辞要改」，驳手没有推翻其中任何一条。要改的是三句话。

第一句，「先用代码规定权限」要说成「先把权限从分册抄录成表和校验」。代码这一步是抄录不是起点：五份角色 json 从 06 逐字照抄，转移表从 04 第三节照抄，行格式从 03 和 02 照抄，actor 判定从 01 和 05 照抄。写 json 的时候每一栏旁边记「来自哪份第几行」，指不回去的条目删掉或者回分册补裁决，这样才防得住「从 json 倒推回来」那种没依据的条目。代码管得住的是写目录（钩子拦住两类）、写账（谁能调、转移表、必填、引用存在）、actor 判定、子会话的工具面收窄；管不住的是读、派活对象、钩子解析不出的 Bash 写法、读的顺序、派活交代的内容、一会话一角色。gyb 举的「能找什么」，按已经裁定的三条只能写进 reads 栏、由测试 13 做文本对照、运行时不拦。要改成运行时拦读，就是推翻三条已经裁定的规矩，这件事我不建议，理由是读的口子太多（查询命令、直接打开文件、搜索），机器拦不全会变成半拦，让人以为拦住了。

第二句，「代码无误之后再翻成自然语言的 skill」要说成「代码和测试绿了之后，SKILL.md 引用代码、写代码管不住的纪律」。把 json 四栏重述进 SKILL.md，测试 13 的第三样会红，修改母版也就不生效。SKILL.md 五栏里只有「可用工具」指到 json，其余四栏（角色设定、使用场景、限制条件、输出样式）从角色分册和角色对分册写。「代码无误」的判据分册已经定了：每步测试全绿，加上真会话手动触发一次 deny 和一次销号（30 第 196、197 行），不是人读代码。

第三句，「类」的清单要写成「五个角色类，加一个不属于任何类的超级用户，各自一张 use case 表」；「实例」要写成「会话，主键是 session_id，子会话的主键和母会话相同」。子会话身份这个缺口今天写代码绕不过去：actor 判定里子会话那一支要么先测试第 5 条再写，要么留下待定注释。

这三句改完，gyb 的做法和分册就是一件事，可以照着排今天的工作。

## 第六节：派活机制，gyb 的偏好和官方文档的事实

gyb 今天说的偏好是：派活优先用子会话，也可以发消息；子会话有时候不能再启动子会话，这时候用新的会话再去启动子会话。

分册里派活的定义是原则 11（00 第 31 行）：上游在后台启动一个子会话，子会话用 `agents/<role>.md` 的类型启动（08 第 90 行），单子上的 dispatch 栏取 auto、manual、none 三个值（04）。auto 就是 gyb 说的子会话，manual 就是 gyb 说的新会话（gyb 手动开一个终端加载角色，接单的时候发现最新一次尝试已经发射还没收尾就认领）。消息在分册里不是派活手段，交流全走账：单子在 handoffs 账上等 owner 上线，问题走 issues 账。

官方文档核对过的事实（claude-code-guide 代理 2026-09-04 查的官方文档，本机版本 2.1.260）：

- 子会话默认能往下套三层（环境变量 `CLAUDE_CODE_MAX_SUBAGENT_SPAWN_DEPTH`，默认 3；2.1.217 到 2.1.218 两个版本默认曾经是 1）。子会话要能再派，子会话的 agent 定义 tools 里要有 Agent，或者不写 tools 字段。所以「subagent 无法再调用 subagent」是老版本的限制，本机现在不是。
- 后台启动的子会话保留 Agent 工具，但是任何子会话都没有 Workflow 工具。
- 插件 agent 定义支持 name、description、model、effort、maxTurns、tools、disallowedTools、skills（预载整份 skill 正文）、memory、background、isolation；不支持 hooks、mcpServers、permissionMode。这和 06 第 126 行「插件 agent 定义里的钩子字段被忽略」一致。
- 跨会话消息用 ListAgents 和 SendMessage，只能传文字，不能替对方批准权限、不能修改对方配置，命令不会在对方执行；用 `-p` 启动的无头会话要打开 crossSessionInbound 才收得到。
- 钩子输入在子会话里带 agent_id 和 agent_type，这是 06 第 102 行判定角色的依据。
- 后台子会话能不能运行几小时、母会话结束会不会被杀，官方文档没写，这是待验证第 9 条。

解读：gyb 的三个办法和分册的 auto、manual 对得上，只是「消息」这一项在分册里只当会话之间打招呼用，不当派活用，理由是消息不落账、会话死了消息就丢。子会话套层的限制在本机版本已经放宽到三层，真正挡在前面的是第 9 条（后台子会话的寿命）和第 5 条（子会话写账算谁）。

推荐（推荐）：今天点名测试第 5 条和第 9 条，测完再写身份判定；测试期间别的底座照写。利是身份判定是底座最核心的一段，一次写对，派活主路上的实例身份有了结论，先例也有；弊是要在真会话里试半天，其他活往后推。备选一：先按「子会话记母会话的角色」写，靠会话账里「怎么启动的」那一栏事后分辨。利是不用等；弊是账上写的人不是真写的人，和「账行如实记谁写的」这条原则对不上，以后改身份判定要牵动钩子、登记、销号三处。备选二：让钩子在子会话开始的时候也给子会话写一份身份文件，写账脚本先找子会话的、找不到再找母会话的。利是两层看到同一个身份；弊是设计里明写子会话不写状态文件，要改一句已经裁定的话并走最后一期。

### 第三题：代码落地之后，设计、表、说明书三层文本改动从哪一层出发

场景：底座建完，仓库里同一条规矩出现在三处：设计分册里的那一段、机器读的表或者 schema、角色说明书里引用这条规矩的那一句。某天你要把「部署角色能不能开分析单」改一下。你 8 月 15 日说过「真源是插件的代码和表，五栏规格是贴着源放的解释层」；8 月 18 日又裁定「拆分文档逐份定稿之后就是为准的那一处」，两条前后相反，分册里没有一句写建完之后哪一层退位。插件自己已经带了改母版的机制：修改角色表或者母版走反馈账，采纳之后版本号加一，各会话按版本号对齐。

## 附：这份指南里的词，一句话解释

- 分册：`plans/research-loop-parts/` 里一份编号的设计文档。
- 冻结：正文不再修改，改动记成欠账等最后一期合并。
- 欠账：sync-inbox 里记的、要改进冻结正文但是还没改的裁决。
- 最后一期：全部分册定稿之后把冻结正文和欠账合并成现行版、再问 gyb 解不解冻的那一轮。
- 现行版：冻结正文加欠账合并之后的那份，代码要抄录的口径。
- 对照单：今天替代现行版的东西，每笔欠账写落在代码哪里。
- 骨架版：所有组件文件都在、已裁定部分测试绿、未裁定处标待裁、说明书是草稿的第一版。
- 账：`loop/` 下一行一条 json 的记录文件，九本。
- 转移表：单子从一个状态到另一个状态的允许表，六栏 16 行。
- actor：一次写账的执行者，五个角色之一或者 gyb。
- 钩子：Claude Code 在工具调用前后自动运行的脚本。
- 入账校验：`bin/rl` 写账之前按 schema 和转移表做的检查。
- 母版：`common/` 五文件，所有角色共用的规矩、词表、模板、读法、检查清单。
- 五栏：角色设定、使用场景、可用工具、限制条件、输出样式，每份角色 SKILL.md 的骨架。
- use case 表：角色分册里列这个角色每种活「读什么、写什么、调什么命令」的表。
- 派活：一个角色把活交给另一个角色，办法是后台启动子会话或者 gyb 手动开终端。
- 子会话：用 Agent 工具启动的下级会话，官方名字 subagent。
- 宿主：装了这个插件的研究仓库，现在是 new1。
- 待验证：30 里列的 11 条要在真会话里试出来的事实。
- 压力场景：写 skill 的时候用来测子会话照不照做的一段任务描述，先不带 skill 运行一遍当对照。
