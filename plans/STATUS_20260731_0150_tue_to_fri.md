## 先把代号讲清楚

后面所有节都要用到这些词，先在这里一次讲完。

**三个环境。** 探针不是训一个通用的，而是在三个互不相干的测试场景里各训一个。第一个叫 bfcl，一个公开的工具调用评测集，用的是它里面多轮对话那一类题：用户来回说几轮话，agent 得在中间调用函数；它的工具种类少、参数格式固定。第二个叫 appworld，一个模拟的手机应用世界，agent 在里面完成订票、发消息这类任务，工具多、参数复杂。第三个叫 tales，一批文字冒险游戏，agent 用文字指令去玩，它能说出来的话几乎没有边界，账上把这一点叫开放动作空间，意思是没有一份固定的动作清单可选。

**三代训练。** 探针一共训了三代，代号 v2、v2fix、v3。v2 是第一代，浮点格式设错了，模型几乎没学动，整批作废、不能引用。v2fix 是把浮点格式改对之后重训的一代。v3 是又补了一批轨迹、样本量翻倍之后重训的一代。还有一个 v3_1，是在 v3 的基础上把 bfcl 的另一种模型轨迹并进去之后的数据集。

**产生轨迹的模型，跟探针不是一回事。** 轨迹是 agent 做完一个任务的完整记录，用来当探针的训练数据。产生轨迹的模型有两种：阿里的 Qwen 系模型（账上写 qwen），和 OpenAI 放出权重的 gpt-oss-120b（账上写 gpt-oss）。探针自己是另一个模型，ModernBERT-base，它只做分类、不做生成。

**C1 到 C4 是论文的四个部分。** C1 是动机部分，用公开的多跳问答数据集 HotpotQA 做注入实验，说明提前拿到工具结果值钱、而且什么时候拿有讲究。C2 是探针本体，也就是能不能从思考文本（agent 在动手调用工具之前先写的那段话，下面简称思考）里提前看出工具调用，又分两半：C2-2t 是离线的，把存好的轨迹重读一遍模拟判断；C2-3 是把探针接进真跑的 agent，账上管这件事叫闭环。C3 是一个新的测评基准，把速度和准确率两条学习曲线画在一张图里。C4 是会师，把自己的探针当成一个参赛选手放到 C3 的基准上跑，产论文的旗舰图。

**T 后面跟数字的是任务编号。** `plans/2026-07-30-task-plan.md` 把要干的事编成 T0 到 T16，就是待办清单的行号。

**一条臂就是一种实验条件。** 后面几条实验都是"同样一批题，换一个条件再跑一遍"，全篇管每一种条件叫一条臂。比如存解法是一条臂、不存解法是另一条臂。

**判定探针合格的三条标准**，在开跑之前就定死了：触发时的预测准确率要到 95%（也就是探针决定触发的那些事件里，猜对工具的比例）；触发比例不能太低（也就是全部事件里探针触发的比例不能接近零）；还要高过先验基线（先验基线的意思是不动脑子，永远猜训练集里出现最多的那个工具，这么做能猜对的比例）。三条同时满足叫**达标**，差一条就叫**不达标**。

**换 agent 模型之后的三种考法。** 跨模型那条线要问的是"用一种模型的轨迹训出来的探针，换到另一种模型的轨迹上还灵不灵"。同一个训练好的探针有三种考法，全篇固定这三个叫法。**主场**：还是考它自己那一侧的数据，拟温度堆和扫门槛堆也都用自己这一侧。**冷迁移**：考另一侧的数据，但拟温度堆和扫门槛堆还用原来那一侧，也就是换了模型之后什么都不重新调。**只换校准**：考另一侧的数据，模型权重一个字节不动，只把拟温度堆和扫门槛堆换成新那一侧的数据重新调一遍。

## 第二节 · 每个实验详解

### 线 1 · 探针主线（C2-2t，9 条记录，全部跑完）

**问的是什么。** agent 在调用工具之前会先写一段思考。问题是：能不能在它还没写完的时候，就从这段半成品文本里看出它接下来要调哪个工具，而且准到敢替它先把这个工具调出去。

**怎么做的。** 把 agent 做任务留下的轨迹切成样本。一个事件是轨迹里的一次工具调用，连同它前面那段思考；把这段思考按句子边界切开，每切一次就得到一条样本，样本的内容是任务描述加上历史加上思考的前缀，标签是这次实际调用的工具名。样本按任务实例分成四堆：七成拿去训练，一成叫拟温度堆，用来拟合温度（一个把模型输出的分数拉成可信概率的参数），一成叫扫门槛堆，用来找触发门槛，最后一成叫测试堆，留出来不参与训练。

训练完之后跑回放。回放的意思是把测试堆那一堆轨迹按原顺序重读一遍，每个事件从思考的第一句开始一句一句送进探针，探针的置信度第一次超过触发门槛的那一刻，就记下它此刻猜的工具，跟这个事件真实调用的工具对一下。门槛调高，探针触发就少但准；门槛调低，触发多但错得多。所以要在门槛上扫一遍，找有没有一个门槛能同时满足前面说的三条标准。

**为什么这么设计才算数。** 95% 这条标准是这么定下来的：投机执行猜错要付真代价——提前发出去的调用如果是错的，要么白花钱，要么把 agent 的状态搞坏。高过先验基线这条是防止把照猜当成学到：tales 里最常见的那个工具本身就占 67.2%（v2fix 那一代的数），一个什么都不学的模型照猜也有 67.2% 的准确率，所以探针的成绩必须明显高过这个数，否则分不清它是学到了东西还是在照猜。触发比例不能太低这条防的是另一种情况：把门槛调到 0.999，准确率能到 100%，但一万个事件里只触发三次，这种情况下投机执行几乎不会发生。

这个设计覆盖不到的地方：回放是离线模拟，探针给出的判断没有真的去执行，所以它算出来的省 token 是估算，不是实测。实测要等闭环那条线。

### 线 2 · 因果探针（T8，1 条记录，跑完）

**问的是什么。** ModernBERT 每探一次要把整段前缀重读一遍，思考越长、探得越勤，总开销涨得越快。问题是：换成一个只能从左往右读的语言模型当底座，读过的部分缓存下来不重读，成绩掉多少、开销省多少。

**怎么做的。** 两个底座各训一遍：Qwen3-0.6B-Base 和 LFM2.5-350M-Base。做法是把整段文本一次前向送进去，在每个句子边界的位置放一个分类监督，训完的评测走跟 ModernBERT 完全一样的回放协议，所以两边的数字可以并排。

**为什么这么设计才算数。** 评测协议一致是这条线成立的前提。如果因果探针换了评测方式，它跟 ModernBERT 的成绩差就分不清是模型造成的还是评测方式造成的。另外开训之前强制过一道对齐检查：同一段文本，整段一次前向，和按分块增量前向的方式送进去，末位置输出的分数必须逐位一致才许开训。这一步是因为 LFM2.5 这类混合架构的模型（指同一个模型里既有注意力层又有别的序列层，不是清一色注意力）在缓存非空又一次喂多个 token 的时候算错过，而且算错了不会报错，只会训出一个看起来正常、其实算错了的模型。账上没有记这个前例具体是哪一次、在哪个版本上发现的。

**看一条真的。** 这条线和线 1 用的是同一批样本，样本长什么样见线 1 那一条。它的输出格式也和线 1 一样，下面是 `envs/bert_runs/appworld_v3_causal_qwen/REPLAY_REPORT.json` 里 `test_frozen` 那一节的原始内容（这个字段名里的 frozen 指门槛一旦从扫门槛堆上选定就钉死不再动，搬到测试堆上只用这一个门槛）：风险 0.05 档门槛 0.975、事件数 791、触发比例 0.3338、触发时的预测准确率 0.9621、提前量 0.356、错误投机率 0.0126。

**实验结果。** 风险 0.05 档（要求 95% 准确率）的数字，两个底座各一套，都来自 `envs/bert_runs/<环境>_v3_causal_<底座>/REPLAY_REPORT.json`：

| bfcl | 0.9779 / 0.8009 | 0.9515 / 0.9115 |

探测开销比（原始字段名 `cost_ratio`，装的是 ModernBERT 探完一条轨迹的计算量除以因果探针探完同一条轨迹的计算量；账上没有记这个计算量用的是什么单位）：bfcl 19.8、appworld 26.4、tales 34.1。

**值得注意的设置细节。**

对齐检查的判定口径改过一次。8192 窗口下 fp32 的舍入误差绝对值顶到 1.1e-4，超过原来定的 1e-4 门槛，但相对误差只有 1.7e-6。所以判定从看绝对差改成看相对差，并加了一个命令行参数 `--align-tol` 用来调这个门槛，默认值仍是 1e-4。

LFM2.5 的许可不是 Apache。

### 线 3 · 输入消融（T5，1 条记录，六格里五格跑完）

**问的是什么。** 探针的本事到底来自哪一段输入。样本里有三段：任务描述、历史、思考。问题是把思考整段砍掉、或者把历史整段砍掉之后，成绩掉多少。

**怎么做的。** 给训练脚本加一个输入模式开关，把样本里 `[THINKING]` 标记后面的内容整段切掉训一遍（下面叫砍思考），再把 `[HISTORY]` 标记后面的内容整段切掉训一遍（下面叫砍历史），其他一切不动：同一批数据、同一个切分、同样用 ModernBERT-base 当底座、同样的训练轮数。训完各自跑回放，跟完整输入那一版的成绩比。三个环境各做这两种，一共六格。全篇管这种"一个环境配一种条件"的组合叫一格。

**为什么这么设计才算数。** 一次只砍一段，掉下来的成绩才归得到被砍的那一段头上。要是同时砍两段，掉了也说不清是哪一段的功劳。判定的方向是开跑前定好的：如果砍思考掉得比砍历史多，说明思考文本里带着主要的增量信号，也就是"提前从思考里看出工具调用"这个主张有支撑；反过来则说明探针主要在读历史，那这条主张就要重写。

这个设计覆盖不到的地方：砍掉一段之后输入变短，模型看到的 token 总数也变了，所以砍掉一段之后成绩的变化里，有多少来自"信息少了"、有多少来自"序列短了"，账上没有做能把这两件事分开的对照，量不出来。

**看一条真的。** 砍的就是线 1 那条样本里两个标记后面的内容。以线 1 那条样本为例，砍掉思考段之后剩下的是任务描述加上一个空历史（那条样本的历史本来就是 `(start)`，意思是这是轨迹的头一个事件、前面没有历史）；砍掉历史段之后剩下的是任务描述加上 `The user wants to move a file called 'final_report.pdf'...` 这句思考。

**实验结果。** 五格已经落地报告，风险 0.05 档的数字（全部来自 `envs/bert_runs/<环境>_v3_no<模式>/REPLAY_REPORT.json`）：

| 环境 | 完整输入 准确率/触发比例 | 砍思考 准确率/触发比例 | 砍历史 准确率/触发比例 |
|---|---|---|---|
| bfcl | 0.9925 / 0.5929 | 0.9412 / 0.0752 | 0.9817 / 0.4823 |
| appworld | 找不到可用门槛 | 0.8889 / 0.1252 | 0.954 / 0.22 |
| tales | 0.85 / 0.1471 | 1.0 / 0.0294 | 还在跑 |

appworld 砍历史那一格的完整数字（`envs/bert_runs/appworld_v3_nohist/REPLAY_REPORT.json`）：门槛 0.975、测试堆事件数 791、触发比例 0.22、触发时的预测准确率 0.954、提前量 0.4311、错误投机率 0.0101、先验基线 0.2984。这一格在风险 0.05 和风险 0.1 两档选出来的是同一个门槛 0.975，所以两档的五个数完全一样。这是三个环境里 appworld 第一次在风险 0.05 档同时满足三条标准。

这六格的数一格都没进 `ops/runs.jsonl`：这条实验的编号 `20260730_1713_bert_t5_ablation` 只有发射记录，没有收尾记录。

**值得注意的设置细节。**

砍思考那一档改了评测方式：一个事件的所有样本合并成一条，原来按样本分配的权重改成按这个事件的样本条数取平均，报的是普通准确率。原因是思考被砍掉之后回放协议退化成每个事件只读一次，没有"一句一句喂"这个过程了。所以砍思考的触发比例和完整输入的触发比例**不是一个口径**，两列不能直接相减。砍历史那一档没有这个问题，它的思考段还在，回放协议和完整输入完全一样，所以砍历史那一列和完整输入那一列可以直接比。

tales 砍思考那一格的准确率是 1.0，触发比例 0.0294。触发比例 0.0294 落在 408 个测试事件上，也就是触发了 12 次；准确率 1.0 是在这 12 次上算出来的。

appworld 完整输入那一格在风险 0.05 档找不到可用门槛，所以上表第二行第一列是空的，没法和同一行右边两格相减。

### 线 4 · 跨模型双向矩阵与混训（T6，2 条记录跑完 1 条在跑）

**问的是什么。** 三件事。一，用一种 agent 模型的轨迹训出来的探针，换到另一种模型的轨迹上还灵不灵。二，如果不灵，只把校准重调一遍能不能救回来，还是必须重训。三，干脆把两种模型的轨迹合在一起训，成绩会怎么样。

**怎么做的。** 先按样本的 `model` 字段把 v3_1 数据集拆成两侧：`model` 以 qwen 开头的归 qwen 侧，以 gpt-oss 开头的归 gpt-oss 侧。然后每一侧各训一个探针，训完每个探针考三次，就是前面定义的主场、冷迁移、只换校准。三个环境各做一套，一侧就是九格，两侧一共十八格。混训那条另算：拿 v3_1 里 bfcl 两侧合在一起的数据训一个探针，然后分别考 qwen 侧和 gpt-oss 侧，拟温度堆和扫门槛堆用的是两侧合起来的那一份。

**为什么这么设计才算数。** 做双向而不是单向，是因为只做一个方向没法区分"探针不通用"和"某一侧数据本身更好"——要是只做 qwen 训、gpt-oss 考，成绩掉了，说不清是迁移不了还是 gpt-oss 那一侧的题本来就难。把冷迁移和只换校准分成两格，是因为这两件事的工程代价差得远：只换校准不用碰显卡，重训要占卡好几个小时。所以判定方向是开跑前定好的：只换校准如果能把成绩救回主场附近，部署时换 agent 模型就只需要做这一步；救不回来，就必须重训。

这个设计覆盖不到的地方：两侧的测试堆不是同一批题，事件数也不一样（bfcl 是 qwen 侧 226、gpt-oss 侧 109），所以主场那一格的成绩本身就带着"这一侧题难不难"的成分；两个训练侧之间的同一列，比的不是同一批题。

**看一条真的。** 两侧的差别长什么样，最直接的看法是拿同一道题的两条样本并排。下面是 `envs/bert_data/v3_1_xmodel/train-gptoss/bfcl/train.jsonl` 的第 1 条记录，任务原文和线 1 那条样本一模一样，产生轨迹的模型换成了 gpt-oss-120b（`model` 字段）：

```
Task: Move 'final_report.pdf' within document directory to 'temp' directory in document. Make sure to create the directory
[HISTORY]
(start)
[THINKING]
We need to parse the user's request: "Move 'final_report.pdf' within document directory to 'temp' directory in document.
```

标签同样是 `cd`。这条样本的 `n_sents` 是 38，线 1 那条 qwen 侧同题样本的 `n_sents` 是 24——同一道题，gpt-oss 的思考切出 38 句，qwen 切出 24 句。两条的 `sent_idx` 都是 0，都是各自事件的第一句；`depth` 分别是 0.0528 和 0.1863，也就是同样是第一句，在 gpt-oss 那段思考里只占到 5.28% 处，在 qwen 那段里占到 18.63% 处。

### 线 5 · 抽取头（T7，1 条记录，三格里一格跑完）

**问的是什么。** 探针猜对的是工具名。要真把调用提前发出去，光有工具名不够，参数的值也得有。问题是：在探针触发的那一刻，能不能同时把每个参数的值在文本里的位置指出来。

**怎么做的。** 在探针上加第二个输出头，输入里拼上一个由工具名、一个点号、参数名连起来的字符串，用它指明这次要找哪个参数，输出这个参数的值在文本里的起止位置。这个头必须支持输出"抽不到"。评测的时候先让分类头按正常回放跑，凡是触发的事件，就在触发那一刻让抽取头去抽这个事件的每一个参数，然后跟真值对。参数按难度分三档：无参（这次调用不带参数）、选择（参数的值是上文里能找到的原字符串）、自由（参数的值得现编）。

**为什么这么设计才算数。** 必须能说"抽不到"，是因为触发的时候参数的值常常还没写出来。任务清单里引用的一个先行试点数据是：提前 25 个 token 的时候，参数的字面串只有 33.8% 已经出现在文本里。不给这个头一个说"抽不到"的选项，它在值还没出现的时候也只能指一个位置，而这时候文本里根本没有真值可指。分三档是因为三档的性质不同：自由那一档的值在触发那一刻常常还不存在于文本里，选择那一档的值只要已经写出来就能定位，两档合在一起报会得到一个介于两者之间的数，看不出哪一档才是瓶颈所在。

判定方向也是开跑前定好的：真正能拿去投机的，是"触发那一刻值已经出现在文本里"的那些事件，所以这个比例是投机能覆盖到的事件占比的上限。

**看一条真的。** 这条线用的是线 1 那批事件，触发的时刻由线 1 那个猜工具名的输出头决定，下面管它叫分类头，管新加的这个叫抽取头。`envs/bert_runs/bfcl_ext_v3/EXTRACT_REPORT.md`（跟同目录下的 `EXTRACT_REPORT.json` 是同一次评测的两个产物，json 装数字、md 装文字说明）里对严格口径为什么不能用，写了一段可以直接引的说明，原文照贴：

```
判对口径:宽松=预测字符区间覆盖真值且多出的只有空白/标点。BPE 把前导空格与引号并进 token,严格逐字会系统性低估——金标 token 跨度自身的严格通过率只有 tales 0.066 / bfcl 0.642 / appworld 0.659,宽松口径下则是 0.997/0.997/0.991。严格列仅供对照。
```

这段话里的三个数是这么读的：真值本身按严格口径去判，在 tales 上只有 6.6% 能算通过，在 bfcl 上 64.2%，在 appworld 上 65.9%；换成宽松口径，这三个数分别是 99.7%、99.7%、99.1%。

同一份报告里还有一句，直接说了该拿哪个数当上限，原文照贴：

```
但真能在触发时刻组出完整调用去投机的,只有值已全出现那一列,它才是投机覆盖面的天花板。
```

**实验结果。** 只有 bfcl 这一格跑完（`envs/bert_runs/bfcl_ext_v3/EXTRACT_REPORT.json`）。门槛 0.95（跟线 1 bfcl 风险 0.05 档那个门槛是同一个），测试堆事件 226 个，其中触发 134 个。这 134 个事件里一共有 202 个参数要抽——一个事件带几个参数就贡献几个参数实例，有的事件不带参数，有的带两个以上，所以 202 和 134 对不上是正常的。

| 档 | 事件数 | 触发时值已出现的比例 | 参数全对率（宽松） | 参数全对率（严格） | 完整调用正确率 |
|---|---|---|---|---|---|
| 无参 | 14 | 1.0 | 1.0 | 1.0 | 1.0 |
| 选择 | 103 | 0.8155 | 0.9029 | 0.4466 | 0.8932 |
| 自由 | 17 | 0.2353 | 1.0 | 0.9412 | 1.0 |
| 整体 | 134 | 0.7612 | 0.9254 | 0.5672 | 0.9179 |

表里"触发时值已出现的比例"是 `params_all_present` 字段，装的是这个事件的全部参数在触发那一刻是不是都已经写在文本里了。"参数全对率"是 `params_all_ok`（宽松）和 `params_all_ok_strict`（严格），装的是这个事件的全部参数是不是都抽对了。"完整调用正确率"是 `full_call_ok` 字段，装的是工具名和全部参数一起都对的比例。

按参数实例算而不是按事件算的三个数：触发时值已出现的比例 0.8168（`param_present_rate` 字段，装的是 202 个参数实例里，触发那一刻值已经写在文本里的占多少），参数级正确率宽松 0.9505、严格 0.5792（`param_acc_loose` / `param_acc_strict` 两个字段，装的是 202 个参数实例里抽对了的占多少，分别按宽松和严格两种判法算）。

appworld 和 tales 那两格的抽取头还在训。

**值得注意的设置细节。**

自由那一档的参数全对率是 1.0，触发时值已出现的比例是 0.2353。判定规则是：抽取头答对"抽不到"也算这个参数正确，所以值大部分还没出现的那一档，参数全对率可以高于触发时值已出现的比例。报告里对这一点的原话是"抽取头答对抽不到也算参数正确，所以参数全对率可以高于值已全出现率"。

### 线 6 · 采集轨迹并建库（T1 + T3，1 条记录，跑完）

**问的是什么。** bfcl 这个环境原来的轨迹全是 qwen 系模型产生的，缺另一种模型的。跨模型那条线要是缺 bfcl 这一列，"换 agent 模型探针还能不能用"这个结论就只有两个环境的证据。

**怎么做的。** 用 gpt-oss-120b 跑 bfcl 的 200 个任务，收 200 条轨迹，然后建库——账上管"把新收的轨迹合进数据集"这个动作叫建库，指的是把散在各处的轨迹文件重新解析、切成样本、按四堆分好，产出一个新版本号的数据集目录。收的时候卡两条判据：思考文本非空、发出的调用能被解析出来。

**为什么这么设计才算数。** 两条判据缺一不可。思考非空是因为探针读的就是思考，思考是空的轨迹对训练没有任何用；调用能解析是因为标签就是从调用里抽的，解析不出来这条轨迹没有标签。

**看一条真的。** 账上记的是 `n_traj=200`（收到的轨迹条数）和 `think_nonempty=200`（其中思考非空的条数），两个数相等，说明 200 条全过。

**实验结果。** 200 条轨迹全部落盘，两条判据全过。建库之后，bfcl 的事件数从 2265 涨到 3325（`bfcl_events_v3_1` 字段，装的是合并成 v3_1 版本之后 bfcl 这个环境的事件总条数）。重新建库两次，产物逐字节一致。

v3 数据集三个环境的训练样本条数：tales 142621、appworld 71002、bfcl 25061（这三个数记在 `20260730_0056_bert_probe_v3` 这条记录的参数字段里，是 v3 这个版本的数，不是并入 gpt-oss 轨迹之后那个 v3_1 版本的数）。

**值得注意的设置细节。**

建库的脚本修过一个排序问题。原来它用递归通配符去找文件，返回的顺序是不定的，又按 id 去重，两次重建出来的事件数会在 2265 和 2267 之间飘。修完之后才建的 v3_1，验收的时候做了两次重建逐字节对比。

### 线 7 · C1 收尾（T11，1 条记录，跑完）

**问的是什么。** C1 这一块要说明的是两件事：提前拿到工具结果能省 token 或提高答对率，以及在不同位置拿到的效果不一样。这条实验补的是两个边界：多跳问题的两种类型分开报，以及换随机种子重跑，看结论稳不稳。

**怎么做的。** 用 HotpotQA 的题，模型是 Qwen3-8B。做法是在模型生成到不同位置的时候，把工具的返回结果直接插进它的上文里（账上把这个动作叫注入），看答对率和花的 token 怎么变。两种题型分开：一种是两跳互相独立（问两个东西然后比较），一种是两跳有依赖（第二跳要用第一跳的答案）。温度设 0.6，换三个生成种子（1、2、3）各跑一遍，每种题型 40 题，切成 8 份并行跑。

**为什么这么设计才算数。** 温度不为零的时候模型每次答的不一样，单跑一遍得出的结论可能只是运气。三个种子跑出来的结论如果一致，才敢说是真的。两种题型分开报是因为混在一起会被问"这个效应是不是只在其中一类上成立"。

**看一条真的。** 下面是 `hotpot_inject/results_t11/hp8b_T06_s1_shard0of8.jsonl` 的第 1 条记录，字段照抄：

题目编号 `5adbf0a255429947ff17385a`，题型 comparison（两跳独立），条件 baseline（不注入，当对照），温度 0.6，生成种子 1。模型答出来的话是：

```
No, the Laleli Mosque is located in the Laleli district of Fatih, while the Esma Sultan Mansion is in the Ortaköy neighborhood of Beşiktaş
```

这条判对（`em` 字段为 True，装的是答案和标准答案是否完全一致）。它调了 2 次工具（`n_calls` 字段），两次调用分别在第 157 和第 211 个 token 的位置发出（`call_toks` 字段），整题生成了 403 个 token（`gen_tokens` 字段），花了 16.5 秒（`wall_s` 字段）。

**实验结果。** 一共 1338 条记录（`n_records` 字段，装的是这一批落盘的结果条数），3 个种子。账上没有记 1338 这个数是怎么由题数、种子数、注入位置数乘出来的。两个数：两跳独立那一类，注入得太早会掉 0.18 的宽松判对率（`comp_early_soft_drop` 字段；宽松判对指的是不要求答案和标准答案完全一致，账上没有记它具体用的是哪种匹配规则）；两跳有依赖那一类，存在一个区间，在那里注入既不省 token 也不帮忙，账上记的是 -153 个 token（`bridge_deadzone_dtok` 字段）。账上的结论字段大意是三条主线结论跨三个种子都稳（这是转述，不是原话），但只列出了上面这两个数，第三条是什么没有记。

**值得注意的设置细节。**

两跳有依赖那一类的第二跳子集样本量小，账上已经标注了这一点。

### 线 8 · C3 基准装配（T12，5 条记录，全部跑完）

这条线有五个互相独立的部分，下面分开讲。

#### 8a · 存解法全矩阵（周二跑的那条）

**问的是什么。** 让 agent 把做过的题的解法存下来、下次做题之前放进提示里，跟什么都不存、每道题从零开始做相比，要处理的文字总量是变多还是变少。

**怎么做的。** 环境是 ALFWorld，一个用纯文字描述的家务模拟器：模型读到一段描述房间的文字，然后一条一条发出动作指令，系统再把这条指令的结果用文字回给它。从模型接到一条任务指令到系统判定成败，这一整个过程叫一轮。模型是 Qwen3-8B，解码时每一步都取概率最高的那个词。

这条实验有两条臂：存解法和不存解法。两条臂各完整连做十轮，不是两条臂分掉十轮。存解法这一边，每做完一轮，如果这一轮做成了，就把这道题的原文和做成功的那串动作指令存下来；下一轮开始之前取最近五轮，这五轮里做成了的才放进提示、整段放在最前面，所以提示里的解法最多五条，最近五轮有几轮没做成就不足五条。不存解法这一边，每一轮都从零开始。

题目按"下一轮和前面做过的有多像"分三档。完全一样的题是同一道题原封不动重复十轮。几乎一样的题是任务要求的文字相同、换一个房间布置。同类但换了东西的题是任务模板相同、都是把某个物品放到某个容器上，但要放的物品和目标容器换成别的种类。三档乘两种条件乘五个随机种子（编号 0 到 4）等于三十次"连做十轮"，一共三百轮。

**为什么这么设计才算数。** 两种条件之间只差一样东西：一轮做完之后解法存不存、放不放进下一轮的提示。题目、模型、解码方式、出题顺序全都一样，随机种子逐轮对齐，所以差别只能来自存不存解法。

判定标准在开跑之前就定死：把发给模型的 token 和模型写出来的 token 加在一起算总量。定这个标准的理由是，存下来的解法要整段放进提示、模型每一步都要重读一遍，所以存解法一定会让发进去的 token 变多，换来的是模型少发几条指令。如果换成只统计模型写出来的 token，存解法那一边就不可能输，因为它多花的那部分根本没被算进去。

分三档而不是只跑一档，是为了看出结论在哪一档反转。只在完全一样的题上测会得出"存解法有用"，只在换了东西的题上测会得出"存解法有害"。

这个设计覆盖不到两件事。第一，做成的轮数在两种条件下三档完全相同：几乎一样的那档五十轮全做成，完全一样的那档五十轮里做成三十轮，同类但换了东西的那档做成四十二轮。也就是说这批题上，存不存解法对做成多少题没有产生任何差别。第二，只存做成功的解法，所以模型本来就做不成的题攒不下任何能用的东西。

**看一条真的。** 下面这些来自 `fig1_pilot/results/8bfull_L1_mem_s0.jsonl`，取前四轮。这个文件名要这么读：`8bfull` 是这一批实验的编号前缀，`L1` 是代码那一套编号里"几乎一样的题"这一档（两套编号的坑见本节最后），`mem` 是存解法那条臂（不存解法那条臂的文件名写 `nomem`），`s0` 是种子 0。

第 0 轮的任务原文（`task` 字段，装的是环境给模型的那句任务指令）：

```
put a toiletpaper in toiletpaperhanger.
```

模型在第 0 轮实际发出的五条指令（`actions` 字段，装的是这一轮按顺序发出的全部指令）：

```
go to toilet 1 → go to countertop 1 → take toiletpaper 2 from countertop 1 → go to toiletpaperhanger 1 → move toiletpaper 2 to toiletpaperhanger 1
```

第 2 轮开跑的时候，提示最前面多出来的那段解法长这样。这段文字是按代码里拼接解法的逻辑、用第 0 轮和第 1 轮的记录重建出来的；原始文件里没有存下这段完整字符串：

```
=== experience from earlier similar tasks ===
Task: put a toiletpaper in toiletpaperhanger.
Successful actions: go to toilet 1 -> go to countertop 1 -> take toiletpaper 2 from countertop 1 -> go to toiletpaperhanger 1 -> move toiletpaper 2 to toiletpaperhanger 1

Task: put some toiletpaper on toiletpaperhanger.
Successful actions: go to drawer 1 -> open drawer 1 -> go to toilet 1 -> take toiletpaper 1 from toilet 1 -> go to toiletpaperhanger 1 -> move toiletpaper 1 to toiletpaperhanger 1
```

存解法存的就是这个东西：一行任务原文，一行做成功的指令序列。没做成的不存，房间里看到的陈设不存。

前四轮的数字，两种条件并排。"步数"是这一轮发出的指令条数（`steps` 字段），"读进"是这一轮里每一步发给模型的提示 token 数加总（`tokens_in` 字段），"写出"是这一轮里模型生成的 token 数加总（`tokens_out` 字段）：

| 轮 | 任务原文 | 存解法 步数/读进/写出 | 不存解法 步数/读进/写出 |
|---|---|---|---|
| 0 | put a toiletpaper in toiletpaperhanger. | 5 / 2901 / 3765 | 5 / 2901 / 3765 |
| 1 | put some toiletpaper on toiletpaperhanger. | 6 / 3226 / 4620 | 5 / 2268 / 4367 |
| 2 | put a toiletpaper in toiletpaperhanger. | 4 / 2669 / 1184 | 4 / 2115 / 3594 |
| 3 | put a toiletpaper in toiletpaperhanger. | 4 / 2873 / 2407 | 4 / 2057 / 2646 |

第 0 轮两边三个数完全一样。第 0 轮的时候还没有任何解法可放，两边的提示逐字相同。

**实验结果。** 下面所有百分比的算法统一是：存解法那一边的数减去不存解法那一边的数，再除以不存解法那一边的数。分母一律是不存解法那一边，正号表示存解法花得更多，负号表示花得更少。总量是这一档五十轮的数字全部加起来的合计，不是平均。

| 档 | 存解法 总量 | 不存解法 总量 | 差 | 存解法 做成 | 不存解法 做成 |
|---|---|---|---|---|---|
| 完全一样的题 | 1005290 | 1112570 | −9.6% | 30 / 50 轮 | 30 / 50 轮 |
| 几乎一样的题 | 417666 | 357630 | +16.8% | 50 / 50 轮 | 50 / 50 轮 |
| 同类但换了东西的题 | 1094894 | 915116 | +19.6% | 42 / 50 轮 | 42 / 50 轮 |

只看种子 0 这一个种子（也就是十轮的合计）：完全一样的题 存解法 52143、不存解法 38500、差 +35.4%；几乎一样的题 存解法 68688、不存解法 71526、差 −4.0%；同类但换了东西的题 存解法 248818、不存解法 237368、差 +4.8%。

**值得注意的设置细节。**

相似度档的编号有两套，取值正好颠倒。写实验脚本的时候，代码里给这三档的标签是 `L0`、`L1`、`L2`：`L0` 是完全一样的题、`L1` 是几乎一样的题、`L2` 是同类但换了东西的题。后来定下来的正式编号反过来数：完全一样的题是 `L2`、几乎一样的题是 `L2⁻`、同类但换了东西的题是 `L1`。两套编号里 `L1` 和 `L2` 这两个符号都存在，指的却不是同一档。原始数据的文件名用的是代码那一套，写进正式文档的数字用的是正式那一套。引用的时候不先查清楚手上这个数字属于哪一套编号，就会把"同类但换了东西的题上存解法净亏"写成"完全一样的题上存解法净亏"，两个档一个是省一个是亏，正好说反。

耗时这一列最后没有写进出厂报告。原始记录里是有耗时的：存解法那条臂的耗时比不存解法那条臂低 7% 到 12%，这个区间是三档各自算出来的三个数的范围。删掉的理由是这三十次"连做十轮"不是全在同一型号的显卡上跑的，不同型号跑同样的计算花的时间本来就不一样，两条臂的耗时之间不能比。

完全一样的题这一档、不存解法那一边，**在同一个种子内部**十轮的数字逐字相同：这一档的十轮是同一道题、同一套房间布置，解码时每一步又都取概率最高的那个词，所以模型每一轮的行为完全重复。但**五个种子之间的数不一样**，每个种子抽到的是不同的题。逐种子从原始文件里直接数出来的每轮写出 token 数是：种子 0 是 1191、种子 1 是 4538、种子 2 是 13778、种子 3 是 2670、种子 4 是 12195。`fig1_pilot/ANALYSIS_8bfull.md` 这份汇总报告里，这一档不存解法那条臂的每一轮写出 token 数都印成 6874。6874 是上面那五个数的平均，不是任何一轮的实际值。

这一档做成的三十轮也不是平均摊在五个种子上：种子 0、1、3 十轮全做成，种子 2 和种子 4 十轮全没做成。两种条件做成的轮数在这一档完全相同，就是因为不存解法那一边每个种子的行为固定，做得成做不成由抽到哪道题决定。

几乎一样的题这一档、不存解法那一边，五个种子的十轮合计完全相同，都是 71526。从原始文件逐条核对过：这五个种子抽到的是**同一批十道题**，只是出题顺序不同——把每个种子的十轮按（任务原文、步数、读进、写出、成败）排序之后，五个种子的清单逐项相同。不存解法那一边每一轮互相独立，所以顺序不影响合计。这批十道题里有 6 道任务原文是 `put a toiletpaper in toiletpaperhanger.`、4 道是 `put some toiletpaper on toiletpaperhanger.`。

"连做十轮"和"取最近五轮"这两个数是当初定下来就没再动过的，账上没有记为什么定这两个数。另外，这条记录的结论字段里写着"8B 红利小于 4B"，意思是同一套做法在一个 4B 模型上先跑过一次、省得比 8B 多；那次先跑的实验记录不在这个窗口内，本文档查不到它的数字。另外两档为什么两种条件做成的轮数也恰好相同，原始记录里没有留下说明。

#### 8b · 完美复用上限

**问的是什么。** 假设复用做到完美无损——凡是之前做过的题，这次一个字都不用重新生成，直接把上次的答案搬过来——最多能省多少。这个数是给上面那条实验的真实成绩定一个上限。

**怎么做的。** 不重新跑模型，直接在上面那条实验里"不存解法"那一边已经存好的记录上算：对每一轮，看它是不是跟前面某一轮完全同一道题，是就假设它一个 token 都不花，不是就照原样算它的 token。

**为什么这么设计才算数。** 这个上限只算逐字复用，所以它管不住任何靠泛化省下来的部分。也就是说，真实成绩如果超过这个上限，多出来的部分一定不是靠照搬来的。

**看一条真的。** `benchmark_design/ORACLE_CEILING_8bfull.md` 里同类但换了东西的题那一档，十行逐轮的数字全是"+0.0%"，可替换集占比全是"0/5"——这一档十轮里没有任何一轮和前面某一轮是同一道题，所以逐字复用在这一档没有定义，上限等于不存解法本身。表里"可替换集占比"这一列的分母 5 是这一档的五个随机种子，分子是其中有多少条能找到可以照搬的前轮。

**实验结果。** 完全一样的题这一档，上限是省 21.0%、23.4%。前一个数是把十轮的成本加总之后算的，后一个数是每一轮各算一次省了多少再取平均。另外两档都是 0%。符号约定跟 8a 一致：这里说"省 21.0%"，写进第三节的对照表时记作 −21.0%。

**值得注意的设置细节。** 这条实验是纯 CPU 后处理，没有占显卡。它跑在那批带有两套编号问题的数据上，账上记的字段名 `ceiling_L2_total` 用的是正式编号，指的是完全一样的题那一档。

#### 8c · 真实负载相似度（周一跑的那条）

**问的是什么。** 上面那些实验都假设"相似的任务会反复出现"。这条实验查的是这个假设在真实负载里成不成立。

**怎么做的。** 拿一批真实的编程 agent 使用记录来算：357000 次交互、4265 个会话，其中可用的 3594 个（账上没有记判定一个会话可用的标准是什么）。这里的"次交互"跟 8a 定义的"一轮"不是一个东西，8a 的一轮指做完一道题，这里的一次交互指一来一回。两个会话之间的相似度，算的是它们各自调用工具的次数向量的余弦相似度。

**为什么这么设计才算数。** 这批记录的内容已经脱敏，所以只能测出"调用的工具构成有多像"，测不出"任务内容有多像"。这是这条实验管不住的地方，论文里已经声明了这条边界。

**看一条真的。** `tracelab_analysis/RESULTS_v0.md` 里的原文写法是"相邻 session 相似度:p50=0.93"，意思是把每个会话和它前一个会话算相似度，这些数排序之后中位数是 0.93。

**实验结果。** 相邻会话的相似度中位数 0.93；大于 0.8 的占 68.4%，0.3 到 0.8 的占 17.2%，小于 0.3 的占 14.5%。96.1% 的会话在往前数 50 个会话的范围里能找到一个相似度大于 0.8 的前驱，这个距离的中位数是 1、九成位数是 4。相似度大于 0.8 的那些配对里，10.8% 分属不同的项目。

**值得注意的设置细节。** 相似度只按工具调用次数算，不看内容。这批数据是外部记录，不是自己跑出来的。

#### 8d · 六个记忆系统冒烟

**问的是什么。** C3 这个基准需要一批用来对照的系统。这条实验验的是：六个别人做的记忆系统，接进自己的评测流程之后能不能跑通。

**怎么做的。** 模型统一换成 Qwen2.5-7B-Instruct，六个系统各跑 15 道题，从头到尾走一遍这五步：拼提示、跑一轮、从模型的回答里抽出答案、给答案评分、把这一轮的题目和结果写回这个系统自己的记忆里。评分的代码同时实现了两种判对算法，一种要求抽出来的答案和标准答案完全一致，一种只看两边重合了多少个词；这次冒烟的判定只用了完全一致这一种。

**为什么这么设计才算数。** 冒烟指的是只验"这五步能不能从头跑到尾、中间报不报错"的一次小规模试跑，不看成绩。所以这次的判定标准是跑通不报错，不是分数高。这批题是两跳题，而且不给模型任何可以查的资料，分数低是开跑前就料到的，所以这条实验不拿分数做任何判断。

**看一条真的。** 下面是 `benchmark_design/l3_2wiki_items.jsonl` 的第 1 条题目，字段照抄：

题号 `2wiki/train/l3_two_hop/000000`，题目：

```
What is the date of birth of the director of film Amateur Crook?
```

标准答案 `July 7, 1901`。这道题的推理链（`chain` 字段）是两跳：先从电影 `Amateur Crook` 查到导演 `Sam Katzman`，再从 `Sam Katzman` 查到出生日期 `July 7, 1901`。中间那个人名 `Sam Katzman` 是连起两跳的那个实体（`junction_entity` 字段，装的就是这个实体）。造这道题用的随机种子是 20260729（`rng_seed` 字段）。

**实验结果。** 六个系统全部跑通，报错 0 次。六个系统的名字是 ExpRAG、ExpRecent、ReMem、DC-Cu、DC-RS、AWM；前两个是自家写的检索基线，后四个是照别人的方法重建的。账上只记了这六个名字，没有记每个系统内部的机制。它们在 15 道题上的完全一致答对率：两个自家写的检索基线各 0.2（也就是 15 道对 3 道），另外四个都是 0.0（一道没对）。每道题调用模型的次数不等：ReMem 在 15 道题上共调 58 次；DC-Cu 和 DC-RS 各在 15 道题上共调 30 次，也就是每题 2 次；剩下三个每题 1 次。

**值得注意的设置细节。**

这次冒烟暴露了两个可以分开修的问题：其中四个系统的答案抽取没有处理长句，以及判定只用了完全一致、没有用词重叠。账上这条记录的结论字段把这两条列为"正式跑分前处理"。

六个系统里有四个是照别人的方法重建的，这四个另有一份保真度核对记录（`benchmark_design/FIDELITY_T12C.md`）。核对表逐个点名给了判语，下面四条都是核对表自己的说法：ReMem 在多轮设定下"忠实"、单轮设定下"简化但方向一致"；DC-Cu 标"失真需声明"；DC-RS 也标"失真需声明"，而且原方法里"先检索再整理再作答"这个用来区分它和 DC-Cu 的机制在重建版里没有实现；AWM 在单轮设定下"机制完全缺失"，核对表建议不报这个系统。剩下两个 ExpRAG 和 ExpRecent 是自家写的检索基线，不在核对范围内。

账上这条记录的结论字段还有一条，大意是每道题调用模型的次数不等这件事要计入 token 账，否则不同系统之间的成本不可比（这是转述，不是原话）。

#### 8e · 全历史臂

**问的是什么。** 8a 那条实验只有两种条件：存解法和不存解法。这条实验加第三种条件，把之前所有轮的完整记录全部放进提示，超出预算就从最旧的一轮开始丢。全篇管这条新加的条件叫全历史臂。它的作用是给存解法那条臂当参照：存解法只放任务原文和成功指令两行，全历史臂把之前每一轮的完整记录都放进去，是"把过去原样放进提示"这条做法里放得最多的一种。（注意别和 8b 那个"完美复用上限"混起来：那个说的是最多能省多少，这里说的是放进提示的内容最多能有多少。）

**怎么做的。** 三档各占一张卡，同一张卡上先跑不存解法再跑全历史臂。种子沿用 0 到 4，相似度档沿用 8a 那三档，每档每种子连做十轮，所以全历史臂一共十五次"连做十轮"、150 轮，配对的不存解法也是 150 轮。放进提示的预算是 24576 个 token，用的是 Qwen3-8B 自己的分词器来数。账上没有记这个预算是怎么定出来的。

**为什么这么设计才算数。** 同一张卡上先跑不存解法再跑全历史臂，是为了让耗时可比。8a 那条实验就是因为三十次"连做十轮"跨了不同型号的显卡，耗时那一整列只能作废。这次把不存解法重跑一遍，就是为了拿到一条和全历史臂跑在同一张卡上的对照。

改代码的时候做了逐字节对比：存解法和不存解法两条臂的产物跟改之前完全一致，25 项单元测试全过，所以加进全历史臂没有污染原来两条臂。

判定方向是开跑前定好的：如果全历史臂在每一档上都比不存解法便宜，说明"把过去原样放进提示"这条做法本身就够用，不需要挑着存；如果它在某些档上明显更贵，说明必须挑着存，也就是需要一个会筛选的记忆机制。

这个设计覆盖不到的地方：这一批的不存解法臂和 8a 那一批的不存解法臂**不是一个口径**，详见下面值得注意那一节，所以这条实验的三个比值只能在这一批内部算，不能拿 8a 表里的数当分母。

**看一条真的。** 这一臂放进提示的内容和存解法那一臂不同。代码里两个提示头是两个不同的字符串，原文照贴（`fig1_pilot/fig1_run.py` 第 59 到 60 行）：

```
MEM_HEADER = "=== experience from earlier similar tasks ==="
FULLHIST_HEADER = "=== full transcripts of all earlier episodes ==="
```

存解法那一臂放的是任务原文加成功指令两行，全历史臂放的是之前每一轮的完整对话记录。下面是 `fig1_pilot/results/fullhist_L0_fullhist_s0.jsonl` 的前四轮，任务原文都是 `put a cellphone in safe.`，`fullhist_eps_included` 字段装的是这一轮实际塞进提示的前几轮记录条数，`fullhist_block_tokens` 字段装的是这一段记录占了多少个 token：

| 轮 | 塞进几轮记录 | 这段记录占多少 token | 步数 | 读进 | 写出 |
|---|---|---|---|---|---|
| 0 | 0 | 0 | 5 | 2659 | 2257 |
| 1 | 1 | 168 | 6 | 4300 | 4913 |
| 2 | 2 | 351 | 7 | 6352 | 5420 |
| 3 | 3 | 549 | 5 | 5449 | 1232 |

第 0 轮塞进 0 轮记录，因为这时候前面一轮都还没做过。

**实验结果。** 三档的合计，全历史臂和同一批的不存解法臂并排。总量是读进加写出，是这一档五十轮全部加起来的合计。做成的轮数分母都是 50。这些数是从 `fig1_pilot/results/fullhist_*.jsonl` 里逐条重算出来的，和 `ops/runs.jsonl` 里那条收尾记录记的九个数全部吻合。那九个数是：三档各自的做成轮数变化、三档各自的总量之比、三档各自的耗时之比。下面第二张表里的读进之比和写出之比不在这九个数里，账上没有这两列，只有重算出来的值。

**值得注意的设置细节。**

这一批的不存解法臂和 8a 那一批的不存解法臂，逐种子对不上。同样是完全一样的题这一档的种子 0，8a 那批的十轮合计是 38500，这一批是 49256。三档十五个种子里差得最多的一格是几乎一样的题的种子 1，8a 那批 71526、这一批 193005，差 121479 个 token。做成的轮数也有出入：完全一样的题的种子 2，8a 那批十轮全没做成，这一批做成 1 轮；几乎一样的题这一档，8a 那批五十轮全做成，这一批做成 49 轮。

上面表里"做成的差"那一列是轮数的绝对差，不是百分比。分母都是 50 轮。

### 线 9 · 闭环（T9 + T10，0 条实验记录）

**问的是什么。** 前面所有数字都是离线回放算出来的估算。闭环要回答的是：把探针接进真跑的 agent，真发调用、真掐表，省下来的 token 和时间是多少。

**怎么做的。** 计划里是三个环境乘五种跑法（账上管这五种叫五个口径，为了不和前面"这两个数不是一个口径"里的口径混起来，本文档一律叫跑法）。基线是不带探针原样跑。截断是探针一触发就停止生成思考、直接提交预测的调用。预取是只读的调用先在后台执行，等 agent 自己发同一个调用的时候，把后台执行的结果和 agent 想发的调用核对一遍，一致就把结果直接交给 agent，省掉这次真实调用的等待。影子记录是探针只记下"此刻会提交什么"但不执行，事后和真实调用对账。fork 对照是在探针触发那一刻把进程的完整状态复制一份，让副本走投机路线跑到任务结束，和原来那条线对比 token 账和成败。

**为什么这么设计才算数。** 五种跑法各回答一个不同的问题，缺一个就有一处没法验证。影子记录是零风险的，全程开着，它的作用是验证离线回放的估算准不准。fork 对照是唯一能给出因果对照的跑法——同一个事件，一个副本走投机、一个走原路，两边的 token 账直接相减。fork 有一条硬规定：每个事件只在第一次过门槛的地方复制一次，副本里面探针关掉，不许嵌套，否则会无限递归。

**看一条真的。** 账上没有实验记录可捞。已经落地的是代码，一共五件：探针服务、流式生成、记 token 账的模块、bfcl 那边处理四种跑法的代码，以及 appworld 和 tales 各自的运行器（把一道题从头跑到尾的那段代码）。bfcl 那边为什么是四种而不是五种、缺的是哪一种，账上没有记。

**实验结果。** `ops/runs.jsonl` 里这条线一条记录都没有。**实验一次没跑。**

**值得注意的设置细节。**

探针服务的性能修过三次，每次都是同一类问题：第一次，服务原来是每来一个请求就开一个线程，每个线程都要重新初始化一次矩阵运算库的上下文，每请求 760 毫秒；改成单线程复用同一个上下文之后降到 14 毫秒（提交 `e9c7a7a`）。第二次，模型每遇到一个没见过的输入长度就重新编译一次计算图，长度一变就付 400 到 560 毫秒；关掉这个自动重编译之后稳定在 8 到 10 毫秒（提交 `b17f1c9`）。第三次，注意力的某个后端每遇到一个新的序列长度要先算一遍执行方案，大约 770 毫秒；换掉这个后端之后任意长度稳定在 11 到 15 毫秒（提交 `715e4bc`）。这几组数字来自这三次提交的说明，不是实验记录里的字段。中间有一次归因错了：先归到重编译上，后来用性能分析器确认是注意力后端的问题。

tales 这个环境的游戏引擎能不能存档还没查清楚。任务清单把这一条标为这条线已知的工程风险。fork 对照需要现场可复制，bfcl 和 appworld 的模拟状态可以复制，tales 不确定。

## 第六节 · 我的判断

**tales 是唯一一个已出结果的做法全部不达标的环境。** 完整输入 0.85、因果探针两个底座 0.9077 和 0.9225、跨模型 qwen 训练侧那三格在 0.71 到 0.81 之间。第四种做法（砍历史）那一格还在跑，没有结果，所以"全部不达标"目前只覆盖已经跑出来的三种；按另外三种的位置看，我不指望砍历史单独跨过 95%，但这是预期不是结果。账上把原因归到开放动作空间（原话见线 1 表格下面那句），我同意。这意味着论文里 tales 只能当负面案例写，不能当第三个正面环境。

**跨模型这条线给出了一个能直接写进论文的部署结论，但只在 bfcl 上成立。** bfcl 上冷迁移掉到 0.8971，只换校准回到 0.9714——也就是换 agent 模型之后不用重训，做一遍只换校准就够了，代价从占卡几小时降到不占卡。appworld 上只换校准只到 0.8824、tales 只到 0.7143，两个都救不回来，必须重训。所以这条结论要写成"在 bfcl 这类工具种类少、参数格式固定的环境上，换 agent 模型只需要做一遍只换校准"，不能写成通用结论。

**混训那条的增益全在触发比例上，准确率是掉的。** bfcl 上混训考 qwen 侧 0.9645，纯 qwen 训练同口径是 0.9913，掉了将近 3 个点；但触发比例从 0.5088 升到 0.7478。考 gpt-oss 侧也是同样方向。我的判断是这么换值得：0.9645 仍然过 95% 这条线，而触发比例多出来的这部分是实打实能拿去投机的事件。前提是 95% 这条线本身不再往上提。

**全历史臂那条实验的结果比我预期的更好读。** 完全一样的题这一档，全历史臂做成 47 轮对不存解法的 31 轮，同时总量还降到 0.84 倍——做得更好而且更便宜。拆开看，省下来的部分在写出那一半（写出的 token 降到 0.84 倍以下，具体是 0.72 倍），读进那一半只降到 0.91 倍。为什么写出的会降，账上没有能支持因果解释的数据，我只能说它和做成轮数上升是同时出现的。往后两档就翻过来了：几乎一样的题总量 1.17 倍、同类但换了东西的题 2.50 倍，读进的 token 涨到 3.69 倍，做成的轮数各只多 1 轮。所以"把过去原样放进提示"这种做法在最像的那一档既做得更好又更省，在相似度更低的两档上迅速变贵。这一条加上 8b 那个上限（只有完全一样的题这一档非零，最多省 21.0%），我认为 C3 这个基准的立论多了一条实测支撑：相似度更低的两档上想省，靠照搬不可能，必须靠会筛选的机制。

**但全历史臂这条实验有一个我必须点出来的问题：它的不存解法臂和 8a 那一批对不上，差得还很大。** 最大一格差 121479 个 token，做成的轮数也有出入。原因查清了，是两批走了不同的推理服务（一套是 transformers 直接起的、一次处理一个请求，一套是 vLLM 0.16.0）。这条实验自己是干净的，因为它重跑了配对的不存解法臂；但它说明这套流水线不是逐位可复现的，同一条臂换个服务重跑一遍就能差出几个百分点到几十个百分点。论文里凡是跨批次比较的数字，都要先确认是不是同一套服务跑的。我建议把服务版本和配置写进每条实验记录的字段里，现在账上只有服务端日志里能翻到。

**抽取头 bfcl 那一格的结果我认为够用了。** 完整调用正确率 0.9179，对照的竞品数是 0.076。真正的限制不在抽得准不准，而在触发那一刻值出现了没有：整体只有 0.7612，自由那一档只有 0.2353。也就是说限制投机覆盖面的是"值还没写出来"，不是抽得准不准。这一条决定了论文里该报哪个数——该报触发时值已出现的比例，把它当成投机覆盖面的上限，而不是拿 0.9179 去说事。报告里已经写了这一点，我同意它的写法。

**消融那两列支撑了论文的核心主张。** bfcl 砍掉思考之后触发比例从 0.5929 掉到 0.0752，砍掉历史只掉到 0.4823。所以思考文本确实带着主要的增量信号。但砍思考那一列换了评测方式，触发比例的口径和完整输入不一致，直接把 0.0752 和 0.5929 并排写进论文，审稿人会指出这两个数不可比。砍历史那一列没有这个问题。我建议表里把砍思考那一列单独标注，或者补一次同口径的评测。

**存解法全矩阵和真实负载相似度这两条，我的判断跟上一版一样。** 存解法在三个档里只有完全一样的题省了 9.6%，另两档分别亏 16.8% 和 19.6%。真实负载那条说明重复相似任务是主体（相邻会话相似度大于 0.8 的占 68.4%），但它只测了工具调用构成，没测任务内容，所以支撑不了"重复的任务能复用同一个解法"。把它的三个相似度区间和 8a 那三个任务相似度档对应起来看着很顺，但两边的相似度定义不是一回事，不能直接换算。

**六个记忆系统那条线我判断有问题。** 保真度核对说四个重建的系统里有两个失真、还有一个的机制在单轮设定下根本不存在。拿一个失真的实现去比，比出高分也没有说服力。我建议按核对记录的建议办：机制不存在的那个直接不报，失真的两个在论文里明确声明失真在哪。

**闭环这条线仍然是最大的问题，因为它还是一次没跑。** 前面所有省 token 的数字都是离线估算。我判断审稿人不会认离线估算，要的是真实计时。代码已经写完、探针服务的三处性能问题也修完了，但端到端演示都还没跑过一次。tales 的现场能不能复制还没查清楚。按第五节列的没跑清单，闭环正式跑分和 C3 正式跑分都排在 C4 旗舰图前面，所以闭环晚一天，旗舰图就晚一天。这一天过去了，这条线的状态没有变化。

**账面上漏记的地方比上一版更多，按严重程度排。** 第一，7 月 30 日到 31 日凌晨的实验结论一条都没进 `TIMELINE.md`，第四节最后一段列出的六条里，至少有三条动了原来的判断（appworld 砍历史达标、全历史臂在最像那一档做得更好还更便宜、bfcl 换模型只做一遍只换校准就够）——这些我只能起草，`TIMELINE.md` 按规矩由人写。第二，落了地却没进 `ops/runs.jsonl` 的报告有 12 份（输入消融 5 份、抽取头 1 份、跨模型 gpt-oss 训练侧 6 份），上一版是 4 份，另外因果探针那八个数还是没进；这批数字目前只存在硬盘上。第三，台账里五块卡上的进程已经退出但还挂在在跑名单上，`ops/jobs.json` 现在标不出哪块卡是空的。第四，窗口内 23 条记录发射时工作树全是脏的，这 23 条结果一条都不能靠 commit 找回当时的代码。

**下一步我建议的顺序，跟上一版比换了第一条。** 先销号——把五块已经退出的卡从 `ops/jobs.json` 的在跑名单里划掉，否则下一次挑卡会挑错。然后补进账（`TIMELINE.md` 的草稿，加上 12 份没进账的报告和因果探针那八个数进账），这是纯 CPU 的活、不占卡，越晚补越记不清。然后盯闭环端到端演示，它是最卡进度的一件事，而且已经过了一整天没有动静。四条还在跑的训练里，抽取头 appworld 和跨模型 tales 都过了八成，等它们自己跑完就行，不需要额外设计。六个记忆系统正式跑分之前，先把答案抽取和评分那两个问题修掉，不然跑出来的分数全要重跑。
