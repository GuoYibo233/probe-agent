## 意见一：评测主报要换成"按触发门槛扫曲线"，报省 token 与正确率变化

**意见原话**（2026-08-01 凌晨，口述）：

> "这个评测协议和我的目的是不一致的，目前可能只是个中间产物，这个得想办法纠正，我的想法是根据触发阈值（这个阈值后日可能是动态的）不同汇报省了多少token，正确率降了多少。"

**当时在讨论什么**：用户复述论文总目的——训练一个小模型辅助大模型，提前把工具调用相关内容塞进大模型上下文，让大模型少出 token；核心指标是"用了比不用少多少 token、正确率降多少"。对照发现现行评测协议报的不是这两个数。

### 实际与目标的差距（事实，逐条带出处）

1. **c1 十二格没有一格报"省多少 token"。** 现行协议是钉死风险档（`RISK_TARGETS = [0.10, 0.05]`，`pipeline/eval/eval_tool.py:39`），在 val 的 20 档 θ（0.5–0.975 步长 0.025，`eval_tool.py:38`）里挑满足精度约束且 coverage 最大的一档（`eval_tool.py:302-311`），报 coverage / trig_acc / earliness。省 token 不在任何一格的产出里。
2. **在跑的注入回放只有一个 θ 点。** `pipeline/inject/runs/aw_gptoss_r10/plan_config.json`：`"theta": 0.925`、`"risk": 0.1`。θ 一变，探针出手位置就变，截断点变，续写整段重跑。探针置信度已落盘（`replay_inject.py` 文件头："探针触发点直接读已落盘的 logits"），换 θ 重排 plan 不需要重训；贵在续写段——本次实测 0.19 req/s、1750 条约 2.5 小时（速率读自 `pipeline/inject/logs/new1_inject_run.log` 进度行，1750 = nofill 1061 + inject 689）。
3. **"正确率降多少"这一轴，本次量的是调用一致率，不是任务成绩。** score 段算"token 账与调用一致率"（`replay_inject.py:11`）。任务级正确率要闭环真执行：把环境重放到该步、执行预测调用、跑完任务看成败——接口留了未实现（`miss_policy=execute`，`replay_inject.py` 文件头："尚未实现,接口已留"）。
4. **猜错的代价被记零。** 本次 `miss_policy=skip`：1061 个出手里 689 个预测与真实调用一致才注入（`plan_config.json` 的 `n_fired`＝探针出手的事件数、`n_inject`＝其中实际注入的事件数），其余 372 个跳过只记账。真部署时探针不知道自己猜错，照样注入错误结果；错误注入的杀伤已有量测——`oracle_inject/FINDINGS.md`：授权措辞下错误注入 acc 崩到 0.02–0.14。skip 口径下的正确率轴偏乐观。

### 修改建议（解读）

1. 主报改成 θ 扫描曲线：横轴 θ（或换算成 coverage），纵轴两条——省 token 比例、正确率变化；每个 θ 一次独立回放。θ 格点从现有 20 档里挑 4–6 个，全扫太贵。
2. 高 θ 端预计自己塌：`closed_loop/RESULTS_v0.md:22` 已量出 lead≤32 的开火平均省 −6.4 token。曲线画出来本身就是"时机要学"的论据，与论文标题一致。
3. c1 不作废：探针与训练不动；风险档选出的两个 θ 改述为"曲线上标注的推荐工作点"。
4. 纵轴要成立必须补两块：(a) 闭环执行拿任务级正确率（实现 `miss_policy=execute`，或单独闭环线）；(b) 猜错事件计入曲线（不再 skip）——过渡期可先跑 `miss_policy=oracle` 给注入机制本身的上界。
5. θ 动态化（学出手策略）是后续项，先把静态 θ 曲线打通。

**改了哪个文件**：截至本笔记，代码未动，只落了本文件。
**还欠什么**：θ 格点选择与排程未定；`miss_policy=execute` 未实现；按 README 规矩 `2026-07-31-direction-notes.md` 应移 `archive/` 并更新索引，本次未动。
