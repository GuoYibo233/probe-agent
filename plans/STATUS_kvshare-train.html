先把全篇要用的名字定死。

  • 探针是另外训练出来的一个小得多的模型，在被探测模型写思考文本的时候读已经写出来的部分，提前猜出下一次工具调用。探针分三种：只判工具类型并决定要不要触发的叫 ctool；生成整条调用串的叫 cgen（训练脚本的文件名里写 callgen，评测 run 的名字里写 ccall，三个写法指同一种探针）；给定工具名只填参数的叫 cparam。项目里把这三种叫三个格。
  • 探针的底座是 Qwen3-Base 系列。四个底座配置（下文简称配置）的代号：b06 是 0.6B 全参微调，b17 是 1.7B 全参微调，l17 是 1.7B LoRA，l4 是 4B LoRA。全参微调是底座全部权重都训；LoRA 是底座权重不动、只训练挂在线性层旁边的小矩阵的训法；全参微调和 LoRA 合称两种训法。p1 批还有一个 l06（0.6B LoRA），这一周没有用。
  • 训练数据分三堆：train 堆、val 堆、test 堆，每堆是一个 jsonl 文件。一行是 jsonl 的一条记录：被探测模型的思考文本在某个句子边界截断的前缀，加上标准答案（label_call 字段，被探测模型接下来真的发出的调用串）。切点就是这个句子边界。一个事件是同一次工具调用之前的那组行，事件全文是这组行里最长那一行的文本（sent_idx 字段最大的那一行，sent_idx 是行在事件里的序号）。一个任务实例是 AppWorld 的一道任务，下面有多个事件。行文本加上分隔串 \n[CALL] 分词之后，和事件全文分词结果相同的开头部分叫公共前缀，公共前缀之后到行末的几个 token 叫尾巴；目标串是标准答案的调用串加结束符；目标段是尾巴加目标串。损失位是打包序列里要算交叉熵的位置，也就是目标段里的每个 token；一个事件的损失位数等于这个事件的目标 token 数。
  • 这一周的主角是缓存复用训练器（文件 train_causal_share.py，cgen 和 cparam 共用；数据与分词的部分在 share_data.py）：一个事件的全文只过一遍底座，每个切点的目标段接在公共前缀后面算损失。设计文档把这种「前缀加全部目标段打包成一条序列一次前向」叫形态 A；形态 B 是前缀过一遍拿到缓存、每行接着缓存算自己的目标段，只做过对照没上训练。对照物是逐行训练器（train_causal_callgen.py 与 train_causal_param.py），每一行各自从头过一遍底座。ctool 有自己的训练器 train_causal_tool.py，不是缓存复用训练器，这一周也改了。
  • 口径指一套定死的训练设置或生成设置。新口径是 8 月 28 日定的这一套：事件全文 token 上限 8192（下文简称上限），超过的事件整条丢弃；一次更新 8 个事件；cgen、cparam 各 1 个 epoch。旧口径是 np821 那批用的：上限 4096、超过的从左边截掉、一次更新 32 行（逐行训练器按行计）或 32 个事件（ctool 训练器按事件计）、3 个 epoch。np821 是 8 月 21 日发射、8 月 26 日收官（收官指训练和评测都做完、账也记完）的十二格探针（四个配置乘三个格）。ks828 是这一周所有 run 名字的开头（TIMELINE.md 8 月 28 日定的批次前缀）。档指一套固定的运行设置：冒烟档、速度档、显存探针档各是一套，具体内容在各实验的「怎么做的」里。
  • 训练里的量：逻辑小批是一次送进训练器的一组事件，下文「每批 N 个事件」说的就是逻辑小批，缓存复用训练器默认 4 个；累积 M 次是连做 M 个逻辑小批才更新一次参数，累积起来做一次更新的那几个逻辑小批叫一个更新组；一次更新等于优化器更新一次参数，日志里叫一个 step，gstep 是累计更新次数；物理块是逻辑小批按 token 预算切出来的一段打包序列，一块里的事件数记作 B；token 预算（--tok-budget，默认 16384）是一块里补齐之后的 token 上限，补齐是把一块里的每个事件补空 token 到同一长度；显存探针（--mem-probe）是开训前挑几块最占显存的物理块各跑前向加反向、记峰值的程序，挑块方式有 tokens、cost、loop 三种（实验五解释）；整程峰值是训练全程 step 日志里 torch 已分配显存峰值的最大值；对齐检查是开训前把 6 个短 val 事件同时喂给缓存复用训练器和逐行训练器、fp32 下逐行比 loss 的检查，对齐差是这个检查量出的逐行最大绝对差，容差 2e-5（决定 18，来历在实验二）；对齐规则是对齐检查判过不过的规则，abs 看绝对差（对齐差不超过容差），rel 看相对差，both 两条都要过；梯度检查点（--grad-ckpt）是反向时重算前向激活来省显存的开关；验证集交叉熵是在 val 堆（或 val 堆的子集）上算的交叉熵，日志字段 val_ce；生成式评估是训练里对 val 堆的 200 行做 greedy 生成、比对调用串的评估，整串全对率是生成式评估报的比例；存最好版本是每次评估验证集交叉熵创新低就存一份权重到 best/。

实验一 · 注意力内核验证

这个实验问的是：形态 A 的打包前向在真实显卡上会用哪个注意力内核，最长的事件要多少显存，逐行 loss 和逐行训练器差多少。内核指 torch 的 scaled_dot_product_attention 接口（下文简称 sdpa）背后四种实现之一：flash、mem-efficient、math、cuDNN。

怎么做的

：在 tokyo108 的一张 H100 上跑一个验证脚本，底座用 Qwen3-0.6B-Base（脚本常量 MODEL），脚本从 val 堆里挑出全文不超过 8192 个 token 的最长事件（结果 JSON 的 longest_event 键：n_rows 64 行，P 前缀 8,167 个 token，L 打包后 9,381 个 token），按顺序做九步（脚本的 steps_done 字段，一个列表，记做完了哪几步）：第 1 步问 torch 四种内核对真实形状的掩码各自接不接；第 2 步强制用省显存的 mem-efficient 内核做一次前向加反向，记峰值和内核名；第 3 步不指定内核再做一次，看默认选中哪个；第 4 步在一个短事件上量 math 内核的峰值，短事件的取法是只取前缀不超过 2,048 个 token 的行、前缀截短到 2,048 个 token、逐行装到拼接长度不超过 2,560 为止，实际装了 42 行、拼接后 2,552 个 token（math_at_short_L 键的 n_rows 与 L）；第 5 步换四种掩码写法（布尔掩码是真假表，加性掩码是 0 和负无穷相加的表；长度补不补到 16 的倍数，16 是 mem-efficient 内核要求掩码在显存里每一维的间隔是 16 的倍数，设计文档 2.4）各记峰值；第 6 步在另一批 5 个短事件 34 行上，bf16 下把打包前向和逐行训练器的逐行 loss 逐行相减；第 7 步同一批 5 个事件 fp32 下再做一次（第 6、7 步就是后来训练器里对齐检查的原型：训练器抽 6 个事件、容差 2e-5 是决定 18 后来定的，这里是验证脚本抽 5 个事件 34 行、判据 1e-5 与 1e-4）；第 8 步开梯度检查点再量一次最长事件；第 9 步挂 LoRA 再量一次。逐行训练器有两种跑法：一次喂一行不补齐（下文叫「单行不补齐」），或者几行一批右补齐到等长（下文叫「整批补齐」），第 6、7 步两种都跑了。账上登记的是一个 run（09:16 start、09:36 finish），发射员在同一个 tmux 会话里把脚本跑了三次（三份日志 .log、.r1.log、.r2.log），账本只登记一次：第一次在第 4 步截前缀时显存不够，第二次在第 6 步报「没有可用内核」，改脚本后第三次九步全过（finish 记录的 conclusion 字段是发射员写的一句话结论，原话「三次发射(第4步截前缀OOM, 第6步GQA拒收, 第三次九步全过)」，GQA 就是分组查询）。

为什么这么设计才算数

：变的只有前向的形态和内核，模型权重、事件、精度设置全部相同，所以 loss 的差只能来自形态和内核。开跑前定的判据（设计文档第五节，8 月 28 日上午写的）是 fp32 下逐行 loss 最大差不超过 1e-5、逐 token 不超过 1e-4，超过就说明掩码或位置编号（打包序列里每个 token 的位置下标，让每段目标段接在自己的公共前缀后面）错了；显存的判据是最长事件的峰值对 H100 的余量不低于 10%。这个设计控制不了的是多个事件同一块的显存，那要等实验二、三。

看一条真的

：结果文件 pipeline/runs/smoke/kvshare_gpu_kernel_check/gpu_result.json（NFS）里第 2 步的原始记录（键名 forced_efficient）是

"forced_efficient": {"L": 9381, "mask": "bool", "backends": ["EFFICIENT_ATTENTION"],
  "peak_alloc_GiB": 31.08, "delta_GiB": 28.86, "seconds": 2.96,
  "kernels": [..., "fmha_cutlassB_bf16_aligned_128x128_k128_sm80(...)", "fmha_cutlassF_bf16_...", ...]}

实验结果（数字都出自 gpu_result.json，ops/runs.jsonl 的 finish 记录抄的是同一份）：

设置细节：第二次发射第 6 步报「没有可用内核」，设计文档第七节的判读是逐行训练器的「单行不补齐」批没有掩码，HF（HuggingFace 的 transformers 库）会让 K/V 保持 8 个头用分组查询，而 mem-efficient 内核不支持分组查询；修法是只给打包前向的路径限定 mem-efficient 内核（用 torch 的 sdpa_kernel 上下文管理器，下文叫内核上下文），逐行训练器的路径用默认内核。设计文档第七节接着按第 1 步的内核资格结果推断：「单行不补齐」那一批用的是 math 内核，和「整批补齐」的 mem-efficient 不是同一个内核，这是基线差比新旧之差还大的原因；这一条没有 profiler 实测。另外这个脚本里没有优化器状态，训练时要再加 AdamW 的两份状态。

实验二 · 三个格的第一次冒烟加 ctool 的显存补测

这个实验问的是：缓存复用训练器（cgen 与 cparam 两个格）和改过三处的 ctool 训练器（超长事件从左截改成整条丢弃、上限从 4096 改成 8192、读取位置改成 spec 11.3 的规则：读取位置是 ctool 取隐状态的那个 token 位置，新规则取起始位置在切点之前的最后一个 token，这个 token 跨过切点并且跨过的部分不是空白时退一个读前一个 token；「找不到读取位置」指没有任何 token 起始位置在切点之前，或者要退一个而已经是第 0 个）在真实数据的小样本上能不能从头跑到尾，三个格的对齐检查过不过；以及 ctool 不截断、上限翻到 8192 之后 H100 的显存够不够。

怎么做的

：三个格各跑一次冒烟档（缓存复用训练器的冒烟档取全文 token 数最短的 40 个训练事件和 16 个评估事件跑 1 个 epoch，40 个事件按 8 个一次更新是 5 次更新，每四分之一 epoch 评估一次共 4 次；ctool 的冒烟档取 200 个训练事件和 80 个评估事件，200 个按 8 个一次更新是 25 次更新），在 tokyo108 的三张 H200 上并行。冒烟档前面先做对齐检查：缓存复用训练器抽 6 个全文不超过 2,048 个 token 的 val 事件，同一份临时文件同时喂给缓存复用训练器和逐行训练器，fp32 并关掉 TF32（一种会降精度的矩阵乘加速）逐行比 loss；ctool 的对齐检查是整个序列一次前向对逐 token 增量前向（每次只喂一个新 token、带缓存），比末位隐状态和分类头 logits 的最大绝对差。ctool 的显存补测另外在一张 H100 上发两次，外面包一层每 2 秒记一次 nvidia-smi 的脚本：第一次用当时的默认值每批 4 个事件累积 2 次，第二次改成每批 2 个事件累积 4 次。

实验三 · 速度档

这个实验问的是：缓存复用训练器在 H100 上每秒处理多少行，比逐行训练器在同一台机器上跑同样行数快多少；token 预算取 16384 还是 24576；PyTorch 显存分配器的 expandable_segments 开关（让分配器扩展已有的显存段而不是新开一段，用来减少碎片，碎片是零散的没法复用的空闲显存）有没有用。速度档是这样一套设置：450 个事件、每 3 次更新记一条 step 日志、只在 epoch 末评估。

实验五 · 第二轮冒烟：三个新配置加 b06 上的三条新代码路径

这个实验问的是：b17、l17、l4 三个配置在缓存复用训练器上能不能跑通、对齐差多大、显存探针量到多少（给学习率扫描排卡用）；b06 上新加的三条代码路径能不能跑通：挑块方式 cost 和 loop、生成式评估、梯度检查点。

怎么做的

：七个 run 都是 cgen 格的冒烟档（最短 40 个训练事件、16 个评估事件），都开显存探针和 200 行的生成式评估（冒烟档的 16 个评估事件一共 81 行，所以实际生成 81 行）。三种挑块方式：tokens 是从 train 全集里挑 token 数最多的两块（最满块和最长事件）；cost 是枚举本次 run 第一个 epoch 的全部物理块，按三个标准各挑一块，共三块（token 数最多的一块，日志里叫 max_tokens_block；损失位数最多的一块，叫 max_losspos_block；token 数和损失位数各除以全部块里的最大值再相加、和最大的一块，叫 max_cost_block）；loop 是对 cost 挑出的块所在的更新组按真实训练循环跑一次更新。b17（不开梯度检查点）和 l17（不开梯度检查点）上 H200，挑块方式 tokens；l4（开梯度检查点）上 H100，挑块方式 tokens；b06 三次都在 H100：smoke2 用 cost、smoke3 用 loop、smoke4 开梯度检查点用 tokens。l4 第一次冒烟在显存探针的第一次反向报错退出，实现者修代码后发射员重发（smoke2）。

为什么这么设计才算数

：spec 16.8 写的理由是冒烟档只取最短事件，cost 和 loop 在冒烟下量到的是小块的数，不能排卡；tokens 另外装全集量最满块，和第一轮 b06 的显存探针同口径可比，所以三个新配置用 tokens。表里的预期数全部是 verify/smoke_check.py（助手 2 写的脚本）按显存模型「固定项加每 token 一个系数加每损失位 1.8 MB」对各自那一块算的，系数在设计文档 9.1 到 9.3。判据是冒烟数和预期数的偏差，偏差大就改显存模型；实际的偏差是 b17 高 3.6%、l17 高 4.2%、l4 smoke2 低 24.4%、b06 smoke4 低 11.5%，开梯度检查点那两个的系数本来就是外推值，设计文档 9.10 记为待实测，显存模型没有改。这个设计控制不了的是 tokens 挑的最满块只有 1,984 个损失位（B 是 2、每个事件补齐到 8,192，设计文档 8.6），比实验四整程峰值那一块（4,736 个）少 2,752 个，比学习率扫描里损失位最多的块（5,696 个，实验七「看一条真的」里 b17 的 max_losspos_block）少 3,712 个，设计文档 8.6 的判读是每个损失位多占约 1.8 MB，按这个判读 tokens 的数会低于整程峰值。

实验七 · 学习率扫描

这个实验问的是：训练口径换成新口径（缓存复用训练器、8 个事件一次更新、1 个 epoch）之后，四个配置在 cgen 格上哪一档学习率的验证集交叉熵最低；全参微调和 LoRA 的最好档差多少倍。

怎么做的

第六节 · 我的判断

这一周站得住的结论只有一条：缓存复用训练器可以替代逐行训练器。理由是第三节的对齐表和速度表：逐行 loss 的差在 5.007e-6 到 1.5378e-5 之间、随底座单调涨、同配置同卡型逐位相同；速度在同一台机器的 H100 上是逐行训练器的 23.3 到 67.8 倍（第三节速度表的倍数列，窗口 17,600 到 19,200 行处最低 23.3，累计 1,600 行处最高 67.8）。这个结论的范围是 b06 的 cgen 格和 450 个事件的样本；cparam 只有冒烟档，ctool 走的是另一条代码路径，两者在 train 堆全集上的数字一个都没有。

学习率扫描回答了扫描要回答的问题，但对「代码默认值改不改」只回答了一半。全参两个配置的最低点都是 1e-5，和默认值相同，两侧 2e-6 和 5e-5 都高（b06 0.2157 / 0.1730 / 0.1857，b17 0.2046 / 0.1636 / 0.1750）；LoRA 两个配置的最低点都是 5e-4，是默认值 2e-4 的 2.5 倍，两侧 1e-4 和 2e-3 都高。所以「要不要改默认值」这个决定实际上只关 LoRA：全参改不改结果一样。这件事是 5.5 九件里的第一件，定不下来，正式训练的每次发射就只能显式传学习率（那三个可选里的第二个）。l4 在 2e-3 上 loss 第 70 次升到 4.2674、第 250 次 1.0461、末条回到 0.5433，梯度范数超中位数 5 倍的有 9 条，我的判断是 4B LoRA 的网格边（最高那一档 2e-3）已经到发散边上，这一档不必再往上试。

显存探针的问题我认为已经解决：cost 挑块方式的显存探针对四个配置的整程峰值只低 0.001 到 0.422 GB，而排卡时乘的 1.1 倍对四个配置各多留 2.20 到 10.23 GB（第三节显存表「显存探针乘 0.1」那一列），多留的量是差额的 5.2 倍（b06）到 8,165 倍（l17），b17 是 222 倍、l4 是 26.6 倍（第三节显存表最后第二列）。1.1 倍是按第一轮显存探针 7.5% 的偏差定的，对 cost 可以降到 1.05，但这只是排卡余量的事，改不改都不动任何实验结论。

第二节和第五节里有两处缺口要点出来。第一，WORKPLAN.md 少了两件事（np821 收官、缓存复用训练器两轮），按规矩由 gyb 改。第二，np821 十二格是现役数据下唯一评测过的探针，而这十二格是旧口径；新口径下连 b06 的三个格在 train 堆全集上的训练都没有跑，5.3 那 99 GiB 的扫描权重是 1 个 epoch 的 cgen，没有评测过。要拿新口径的探针去做任何下游的事（活跑、矩阵对比），先要决定学习率，再跑四个配置各三个格的全集训练，再评测；按实验七的整程墙钟，cgen 格 1 个 epoch 的一个 run，b06 在 Ada 上 3494.7 到 3678.9 秒，b17 在 H200 上 2299.3 到 2830.4 秒，l17 在 H200 上 2883.8 到 3077.9 秒，l4 在 H100 上 7081.2 到 7284.8 秒，每个 run 另加 13 到 15 分钟的装模型与分词。
