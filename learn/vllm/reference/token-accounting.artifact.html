前缀缓存开着的时候，"prompt 有多长"有三个不同的答案。这张卡说清哪个数从哪来、我们存了哪个、想要另一个要动什么。

三个数，别混用

叫法是什么哪里拿得到我们存了吗
发过去的整段提示词的完整长度响应里的 usage.prompt_tokens存了（usage.in）
重算的真正过了一遍模型的部分要开 --enable-prompt-tokens-details没存
命中的直接拿现成 KV 的部分同上，prompt_tokens_details.cached_tokens没存

三者的关系在引擎里写死了，v1/metrics/stats.py:288：

重算的 ＝ 发过去的 － 命中的

num_computed_tokens = num_prompt_tokens - num_cached_tokens

服务端日志里的两个字段

字段数的是口径在哪写死的
Avg prompt throughput只数重算的，命中的不算v1/metrics/loggers.py:146-147
Prefix cache hit ratetoken 命中率，不是请求命中率v1/metrics/stats.py:119, 141
↑ 它的窗口最近 1000 条请求，滑动v1/metrics/stats.py:38, 42
命中率是滑窗值，不是累计值。同一台服务不同时刻印的两个百分比，不能当成"整轮实验的平均命中率"来比。要整轮的口径，得自己按请求聚合。

一条命令看当下命中率

grep -o "Prefix cache hit rate: [0-9.]*%" <日志> | tail -1

看一整段时间的走势：

grep -o "Prefix cache hit rate: [0-9.]*%" <日志> | uniq -c | tail -20

要把"重算了多少"存下来，得动两处

只加一半等于没加。服务侧给 --enable-prompt-tokens-details，客户端才读得到 prompt_tokens_details.cached_tokens；只改客户端会永远读到 None，只改服务端则没人存。要加就按三件套走：改代码 + 挂 run.py 注册表 + 回写 skill，同一个 commit。

本仓库现在存 token 用量的两处：envs/collect/common.py:68 与 :89（采集线的 raw / chat 两条路），pipeline/inject/replay_inject.py:818（注入线）。三处存的都是完整长度。
