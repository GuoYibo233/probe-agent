Lesson 0002 · vLLM 0.26.0

One prompt, two numbers from the service

One is the length you sent. One is the length it actually computed. Prefix caching splits these two numbers apart, and our jsonl only stores one of them. This lesson first sorts out which is which, then sorts out whether our existing data can be split apart.

Answering your question first: this feature was not something we chose

Your question was "why did we choose this one out of the several optional features." Prefix caching's answer is blunt: we did not choose it, it is on by itself.

This is line 93 of envs/vllm-env/…/vllm/config/cache.py. Turning it off requires explicitly giving --no-enable-prefix-caching (that is how vLLM's own source writes it too, see kv_transfer/…/nixl/base_worker.py:1712). I searched the whole new1 repo for prefix_caching and prefix-caching, and other than my own teaching notes, there is not a single hit, not in any of the three launchers, the generator, or any job script.

So the real choice is not this flag. What we chose is the shape of the prompt, and that shape decides how far this default feature actually reaches. The two lines below share the same shape.

Both of our lines keep resending the same opening over and over

Chat collection: every step carries the whole preceding stretch along envs/collect/run_appworld.py

One msgs list per task, only ever appended to, never trimmed. The request at step 13 sends everything from the previous 12 steps plus one new segment. The step count is right there in the client log: new1_awdiag_chat_s0.log, from line 2 on, steps=13, steps=18, steps=30, meaning 13, 18, and 30 requests, each one's opening identical to the one before it.

Inject line: several shots at the same event, only the tail differs pipeline/inject/replay_inject.py

The three marked segments are fixed by the event itself, unchanged no matter how many arms run on that event; only the final splice changes. Running four arms means four requests, sharing an opening of several thousand tokens, branching apart only from some point onward.

This is prefix caching's ideal shape. Its rule is simple: if this opening was just computed by the service and is still sitting in the KV pool, it gets reused directly, not recomputed. Nothing in the repo records that these two shapes were chosen to suit the cache, they each have their own reasons, and the cache hit is incidental.

Seeing how much it took effect, from the log

Look at that 149.4 tokens/s first. Nine requests running at once, each one's prompt a conversation history of several thousand to tens of thousands of tokens, and it "processes" only 149 prompt tokens a second. That sounds wrong.

It is not wrong, it is just counting something different from what you would assume:

The source's own comment says it. Avg prompt throughput counts only the part that was actually recomputed; whatever hit the cache does not count. 149.4 does not mean "the prompt was processed slowly," it means "almost none of the prompt was recomputed at all."

What "97.1%" is actually a percentage of

This number is easy to misread as "97% of requests hit the cache." It is not. Two places in the source pin down its exact meaning:

So the full reading is: among the most recent 1000 requests, 97.1% of the tokens queried were served directly from what already existed, without recomputation. Both numerator and denominator are tokens, not request counts, and it is a sliding window, older requests get pushed out. The hit rate printed by the same service at different moments cannot be treated as a cumulative value for comparison.

The number we store into jsonl is a different one

Both the collection line and the inject line store token usage, and both store usage.prompt_tokens:

Internally, the engine actually does split this apart, stats.py:288 has the one line num_computed_tokens = num_prompt_tokens - num_cached_tokens. But getting that split into the API response requires turning on a flag:

Off by default, and we have never turned it on once. Conclusion: in our existing data, how many tokens each request actually computed cannot be split out. All that is visible is the hit rate aggregated over a 1000-request sliding window in the server log.

This needs to go into the settings record. Wherever token cost gets reported, it has to say clearly which number is being reported. And on the inject line, several arms of the same event share one large prefix, adding up the prompt_tokens across arms gives you the amount sent, not the amount the service actually computed. A hit rate of 97 to 98 percent means directly: of the tokens queried, only two or three percent were actually recomputed.

The log level does not reach the response body. What is needed is --enable-prompt-tokens-details, it decides whether the field exists in the response.

Three things to do before the next batch of experiments starts

  1. Glance at any service's current hit rate to judge whether your prompt shape is wasting compute: 
    grep -o "Prefix cache hit rate: [0-9.]*%" <log> | tail -1
    A low hit rate where your workload should have a long shared prefix means the prefix got broken somewhere (for example, a different timestamp stuffed into each request).
  2. Decide whether to turn on --enable-prompt-tokens-details. If you do, add both halves together: give the flag server-side, and have the client store prompt_tokens_details.cached_tokens into jsonl alongside it. Adding only half is the same as not adding it, either the server gives it and nobody stores it, or the code reads a field that is always None.
  3. If you add it, follow the repo's three-part rule: change the code + register in run.py + write back to the skill, all in the same commit.
