挂断连接就是叫服务端别算了

活跑驱动靠这一招实现干预：一边流式收字，探针一开火就把连接关掉，改完 prompt 再发一次。这一课讲清楚服务端那边真的会停，以及为这一招付出的两笔账。

一步之内可能开好几个流。每次重开，prompt 都是"原前缀 + 到目前为止已经写出来的（改过的）内容"。

服务端真的会停吗：会

客户端断开 → 生成协程被取消 → 走到这个 except → 调 abort。这条路是源码里明写的，注释也说清了触发条件。所以 close() 不只是我们这边不听了，是服务端那条请求被真的撤掉，KV 槽位释放。

但我们的日志证明不了这一点。上面那行 logger.info("Request %s aborted.") 卡在 if self.log_requests: 后面，而这个开关默认是关的——engine/arg_utils.py:2724，enable_log_requests: bool = False。我在三台服务的日志里 grep 过 aborted，零条。这是"没开日志"，不是"没发生 abort"。想亲眼看见，起服务时加 --enable-log-requests。

第一笔账：被中止的那一段，token 数是估的

我们给流加了 stream_options={"include_usage": True}，正常收尾时最后会来一块带 usage 的数据。中途挂断，这一块永远不会到。代码里就是这么兜的：

"一块 ≈ 一 token"是个经验假设，注释里自己标了"近似"。凡是发生过注入的步，它的 gen_tok 里就掺了估计值。这条要写进口径——省 token 那条轴上，分子里有一部分不是数出来的。

第二笔账：重发的那一段，其实很便宜

回到第 2 课。重开流时 prompt = prompt_head + raw——前面那一大段刚刚才算过，KV 池里还热着。前缀缓存直接接上，重发的代价只有真正新增的那一小段。

两笔账方向相反，别互相抵消着算。算力上重发很便宜（前缀命中）；账面上被中止的段落 token 数是估的（没有 usage）。前者是性能，后者是口径。报告里该分开写。

练一练

不许翻上面。答错立刻有反馈，答完就锁。

1. 流式读到一半把连接关掉，服务端会怎样？

对。async_llm.py:587-594：断开会让生成协程被取消，走到 except 里调 abort。

不会白算。源码里专门为这种情况留了 abort 路径（async_llm.py:587-594）。

不报错。这是正常路径，被当成客户端主动中止处理。

2. 我们日志里一条 aborted 都没有，说明了什么？

对。那行 log 卡在 if self.log_requests: 后面，而 enable_log_requests 默认 False（arg_utils.py:2724）。

推不出来。日志开关是关的，abort 发没发生这份日志根本不记。

支持。0.26.0 的 abort 路径就在 async_llm.py:587-594。

3. 被中止的那一段，生成了多少 token 是怎么来的？

对。live_appworld.py:317 用 st.n_chunks，注释自标"近似"，因为 usage 那块永远不会到。

中途挂断的话，带 usage 的那一块根本不会送到。所以才要退回块数近似。

代码里没有这么做。它用的是收到的增量块数。

4. 注入后重发整段前缀，主要成本落在哪？

对。prompt = prompt_head + raw，那段刚算过还在 KV 池里，前缀缓存直接接上（第 2 课）。

不会整段重算。前缀缓存默认开着，刚算过的那段直接复用。

跟温度无关。决定它的是前缀在不在 KV 池里。

5. 切口之后被丢弃的那些字，该怎么记账？

对。代码把它记在 discard 里（live_appworld.py:297-298）。生成过就是花过，只是没进最终文本。

那是拿丢掉的东西充业绩。这些 token 真的被生成过。

重发补的是新内容，不是这些被丢的字。它们的算力回不来。

下次动流式代码之前做这三件事

  1. 确认你的 usage 是完整的还是估的。凡是可能中途挂断的路径，末尾那块 usage 就不会来，账上必须标出哪些是近似值。
  2. 想亲眼看 abort 有没有发生，起服务时加 --enable-log-requests，然后： 
    grep -c "aborted" <日志>
    不开这个旗标，grep 出零条不代表任何事。
  3. 被丢弃的生成内容单独一列记，别并进"省下的 token"。这两个数在报告里代表相反的东西。
