Lesson 0001 · vLLM 0.26.0

一台服务的真实口径，只在启动日志里

命令行写的是你的意图，日志写的是实际发生的事。两者经常不一样，而且不一样的时候没人报错。这一课教你从启动日志里读出五件事，然后拿我们自己四台服务的真实数字做练习。

为什么先学这个

你的四个目标——判断配置对不对、下一批选对功能、论文里说清口径、看懂现有代码——第一步是同一件事：能说出一台服务此刻的真实口径。这件事不看命令行，看启动日志。

命令行不够用，有三个具体原因。第一，你没写的旗标有默认值，默认值随版本变。第二，vLLM 会替你自动决定一些事（挂哪个解析器、上下文取多长），命令行上看不见。第三，有些旗标你写了会被无视——下面第五行日志就是一例。

五行日志，五件事

下面全部来自同一个文件：new1_diag_srv_a.log，2026-08-02 17:08 那次启动，gpt-oss-120b 跑在 tokyo108 GPU 0。左边挂的是它在那个文件里的行号。

① 我实际传了什么

vLLM 只打印与默认值不同的参数。这台服务命令行上明明写了 --gpu-memory-utilization 0.92，这一行里却没有它——因为 0.26.0 的默认值就是 0.92，写了等于没写。这一行是查"我以为我改了、其实没改"的最快入口。

② 上下文上限最终定成多少

这台没给 --max-model-len，vLLM 从模型 config 自动取了 131072。这是刻意的：那批实验要复刻 w0 采集时的原样配置，理由写在 envs/serve_logs/launch_vllm_awdiag.py 文件头。同期另一批服务给了 65536——同一个模型，两个口径，产出的数据不能混着比。

③ 显存被切成了几块

整张卡 93.1 GiB，按 0.92 圈走 85.65 GiB，其中权重吃掉 61.43 GiB，剩下 20.45 GiB 才是 KV 缓存池。"KV 缓存池"就是服务用来存已经算过的上下文的那块显存——它决定这台服务能同时扛几条请求。

④ 池子能装多少、能同时扛几条

这两行是整份日志里最该记住的。第一行是池子的总容量，按 token 数算。第二行是它的直接推论：

并发上限 ＝ KV 池容量 ÷ 单条上下文上限

528,934 ÷ 131,072 = 4.04

日志印的就是 4.04x。这是一道除法，你可以自己验算。意思是：如果每条请求都用满 131072 的上下文，这台服务只能同时伺候四条。

所以第 ② 行那个数不是随便填的。上下文上限翻一倍，并发就砍一半。

⑤ 有些旗标给了也白给

vLLM 明说了它无视这个旗标。同一份日志的第 14 行还能看到它自动挂上了 reasoning_parser='openai_gptoss'——这两件事命令行上一个字都没有。

练一练

不许翻上面。答错立刻有反馈，答完就锁。

1. H100 那张卡上、上下文上限 65,536 的那台服务，KV 池是多大？

对。splice_srv_a，H100 + 65,536 + 0.92 → 475,669 tokens，并发 7.26x。

这是 diag_srv_a 的数——同一张 H100，但上下文上限是 131,072。答案是 475,669。

这是 splice_srv_echo 的数——它的显存比例是 0.80，不是 0.92。答案是 475,669。

2. 日志里那个 22.51x 是怎么算出来的？

对。1,475,384 ÷ 65,536 = 22.51。一道除法，随时可以自己验。

不是。显存那笔账在另一行（"Free memory on device …"），并发这一行只跟 KV 池和上下文上限有关：1,475,384 ÷ 65,536 = 22.51。

不是。这台服务的并行分片数是 1（单卡单实例）。正解是 1,475,384 ÷ 65,536 = 22.51。

3. 两台 H100 的 KV 内存都是 20.45 GiB，为什么并发一个 7.26x 一个 4.04x？

对。65,536 对 131,072，分母翻倍，并发几乎砍半。这就是为什么给不给 --max-model-len 是个真决策。

不是。两台都是 93.1 GiB 的 H100。差在上下文上限：65,536 对 131,072。

不是。两台的显存比例都是 0.92，KV 内存都是 20.45 GiB。差在上下文上限：65,536 对 131,072。

4. 我们脚本里写的 --gpu-memory-utilization 0.92，在装着的 0.26.0 上是什么处境？

对。vllm/config/cache.py:68 写着 Field(default=0.92)。所以它压根不出现在 "non-default args" 那一行里。

不是。0.26.0 的默认值正是 0.92（vllm/config/cache.py:68）——这个旗标在这个版本上等于没写。

不是。0.26.0 的默认值正是 0.92（vllm/config/cache.py:68）——这个旗标在这个版本上等于没写。

5. 给 gpt-oss 的服务加上 --enable-auto-tool-choice，会发生什么？

对。日志第 72 行原话："For gpt-oss, we ignore --enable-auto-tool-choice and always enable tool use."

不是。日志第 72 行原话："we ignore --enable-auto-tool-choice and always enable tool use." 对 gpt-oss 它是空转的。

不是，服务照常起来。日志第 72 行只是一条 WARNING："we ignore --enable-auto-tool-choice and always enable tool use."

下次起服务时做这一件事

  1. 服务起来后，从日志里抓这三行，贴进你的实验记录： 
    grep -E "Using max model len|GPU KV cache size|Maximum concurrency" <日志>
  2. 手算一遍：KV 池 ÷ 上下文上限，看等不等于日志印的并发倍数。等，说明你读对了行。
  3. 把这个并发倍数跟你实际起的客户端分片数比一比。分片数超过它，多出来的请求会排队而不是并行。

先读这一份：vLLM Engine Arguments——只看 --gpu-memory-utilization、--max-model-len、--max-num-seqs 三条。⚠️ 它写的是最新版，默认值可能跟我们装的 0.26.0 不同；拿不准就去翻 envs/vllm-env/lib/python3.12/site-packages/vllm/config/。
