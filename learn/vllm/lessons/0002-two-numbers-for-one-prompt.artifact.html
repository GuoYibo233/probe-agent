Lesson 0002 · vLLM 0.26.0

同一段 prompt，服务报两个数

一个是你发过去的长度，一个是它真正算了的长度。前缀缓存把这两个数劈开了，而我们的 jsonl 里只存了其中一个。这一课先说清哪个是哪个，再说清我们现有的数据能不能拆。

先回答你那个问题：这个功能不是我们选的

你问的是"为什么从几个可选功能里选了这个"。前缀缓存的答案很直白：我们没选，它自己就开着。

这是 envs/vllm-env/…/vllm/config/cache.py 第 93 行。要关掉得显式给 --no-enable-prefix-caching（vLLM 自己的源码里就是这么写的，见 kv_transfer/…/nixl/base_worker.py:1712）。我在整个 new1 仓库里搜过 prefix_caching 和 prefix-caching，除了我自己写的教学笔记，一处都没有——三份发射器、生成器、所有 job 脚本，全都没提过它。

所以真正的选择不在这个旗标上。我们选的是 prompt 的形状，而这个形状决定了这个默认功能生效到什么程度。下面两条线，形状是一样的。

我们的两条线，都在反复重发同一段开头

chat 采集：每一步都把前面整段带上 envs/collect/run_appworld.py

一道题一个 msgs 列表，只往后加，从不裁剪。第 13 步那次请求，发过去的是前 12 步的全部内容加上新的一段。客户端日志里能直接看到步数：new1_awdiag_chat_s0.log 第 2 行起，steps=13、steps=18、steps=30——那就是 13 次、18 次、30 次请求，每次的开头都跟上一次一模一样。

注入线：同一个事件发好几枪，只有尾巴不同 pipeline/inject/replay_inject.py

划出来的三段由事件本身定，一个事件上不管跑几个臂都不变；变的只有最后的 splice。跑四个臂就是四次请求，共享一段几千 token 的开头，从某个位置起才分岔。

这就是前缀缓存最理想的形状。它的规则很简单：这段开头如果服务刚算过、KV 池里还留着，就直接接着用，不重算。仓库里没有任何一处记录说这两个形状是为了迁就缓存才这么定的——它们各有各的来由，缓存是顺带命中的。

它没错，只是数的东西跟你以为的不是一个：

源码自己写了注释。Avg prompt throughput 数的是真正重算的那部分，命中缓存的不算。149.4 不是"prompt 处理得慢"，是"绝大部分 prompt 根本没重算"。

"97.1%" 到底是什么的百分比

这个数很容易读成"97% 的请求命中了"。不是。两处源码定死了它的口径：

所以完整的读法是：最近 1000 条请求里，被查询的 token 中有 97.1% 是直接拿现成的，没重算。分子分母都是 token，不是请求条数；而且是个滑动窗口，老的请求会被挤出去——同一台服务在不同时刻印出的命中率不能当成累计值来比。

我们存进 jsonl 的那个数，是另一个

采集线和注入线都存了 token 用量，两处存的都是 usage.prompt_tokens：

引擎内部其实是拆开的——stats.py:288 一行就写着 num_computed_tokens = num_prompt_tokens - num_cached_tokens。但这个拆分要传到 API 响应里，得开一个旗标：

默认关着，我们一次都没给过。结论：现有数据里，每条请求实际算了多少 token，拆不出来。能看到的只有服务端日志里那个按 1000 条滑窗聚合的命中率。

这条要写进口径。如果哪里要报 token 成本，得说清报的是哪一个数。而且注入线上同一事件的几个臂共享一大段前缀——把各臂的 prompt_tokens 加起来，得到的不是服务实际算的量，是发过去的量。命中率 97%–98% 的直接含义就是：被查询的 token 里只有百分之二三真的重算了。

下一批实验开跑前做这三件事

  1. 随手看一眼任何一台服务当下的命中率，判断你的 prompt 形状有没有在浪费算力： 
    grep -o "Prefix cache hit rate: [0-9.]*%" <日志> | tail -1
    命中率低而你的负载本该有长共享前缀，说明前缀在某处被打断了（比如每条请求里塞了不同的时间戳）。
  2. 决定要不要 --enable-prompt-tokens-details。要就得两半一起加：服务侧给旗标，客户端把 prompt_tokens_details.cached_tokens 一起存进 jsonl。只加一半等于没加——服务给了没人存，或者代码去读一个永远是 None 的字段。
  3. 如果加，按仓库的三件套规矩走：改代码 + 挂 run.py 注册表 + 回写 skill，同一个 commit。
