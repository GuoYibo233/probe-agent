Lesson 0004 · vLLM 0.26.0

temperature=0 不等于逐字可复现

把温度调到 0，采样这一步确实没有随机性了。但同一条 prompt 跑两次仍可能写出不同的字——因为跟它同批的请求变了。这一课把这件事从源码里挖出来，再看我们仓库早就为它立过的规矩。

temperature=0 到底做了什么

温度低于 1e-5 就整个切到贪心档，另外三个采样参数一并被覆盖成"不筛选"。贪心档本身只有一行：

取最大值，没有抽签。所以 seed 在这条路上没有作用——随机数发生器只在随机采样那条分支里用得到（sampler.py:288）。我们的客户端代码里也确实一次都没给过 seed。

那不确定性从哪来

不在采样这一步，在它前面那一步：算出 logits 的那次前向。0.26.0 自己承认了这件事，在环境变量表里：

反过来读这句注释：不开它，结果就不是"与批组成无关"的。默认值是 "0"，也就是关着。我们从没设过这个变量。

批组成是什么。vLLM 每一步把当下在跑的若干条请求凑成一批，一起做前向。凑进来的是哪几条、总共多长，决定了矩阵乘法的形状；形状变了，浮点数的累加顺序就变，末位会差一点点。绝大多数时候差异被 argmax 吃掉了，但在两个候选 token 分数几乎打平的地方，末位那点差异足以把 argmax 翻过去。翻一次，后面整段就分岔了。

而批组成由什么决定？由你开多大并发、别人同时在这台服务上跑什么、请求什么时候到。这些都不在你的请求参数里。

我们仓库为这件事立过两条规矩

一、nofill 臂只当体检线，不当主对照 pipeline/inject/replay_inject.py

二、一条曲线的各点必须同并发 pipeline/inject/sweep_theta.py

所以 sweep_theta 对六个 θ 点用同一个 --concurrency。这不是洁癖：并发不同的两个点，它们之间的差里混着一份跟 θ 无关的抖动。

别把两件事混引。sweep_theta.py:39–48 里那个实测数字——两次跑同一批、14/1061 条（1.3%）写出了不同的调用——量的是探针那条 0.6B 参数产线，用的是 HF 批量推理，机理是 left padding 长度随 batch size 变。跟 vLLM 这边是同一类现象、不是同一次测量。vLLM 侧我们没有做过对照实测。

那到底哪些东西是可复现的

把"可复现"拆开看，我们手上有一个现成的例子（同一份 sweep_theta.py 的注释，2026-08-01 那次两跑对拍）：

这一层两次跑的结果
探针出手的事件集合零差异
触发句的位置零差异
深度零差异
工具级预测零差异
置信度数值446/1061 在第 7 位小数上不同
写出来的整条调用14/1061 不同

出自 pipeline/inject/sweep_theta.py:39–48。置信度那行的原因注释里写了：CPU softmax 的归约顺序随线程数变；它不改变任何出手决定。

规律很清楚：离散的判定层复现得住，连续的数值和长程生成复现不住。报数字的时候按这条分层来说，比笼统说一句"用了 greedy 所以可复现"要诚实。

练一练

不许翻上面。答错立刻有反馈，答完就锁。

1. temperature=0 时，seed 起什么作用？

对。贪心档就是 logits.argmax（sampler.py:240-241），随机数发生器只在随机分支用。

温度 0 走的是 argmax，根本没有抽签这一步（sampler.py:240-241）。

批怎么组由调度器和并发决定，跟 seed 无关。

2. 同一条 prompt 两次跑出不同结果，源头在哪一步？

对。批组成变了，矩阵形状变了，累加顺序变了，末位差异在打平处把 argmax 翻过去。

温度 0 没有随机抽样。分岔发生在算 logits 那一步（见 envs.py:600-602 的注释）。

解码是确定的。问题在更早的前向计算里。

3. VLLM_BATCH_INVARIANT 在 0.26.0 上的默认值是？

对。envs.py:602 的默认字符串是 "0"。它的注释反过来读就是这一课的全部。

默认是 "0"（envs.py:602）。要那个保证得自己设，且要求算力 ≥ 9.0。

不是自动的。它读的就是一个环境变量，默认 "0"。

4. 一条 θ 曲线的六个点，为什么必须用同一个并发？

对。sweep_theta.py:19-22 写死了这条：批组成一变，greedy 续写就有数值抖动，混进曲线就是异构点。

显存不是这条规矩的理由。理由是批组成变了会引入跟 θ 无关的抖动。

上下文上限由服务端定，跟客户端并发无关。

5. 那个 14/1061 的实测分岔，量的是哪条产线？

对。0.6B、HF 批量推理、left padding 随 batch 变（sweep_theta.py:39-48）。同类现象，不是 vLLM 的测量。

不是。vLLM 那一侧我们没做过对照实测，别把这个数字挪过去用。

环境重放是逐步核对过的，那条线上有单独的保真度检查。

下次报「可复现」之前做这三件事

  1. 说清是哪一层可复现。离散判定层（出手事件、触发位置、工具级预测）和长程生成层，结论不一样，混在一句话里就是虚报。
  2. 把并发写进报告，跟温度、max_tokens 并列。它现在是个隐藏变量，但它确实会改结果。
  3. 真需要逐字可复现的对照，先确认卡的算力够不够，再考虑开那个开关： 
    nvidia-smi --query-gpu=name,compute_cap --format=csv
    envs.py:601 要求 ≥ 9.0。够了再谈 VLLM_BATCH_INVARIANT=1——它有性能代价，值不值得看你要它干什么。
