# invariants: conventions where not a single character may change

This file lists the constants and rules in the probe pipeline that **must not be touched when changing the dataset, changing the agent model, or changing the environment**.
**Changing any entry here means the new and old numbers are no longer comparable**; you must start a new dataset version number / run_id batch number, and add an entry in `TIMELINE.md` explaining what was changed, why, and which old numbers it invalidates.

See `stage-commands.md` for how to type the command line; see `gates.md` for gates and contingencies (both in this directory).

## 1. Why this checklist exists

A drift in conventions is silent: change the batch size, change the split, move a threshold, and the code still runs, the report still produces numbers. It's just that this batch's numbers are no longer measured with the same yardstick as the historical batch, and nowhere does it raise an error.

This project has already been bitten by this three times: the C3 line had two sets of tier numbering, and the code's set and the official set had **their values exactly reversed** (`DATA.md` §6.1); BFCL's frequency prior baseline changes with the data version, the same environment has three values, 0.038 / 0.049 / 0.042, and picking the wrong one flips the reading of the probe's "how much it beats the baseline by" (`DATA.md` §4, §7.2); the wall-clock-time column requires both arms to run on the same model of card, otherwise the whole column is invalidated (`DATA.md` §6.2, §7.4).

So the rule is: copying takes priority. Functions, constants, and regexes marked [copy verbatim] are copied unchanged from the source file, not one character altered; when unsure whether to copy or write it yourself, the default is to copy; for a decision point the spec doesn't cover, stop and ask the user, don't guess (`plans/2026-07-31-pipeline-engineering.md` §0.2, §0.4).

## 2. Data-side conventions

| Convention | Fixed value | Where it's hard-coded | What happens if changed |
|---|---|---|---|
| Seed SEED | **the seed family `42 / 67 / 4267 / 6742`, drawn in order** (since np821): if collection needs K trajectories, take the first K in order and write each one into the trajectory meta; every single-seed position inside the pipeline (splitting, smoke sampling, `torch.manual_seed`) always takes the first one, **42** | `pipeline/annotate/rules.py`'s `SEED` and each of the three causal training scripts' own `SEED` have all been switched to 42; **the two mbert training scripts are still `20260729`** (the m-line is retired and wasn't switched along with it); an explicit `20260729` written in an old config still takes effect as-is and overrides the default (this is what G8's byte-for-byte reproduction relies on) | rerunning no longer matches sample-for-sample, the chain of evidence for "reproducible" breaks; DATA.md §7.5 explicitly states this is a hard rule. Changing the family members or the draw order = new and old data are not comparable |
| How many trajectories per task | since np821, `trajs_per_unit`, **4** this batch (temperature 1.0, one seed per trajectory, `_r0..r3`); left unset by default = 1 per task = the old behavior | a batch config field; the collect-side manifest's `traj_per_task` + `seed_family`; filename `appworld_<tid>_r<k>.jsonl` | the K trajectories of the same task naturally fall in the same split via `unit` (the meta's task_id), split assignment is unaffected; but the sample count grows by a factor of K, and gate B judges completeness by K (`stage-commands §7`); changing K = changing the dataset version |
| Collect generation settings | **the sole source of truth is `configs/presets/<name>.json`, the manifest only writes the preset name**; np821 uses `default` (harmony, effort high, **temperature 1.0**, top_p 1, max_tokens 8192). Warning: `default` and `gptoss_default` are two different files (the latter is OpenAI's official recommended convention, effort medium) | the manifest's top-level `gptoss_client_preset`, defaults to `default`; the preset name and the expanded gen_settings are automatically written into the trajectory meta | changing the temperature = changing the behavior distribution being probed, **numbers in the same table must come from the same preset** (np821 uses `default`, p1 uses p1's own batch preset, the two batches' numbers each belong to their own table); getting one character of the preset name wrong changes the convention, check the preset name in `MANIFEST.md` before launching |
| Minimum thinking length MIN_THINK | `40` characters | `rules.py` (ENG §2.2) | the cut-point set changes → the sample count changes → every sample's w and the total volume all change → not comparable to any historical version |
| Max cut points per event MAX_BOUNDS | still defaults to `64`, but since np821 it is a **batch config field** `max_bounds` (the CLI `--max-bounds` overrides the config); over the limit, thin it out by approximately equal-spaced index sampling, **the final cut point is always kept** | `rules.py`'s `MAX_BOUNDS` is only the default value, the real value flows through the `max_bounds` argument of `rules.boundaries(text, max_bounds)`; `build.py` reads it from the config | same as above; and gptoss's cut-point median has already reached 51, right up against 64 (DATA.md §3.1), moving it will make gptoss's sample count jump. The limit directly determines the sample count, so the driver makes it an explicit stopping point in a1_stats: first print the **untruncated** cut-point distribution and let a human decide (each batch's measured distribution belongs in DATA.md / the batch worklog). Once a batch is set, it must not be changed midway |
| History rounds HIST_ROUNDS | `3` | `rules.py` (ENG §2.2) | the input text changes → the context the probe sees changes → trigger accuracy is not comparable |
| Result truncation RESULT_CAP | `400` | `rules.py` (ENG §2.2) | same as above |
| Sentence-boundary regex SENT_RE | `(?<=[.!?])\s+\|\n` | `rules.py` (ENG §2.2) | cut-point positions change, `depth` and earliness both change entirely |
| Text layout template | `Task: …\n[HISTORY]\n…\n[THINKING]\n<prefix>` (produced by `assemble()`) | `rules.py` (ENG §3.2) | the training distribution and the live distribution at injection time no longer match, the inject stage fails outright |
| Sample weight | **equal weight per step `w = 1`** (the long-term convention since np821, `weight_mode` defaults to `uniform`); the old convention, equal weight within an event `w = 1/m` (m = that event's cut-point count, rounded to 6 places), is only obtained with an explicit `per_event`, its only remaining use is byte-for-byte reproduction acceptance | `build.py`'s `make_samples(events, weight_mode, max_bounds)`, config field `weight_mode`, CLI `--weight-mode` (PLAN §1.2, ENG §3.2) | numbers from the two conventions are not comparable with each other: under `per_event` every event's total contribution is a constant 1, under `uniform` long-thinking events carry proportionally more weight by their cut-point count. **Rerunning an old config without adding the flag gets equal-weight data, not the old 1/m**: reproducing an old artifact requires an explicit `--weight-mode per_event` |
| Parameter value normalization | `strip()` then `strip("\"'")`, empty values skipped | copied verbatim from `envs/bert/param_label.py` (ENG §3.3) | the gap between the loose/strict tiers gets artificially widened or flattened (this round's conclusion, "the gap only shows up in the extraction path," holds on the strength of this convention, TIMELINE 2026-07-31 c1 entry ③) |
| Parameter name rule | kwargs take their name, positional args take `pos0/pos1/…` | copied verbatim from `split_args_named()` (ENG §3.3) | the key-match judgment changes, parameter accuracy drifts overall |
| `label_call` format | `f"{label}({', '.join(f'{k}={v}')})"`, `f"{label}()"` when there are no parameters | `build.py` (ENG §3.3) | cgen's training target string and cparam's target derivation (stripped by the `label+"("` prefix) both get deformed together, numbers like `val_exact_call` and `full_call_ok` are not comparable to history |
| Parameter span location | `str.rfind`: the span of the value's **last** occurrence in that sample's own text, `found=false` if not found | `param_label.py` (ENG §3.4) | mext's span labels change, the extraction head's training target changes |
| Split assignment rule | goes by the official task list, assignment at the task-instance level; a unit not found in any task list **errors out**, silently dropping it is not allowed | `build.py` [change ②] (ENG §4.2.3, PLAN §1.6) | silently dropping a task would make the three models' task lists no longer match, and the premise of "comparing the same tasks" would collapse (DATA.md §3.1) |
| Split names | only three splits: `train / val / test`; anywhere the old code reads `calA`/`calB` now always reads `val` | ENG §2.5 | temperature and the threshold must be set on the same val; setting them separately becomes a different evaluation method entirely |
| Annotation policy | fully automatic, **failed trajectories are used as-is**: this learns "what the model would do," not "what it should do" | PLAN §1.3 | filtering out failed trajectories amounts to changing the learning target, the probe no longer captures the model's real behavior |
| Trajectory directory naming | `appworld_<model_key>`, the tail must match a key in `MODEL_OF` | `build.py`'s glob pattern (ENG §4.2.1) | a non-standard name → the whole directory gets **silently skipped** by event extraction, the dataset loses a whole chunk with no error (a pitfall hit in practice, see gates.md §3.6) |
| Old data | every old file under `envs/`, `envs/bert_data/v3*`, `envs/bert_runs/*` is read-only | ENG §0.5, PLAY §0.7 | the reproduction baseline for the old numbers gets destroyed, both acceptance lines can never be rerun again |

## 3. Training-side conventions

| Convention | Fixed value | Where it's hard-coded | What happens if changed |
|---|---|---|---|
| mbert hyperparameters | lr 2e-5 / bs 8 / accum 4 / epochs 3 / maxlen 4096 / left truncation / fp32 weights + bf16 autocast / warmup 5% / clip 1.0 | `train_mbert_tool.py`, `train_mbert_extract.py` (ENG §5.1, §5.2) | if the effective batch size or learning rate changes, the same cell's cross-model results are no longer a comparison under the same training recipe |
| causal hyperparameters | lr 1e-5 (LoRA goes through `lora_util.resolve_lr`, default 2e-4) / warmup 5% / clip 1.0 / fp32 + bf16 autocast, unchanged across the three cells. **One update is uniformly 8 events, but since 2026-08-28 how bs/accum split it and the epoch count have gone their separate ways** (a change of implementation, spec section 1): ctool `--bs 2 --accum 4` (decision 15: under the 8192 ceiling `--bs 4`'s first training batch OOM'd on H100, the process at 92.94 GiB, backed off to `--bs 2`, see `ops/runs.jsonl`'s `ks828b06_gptoss_ctool_h100mem_bs2`), `--epochs` is still 3; cgen/cparam (`train_causal_share.py`) uses `--events-per-mb 4 --accum 2`, `--epochs` changed to 1 (the reason is that all 8 of np821's cgen/cparam runs had val_ce lowest at epoch 0, while the 4 ctool runs kept climbing across three epochs, `plans/2026-08-28-plan.md` sections 12.7 and 12.8, draft 2.5; the new trainer still passes every cut point once per epoch, it's just that shared-prefix computation is faster, the epoch count is unrelated to compute). The update unit for all three cells is still 8 events, the "same skeleton, multiple heads" comparison hasn't been broken. **The np821 batch used bs 4 events / accum 8 (32 events per update) / epochs 3**, all three cells used the same set of hyperparameters at the time | `train_causal_tool.py` (ticket 02), `pipeline/train/train_causal_share.py` (cgen/cparam, currently in service, ticket 03); the old row-by-row scripts `train_causal_callgen.py`, `train_causal_param.py` are frozen as a reference, launched via `train-cgen-rows`/`train-cparam-rows`, still unchanged from the np821 convention (ENG §5.3, §5.4) | same as above; and cgen/cparam's hyperparameters are **deliberately aligned with ctool**, changing one breaks the "same skeleton, multiple heads" comparison (the comparison of cgen against cparam is even more so: the same batch of samples, the same answers, differing only in the concatenation string; once the hyperparameters diverge the gap can no longer be attributed to "whether the tool name is given"); it's also worth noting that ctool and cgen/cparam no longer have the same epoch count, when comparing the three cells against each other, "how many passes over the data" is no longer the same number |
| Left truncation | `truncation_side="left"`, `padding_side="right"`, pad=eos | copied verbatim from `train_causal_probe.py`'s `build()` (ENG §5.4) | right truncation would eat the tail of the thinking text right before the call, exactly the part the probe most needs to see. **This row doesn't apply to the cgen/cparam trainer currently in service since 2026-08-28**: it doesn't truncate any input, see the "ceiling" row below |
| Ceiling `--max-len` (unified across the three cells) | defaults to `8192`, not backed off (2026-08-28 smoke ruling); if an event's full-text token count exceeds it, the **whole event is dropped** (not truncated row by row), counted into `dropped_events_train`/`dropped_events_val` (ctool) or the `start` event's `dropped_events` (cgen/cparam); the three cells share the same ceiling so the training event set doesn't fork (spec §15). Basis: `ks828b06_gptoss_cgen_speed_b16k` (H100) had a training-step peak of 60.59 GB, 39% of the 93.10 GiB headroom; ctool smoke at the 8192 ceiling with `--bs 2` had an nvidia-smi maximum sample of 56,859 MiB (`pipeline/runs/smoke/ks828b06_*`, `ops/runs.jsonl`) | `pipeline/train/share_data.py`'s `load_events` (cgen/cparam, ticket 01), `train_causal_tool.py`'s `load_events` (ctool, ticket 02) | if the ceiling changes, the three cells' training event sets and drop ratios change together, and are not comparable to the `dropped` statistics from before this new convention; the three cells must be changed in sync, otherwise one cell sees a narrower event set than another. **The np821 batch used `max_length=4096`, row-by-row left truncation instead of whole-event dropping** |
| cgen target construction | the target-string construction is unchanged: tokenize the target first without truncating it (an instance with >160 tokens is dropped and counted into `dropped_rows_tgt`), the `labels` prefix segment is filled with `-100`. **The input-side left-truncation rule, since 2026-08-28, only still applies in the frozen old row-by-row script** (`train_causal_callgen.py`, launched via `train-cgen-rows`): it left-truncates the input at `max_length = 4096 - L_t`; **the cgen/cparam trainer currently in service does not left-truncate**, the event's full text goes through in a single forward pass, the target segment beyond the shared prefix is simply concatenated after it, and only when the whole event exceeds the `--max-len` from the "ceiling" row above is the whole event dropped (not truncated row by row) | `train_causal_callgen.py` (old convention, frozen, ENG §5.4); `pipeline/train/share_data.py`'s `load_events`/`pack_event` and `train_causal_share.py` (currently in service, tickets 01/03) | if the old script's order is reversed, left truncation would eat the target and the loss would be computed at the wrong position (this row still holds only for the frozen reference script); the current trainer doesn't truncate, so the risk becomes "setting `--max-len` too small drops long events whole and the sample count plummets" rather than "truncation damages the target". **The np821 batch used `max_length = 4096 - L_t` to left-truncate the input** |
| cgen loss | per-instance target-segment mean CE, batch loss `Σ(w_i·ce_i)/Σw_i`. **When the weights are all 1 (`uniform` data), it degenerates into a plain average**, the scale is unchanged, so learning rate / batch size / epochs / warmup don't need to change along with the weighting convention (np821's three cells were run directly with the same set of hyperparameters, measured) | `train_causal_callgen.py` (ENG §5.4), ctool / cparam use the same weighting | dropping the w weighting means dropping the chain "compute loss by the weighting convention," and diverging from the other three cells' convention |
| cgen/cparam best selection | the sole basis is val's full-volume masked-CE (lower is better); `val_exact_call` / `val_exact_params` only go into the log and don't select best. **In the trainer currently in service (`train_causal_share.py`, since 2026-08-28) this generative evaluation is behind a switch**: `--gen-eval` defaults to 200 rows (0 turns it off), `--gen-eval-at` defaults to `last` (generation only happens at the evaluation at the end of the epoch); the default set by decision 28 is exactly "same scale as the old convention, log only, doesn't select best" | ENG §5.4; cparam followed the same convention since 2026-08-21; the `--gen-eval`/`--gen-eval-at` defaults are in spec 16.3 (ticket 08) | selecting best with the exact metric would make val get used twice (choosing the point + reporting the number), breaking the val/test division of labor; changing `--gen-eval-at` from `last` to `all` just does a few more rounds of generation, doesn't enter the best criterion, and doesn't count as breaking the convention |
| cparam concatenation | input = `text + "\n[CALL] " + label + "("`, target = the remaining segment of `label_call` after stripping the `label+"("` prefix (including the closing parenthesis) + eos; the sole source of truth for the derivation is prefix-stripping applied to make_call's output, if it doesn't match the whole thing is dropped and counted into `assembly_mismatch` | `train_causal_param.py`'s `param_target` (2026-08-21) | changing the concatenation method = changing the task definition, invalidating the cgen-vs-cparam comparison of "the benefit of the tool name being given" |
| LoRA hyperparameters (when `--lora` is on) | rank 16 / alpha 32 / dropout 0.05 / lr 2e-4; target modules are Qwen3's seven-piece set (`q,k,v,o_proj` + `gate,up,down_proj`), `bias="none"`; **before saving `best/`, `merge_and_unload` first and fold back into the base**, so `best/` is item-for-item isomorphic with what full-parameter training saves, zero changes needed on the eval side | `pipeline/train/lora_util.py` is the **sole shared implementation** across the three causal cells (constants `DEFAULT_RANK/ALPHA/DROPOUT/LR` + `TARGET_MODULES`), no second copy of this isomorphic table may be kept anywhere else | changing rank/alpha/lr changes the training recipe, the LoRA batch and the full-parameter batch are no longer the same yardstick; saving the adapter directly without merging would make the eval scripts unable to load it back (they all use `from_pretrained(best/)`) |
| Smoke scale | mtool / mext (retired): **randomly drawn using each script's own `SEED` constant** (20260729), 500 training / 200 eval **instances** (mext's two numbers land on the expanded **parameter instances**, not samples); ctool: randomly drawn the same way (`SEED`=42), 200 / 80 **events** (it counts by event, not instance); **the cgen/cparam trainer currently in service (`train_causal_share.py`) switched to deterministic sampling since 2026-08-28**: `--smoke` defaults to 40 training events / 16 eval events, **taking the top N sorted ascending by the full event's token count** (train and val follow the same rule, not dependent on `SEED`, not a random draw); the old row-by-row scripts (via `train-cgen-rows`/`train-cparam-rows`) still use the old convention of randomly drawing 500/200 instances. Every cell/convention is 1 epoch | ENG §5.1, §5.4 (mtool/mext/ctool and the old row-by-row scripts, `random.Random(SEED).shuffle(...)` then slice the first N rows, **not truncation in original order**); `share_data.load_events(order="shortest")` (cgen/cparam, currently in service, tickets 01/03) | only affects smoke, but changing it loses the reference value of "same convention as the historical smoke"; changing the seed or switching to original-order truncation would both swap out the batch of samples drawn. **After cgen/cparam switched to deterministic ascending sampling, the old- and new-generation smoke numbers are not comparable**: rerunning the same `--smoke` gets exactly the same event set, but it is no longer a comparison under "the same convention as the historical smoke" |
| Default block-picking method for the VRAM probe (since 2026-08-28) | `--mem-probe-pick` defaults to `cost` (enumerate the physical blocks of the events sampled for this run, pick three blocks by largest token count / largest loss-position count / largest normalized sum, and take the larger peak); `tokens`/`loop` are both still there, switching between them is a tunable knob | `train_causal_share.py` (spec 16.5, ticket 10) | only affects which block the probe picks to measure the peak, doesn't enter the gradient; changing the default needs to be recorded in TIMELINE, so that later on "the probe picked a different block" doesn't get mistaken for the real VRAM having changed |
| Interpreter | mbert cells use `mbert-env` (transformers 4.57.6 pinned), causal cells use `cprobe-env` (>=5.14), neither is allowed to be upgraded to match the other | PLAY §0.13, ENG §2.1 | a mixed architecture on the old version will **silently compute wrong** (chunked incremental feeding), this is the reason the alignment check exists |
| Alignment check | must pass before a causal cell starts training, FAIL means `exit 2` | `train_causal_tool.py` (ENG §5.3) | skipping it = allowing a numerically wrong skeleton into training, everything that comes out of it counts for nothing |
| Default alignment criterion (since 2026-08-28) | `--align-rule` defaults to `abs` (absolute per-row/per-token difference, the status quo); the four coarse-screening thresholds for cgen/cparam (`--align-tok-tol`/`--align-bf16-mean-tol`/`--align-bf16-max-tol`/`--align-baseline-factor`) default to exactly the constants that were hard-coded in the first round (`3e-4`/`2e-2`/`1e-1`/`3.0`); `--align-rel-tol` defaults to `1e-5` (both ctool and cgen/cparam) | `train_causal_share.py`/`train_causal_tool.py` (spec 16.4, ticket 09) | switching `--align-rule` or adjusting a threshold is a tunable knob (the same criterion as the `--align-tol` row in invariants §6), changing it needs to be recorded in TIMELINE; not changing the defaults means "the same yardstick as the first round" |
| `--out` | required, no default value | ENG §5.1.3 | a default value would let two training runs silently overwrite the same directory |

## 4. Eval-side conventions

| Convention | Fixed value | Where it's hard-coded | What happens if changed |
|---|---|---|---|
| The three eval steps | fit the temperature on val → sweep theta on val → **freeze and test once on test** | `eval_tool.py` (PLAN §1.2, ENG §6.1.1) | going back and tuning theta on test = using the test set to choose the point, every coverage/accuracy number becomes inflated, invalidating it at the paper level |
| Default handling of overlong events on the eval side (since 2026-08-28) | `--overlong` defaults to `left` across the three eval scripts (prompt/full-text overlong still gets left-truncated as before, byte-identical to the behavior before this switch existed); `skip`/`drop-event` change the accounting convention and must be passed explicitly | `eval_causal_call.py`/`eval_causal_param.py`/`eval_tool.py` (spec 16.2, ticket 07) | switching to a non-default value changes the row/event set that goes into the denominator, the matrix only accepts eval results from `left` (spec 16.10 #35), numbers from the other modes only go into their own reports |
| theta grid | 0.5 → 0.975 in steps of 0.025, 20 tiers total | `THETAS` (ENG §2.2) | if the grid changes, the meaning of a judgment like "both tiers have no solution" changes with it (this round, `c1_q35_mtool` was exactly judged as having no solution) |
| Risk target | `RISK_TARGETS = [0.10, 0.05]`, the matrix summary table reports the 0.05 tier | ENG §2.2, §6.4 | loosening the risk target = changing the contract, equivalent to issuing a pass to a cell that doesn't qualify (see the ruling in gates.md §3.4) |
| bootstrap | `BOOT = 1000`, the order in which random numbers are drawn also counts as part of the convention | ENG §2.2 | the confidence interval can no longer line up digit-for-digit with the old report; this round's ACCEPT_EVAL specifically confirmed this point (`ACCEPT_EVAL.md` §2) |
| Source of the trigger point | mext uses mtool's REPLAY_REPORT (temperature + `chosen_theta`), both cgen and cparam use ctool's | ENG §6.2, §6.3.1 | borrowing another cell's trigger point = the parameter cell is no longer evaluating its own line (this practice was rejected by the ruling in gates.md §3.4) |
| Where cparam's matrix numbers come from | `summarize_matrix`'s four cparam columns always read the **pred_tool block** of `PARAM_REPORT.json` (the tool name is fed ctool's argmax, i.e. the real convention of system B, ctool+cparam); the gt_tool block (fed the ground-truth tool name, pure parameter-filling ability) only goes into the report | `pipeline/eval/summarize_matrix.py` (2026-08-21) | mixing up the blocks would mistake "pure parameter-filling ability" for the system number; the gap between the two conventions is exactly the loss leaking through from ctool picking the wrong tool, mix them up and it can't be measured |
| Three parameter tiers | loose (equal after normalization) / strict (equal as raw strings) / whole call; a key mismatch means that parameter is wrong; parameter-free events get their own column | ENG §6.3.5, PLAN §1.4 | if the scoring strictness changes, cross-line comparison is invalidated |
| Report field names | always keep the old names: `theta_sweep_calB`, `stoptime_calibration_test`, `depth_bucket_acc_test`, `prior_baseline_event_acc`, `speculation_economics`, `temperature` | ENG §3.6, §2.5, `ACCEPT_EVAL.md` §4.7 | downstream scripts read by name; `probe_server.py` loads the probe via the `temperature` key, renaming it breaks the chain |
| Prior baseline | each dataset reports the test split's frequency prior, which changes with version and model; under `--readonly-env` it's **taken as the highest frequency on the folded vocabulary** (de1c781) | `ANNOTATE_REPORT.md` / `router_stats.md` (ENG §4.2.7, DATA.md §3.1); the folded version is in `eval_tool.py`'s `readonly_stats` | picking the wrong baseline would overestimate the probe's score for gptoss (prior 0.404), whose threshold is more than double q35's 0.174; taking it before folding would misprint the prior as 0.0 for an environment (bfcl) whose highest-frequency tool is non-read-only, manufacturing a fake advantage for the probe |
| readonly trigger condition (when `--readonly-env` is on) | trigger = conf >= theta **and argmax != the abstention sentinel**; the parameter metric only counts triggered events whose ground truth is read-only | the three evals' `replay`/`replay_fire` (since the ro1 batch) | without the sentinel gate, the abstention class becomes meaningless, and non-read-only events would get speculatively executed, exactly the accident this scheme is meant to block |
| self-fire point selection | theta_fire is swept on val and frozen once on test (the same discipline as theta); the constraint is **`fire_acc >= 1-risk`** (fire accuracy), not the `wrong_fire_rate` in the sweep table that's normalized over all events | the two call scripts' `pick_theta` (the same mechanism eval_tool uses to select theta) | switching to a wrong_fire_rate constraint amounts to changing the contract, invalidating ro1's judgment that "only 2 of 14 cells have a working point" |

|---|---|---|---|
| run_id consistent across four places | raw-data directory name = tmux session prefix = ledger name = commit message | `CLAUDE.md`, PLAY §0.10 | if something goes wrong, you can't trace back which run it was or which version of the code was used |
| Training run_id template | `<batch>_<model_short>_<cell>`, cell in `{mtool, mext, ctool, cgen, cparam}`; the template has **neither a base-tier segment nor a training-method segment** → **one batch runs only one `--base` tier, only one training method** (full-parameter or LoRA, extending §3.4). The tier and the training method are written into the batch prefix (np821's four batches `b06 / b17 / l17 / l4` = 0.6B full-parameter / 1.7B full-parameter / 1.7B LoRA / 4B LoRA) | ENG §2.4 | the summary script recognizes cells by directory name, if the naming gets messy the matrix table can't be assembled; mixing tiers or training methods collides on the same rid, and the two runs' artifacts can't be told apart |
| Model naming | qwen3.5 and qwen3.6 are **always two different models**, never written as "the qwen side" in any context | PLAY §0.6 | merging them would hide the difference between the two model generations, this is a line the user has explicitly drawn |
| Dual bookkeeping | **the dual write is guaranteed by launch; for a hand-rolled launch that bypasses launch, the responsibility for dual registration falls back to the human**: once `python3 run.py launch`/`launch-probe`/`launch-eval` launches successfully it automatically completes `record.py start` + `gpu-jobs register`; wrap-up still requires manually running `python3 run.py record finish` + `python3 run.py gpu-jobs finish` | `CLAUDE.md`, `ops/launch_common.py`, PLAY §0.10 | missing a registration means holding a card without retiring it; numbers that don't make it into `runs.jsonl` don't make it into `RESULTS.md` |
| Append only, never edit | `ops/runs.jsonl` is append-only; `RESULTS.md` is a rendered artifact and must not be hand-edited | `CLAUDE.md`, ENG §0.5 | a hand-edit to a rendered artifact gets overwritten the next time it's rendered, and the record no longer matches reality |
| Commit before launching | the working tree must be clean | PLAY §0.11 | the HEAD stored in the record can't be traced back to the real code, the experiment leaves no trace at all |
| New artifacts, new directory | not one byte of the old data or old numbers gets touched, everything new always goes into a new directory + a new version number | PLAY §0.7 | overwriting an old artifact = permanently losing the reproduction baseline |

## 6. Knobs that are allowed to be tuned

There is only one criterion: **does this knob affect VRAM and wall-clock time, or does it affect the gradient and the numbers?** The former can be tuned freely, the latter goes into sections 2-5.

| Knob | Tunable range | Why it doesn't affect the numbers |
|---|---|---|
| `--grad-ckpt` (gradient checkpointing) | switch on/off anytime | mathematically neutral: it just discards the intermediate activations and recomputes them on the backward pass, the gradient and parameter update are bit-for-bit identical, what changes is VRAM and speed. This round's `c1_gptoss_cgen` OOM was resolved with this rather than lowering bs (gates.md §3.2); the 8 OOMs (ctool 4 + mext 4) that the ro1 batch's fire-head double forward pass caused on the q36/gptoss long-sequence tiers were likewise resolved with just this (gates.md §3.8); this flag was added to mext specifically for that occasion (fbe4d15) |
| Card placement and machine assignment (which machine, which card, A6000/H200) | free | doesn't enter the gradient. **The only constraint**: comparing time costs requires both arms to run on the same model of card, otherwise the time-cost column is invalidated (`DATA.md` §7.4). `c1_gptoss_cgen` was moved to H200 and rerun, the accuracy convention was unaffected, only the wall-clock changed from an ETA of 26.7h to 5h13m (TIMELINE 2026-07-31 c1 entry, tradeoff two) |
| Collection concurrency, shard count, streams per instance | free | doesn't enter the gradient. Each task is solved independently, `--resume` is idempotent, sharding only decides who runs which tasks, and neither the trajectory content nor the task assignment changes. This round the model with more tasks deliberately had its concurrency opened one notch higher to even out the wall-clock (PLAY §3.4) |
| Service port, session name suffix, instance count | free | doesn't enter the gradient. The service just serves up the same set of weights; if one instance dies, point the shard at another instance of the same model, the result is the same (PLAY §3.7) |
| `--align-tol` | **can be loosened, but must be recorded in TIMELINE with the reasoning and the measured differences written down** | it's a gate threshold, not a training hyperparameter, it doesn't enter the gradient. But loosening it = lowering the bar for judging "implementation correctness", so a chain of evidence must be kept. This round, following the T8 precedent, it was loosened to `3e-4`, based on the three ctool runs' hidden maxdiff of 8.39e-5 ~ 1.68e-4 and relative difference of 2.3e-6 ~ 3.3e-6, judged as fp32 numerical noise (TIMELINE 2026-07-31 c1 entry, tradeoff one) |
| eval's `--report-dir` / `--device` / `--cached-logits` | free | only changes "where the report is written, where it's computed, whether to reuse already-stored logits", the post-processing math is unchanged. This round, ACCEPT_EVAL produced output **byte-for-byte identical** to the old report under `--device cpu` + `--cached-logits`, which proves it (`ACCEPT_EVAL.md` §1, §4.1, §4.2). Note that `--cached-logits` only skips the model, not the tokenizer, `probe_cost_test` needs it to count tokens (`ACCEPT_EVAL.md` §4.4). Since 2026-08-02 it has an additional **weight-fingerprint check**: the `logits_<sp>.meta.json` next to the cached `logits_<sp>.pt` records the fingerprint of the `best/` weights that produced it (**file size + a sha1 of the first and last 64KB, no mtime**, so a normal copy/restore doesn't invalidate the cache) and the row count; missing or mismatched fingerprint means SystemExit (see `stage-commands.md §4.4` for details). **Old logits produced before the fingerprint mechanism always lack `.meta.json`**: either backfill them first with the same command plus `--adopt-logits-fingerprint` (this is only allowed when every weight file under `best/` has an mtime no newer than the logits, it exits right after claiming them, without evaluating), or drop `--cached-logits` and recompute once (recomputing automatically writes the fingerprint). This doesn't change the convention, it just blocks "passing off old logits as the result of retrained weights" |
| run_id's batch prefix (`c1_` → `c2_` …) | free, and **should** change when the data changes | pure naming, but it must change in all four places together (section 5) |
| Log/report title text | free, **except when doing byte-for-byte acceptance** | acceptance requires the md to also be byte-for-byte identical, so on the acceptance path the title has to stick with the old wording (`ACCEPT_EVAL.md` §4.6) |

**Three temptations that are explicitly not knobs**: (1) lowering the batch size to solve OOM: the effective batch size changes, and it's no longer the same recipe across models (gates.md §3.2); (2) loosening the risk target or borrowing another cell's trigger point to rescue a cell with "no solution": both directly break the convention (gates.md §3.4); (3) using `--lora` or switching `--base` tiers to solve OOM: both of these enter the gradient, what changes is the object being compared itself, this belongs to "opening a new batch" rather than "tuning a knob" (section 5, the run_id template row). There are only two compliant ways to handle insufficient VRAM: `--grad-ckpt`, or a bigger card.

## 7. What **must** be changed together when changing environments / changing datasets

These are the things that should change; listed clearly so nothing gets missed (cross-reference ENG §2.3's config schema):

1. **The `env` name**: the config's `"env"` field; it decides which event-extraction branch `build.py` takes and whether call parsing uses `AW_CALL` or `BFCL_CALL` (ENG §4.1, §6.3.4). A new environment needs a new extraction branch and a new call regex written for it.
2. **Task-list files**: `official_split_files`'s three paths. **An environment without an official multi-partition scheme has to split its own three splits once** (bfcl is this kind, PLAN §1.6); splitting it yourself requires fixing the seed and writing the splitting method into `DATA.md`.
3. **Trajectory source**: the `traj_runs` list, list every collection directory this dataset needs to consume; this round the three models share the same set of directories, split apart by filtering on `model_full` (ENG §4.2 change ①, DATA.md §3.1).
4. **Model fields**: `model_short` / `model_full`, and `model_short` must match a key in `MODEL_OF` and the tail of the collect outdir (ENG §2.2, §4.2.1).
5. **`data_out` version number**: a new dataset always gets a new version directory (this round it's `aw_official_v1`). At the same time add a version entry in `DATA.md` §3, and add the scale and prior baseline in §4 (PLAY §5.1).
6. **run_id batch prefix**: a new round of training gets a new prefix, changed in all four places together (section 5).
7. **`tool_vocab.json` and the prior baseline**: automatically recomputed with the data, but **when reporting numbers you must cite this version's baseline**, you can't keep using the previous version's number (`DATA.md` §7.2).
8. **The comparison baseline for the two acceptance lines**: after changing environments, ACCEPT_V3DIFF must point at that environment's own old data; for a brand-new environment with no old data, this gate degenerates into "comparing the new and old code against the same input", and this must be stated explicitly in the acceptance file (this round both bfcl and appworld sides have old baselines, `ACCEPT_V3DIFF.md`).
9. **`TIMELINE.md`**: changing the venue or changing the main-line convention both require an added entry (this round's entry was "appworld's official partition becomes the standard venue", TIMELINE 2026-07-31).
