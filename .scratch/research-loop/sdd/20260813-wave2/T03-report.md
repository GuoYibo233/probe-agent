### 分发器 `research-loop/scripts/ledger.py`

- argparse 注册 plan.md §C2 的全部顶层子命令名（16 个动词组合出的完整清单：
  `gen-schemas`/`config-check`/`init`/`blocked`/`grant`/`decision`/
  `decision-withdraw`/`story`/`feedback`/`runs-append`/`launch-order`/
  `approve-spec`/`query`/`status`/`principles-lint`/`render`/`freeze-legacy`），
  含还没实现的。子命令名 → `ledger_cmds` 模块名的映射按 plan.md 目录树抄成
  `_SUBCOMMAND_MODULES` 字典（一个模块可以拥有多个子命令名，例如
  `grant`/`decision`/`decision-withdraw` 都归 `decisionscmd`——该模块的一次
  `register()` 调用负责把这几个子解析器都加上）。
- 模块协议：分发器按模块名分组后逐模块 `try: importlib.import_module(...)`；
  成功且同时有 `register`/`run` 两个属性才算"模块就绪"，调它的
  `register(subparsers)` 一次加完这一组的全部子命令；否则（`ImportError`，
  或模块存在但缺 `register`/`run`）给这一组里的每个子命令名各挂一个占位
  parser——`add_parser(name, add_help=False)` + 一个 `nargs=REMAINDER` 的
  positional，保证任何参数组合都能被 argparse 接住，不会在到达"未实现"分支
  之前就被 argparse 自己拒掉。
- 工程门禁：`args.command` 不在 `{gen-schemas, init, config-check}`
  时，解析完子命令名之后、真正 dispatch 之前跑
  `_lib.find_project_root()`；`None` → stderr
  `project not wired: research-loop.json not found (run: ledger.py init)`，
  `return 2`。
- `RLError` 在 `main()` 里用一个 `try/except` 包住"建 parser → 解析参数 →
  门禁检查 → dispatch"整段（不只包 dispatch 那一步），命中打
  `exc.message` 到 stderr、`return 2`；别的异常不接，原样往外抛。
- `render principles|blocked` 单独处理：这一个 CLI 子命令的两个 target
  分属两个不同模块（plan.md 目录树：`principlescmd.py` 拥有
  "render principles"、`querycmd.py` 拥有 "render blocked"），没法用
  "一个子命令一个模块"的通用注册路径。`ledger.py` 自己注册 `render`
  parser（固定只有一个 `target` positional，`choices=["principles",
  "blocked"]`——CLI 面上没有别的参数），在 `_dispatch()` 里按
  `args.target` 查 `_RENDER_TARGET_MODULES` 再走同一套
  懒导入/占位/exit-3 逻辑，未就绪时打
  `not implemented yet: render <target>`。这是工单与 plan.md 都没有明说
  的一处设计缺口（"render"到底是不是严格的一子命令一模块），详见下文
  "自查发现"第 1 条。

## 四、自查发现与存疑

1. **`render principles|blocked` 的模块归属不是工单/plan.md §C2 明写
   的，是我按 plan.md 目录树的注释（`principlescmd.py` 注释
   "render principles"、`querycmd.py` 注释 "render blocked"）推出来的
   设计决定，记在这里留痕：**

   plan.md §C2 把 `render principles|blocked` 写成一行 CLI（一个子命令、
   一个必填的 target 位置参数），但目录树把两个 target 的渲染逻辑分给了
   两个不同的模块（T07 的 `principlescmd.py`、T09 的 `querycmd.py`）。
   工单"模块协议"原文是"每个子命令 lazy import 一个模块"，字面上没法
   覆盖"同一个子命令按参数值分流到两个不同模块"这种情况。我的处理：
   `render` 的 parser 由 `ledger.py` 自己注册（不委托给任何模块——它的
   参数面固定只有 target 一个位置参数，没有子模块需要额外加参数），
   `_dispatch()` 里按 `args.target` 查一张
   `{"principles": "principlescmd", "blocked": "querycmd"}` 的映射表，
   再走跟其它子命令一样的"懒导入 → 缺失就 exit 3"逻辑。这个决定不影响
   T03 自己的任何一条验收测试（7 条测试都没碰 `render`），但会约束
   T07/T09 落地时各自的 `principlescmd.py`/`querycmd.py` 该怎么跟
   `ledger.py` 对接——它们不需要自己注册 `render` 的 parser，只需要在
   各自的 `run(args)` 里认得 `args.command == "render"` 这个分支
   （区别于各自本职的 `principles-lint`/`query`）。如果 T07/T09 的
   实现者认为这个映射不对，需要回来改 `ledger.py` 的
   `_RENDER_TARGET_MODULES` 字典。

2. **"not implemented yet: `<subcommand>`" 里 `<subcommand>` 的取值
   规则是我定的，工单没给例子之外的规则**：对分组类命令（`blocked`/
   `grant`/`story`/`feedback` 等）取的是顶层子命令名本身（例如
   `blocked open` 没模块时打的是 `not implemented yet: blocked`，不是
   `not implemented yet: blocked open`）；对 `render` 例外地带上
   target（`not implemented yet: render principles`），因为 target
   才是决定"该由哪个模块实现"的那个信息。工单给的唯一例子是单词子命令
   `status`（`not implemented yet: status`），两种设计在这条测试上
   结果一样，分不出工单到底要哪种；等 T05/T06/T07/T09 的测试真的需要
   断言这条 stderr 文案时，如果发现跟这里的选择不一致，需要回来改
   `ledger.py` 的 `_dispatch()`。

3. **`--check` 不一致时的 stderr 格式我自己定的**：
   `gen-schemas --check: out of date with tables/: <file1>, <file2>`。
   工单原文只说"不一致列文件名"，没给固定格式；测试只断言
   `"story.schema.json" in err`，没有锁死整行文案，所以这条格式将来

4. `tests/helpers.py`（T02 产出）里 `make_sandbox()` 已经预留了

### F1 —— `--check` 测试污染真实仓库文件，断言失败时不回滚

**问题**：`test_check_flag_catches_mismatch_without_writing_then_clean_again`
里 `_SCHEMAS_DIR = _lib.plugin_root() / "schemas"` 解析到的是仓库里真实
的、随代码一起 commit 的 `research-loop/schemas/`，不是沙盒。测试流程是
"读原始字节 → 写入被污染字节 → 断言 `--check` 拦截且不写盘 → 写回原始字
节"，但写回和三条断言之间原来没有 `try/finally`：一旦 `--check` 真的有
bug（这三条断言里任何一条失败），异常会在写回原始字节之前抛出，
`run_all.py` 的 runner 捕获异常继续跑下一个测试，但仓库里的
`story.schema.json` 就永久留在被污染状态，直到有人手动重跑一次干净的
`gen-schemas`。

**修复**：把"写入被污染字节 → 三条断言"包进 `try`，写回原始字节挪进
`finally`，保证不论断言是否失败，磁盘上的字节都会被复原。改动只在
`research-loop/tests/test_genschemas.py`，未动生成逻辑本身。

### F2 —— 分发器每次调用都导入全部子命令模块，无故障隔离

**问题**：`ledger.py` 的 `build_parser()` 原实现对 `_SUBCOMMAND_MODULES`
里全部 16 个子命令名对应的模块组，不论这次调用实际请求的是哪个子命令，
逐一 `_import_cmd_module()` 尝试导入。`_import_cmd_module()` 只捕获
`ImportError`；如果某个已落地模块在 import 期抛别的异常（语法错误、顶层
`NameError` 等），这个异常会穿透 `build_parser()` 一路抛到 `main()` 的
`try` 块外（`main()` 只捕获 `RLError`），导致整个 `ledger.py` 崩溃——哪怕
用户此次只想跑一个跟出问题模块完全无关的子命令（比如 `gen-schemas`）。
工单原文"每个子命令 lazy import"的本意是"只在该子命令被调用时才导入它自
己的模块"，原实现是"不管调用哪个子命令，每次都尝试导入全部模块"，子命令
之间没有故障隔离。

**修复**：新增两个纯函数——`_peek_positional(argv)`（在真正的 parser 建
出来之前，从原始 argv 里摘出第一个不以 `-` 开头的 token，仅用来猜这次调
用需要哪个模块，不参与真正的参数校验/报错）和
`_module_name_for_argv(argv)`（对 `render` 特判：再摘一次紧跟在 `render`
后面的 target token，查 `_RENDER_TARGET_MODULES`；其余子命令直接查
`_SUBCOMMAND_MODULES`；猜不出就返回 `None`）。`build_parser(argv)` 签名
新增 `argv` 参数，只对猜出来的那一个模块名调用一次
`_import_cmd_module()`，其余全部子命令组一律走占位 parser（不尝试导
入）。`main()` 相应地显式算出 `argv`（`argv is None` 时取
`sys.argv[1:]`）并转手给 `build_parser(argv)` 和 `parser.parse_args(argv)`
用同一份 argv。`render` 的模块解析本来就在 `_dispatch()` 里按
`args.target` 懒加载（未改动），不受这次修复影响。

猜测只用来决定"要不要导入"，不参与真正的合法性判断——猜错了（罕见：顶层
只有子命令一个位置参数，没有别的全局 flag，正常情况下猜不错）该子命令组
退化成占位 parser，走到 `_dispatch()` 时 `dispatch.get(args.command)` 为
`None`，报 "not implemented yet"，这跟"模块确实还没落地"是同一条路径，
不会误报成功；而且这个场景只会在用户传入的 argv 本身就诡异到连 argparse
自己都可能拒绝的地步才会出现，真实场景里不会发生。

**自查**：这处改动比 F1 大，逐字过了一遍是否超出 finding 范围——没有碰
`_dispatch()`、`_UNWIRED_EXEMPT`、`_RENDER_TARGET_MODULES` 的既有语义，
`_import_cmd_module()` 本身（只捕获 `ImportError` 这条规则）也没有改，
只是改了"什么时候调用它"，跟 finding 描述的病灶（"每次调用导入全部模
块"）对得上，没有顺手重构别的东西。

### N1 —— 顶层 `ledger.py --help`/`-h`（不带子命令）丢失所有已实现子命令的帮助文案

**问题**：F2 把 `build_parser(argv)` 改成"只对 argv 猜出来的那一个子命令对
应的模块调用 `_import_cmd_module()`，其余全部子命令组一律走占位 parser（不
尝试导入）"。但 `_peek_positional(argv)` 对不带任何位置参数的 argv（典型场
景：`ledger.py --help` 或裸 `ledger.py -h`，`_peek_positional` 跳过所有以
`-` 开头的 token，`-h`/`--help` 本身也被跳过，循环耗尽后返回 `None`）永远
返回 `None`；`_module_name_for_argv(argv)` 因此也返回 `None`，`build_parser`
里没有任何 `module_name` 能匹配 `wanted_module_name`，于是全部 16 个子命令
——包括已经实现、有真实 `register()` 的 `gen-schemas`——都退化成
`_add_placeholder` 占位 parser（`add_parser(name, add_help=False)`，不传
`help=`）。顶层 `--help` 里这些子命令名旁边就是空的。复现对比：`git stash`
把 `ledger.py` 退回本轮修复前的 `34c615b`，跑 `python3 scripts/ledger.py
--help`，输出的 positional arguments 列表里只有 `render` 一行带描述
（`Render a maintenance view (principles|blocked).`），`gen-schemas` 只剩
命令名；子命令自己的帮助（如 `ledger.py gen-schemas -h`，argv 里带了具体子
命令名）不受影响。

**修复**：`build_parser(argv)` 新增一个分支——`import_all = _peek_positional
(argv) is None`。`import_all` 为真时（argv 里压根找不到任何位置参数：裸
`--help`/`-h`/空 argv，"想看有哪些命令"的探索路径，没有单一模块可猜），对
`_SUBCOMMAND_MODULES` 里全部模块组逐一调用 `_import_cmd_module()`（真正导
入、注册真实 parser），不再走"猜一个模块，其余全占位"的逻辑；`import_all`
为假时（argv 里能找到具体子命令），行为跟 F2 修复后完全一致——只导入猜出
来的那一个模块，其余占位，不动 `_module_name_for_argv`/`_peek_positional`
本身。改动只在 `build_parser()` 函数体的模块选择那几行 + 顶部/函数 docstring
更新为文字说明这条例外，其余代码（`_dispatch()`、`_UNWIRED_EXEMPT`、
`_RENDER_TARGET_MODULES`、`_import_cmd_module()` 的 `try/except ImportError`
契约）一律未动。

**自查**：这条修复是否会重新引入 F2 要解决的"无关模块崩溃"问题——会，但
只在"没点名任何子命令"这一条路径上（即 `--help`/`-h`/空 argv）：如果某个
模块在 import 期真的抛异常，运行 `--help` 会跟这次修复前的老代码（`dc6caae`）
一样崩溃、带完整 traceback。这是刻意保留的行为，不是回归：F2 finding 描述
的场景是"用户只想跑一个跟坏模块无关的具体子命令"（如 `gen-schemas`），这
条路径完全不受影响（下面手工验证过）；而"探索有哪些命令"这个路径本来就需
要知道全部模块的信息才能给出正确帮助，跟 F2 finding 描述的问题不是同一个
场景，finding N1 本身的复现步骤也只涉及 `--help`/`-h`，没有要求"`--help`
也要对坏模块免疫"。
