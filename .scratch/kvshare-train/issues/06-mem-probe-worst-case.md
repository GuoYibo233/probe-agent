# 06 Make `--mem-probe` reflect the real worst case (optimizer state already built, the fullest block doing two backward passes)

Status: resolved
Blocked by: 05
Spec: `.scratch/kvshare-train/spec.md` section 10's "worst-case block" clause (this ticket updates its wording to match); changes only in `pipeline/train/train_causal_share.py`, `pipeline/train/train_causal_tool.py` (adding a log field only), `tests/test_share_trainer.py`, `tests/test_ctool_readpos.py`, and that one clause in spec section 10.

## Background (measured)

ks828b06 speed tier (H100, `--tok-budget 16384`): the `mem_probe`'s fullest block (B=2, L_pad 8192, including a zero-lr `opt.step`) reports 51.11 GB, while the training run's `step` event peaks at 60.59 GB; at `--tok-budget 24576`, the probe reads 75.05 against training's 80.91. The mechanism behind the gap (8-28-assistant-2's read): the probe's peak is the larger of two moments -- "during backward: weights + activations + the gradient being produced" and "right after step: weights + gradient + optimizer state" -- while the real training peak occurs during the second logical mini-batch's backward pass in a group, when the optimizer state (4.8 GB for 0.6B full-parameter) and the gradient left over from the first mini-batch (2.4 GB) are both still resident; with `accum=2`, two fullest blocks landing in the same group is a real worst case that occurs.

## What to do

1. Change `run_mem_probe` (around `train_causal_share.py` lines 220-245): first `opt.zero_grad(set_to_none=False)` and do one `opt.step()` with lr set to 0 to build the optimizer state (`torch.cuda.reset_peak_memory_stats()` comes after this); then run "forward + backward" twice on the fullest block, without `zero_grad` in between (gradient accumulation); read `max_memory_allocated` after the second backward as `fullest_block`'s `peak_mem_gb`; do the same for the longest-event block -- one forward-plus-backward under the same "state already built, gradient not yet cleared" condition -- and read its peak; finally `opt.state.clear()`, restore lr, and `opt.zero_grad(set_to_none=True)`. Add `n_backward` (1 or 2) and `optimizer_state_prebuilt: true` to the `mem_probe` event's fields.
2. Change spec section 10's "worst-case block" clause to describe the above (change only that one clause).
3. Add `peak_mem_gb` to `pipeline/train/train_causal_tool.py`'s `step` and `eval` events (on cuda, `torch.cuda.max_memory_allocated() / 1e9`, resetting via `reset_peak_memory_stats()` right after; 0.0 on CPU), matching the new trainer's convention. Reason: this round, ctool's memory can only be read via external nvidia-smi sampling, because it doesn't record it itself. Add an assertion in `tests/test_ctool_readpos.py` that the `step` event contains this key (if there's no existing case that reaches a step on CPU, just test the function that writes the log).
4. Add a small-model CPU case to `tests/test_share_trainer.py`: after calling `run_mem_probe`, `opt.state` is empty, each param_group's lr has been restored to its original value, every parameter's `.grad` is None, and the two `mem_probe` events' fields are complete (recorded/returned) (`peak_mem_gb` may be 0 on CPU).
