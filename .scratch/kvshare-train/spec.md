## 1 Goal and scope

This round delivers a new training program, `pipeline/train/train_causal_share.py`, serving the cgen and cparam cells (`--mode cgen|cparam`), doing four things: an event's full text goes through the base model only once, with each cut point's target segment appended after the shared prefix to compute loss; no sample is truncated, and an event whose full text exceeds the limit is dropped whole and counted; the limit defaults to 8192 (may retreat to 6144 after smoke testing); epochs default to 1. At the same time, ctool (`train_causal_tool.py` and `eval_tool.py`) takes on three changes: the drop rule, the limit's default value, and the cut-point read-position rule, and changes its update unit to 8 events.

Cell names are unchanged (still cgen / cparam / ctool), the data is unchanged, the four eval scripts' scoring logic doesn't change by one line, input construction is unchanged in round one and in round two only gains a `--overlong` switch per 16.2 (unchanged field-for-field when it's the default, `left`); `eval_tool.py` only swaps out the read-position section per section 11.3. Per the criteria at `extending.md` lines 113-121, this round is "swapping in a new implementation," not "adding a new cell," so it doesn't go through section 3.1's new-cell checklist (decision 3).

Out of scope: how the eval side handles overlong events, the learning-rate sweep, `--fire-head` (decision 4), and the six experiments in section 14. The old row-by-row trainers `train_causal_callgen.py` and `train_causal_param.py` are changed by not one line, frozen as the alignment reference (decision 3).

What success looks like: section 9's alignment check passes (fp32 per-row loss max absolute difference <= 2e-5, based on `design-attention.md`'s CPU measurement of 2.15e-6 and H100 measurement of 4.41e-6); on H100, the new trainer's rows per second, at matching cumulative-row-count ratios, is higher than the old trainer's, with each pair of comparisons matched (decision 9, all numbers from `pipeline/runs/np821b06_gptoss_cgen/train_log.jsonl` ep 0, tokyo108 H100, re-checked by 8-28-assistant-1 on 2026-08-28): the cumulative value `ips` (this epoch's cumulative rows divided by training seconds) at rows 1,600 / 9,600 / 19,200 is 2.76 / 3.26 / 3.97; the windowed value `ips_win` over the three windows rows 0-1,600 / 8,000-9,600 / 17,600-19,200 is 2.77 / 3.94 / 6.24 (the three numbers in `plans/2026-08-28-plan.md` section 12.10 are windowed values; section 9.2's A_h100 value of 2.75 is the cumulative value at row 1,600). All six numbers must be higher; the memory peak, measured per section 10's worst-case block, must leave 10%+ headroom.

## 2 Names (used exclusively throughout)

- Event: a group of rows in train.jsonl sharing the same `event` field. An event's full text = the `text` of the row with the largest `sent_idx` in that group.
- Row: one jsonl record, also one training instance. A row's text = that row's `text`, a prefix of the event's full text.
- Cut point: the character length of the row text, `len(text)`.
- Prefix tokens: the token sequence `full_ids` obtained by tokenizing the event's full text.
- Old sequence: the prompt token sequence `old_ids` the old trainer builds for a row (section 3.4).
- Target-string tokens: `tgt_ids` (section 3.3).
- Common prefix length p: the token count of the longest common prefix between `old_ids` and `full_ids`.
- Target segment: `old_ids[p:] + tgt_ids`.
- Packed sequence: for one event, "the prefix tokens (cut at the max p) plus every target segment concatenated in row order."
- Logical mini-batch: all the rows of 4 events, the normalization unit for loss.
- Physical block: the events one forward pass covers, sliced from a logical mini-batch by token budget.
- Update: one `opt.step()`; one update = `--accum` logical mini-batches, default 2, i.e. 8 events.
- Limit `--max-len`: the upper bound on an event's full-text token count; exceeding it drops the event whole.
- Token budget `--tok-budget`: the upper bound allowed for one physical block's "event count x the block's longest packed-sequence length."

## 3 Data and tokenization

### 3.1 Input

`<data>/train.jsonl` and `<data>/val.jsonl`, with the same fields as the old trainer: `event`, `sent_idx`, `n_sents`, `text`, `label`, `label_call`, `w`. The live data, `pipeline/data/nyapass_aw_v1/gptoss/`: train has 186,479 rows across 4,127 events, val has 115,211 rows across 2,556 events, `w` is 1.0 throughout (counted 2026-08-28).

### 3.2 Event grouping and the prefix property

Group by `event` (event order = order of first appearance in the file, not reordered by event name), ascending `sent_idx` within a group, taking the event's full text as the `text` of the row with the largest `sent_idx` (taken before `--readonly-env` filtering, since filtering only drops rows, never changes the full text). The prefix-property check follows `train_causal_tool.py` lines 112-115: `random.Random(SEED)` samples 50 events and asserts every row's `text` is a prefix of the full text. SEED = 42.

The order of steps inside `load_events` is fixed (the random-number generator's consumption order determines the sampling result): group -> prefix-property spot-check (`random.Random(SEED)`, over every event before any dropping) -> tokenize each event's full text to get `n_full`, dropping over-limit events per 3.5 -> take a subset by `limit` and `order` (`order="random"` shuffles with a freshly built `random.Random(SEED)`; `order="shortest"` sorts ascending by `n_full`) -> tokenize only the surviving events row by row (3.3, 3.4) and apply row-level dropping. Row-by-row tokenization is new overhead (186,479 rows for train), placed after taking the subset so that `--smoke` / `--max-events` can skip most of it; `--mem-probe` needs the full set's packed lengths, the one exception where the full set is tokenized row by row.

### 3.3 Which rows to keep and the target string (copied from the old trainer as-is; do not write a second version)

- cgen: target string = `tok(label_call, add_special_tokens=False) + [eos]` (`train_causal_callgen.py` lines 162-163); a row with `len(tgt_ids) > MAX_TGT_TOK` (160) is dropped and counted as `dropped_rows_tgt` (lines 164-166). With `--readonly-env` on, a non-readonly row is dropped whole, counted per `readonly_map`'s convention (lines 133-142).
- cparam: prompt tail = `param_prompt_tail(label)` = `CALL_SEP + label + "("`; target string = `param_target(label, label_call) + [eos]`, and a row where `param_target` returns None is dropped and counted as `assembly_mismatch` (`train_causal_param.py` lines 89-106, 129-136).
- Every row is an instance; there is no other filtering.
- Both of the old scripts' hard stops are carried over as-is: cparam's stripping-failure rate (the fraction of rows where `param_target` returns None) exiting if it exceeds 5% on train or val (that gate in `train_causal_param.py`; the implementer should grep to the original text via `assembly_mismatch` and copy the threshold and wording exactly); and exiting if train or val loads 0 rows.
- Implementation approach: `share_data.py` directly `import`s the two old scripts' constants and functions (`CALL_SEP`, `MAX_TGT_TOK`, `param_prompt_tail`, `param_target`, `MODELS`, `SEED`); copy-pasting a second copy is not allowed. These two import statements must be written inside `load_events`'s function body (a lazy import); `share_data.py`'s module top level may only import stdlib and torch. Besides the `__main__` guard, the three old scripts also have a `transformers >= 5.14` version gate at module level (`train_causal_callgen.py` lines 55-60, `train_causal_param.py` lines 53-58, `train_causal_tool.py` lines 50-55, `raise SystemExit` if not satisfied); mbert-env is pinned to transformers 4.57.6 (`invariants.md` line 53), and `eval_tool.py` is a script shared by both the mbert and causal lines (`run.py`'s `eval-tool-mbert` uses `py="mbert"`) -- a top-level chained import would make `eval-tool-mbert` and `eval-mcall` exit during import (`tests/test_cparam_assembly.py` lines 8-12 recorded this same phenomenon). `read_position` doesn't touch any training script.

### 3.4 The common-prefix rule (draft 2.4, locked by gyb)

For every row:

```
old_ids  = tok(text + TAIL, add_special_tokens=False)     # TAIL: CALL_SEP for cgen, param_prompt_tail(label) for cparam
full_ids = tok(full_text, add_special_tokens=False)
p        = LCP(old_ids, full_ids)                          # compared token by token up to the first difference
seg_ids  = old_ids[p:] + tgt_ids
seg_lab  = [-100] * len(old_ids[p:]) + tgt_ids
```

Assert `len(old_ids[p:]) >= 1` (the separator string's four tokens, `[`, `CALL`, `]`, `Ġ`, never appear in the full-text continuation; measured, the tail's extra token count is only ever -1, 0, or 1; draft 4.3). This rule makes the new trainer's per-row token sequence identical to the old trainer's, token for token.

The value of `add_special_tokens`, and the tokenizer settings for pad/eos/truncation direction, follow `train_causal_callgen.py`'s `build()` lines 216-223; the new trainer calls the old script's `build()` directly to get the tokenizer and model (decision 6). `build()` is only allowed to gain two keyword arguments with defaults: `attn_impl=None` (None preserves the old behavior; otherwise it's passed as `from_pretrained`'s `attn_implementation`) and `path=None` (None looks up `MODELS[base]` as before; otherwise it loads the model and tokenizer directly from this directory, for the small-model tests in section 12).

### 3.5 The drop rule (draft 2.1, locked by gyb; decision 5)

- Event level: an event with `len(full_ids) > max_len` is dropped whole, counted as `dropped_events` (one number each for train / val, written into the `start` event). The criterion looks only at the event's full-text token count, not the packed-sequence length (the packed sequence's memory is backstopped by the token budget). The table in `plans/2026-08-28-plan.md` section 4: at 8192, train drops 1 event; at 6144, it drops 58.
- Row level: the two rules from 3.3, unchanged.
- No truncation whatsoever: `tok(...)` always uses `truncation=False`. After loading the data, assert "the longest packed-sequence length <= `max_len + MAX_BOUNDS x (MAX_TGT_TOK + 8)`," with `MAX_BOUNDS` imported from `pipeline/annotate/rules.py` (currently 64, the row-count cap per event; the average of 45.2 rows is just a mean, with 1,930 events hitting the 64-row cap, `plans/2026-08-28-plan.md` section 12.3); if the assertion fails, error out (guarding against a tokenizer version drift stretching the tail longer).

## 4 Forward-pass form

The semantics are defined here; the kernel choice and implementation path follow `design-attention.md` (delivered 2026-08-28, CPU equivalence verified, verification scripts and results under `verify/`). The settled implementation path (decision 12):

- Form A: an event is packed into one sequence and run through one forward pass; multiple events are laid out along the batch dimension, batched by token budget. Form B (a prefix pass with `use_cache`, then each segment attached to the cache) isn't used: it's mutually exclusive with `--grad-ckpt`, and the K/V copies each segment's cat produces total about 20 GB on an 8192-token event.
- Kernel: `attn_implementation="sdpa"`; on cuda devices, the training, evaluation, and alignment-check forward passes are all wrapped in `torch.nn.attention.sdpa_kernel([SDPBackend.EFFICIENT_ATTENTION])`. With a mask present, flash rejects outright; measured on H100, torch's default selection falls to cuDNN (`design-attention.md` section 7: peak 31.47 against mem-efficient's 31.43 GiB), so mem-efficient must be explicitly pinned, not left to drift with torch's default order and the cuDNN version (the sdpa docs state the cuDNN path may pick a non-deterministic algorithm); once explicitly pinned, falling back to math should error out rather than OOM (the math kernel holds one fp32 `(1, 16, L, L)` per layer: at L = 9,100 that's 5.3 GB per layer, 148 GB across 28 layers). This context isn't wrapped on CPU (it would raise `No viable backend for scaled_dot_product_attention`); CPU uses the default kernel. `--attn-impl` defaults to `sdpa`, and only accepts `sdpa` (flex_attention is kept as a post-smoke-test optimization, not in this round).
- Mask: the caller builds its own additive mask (0 = visible, -inf = not visible), shape `[B, 1, L, L]`, one built per physical block, with L padded to a multiple of 16. The mask's dtype must equal the query's dtype entering sdpa: bf16 under autocast, fp32 under section 9's fp32 alignment check (an fp32 query with a bf16 mask would be rejected by torch: `Expected attn_mask dtype to be bool or float or to match query dtype`; an fp32 mask under autocast would get cast into 28 separate per-layer copies). A bool mask is not allowed (torch's sdpa converts one float copy per layer, `attention.cpp`'s `convert_boolean_attn_mask`, 28 x 166 MB ~= 4.6 GB).
- position_ids: passed explicitly as a tensor, each segment continuing to count from p_k (`modeling_qwen3.py` takes the caller's position_ids directly); pad positions padded up to 16 also need position_ids (continuing the count).
- Loss positions: use an index table of `(batch index, query position, target token id, row number)`, gathering the loss positions from the final hidden state before passing through `lm_head` (or using `logits_to_keep`), never computing full-position logits (at L = 9,100, full-position logits are 2.8 GB bf16; an evaluation block of 32,768 positions would be 10 GB). Each row's ce is still defined as in section 4's closing paragraph.
- Both `--grad-ckpt` and `--lora` are verified under this form (on CPU: loss differs by 0 with gradient checkpointing; loss differs by 0 under peft, with only the adapter parameters receiving gradients).

An event's packed sequence:

```
tokens    = full_ids[:P] + seg_1 + seg_2 + ... + seg_K        # P = max_k p_k, K = the event's row count
positions = [0..P-1] + [p_1, p_1+1, ...] + [p_2, p_2+1, ...] + ...
labels    = [-100]*P + seg_lab_1 + ... + seg_lab_K
```

Attention's allowed relations (True = visible): causal within the prefix; segment k's i-th token can see the prefix's first p_k positions and this segment's first i+1 tokens; segments cannot see each other; the prefix cannot see any target segment. Within a physical block, multiple events go along the batch dimension, padded on the right: real tokens can't see pad, and rows where pad is the query only let pad see itself (a fully invisible row would make softmax produce NaN, `design-attention.md` section 2.3); pad positions don't count toward loss.

Per-row loss: per `inst_ce`'s convention (`train_causal_callgen.py` lines 231-248), the mean cross-entropy over this segment's target-token positions (logits at position t predict the token at position t+1, computed only where `label != -100`, with the denominator being this row's target-token count). The first target token is predicted by this segment's last prompt token, which lies within this segment (guaranteed by 3.4's assertion).

## 5 Loss and the update unit (draft 2.2, locked by gyb)

- Logical mini-batch = all the rows R of 4 events (`--events-per-mb` default 4). `W = sum_{r in R} w_r`.
- A logical mini-batch is split into physical blocks C_1..C_m by token budget: events are packed greedily in descending order of packed-sequence length, with a block's "event count B x the block's longest packed-sequence length padded to a multiple of 16, L_pad" <= `--tok-budget` (the criterion uses L_pad, matching the mask's padding convention); a single event over budget becomes its own block (allowed to exceed the budget).
- For each physical block: `loss_C = sum_{r in C} w_r . ce_r / W`, then `(loss_C / n_g).backward()`, where `n_g` is the actual number of logical mini-batches in this group (every earlier group is `accum`; the last group of the epoch is `min(accum, M - the group's starting index)`). The sum of gradients across the m blocks equals the gradient from computing the whole logical mini-batch in one shot, which also equals the old trainer's `loss = (ce.w).sum()/w.sum()` followed by `(loss/accum).backward()` (lines 494-505).
- For every group (`--accum` logical mini-batches, default 2): `clip_grad_norm_(1.0)` -> `opt.step()` -> `sch.step()` -> `opt.zero_grad()`. A final group short of `accum` at the epoch's end still triggers one update, with the divisor taken as `n_g` above (the old trainer doesn't update on the tail group, letting its gradient leak into the next epoch; the new trainer must not leak, and must not shortchange the tail group's step size either).
- Optimizer and scheduler unchanged: `AdamW(weight_decay=0.01)`, `get_linear_schedule_with_warmup(opt, int(steps*0.05), steps)`. The number of updates per epoch is `U = ceil(M / accum)`, where `M = ceil(n_events / events_per_mb)` is the number of logical mini-batches; `steps = U . epochs`. This U is exactly the U used for evaluation timing in section 6.
- Event order: each epoch shuffles the event list with `random.Random(SEED + ep)`, then takes every 4 in order as one logical mini-batch (the last one may be short).
- Learning-rate defaults unchanged: full-parameter `FULL_LR = 1e-5`, LoRA goes through `lora_util.resolve_lr` (default 2e-4). Wiring for `--lora` and `--grad-ckpt` follows the old trainer (`lora_util.wrap / prepare_grad_ckpt / opt_params / save_merged / meta_block`).
- `--epochs` defaults to 1.

## 6 Evaluation and the best version (draft 2.7)

- `val_ce`'s convention follows `eval_ce` (lines 259-291): `sum w.ce / sum w` over all val rows, computed with section 4's packed forward pass (likewise passing only the loss positions through `lm_head`), under `torch.no_grad` plus bf16 autocast, with a physical-block budget of `--eval-tok-budget` (default = 2 x `--tok-budget`). The `w_tot <= 0` hard stop is unchanged.
- Timing: each epoch evaluates `E = --eval-per-epoch` times (default 4); the evaluation points are the set `{ceil(U.k/E) : k = 1..E}` (when U < E, duplicate points merge and are evaluated once); once this epoch's update count reaches one of these points, a full val evaluation runs; the point where k = E is the epoch's end.
- Best version: whichever evaluation has the lowest `val_ce`, written to `<out>/best/`, in a layout structurally identical to the old trainer's, item for item (lines 530-552): full-parameter uses `model.save_pretrained`, LoRA uses `lora_util.save_merged`; `tok.save_pretrained`; `meta.json`'s old fields are written exactly as the old trainer does (`base, base_path, data, max_len, seed, epoch, call_sep, transformers`; `readonly_env` is written only when it's on -- `eval_causal_call.py` checks whether the key is present, not its value; `lora`, `grad_ckpt` unchanged; cparam's `param_only: true`), plus new fields `trainer: "share"`, `frac` (the evaluation point's index, 1 to E), `gstep`, `tok_budget`, `events_per_mb`, `accum`, `attn_impl`. The eval scripts read `call_sep`, `max_len`, `param_only`, `data` (cross-checked three ways), `readonly_env` (whether the key is present) (`eval_causal_call.py` lines 513-516, 585-586; `eval_causal_param.py` lines 342-345, 415-416). Once `max_len` is written as 8192, the two call-eval scripts' prompt left-truncation length changes from 4,000 to 8,096 (they use `max_len - max_new`) -- this is intentional: no truncation on the eval side matches the training side's convention; eval-side memory is estimated at 8192 when placing eval jobs on cards (decision 13).
- No generation-based evaluation (the old `val_exact_call` / `val_exact_params` and `--gen-bs` are dropped, decision 4).

## 7 Log `<out>/train_log.jsonl`

- `mem_probe` (written as two entries before training starts, when `--mem-probe` is on): `kind` (`longest_event` / `fullest_block`), `n_events, packed_len_max, peak_mem_gb`. See section 10 for the method.
- Heartbeat (`extending.md` line 144: a script that doesn't wire this in stays stuck at warm-up in the monitoring window forever): follows the old trainer's lines 71, 481, 517, 554 -- `import heartbeat` (`ops/heartbeat.py`), `heartbeat.emit(0, steps, "step")` before training starts, `heartbeat.emit(gstep, steps, "step", loss=...)` alongside every `step` log entry, and `heartbeat.emit(gstep, steps, "step", status="done")` at the end.
- `eval`: `ep, frac, gstep, val_ce, n_eval_rows`.
- `save_best`: `ep, frac, gstep, val_ce`.
- `done`: `best_val_ce, best_ep, best_frac, total_rows, wall_s`. The driver only checks whether a `done` event exists (`pipeline/driver.py` lines 772, 810).
- If `<out>/train_log.jsonl` already exists, a second training run is refused; `--force` overrides this (unchanged, lines 380-383).

### 16.4 Parameterizing alignment tolerances and adding a relative criterion (ticket 09)

`train_causal_share.py`: all five thresholds from section 9 become parameters, with defaults equal to the current constants: `--align-tol 2e-5` (already exists), `--align-tok-tol 3e-4`, `--align-bf16-mean-tol 2e-2`, `--align-bf16-max-tol 1e-1`, `--align-baseline-factor 3.0`; the module-top constants `TOK_DIFF_TOL / BF16_MEAN_TOL / BF16_MAX_TOL` are deleted, leaving only the parameter defaults as the one source of truth. New parameters `--align-rule {abs,rel,both}` (default `abs`) and `--align-rel-tol` (default 1e-5):

- `abs`: current behavior -- the max per-row absolute difference <= `--align-tol` and the max per-token absolute difference <= `--align-tok-tol`.
- `rel`: `rel_max_abs_diff <= --align-rel-tol`, where `rel_max_abs_diff = max_abs_diff / ref_scale`, `ref_scale = mean(|ce_ref|)` (the mean absolute value of the reference path's per-row ce). - `both`: both `abs` and `rel` hold.

Regardless of which rule is used, `ALIGN_CHECK.json` always writes all of `rule, tol, tok_tol, rel_tol, ref_scale, rel_max_abs_diff, bf16_mean_tol, bf16_max_tol, baseline_factor`, with the existing keys unchanged -- these are exactly the numbers gyb will compare later, with no need to rerun anything. ### 16.10 Silent-failure points (written back to `extending.md` section 5)

- #28: cgen / cparam eval's `drop-event` counts depend on which `overlong_mode` ctool eval used (an event ctool has already dropped can't be counted by cgen), so each report records its own `overlong_mode`.
- #29: generation (`model.generate`) cannot be wrapped in `_attn_ctx` -- with no mask it goes through GQA, and mem-efficient raises `No available kernel`.
- #30: `share_data`'s row-tuple slot 6 is the `gen` dict; a hand-built row tuple must carry all 7 slots.
- #31: the probe consumes the random-number stream (LoRA dropout); without restoring RNG state, a run with the probe and one without won't match bitwise.
- #32: the `loop` probe's zero-lr `opt.step()` still writes AdamW's `exp_avg / exp_avg_sq` and the `step` counter, so `opt.state.clear()` is required after the probe.
- #33: ctool eval's `--cached-logits` cache has the same row count but different content under different `--overlong` values, so caches from different modes would impersonate each other if `.meta.json` doesn't record the mode; `.meta.json` records `overlong_mode`, hard-stopping on a mismatch.
- #35: ctool eval's `skip` / `drop-event` changes `n_events_scored` (which `summarize_matrix.py` reads for the pred_tool block), and the matrix has no visibility into `overlong_mode`, so runs from different modes mixed into one matrix can't be told apart; the matrix only accepts `left`-mode eval, with other modes' numbers going only into their own reports.
- #36: `mem_probe_summary`'s `worst_gb` under `scope=run` only covers this run's events, giving a small-sample number under `--smoke` / `--max-events`; placing a full run on a card needs `scope=full`'s (`tokens`'s) number.
- #37: `--grad-ckpt`'s recompute happens inside `.backward()`; if the kernel context only wraps the forward pass, the recompute runs on the default kernel, and torch raises `CheckpointError: Recomputed values ... have different metadata` (measured on 2026-08-28 in l4's smoke test, `ks828l4_gptoss_cgen_smoke`, crashing on the probe's first backward pass; b06 with checkpointing would hit the same). `.backward()` is also wrapped in `_attn_ctx`. This wasn't hit in round one because neither round one's smoke tests nor its final verification used checkpointing.
- #34: "an event's full text" has two definitions -- ctool's trainer filters by `label in label2id` first, then takes the last row (`train_causal_tool.py` lines 93-96), while share_data doesn't filter (lines 121-131); when the row with the largest `sent_idx` has a label not in the vocabulary, the two sides get different text, and `dropped_events` may differ too (both sides reading 1 / 3 in the smoke test is a coincidence on that one dataset). Each eval script follows its own trainer's rule.
