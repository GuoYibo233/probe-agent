## 2. The recommended form A packs one forward pass, paired with one mask and one custom position_ids

### 2.1 The sequence is the prefix followed by K target segments

An event's sequence is the "prefix" followed by K target segments. The prefix is the P tokens split out of the event's full text (the row with the largest sent_idx) with `add_special_tokens=False`. Row k is tokenized the old trainer's way: `prompt_k = tok(text_k + "\n[CALL] ")`, `tgt_k = tok(label_call_k) + [eos]`; `p_k` is the length of the matching prefix between `prompt_k` and the event prefix, compared token by token from the start (the common-prefix rule from draft section 2.4); the tail `tail_k = prompt_k[p_k:]`; the target segment `seg_k = tail_k + tgt_k`. Among the 34 rows sampled this round, `len(prompt_k) - p_k` is 5 (32 rows) or 4 (2 rows), meaning the tail is exactly the 5 tokens of the separator string, or the 4 left over after the separator's leading newline merges with the end of the row text into one token; no row had an empty tail.

### 2.2 The mask, position_ids, and loss positions are built by the code below (a trimmed-down copy of the script `packed_common.py`'s `build_packed`, verbatim)

```python
P = len(full_ids); seq = list(full_ids); pos = list(range(P)); segs = []
for k, r in enumerate(rows):
    p = lcp(r["prompt"], full_ids)           # common prefix length
    tail = r["prompt"][p:]; start = len(seq); seg = tail + r["tgt"]
    seq += seg; pos += list(range(p, p + len(seg)))          # position numbering continues from p
    segs.append(dict(p=p, start=start, end=start + len(seg), n_tail=len(tail)))
L = len(seq)
allow = torch.zeros(L, L, dtype=torch.bool)
allow[:P, :P] = torch.ones(P, P, dtype=torch.bool).tril()   # causal within the prefix
for s in segs:
    allow[s["start"]:s["end"], :s["p"]] = True               # segment k sees the first p_k prefix positions
    n = s["end"] - s["start"]
    allow[s["start"]:s["end"], s["start"]:s["end"]] = torch.ones(n, n, dtype=torch.bool).tril()  # causal within the segment
# loss positions: logits at position j predict seq[j+1]; a target token t's predicting position is the position of the token right before target token t
qpos, ys, row_id = [], [], []
for i, (r, s) in enumerate(zip(rows, segs)):
    for t, y in enumerate(r["tgt"]):
        j = s["p"] - 1 if (t == 0 and s["n_tail"] == 0) else s["start"] + s["n_tail"] + t - 1
        qpos.append(j); ys.append(y); row_id.append(i)
```

Forward pass and loss:

```python
out = model(input_ids=seq[None], attention_mask=allow[None, None],     # bool, [1, 1, L, L]
            position_ids=pos[None], use_cache=False,
            logits_to_keep=torch.tensor(sorted(set(qpos))))            # only run the loss positions through the output layer
ce = F.cross_entropy(out.logits[0, col_of(qpos)].float(), torch.tensor(ys), reduction="none")
row_ce = index_add(ce, row_id) / count(row_id)                        # each row = mean of its target-token CE, same convention as inst_ce
loss = (row_ce * w).sum() / w.sum()                                    # weighted by w within the logical mini-batch (draft 2.2)
```

labels don't need to be laid out as a shifted-by-one `[B, L]` tensor; use the three index tables `(qpos, ys, row_id)` directly. Reason: an empty-tail row's first target token has its predicting position land inside the prefix, which a shifted tensor can't express but an index table can.

### 2.3 When a batch holds multiple events, the sequences are laid out along the batch dimension

When several events are placed into one physical batch by token budget (draft 2.2's physical layer), the sequences are laid out along the batch dimension, each padded to the longest L in the batch: `input_ids [B, L]`, `position_ids [B, L]`, mask `[B, 1, L, L]`. A pad position's mask row only lets the pad see itself (an all-False row would make softmax produce NaN), and pad positions never enter the loss-position table. Don't concatenate several events into one longer sequence -- attention compute grows quadratically with L, and only laying them out along the batch dimension keeps it linear.

### 2.4 The mask is a bf16 additive tensor, built once per physical batch, with L padded to a multiple of 16

On CPU, a bool mask and a 0 / -inf float mask produce identical loss position by position (section 4). On GPU, bool and float masks differ in memory: measured with `saved_tensors_hooks` (the CPU-side flash kernel, bf16), a bool mask gets converted into a fresh bf16 additive mask on every sdpa call and saved for backprop, so two calls save two distinct storages; passing a ready-made bf16 additive mask directly, two calls save the same storage. Folded across 28 layers: at L = 9,100, a bool mask costs an extra 28 x 9,100^2 x 2 bytes, about 4.6 GB, while a bf16 additive mask holds only one 166 MB copy. So the recommendation is to build one bf16 additive mask (0 / -inf) per physical batch, not rebuild it per layer. The mem-efficient kernel has one more alignment requirement: in torch v2.11.0's source, `aten/src/ATen/native/transformers/attention.cpp`'s `preprocess_mask` first uses `aligned_tensor<16>` to check that every dimension of the mask except the last has a stride that's a multiple of 16 and the last dimension has stride 1; if not, `pad_bias` pads the last dimension with `at::pad` and slices it back (one copy), then `expand`s it to `[batch, heads, L, L]` (a view, no copy); in the same file, a bool mask is converted with `convert_boolean_attn_mask` using `at::where` into a 0 / -inf float tensor before entering the kernel, freshly built on every call. So building the mask as bf16 additive, contiguous, with L a multiple of 16 lets all 28 layers share one storage; exactly how much memory this saves is measured on GPU (section 6, step 5).

### 2.5 The alternative form B (cache relay) can carry gradients, but is kept only as a comparison, not used for training

Form B is: run the prefix through once with `use_cache=True` to get a `DynamicCache`, sort rows by `p_k` descending, and for each row first `cache.crop(p_k)`, then feed the target segment as a new input continuing from there, with position_ids continuing from `p_k`. Measured on CPU (the form_b item in section 4): the 3-row loss differs from the old trainer by at most 1.3e-6; after backprop through the loss, the prefix input embedding's gradient is non-empty, 462 of the 463 prefix positions having a non-zero gradient (the only zero one is the prefix's last token -- no target segment sees the prefix's last token, and the prefix's last token isn't a loss position either). So form B can carry gradients under transformers 5.14.1. It also works under LoRA: peft only swaps out nn.Linear, and doesn't touch forward's parameters.

Form B's two structural flaws were read straight out of the code. First, `modeling_layers.py` lines 82-84 make gradient checkpointing and `use_cache` mutually exclusive; 1.7B and 4B only fit on a 48G card via `--grad-ckpt` (experience from `plans/archive/2026-08-22-np821-exec-worklog.md`), so form B effectively turns off `--grad-ckpt`. Second, `DynamicLayer.update` produces a fresh K, V tensor via `torch.cat` every time, and the cat'd K, V tensor gets saved by that segment's attention backward pass, so each of the 45 segments keeps its own copy of K, V of length `p_k`: at an average `p_k` of 4,000, 8 KV heads, head_dim 128, bf16, K and V each, 28 layers, an 8192-token event needs to hold 45 x 4,000 x 8 x 128 x 2 x 2 x 28 bytes, about 20 GB, whereas form A saves only one copy of K, V for the whole sequence (16 heads after repeat_kv), 9,100 x 16 x 128 x 2 x 2 x 28 bytes, about 2.1 GB. Merging the 45 segments into one padded batch against the cache would be worse: the cache would need to expand along the batch dimension into 45 copies before cat'ing, each layer costing 45 x 8 x 8,300 x 128 x 2 x 2 bytes, about 1.5 GB, 28 layers about 43 GB.

Verdict: use form A. Form A differs from ctool's whole-segment single forward pass by only one mask and one position_ids; gradient checkpointing, LoRA, and batching along the batch dimension by token budget are all directly usable, all three verified on CPU. Form B is kept only as a comparison implementation, not used for training.

## 3. The kernel is explicitly pinned to mem-efficient; the math kernel doesn't fit at 8192

### 3.1 Form A must explicitly pin mem-efficient on GPU (the default order falls to cuDNN on H100, see section 7)

Reasoning from section 1's facts: with a non-empty mask, flash rejects outright; next in priority is mem-efficient, which accepts a 4D mask (bool or float), with head_dim 128, bf16, dropout 0, a mask that doesn't require grad, and batch and head dimensions of 1 -- all within the allowed range; as long as mem-efficient's eligibility check passes, math never gets a turn. cudnn sits behind math, and by default is never reached. Section 7's GPU measurements overturn half of this reasoning: on H100 the default selection fell to cuDNN, and mem-efficient only gets used when explicitly pinned. Every piece of this reasoning must be checked on GPU against real shapes with `torch.backends.cuda.can_use_efficient_attention(SDPAParams(q, k, v, mask, 0.0, False, False), debug=True)`, and the kernel name confirmed with the profiler (section 6, steps 1-3, script `gpu_kernel_check.py`).

The training code should wrap the forward and backward passes in `with torch.nn.attention.sdpa_kernel([SDPBackend.EFFICIENT_ATTENTION]):`. That way, when mem-efficient isn't usable, torch errors out immediately instead of silently falling back to math and then OOMing on an 8192-token event.

### 3.2 The math kernel needs to hold onto a 120 GB attention matrix at 8192

The math kernel saves one `(1, 16, L, L)` float32 attention matrix per layer (measured in section 1), i.e. 16 x L^2 x 4 bytes per layer, 28 x 16 x L^2 x 4 bytes total across 28 layers. The numbers for three values of L:

| Sequence length L | Attention matrix saved per layer | Total across 28 layers |
|---|---|---|
| 8,192 (prefix only) | 4.29 GB (4.00 GiB) | 120.3 GB (112.0 GiB) |
| 9,100 (8192-token prefix + 45 segments x about 20 tokens each) | 5.30 GB (4.94 GiB) | 148.4 GB (138.2 GiB) |
| 10,000 | 6.40 GB (5.96 GiB) | 179.2 GB (166.9 GiB) |

These three numbers are only the part backprop needs to hold onto; while computing each layer in the forward pass, the score matrix, the masked copy, and the softmax output all exist at the same time, so the instantaneous peak is even higher. H100 has 95,830 MiB total (93.6 GiB, `plans/2026-08-28-plan.md` section 9.2), H200 has 143,771 MiB (140.4 GiB). The math kernel already needs 30 GB at L = 4,096, so form A, starting at 8192, doesn't fit on any card under the math kernel.

### 3.3 The activations mem-efficient holds onto grow linearly with L; a 9,100-token event costs about 33 GB

mem-efficient doesn't materialize an L x L x head-count matrix; what it saves for backward is each query position's logsumexp (16 x L numbers) and K, V themselves. The only thing that still grows quadratically with L is the mask: one bool copy costs L^2 bytes, one bf16 additive copy costs 2 L^2 bytes -- at L = 9,100 that's 83 MB and 166 MB respectively; per the measurement in section 2.4, a bool mask gets converted once per layer, costing an extra ~4.6 GB. The rest of the activations grow linearly with L; the bytes per token were measured on CPU with `saved_tensors_hooks`:

The script `mem_probe.py` (result `mem_probe.json`) runs form A's forward pass once on CPU (random tokens, a prefix plus 8 segments of 20 tokens each), using `saved_tensors_hooks` to record every tensor autograd saves for backward, deduplicated by storage, classifying anything whose last two dimensions both equal L as the "L x L class" and everything else as the "other class." For the L = 2,048 group (the L = 1,024 group misclassified the 1,024-dim hidden state and the 1,024 x 1,024 weight into the L x L class, and is used only for the differencing below):

| Kernel | Precision | Tensors saved in the L x L class | L x L class total | Bytes per layer per L^2 | Other class total |
|---|---|---|---|---|---|
| flash-cpu (CPU stand-in for GPU mem-efficient) | bf16 autocast | 1 copy of a `(1, 1, 2048, 2048)` bf16 mask | 8.4 MB | 0.07 | 6.23 GB |
| math | bf16 autocast | 28 copies of `(1, 16, 2048, 2048)` fp32 plus 28 copies of a `(2048, 2048)` bf16 mask copy | 7.75 GB | 66.0 (64 is the attention matrix, 2 is the mask copy) | 6.69 GB |
| flash-cpu | fp32 | 1 fp32 mask copy | 16.8 MB | 0.14 | 10.00 GB |
| math | fp32 | 28 fp32 attention matrices plus 28 fp32 mask copies | 7.99 GB | 68.0 | 9.53 GB |

The math kernel's 64 bytes per L^2 per layer matches the analytic formula of 16 heads x 4 bytes from section 3.2; the math path also copies the mask once per layer, while flash-cpu takes the ready-made float mask and shares one copy across all 28 layers.

The "other" class contains one chunk that doesn't change with L (autocast's bf16 copy of the 0.6B weights, needed for backward), so the bytes per token are computed by differencing the L = 1,024 and L = 2,048 points (adding back the misclassified hidden state at the 1,024 point): under bf16 autocast, 2.42 MB per token, with a fixed amount of about 1.2 GB; under fp32, 3.68 MB per token, with a fixed amount of about 2.4 GB (under fp32 this chunk is the weights themselves, no extra memory). Extrapolating to GPU training (bf16 autocast, mem-efficient): at L = 8,192, activations held onto are about 19.8 plus 1.2 equals 21 GB; at 9,100, 22.0 plus 1.2 equals 23 GB; at 10,000, 24.2 plus 1.2 equals 25 GB. Add the static part: fp32 weights 2.4 GB, gradients 2.4 GB, AdamW's two states 4.8 GB, totaling 9.6 GB. A single 9,100-token event as its own batch holds onto a total of about 33 GB, leaving 60% of H100's 93.6 GiB. 33 GB is "held onto," not "peak": by the same coefficients, the old trainer's A_h100 smoke test at 4 rows of 4096 per batch holds onto about 55 GB (16,384 tokens x 2.42 MB plus full-position logits' 5.0 GB plus the static 9.6 GB), while the measured peak is 80.0 GB (section 9.2) -- the peak is over 40% higher than the held-onto amount, with transient tensors and allocator fragmentation both inside it. So the 9,100 peak is estimated with a 40-50% margin at 45-50 GB, with the final number to be measured in section 6, step 2.

Another quantity that grows with L is the output layer: the old trainer computes vocabulary logits over all positions (section 9.4); at L = 9,100, bf16 logits are 9,100 x 151,936 x 2 bytes, about 2.8 GB; form A uses `logits_to_keep` to compute only the loss positions, needing only 0.27 GB for 45 rows' roughly 900 target tokens, and the `.float()` copy used in CE is only 0.55 GB.

### 3.4 flex_attention saves half the attention compute, but needs compilation, kept as a later option

flex's advantage is block sparsity: in form A's mask, causal masking within the prefix removes half, and each target segment only sees itself and the first p_k positions of the prefix; flex skips all-False blocks at a granularity of 128 x 128, cutting attention compute roughly in half; mem-efficient, taking an explicit mask, has to compute all L^2 scores before applying the mask, saving no compute. There are three costs. First, it needs a Triton kernel compiled via `torch.compile` on the GPU node (HF compiles once and caches at `flex_attention.py` line 92, recompiling when the shape changes, until dynamo converts to dynamic shapes); the first compile takes tens of seconds to a few minutes, and whether inductor can compile has not been verified on the np821 training environment; second, each physical batch needs a block mask built on GPU via `create_block_mask`, itself a few to a few tens of milliseconds of overhead; third, the model needs to load with `attn_implementation="flex_attention"`, while the eval side and ctool both still use sdpa, so the two paths' numbers will differ at the bf16 level.

Compute accounting (rough): attention's forward pass per layer is about 4 x L^2 x 128 x 16 floating-point operations, 28 layers, with forward plus backward counted as 3.5x the forward alone (mem-efficient's backward has to recompute the forward pass); the linear layers, by non-embedding parameter count of 0.44B, cost 2 x 0.44e9 per token forward, with forward plus backward at 3x. At L = 9,100, attention is 6.6e13, the linear layers 2.4e13 -- attention is 70%; for a median event (prefix 1,271 plus 45 segments, about 2,200 tokens total), attention is 3.9e12, the linear layers 5.8e12 -- attention is 40%. flex halves attention compute, which translates to a 20% (median event) to 35% saving on the whole event.

Verdict: the first version uses sdpa plus mem-efficient, because mem-efficient's memory use is already good enough (section 3.3), while the inductor compilation chain hasn't been verified on the training node; flex is kept as a speed optimization for after smoke testing, with an expected gain of 20-35%, to be decided once smoke testing measures rows per second. Form A's `allow` matrix translates directly into flex's `mask_mod`: pre-build three length-L tensors, `seg_of` (0 for the prefix, k for segment k), `p_of` (each position's segment's p_k; for a prefix position, its own index plus 1), `start_of`, giving `mask_mod(b, h, q, kv) = (kv <= q) & ((seg_of[q] == 0) | (kv < p_of[q]) | (seg_of[kv] == seg_of[q]))`.

## 5. The alignment tolerance is split into two gates: an fp32 gate of 2e-5 per row, a bf16 coarse screen averaging 2e-2 per row

### 5.1 ctool's `--align-tol` verifies that the cache-incremental forward pass and the whole-segment forward pass are the same function

`train_causal_tool.py` lines 200-240, `align_check`: take the val set's single event with the longest full text (line 335), truncate to `--max-len`, and under fp32 with `torch.set_float32_matmul_precision("highest")` (line 208, TF32 off), run the base model's forward pass two ways: one whole-segment forward pass, and one token-by-token incremental forward pass (feeding 1 token at a time with `past_key_values`, lines 218-222), comparing the max absolute difference in the last position's hidden state and classifier-head logits (lines 226-228); it only PASSes if both differences are under `tol`, otherwise `sys.exit(2)` refuses to start training (lines 345-354). The default is `ALIGN_TOL = 1e-4` (line 76). `3e-4` is the value the c1 batch loosened to, following the T8 precedent (`.claude/skills/probe-pipeline/references/invariants.md` line 97: three ctool runs had hidden maxdiff of 8.39e-5 to 1.68e-4, relative difference 2.3e-6 to 3.3e-6, judged to be fp32 noise, recorded in the TIMELINE's 2026-07-31 c1 entry); np821's four ctool runs' `align_maxdiff_hidden` is 9.78e-5 to 2.37e-4 (`RESULTS.md` lines 23-32). `--align-tol` verifies that "the cache-incremental forward pass and the whole-segment forward pass are the same function," measuring the hidden state's absolute difference after 4096 tokens, entirely in fp32, unrelated to bf16 training, and it doesn't compare loss.

### 5.2 The correctness gate is set on fp32; bf16 is only a coarse screen

The new trainer's alignment acceptance splits into two gates.

The first is the correctness gate: under fp32, `highest` precision, TF32 off, on a random sample of events, form A's per-row loss must not differ from old-trainer-batched by more than 2e-5 max absolute, and per-token by more than 3e-4 max absolute (loosened on 2026-08-28 from 1e-5 / 1e-4 based on section 7's GPU measurements). Basis: on CPU, 5 short events measured 2.15e-6 per row, 2.77e-5 per token; 3 large events (up to 64 rows, 3,689 after packing) measured 2.62e-6 per row, 2.38e-5 per token; on GPU (H100, the new path under mem-efficient), the same 5 short events measured 4.41e-6 per row, 3.05e-5 per token, with a padding baseline of 5.01e-6 per row, 6.91e-5 per token; spec section 9's sampling scale (about 380 rows, 7,000 tokens) is 10x larger than this, and the max value will climb further, so the threshold is loosened one more notch from the GPU numbers, with the reasoning and estimate in section 7; a single wrong position in the mask or position_ids would move a row's loss by 1e-2 to 1, far above the threshold. Print the difference alongside the same run's "old trainer single-row vs. batched" baseline difference, and flag it as suspicious if the difference exceeds 3x the baseline, even when the difference itself is still under 2e-5 (on GPU, the single-row batch in the baseline has no mask, and per section 7's eligibility table, by elimination it runs on the math kernel; the measured baseline difference is actually larger than the new path's difference against the batched version, so the baseline line is only a warning, not a gate).

The second is a bf16 coarse screen, run once with the real kernel before GPU smoke testing (`gpu_kernel_check.py` step 6), on 34+ rows: form A's per-row loss must not differ from old-trainer-batched by more than 2e-2 mean absolute, or 1e-1 max absolute. Basis: CPU measured a mean of 8.9e-3, max of 3.6e-2; GPU (H100, mem-efficient) measured a mean of 9.31e-3, max of 3.07e-2; bf16 vs. its own fp32 already differs by a mean of 8.0e-3, max of 3.0e-2, so the threshold keeps a 2-3x margin. This screen can only catch errors like "whole-segment misalignment" that shift loss by 0.1 or more; it can't catch subtle mask errors, so it can't substitute for the first gate.

It is not recommended to reuse ctool's 3e-4: that's the fp32 hidden state's absolute difference, differing from the bf16 loss difference in what's measured, the precision, and comparability.

### 7.1 The cause of step 6's error, and the constraint the trainer must work around

Cause: one batch in the alignment check's reference path is "single-row, unpadded," with no padding, so HF's `_ignore_causal_mask_sdpa` skips building a mask, `use_gqa_in_sdpa` returns True when the mask is empty, K, V stay at 8 heads with no `repeat_kv`, and `enable_gqa=True` is passed straight into sdpa; the mem-efficient kernel doesn't support GQA (sdpa's docstring verbatim: `Grouped Query Attention (GQA) is an experimental feature. It currently works only for Flash_attention and math kernel on CUDA tensor`), and inside the forced EFFICIENT context, flash and cudnn are also turned off, leaving no usable kernel. The new path always carries a mask, with `repeat_kv` up to 16 heads, so it never hits this; steps 2, 3, 5, 7 all running successfully inside the same context is the evidence.

The script's fix: `alignment()` only wraps the new path in `sdpa_kernel([EFFICIENT_ATTENTION])`, leaving the reference path on default selection; step 1 asks two more eligibility questions (fp32 query with an fp32 mask; bf16 with no mask and 8 KV heads) to record the "mem-efficient doesn't accept GQA" constraint into the JSON. That's how the third run's step 6 succeeded; the numbers are in item 6 above, and section 5.2's thresholds were changed based on these numbers.

The constraint the trainer must work around (to be added as a sentence in spec section 9): the alignment check's reference path (the old `collate` plus `inst_ce`) does not wrap `sdpa_kernel([EFFICIENT_ATTENTION])`, using default kernel selection; only the new path (form A, which always carries a mask) wraps it. The general rule: any sdpa call with no mask (HF skips building a mask and turns on `enable_gqa` when the 2D mask is all True or the mask is empty) must never be placed inside a forced EFFICIENT context. The trainer's own training and evaluation forward passes are both form A, both always carrying a mask, so they're unaffected.

### 8.5 Interpretation and verdict (decision 21 already adopted)

Keep the limit `--max-len` at 8192: the longest event's probe is 31.4 GB; b16k's training peak of 56.4 GiB leaves 39% headroom against 93.10 GiB, and b24k's 75.4 GiB still leaves 19% -- both above the 10% verdict line.

Set the budget `--tok-budget` to 16,384: b24k's tail cumulative rows-per-second is 15% slower than b16k's (the last step log's `ips` is 157.1 vs. 183.7), with the six comparison points individually slower by 17.8 / 18.1 / 15.4 / 17.8 / 17.3 / 7.0%, averaging 16% slower; its peak is 20 GB higher, and the probe undercounts the true peak (next paragraph) -- b24k, if two fullest blocks land in the same group, would climb to 85-90 GB, pushing the headroom down near the 10% line; b16k is both faster and more stable.

Don't turn on `expandable_segments`: b16k_es is 3% slower than b16k with the same peak, showing no benefit over 57 updates; whether fragmentation builds up late in a full epoch wasn't tested -- revisit if full training hits an OOM.

Don't do S4 (building the mask on the main thread): each window's throughput by padded token count is stable at 12.9k-16.9k tokens per second, and CPU mask-building's share can't be distinguished from the logs alone, with the estimated gain not exceeding 10%. The bigger lever in the data is the 28% padding waste: within a 4-event logical mini-batch, a block of B = 2 to 4 pads short events up to the block's longest; changing the packing strategy only touches the physical layer, not the update convention, and is left as an optimization for after the full run.

Why the probe reads 9.5 GB below the training peak (b16k 51.1 vs. 60.6 GB): the probe's peak is the larger of two moments -- during backward, it's "weights 2.4 GB plus activations plus the gradient being produced," with the optimizer state not yet allocated (built only at the first `opt.step()`); after `opt.step()`, it's "weights plus gradient plus state = 9.6 GB," but the activations have already been freed. The real training peak occurs during the second logical mini-batch's backward pass within a group, a moment when the optimizer state's 4.8 GB and the first mini-batch's gradient of 2.4 GB are both present -- that 7.2 GB is the bulk of the gap, with the remaining ~2.3 GB from block-shape differences. The probe's fix (ticket 06): first `zero_grad(set_to_none=False)` plus one zero-lr `opt.step()` to build the state, then run the fullest block through two forward-backward passes back to back with no `zero_grad` in between (with accum = 2, two fullest blocks landing in the same group is a real worst case), reading the peak after the second backward, then `opt.state.clear()`. Expected b16k to come out to about 60 GB.

The tail window's 145 rows per second isn't caused by the tail group or by evaluation: `train_s` excludes evaluation, which happens after the 57th update; section 8.3's reproduction shows the 51st and 54th windows land exactly on the stretch with the most tokens per row (87.6 and 94.9), and the throughput by token count is the same order of magnitude as the other windows -- the slight dip on long sequences is attention's L^2 share growing larger. All three runs having identical window shapes also shows this is determined by the data.

ctool on H100 runs at `--bs 2 --accum 4`: `--bs 4` OOMs on the very first batch at the 8192 limit; at the crash, PyTorch had 77.61 GiB allocated plus 14.58 GiB reserved-but-unallocated, i.e. fragmentation filled up the 93.10 GiB; `--bs 2`'s nvidia-smi peak of 56,859 MiB (55.5 GiB, including allocator caching) leaves 40% headroom against 93.10 GiB. Section 8.4's ctool numbers are at the smoke-test scale of 200 events; a full training run's batches will produce longer event combinations, so `--bs 2`'s headroom should get another look at nvidia-smi during the full run's first epoch.

A full epoch's training time, estimated at b16k's 185 rows per second: the train set's 186,479 rows take about 1,008 seconds, plus four evaluations, the alignment check, and `--mem-probe`'s full-set loading (these three weren't timed separately in the smoke test; `wall_s` minus `train_s` is 471 seconds, one of which is a 20,034-row evaluation).

First, the probe's remaining 4.1 GB gap comes from the number of loss positions -- the guess that "the block with more rows has more loss positions" holds, but needs one qualifier: the peak block also needs its token count to be near the budget. Each loss position holds onto four 151,936-dim vectors at the output layer (the bf16 logits lm_head produces under autocast, the fp32 copy CE uses, the fp32 gradient on the logits, and the bf16 gradient passed back to lm_head, totaling about 1.8 MB); the peak block has 2,752 more loss positions than the probe's block, which is about 5.0 GB, minus about 1.0 GB back for its 352 fewer tokens at 2.7 MB per token, netting a difference of about 4.0 GB, matching the measured 4.1 GB. The correlation of 0.73 vs. 0.49 shows token count is still the primary term and loss positions the secondary one; the true worst block is whichever maximizes "a x token count + b x loss-position count," and a probe that picks only by token count misses that second term. The longest event's probe (36.5 GB) is far from the peak, and is never the binding constraint at a budget of 16,384.

Second, the drop from 60.59 to 58.47 is S1's effect; the mechanism isn't the `hidden_states` tuple itself, but that the old code called `Qwen3ForCausalLM.forward`, whose default `logits_to_keep=0` runs every position through lm_head -- a 16,384-token block means a bf16 tensor of 16,384 x 151,936 x 2 bytes = 4.98 GB, alive at the moment the forward pass finishes alongside all the activations; after S1 changed it to call the backbone directly, this is gone. The drop of 1.9 to 3.9 GB being less than 4.98 GB is because the peak moment doesn't always land at the end of the forward pass: a block with more loss positions has a larger logits gradient right as backward starts, so its peak occurs at the start of backward, by which point the full-position logits have already been freed -- which is why the 42nd update's window (4,736 loss positions) has the smallest drop, 2.12, and the 21st update's window (whose most-tokens block has only 1,475 loss positions) has the largest drop, 3.94.

Third, the longest-event probe's increase from 31.43 to 36.47, an extra 5.04 GB, has as its main term the optimizer state's 4.77 GB (596 million parameters x 2 fp32 copies), with two other terms roughly canceling out: the fixed probe holds a resident gradient of 2.38 GB from the start, while the old probe's peak moment hadn't finished producing the gradient yet; S1 also removed the longest event's full-position logits, 9,504 x 151,936 x 2 bytes = 2.89 GB. These three terms total about 4.3 GB, 0.7 GB off from 5.04; the logs have no moment-by-moment breakdown, so this can't be resolved further.

Fourth, recommendations for the probe. Decision 25 uses "fullest block x 1.1, then apply the fragmentation discount" as a lower-bound estimate, and this round's numbers support it: 4.1 / 54.4 = 7.5%, within the 1.1x margin. Correcting this round's probe with the same formula: 54.38 + 1.83 x 2.752 - 2.7 x 0.352 = 58.5 GB, 0.1 GB off from the measured 58.47. The "longest event" probe can be dropped, replaced by the block with the most loss positions.

### 9.5 Second question: the probe's `cost` block-picking method

Below is the interpretation. `cost` mode, without coefficients, running only two blocks, will miss the true peak on epoch 0, but not by much, and a third block closes the gap. 9.2's enumeration gives a counterexample: without checkpointing, the highest-cost block is 16,384 tokens plus 4,271 loss positions, which is neither the "block with the most tokens" the script would pick (16,384 plus 2,249, estimated 54.9 GB) nor the "block with the most loss positions" (12,736 plus 5,696, estimated 52.2 GB); the true peak of 58.5 GB is 3.6 GB (6%) higher than the larger of those two. With checkpointing on, the loss-position term dominates (1.8 MB versus 0.21-0.60 MB per token), so the block with the most loss positions is the highest-cost block, and the two-block mode doesn't miss it. The miss happens because there are 8 blocks tied for the most tokens (all 16,384 tokens, loss positions ranging 1,649 to 4,271), and which one the script picks depends on sort stability. Two fixes, neither needing coefficients: when picking the block with the most tokens, break ties toward more loss positions; when picking the block with the most loss positions, break ties toward more tokens; then add a third block, whichever maximizes "token count / max token count + loss-position count / max loss-position count" (on epoch 0 that's 15,360 plus 4,992, estimated 57.3 GB). Each of the three blocks is measured under "state already built, two backward passes back to back," with `worst` taking the max of the three. Checked against 9.1's five sets of coefficients over the 1,577 blocks: the max of the three blocks equals the linear model's max under all five sets (zero difference); picking only two blocks without the tie-break rule undercounts by 7.6% for 0.6B without checkpointing (the activations-plus-loss-positions term, 44.0 against 47.7 GB), 5.4% for 1.7B without checkpointing, 1.7% for 4B with checkpointing, and 0 for 0.6B and 1.7B with checkpointing. The "longest event" item doesn't need to run separately under `cost` mode: since real physical blocks are enumerated, the longest event either already sits inside some block, or becomes its own block when the budget is smaller than its packed length -- both cases are covered by the enumeration; epoch 0's longest event (9,492 tokens, 1,344 loss positions) doesn't rank in the top three under any coefficient. Enumeration should use the same path as the training loop: `random.Random(SEED + ep)` shuffle, slice into logical mini-batches by `events_per_mb`, `chunk_by_budget`; when `--epochs` is greater than 1, enumerate each epoch separately and take the union (a few seconds on CPU). The `tokens` mode is kept as a conservative upper bound: a block made of the two longest events in the full set isn't a real block, and its token count can only be larger than any real block's.

I see six pitfalls in `loop` mode, the third of which applies to all three modes. First, `sch.step()` must not be called: calling the scheduler consumes a step, and with only 25 warmup steps, one fewer step is 4%. Second, the zero-lr `opt.step()` writes the real gradient into AdamW's two states and increments the `step` counter to 1, so `opt.state.clear()` is required after the probe (the current `run_mem_probe` line 299 already does this); the `weight_decay` term `p.mul_(1 - lr x wd)` is a no-op at lr = 0, leaving parameters unchanged. Third, randomness: LoRA dropout at 0.05 consumes the CUDA random stream during the probe's forward pass, so every subsequent layer's dropout mask in real training would then differ from a run without the probe (Qwen3 has no dropout, so only `--lora` is affected); all three modes should save and restore `torch.get_rng_state()` and `torch.cuda.get_rng_state()` around the probe, while `random.Random(SEED + ep)` is a separate instance and unaffected. Fourth, the peak counter should `reset_peak_memory_stats` right before the chosen update group's first forward pass, and be read after the second logical mini-batch's last block's backward pass -- reading it after `clip_grad_norm_` or after `opt.step()` gives the same result (`max_memory_allocated` is the high-water mark since the last reset, unaffected by subsequent frees; with the state already pre-built, `opt.step()` allocates nothing further). Fifth, at the end, `opt.zero_grad(set_to_none=True)`, or the accumulated gradient would carry into the first real update. Sixth, `loop` only runs one group, and the second logical mini-batch's resident gradient during its backward pass is the same condition as `cost` mode's "two backward passes on the same block back to back," so `loop` can't produce a number for the true peak that `cost` can't; the only thing `loop` adds is allocator behavior from changing block shapes, and one group of two mini-batches can't reveal fragmentation (the 14.58 GiB reserved-but-unallocated in that ctool OOM built up over the whole run). So my recommendation is that `tokens` and `cost` are both required, with `cost` as the default, and `loop` can be skipped; if it is done, write it per the six points above, and define the group-picking rule as "the group containing the highest-cost block."

One more thing, unrelated to the probe but in the same section of code: the probe runs after `lora_util.wrap` and `gradient_checkpointing_enable` (`main()` lines 657-663 come before line 750), so what it measures is the form actually used in training; the probe running after wrapping and checkpointing is already the correct order in the current code.

### 9.6 Third question: the cost of bringing back generation-based evaluation

Below is the interpretation. One round of 200 greedy generations on H100, converted from the eval script's measurements, takes: a per-8-entry-batch median of 2.5 to 4.4 seconds, an overall rate across the four base models of 1.57 to 2.02 entries per second (9.3), so 200 entries at 25 batches, by overall rate, is 100 to 130 seconds. Base-model size barely affects the overall rate (l4 1.57 against b06 1.70), showing that bs-8 token-by-token decoding is timed by kernel-launch count, not FLOPs. Conditions inside the trainer differ from the eval script in three ways: fp32 weights under autocast and inside `no_grad` means autocast's weight cache doesn't take effect, re-converting all 28 or 36 layers' seven weight tensors to bf16 every step (seven extra launches per layer, about 20% more); under `--lora`, the adapter isn't merged, so each linear layer has two extra small matrix multiplies plus one scale and one add (seven modules per layer, nearly doubling launch count); the prompt is left-truncated to `max_len - 96`, i.e. 8,096 tokens rather than 4,000, doubling the prefill (on 4B, a batch of 8 x 8,096 tokens of prefill is about 0.5 PFLOP, about 1 second). The minute figures above are estimates extrapolated from the eval script's rate; the actual numbers inside the trainer will only be available once the first run with `--gen-n` has run. ### 9.7 Fourth question: the learning-rate grid

Below is the interpretation. First, compute three anchor points. The old trainer updates once per 32 rows (`--bs 4 --accum 8`), 5,828 updates per epoch; the new trainer updates once per 8 events, averaging 361 rows (186,415 / 516), 516 updates per epoch -- 11.3x the rows and 1/11.3x the updates. The first anchor is "batch size doesn't affect the optimal learning rate," i.e. the old value, 1e-5. The second anchor is Adam's common square-root rule, scaling the learning rate with the square root of the batch-size ratio; the square root of 11.3 is 3.4, giving 3.4e-5; the survey notes section 2.4's citation of Measuring the Effects of Data Parallelism says verbatim that no rule for scaling the learning rate with batch size is reliable, and it needs retuning whenever the batch size changes, so the square root is only a rough order of magnitude. The third anchor is equal total displacement: the integral of learning rate over update count determines how far the parameters travel along the average gradient direction; the old schedule (17,484 steps, warmup 874, linear decay to 0) has an epoch-0 integral of 4,653x its peak, while the new schedule (516 steps, warmup 25, linear decay to 0) has a whole-run integral of 258x its peak, a ratio of 18.0 -- for the new trainer to cover in one epoch the same ground the old trainer covered in epoch 0, its peak would need to be 1.8e-4; the old b06 cgen's `val_ce` was lowest at the end of epoch 0 (0.4793, rising over the next two epochs), showing the displacement near the end of epoch 0 was already enough for the old trainer, with further movement overfitting. The three anchors span an 18x range, so a 5x-span grid (draft 2.3's {1e-5, 2e-5, 5e-5}) only covers the first two anchors, leaving the third outside the grid; conversely, covering only the third anchor doesn't work either, because the 361 rows in one update come from the same batch of 8 events, with rows sharing prefixes and highly correlated targets -- the effective independent sample count for the gradient sits somewhere between 8 events and 361 rows, so the noise-scale reduction is less than 11.3x, and the square-root rule could either overestimate or underestimate.

Recommended grid: full-parameter {1e-5, 5e-5, 2e-4}, LoRA {1e-4, 5e-4, 2e-3}, with each of the four base-model configurations using the set matching its training method, not varied by base model. How the three full-parameter points were chosen: 1e-5 is the old value and the first anchor, 2e-4 is the third anchor (1.8e-4 rounded), 5e-5 is the log-midpoint (the geometric mean 4.5e-5 rounded, also covering the neighborhood of the square-root anchor at 3.4e-5); the span is 20x, with adjacent points 4-5x apart, matching the survey notes' observation that adjacent steps in sweep-type sources run 2-5x (SDFT's {5e-6, 1e-5, 5e-5} itself has one 5x step). The three LoRA points were obtained by multiplying each of the three full-parameter points by 10, per the survey notes section 2.2's two empirically measured 10x relationships (LoRA Learns Less and Forgets Less, LoRA Without Regret); the resulting three pairs, (1e-5, 1e-4), (5e-5, 5e-4), (2e-4, 2e-3), let us directly test whether the 10x relationship holds on this data; the currently used 2e-4 falls between 1e-4 and 5e-4, within one step of both ends; 2e-3 falls within the 1e-5 to 3e-3 range swept by Beware of the Batch Size, and is the LoRA point most likely to diverge -- divergence itself is also an answer (an upper bound), and one run only costs an hour or two. The reason for not varying by base model is the same as the 08-21 ruling: change only one variable, the base model; survey notes section 2.7's width-based rule (LoRA's optimal learning rate scaling with width to the -1/2 power) gives a ratio of 0.63 from 0.6B to 4B, and muP's 1/width rule gives a ratio of 0.5 from 0.6B to 1.7B -- both smaller than one grid step (4-5x); torchtune's recorded 5e-6 for 4B full-parameter doesn't apply here, since this round's 4B is LoRA. Difference from the minimal-version grid: the minimal version's {1e-5, 2e-5, 5e-5} and {1e-4, 2e-4, 5e-4} both step up one or two notches from the old values with a 5x span, reasonable when the update unit hadn't changed; once the update unit changed, the third anchor falls outside the minimal version, so the grid span widened from 5x to 20x, with the top end raised from 5e-5 to 2e-4 and the bottom end keeping the old value as a control. The judging rule, decided in advance: if the best point lands at an edge of the grid (1e-5 or 2e-4), add one more notch on that side (3e-6 or 5e-4); if it lands in the middle, the sweep is considered complete.

Two side notes. Warmup at 25 steps is much shorter than the old 874 at 2e-4; spec section 5's 5% stays unchanged, but the step logs have no gradient norm; `clip_grad_norm_`'s return value should be recorded in the `step` event, since only the logs can show whether the high-learning-rate configuration is being clipped constantly. Selecting the best version uses whichever of the four evaluation points has the lowest `val_ce`; under a schedule that linearly decays the learning rate to 0, the fourth point is likely the lowest, and the four points' curve is itself the basis for interpreting the grid, so it should be kept in `train_log.jsonl`.
