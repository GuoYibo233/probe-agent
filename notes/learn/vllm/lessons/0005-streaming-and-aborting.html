Hanging up the connection is telling the server to stop computing

The live run driver implements intervention with this one move: receive streamed text, and the moment the probe fires, close the connection, edit the prompt, and send it again. This lesson makes clear that the server side really does stop, and the two costs this move pays.

What our code looks like

Plain urllib, no SDK used. close() is just self.resp.close() (L173–177). The outer loop uses it like this:

Within one step, several streams may open. Each time it reopens, the prompt is "the original prefix + what has been written so far (as edited)."

Does the server side really stop: yes

Client disconnects → the generation coroutine gets cancelled → execution reaches this except → abort gets called. This path is written explicitly in the source, and the comment spells out the trigger condition too. So close() is not just us no longer listening on our side; the request on the server side is actually torn down, and the KV slot is freed.

But our logs cannot prove this. The logger.info("Request %s aborted.") line above sits behind if self.log_requests:, and that switch defaults to off — engine/arg_utils.py:2724, enable_log_requests: bool = False. I grepped for aborted in the logs of three services, zero hits. That is "logging wasn't turned on," not "abort didn't happen." To see it with your own eyes, add --enable-log-requests when starting the service.

The first cost: for the aborted segment, the token count is estimated

We added stream_options={"include_usage": True} to the stream; on a normal finish, one last chunk carrying usage data arrives at the end. If it hangs up midway, that chunk never arrives. The code handles it exactly like this:

"One chunk ≈ one token" is an empirical assumption, and the comment itself flags it as an "approximation." For any step where injection happened, its gen_tok has an estimated value mixed into it. This needs to go into the methodology notes — on the token-savings axis, part of the numerator was not actually counted.

The second cost: the resent segment is actually cheap

Back to Lesson 2. When the stream reopens, prompt = prompt_head + raw — the large preceding segment was just computed, and it is still warm in the KV pool. Prefix caching picks it up directly, so the cost of resending is only the small segment that is genuinely new.

The two costs point in opposite directions; do not net them against each other. Computationally, resending is cheap (prefix hit); on the books, the aborted segment's token count is estimated (no usage). The former is performance, the latter is methodology. The report should keep them separate.

This text has already cost compute, it just did not make it into the final text. The code is right to record it separately in discard — counting it as "tokens saved" would be padding results with what got thrown away.

Practice

No scrolling back up. A wrong answer gets feedback immediately, and each question locks once answered.

1. If the connection is closed partway through a stream read, what happens on the server side?

Correct. async_llm.py:587-594: disconnecting gets the generation coroutine cancelled, and execution reaches the except block that calls abort.

It does not keep computing for nothing. The source code has an abort path specifically for this case (async_llm.py:587-594).

It does not throw an error. This is a normal path, handled as the client actively aborting.

2. Our logs have not a single aborted entry. What does that show?

Correct. That log line sits behind if self.log_requests:, and enable_log_requests defaults to False (arg_utils.py:2724).

That cannot be concluded. The logging switch is off, so this log does not record whether abort happened at all.

It is supported. 0.26.0's abort path is right there in async_llm.py:587-594.

3. For the aborted segment, how is the number of generated tokens obtained?

Correct. live_appworld.py:317 uses st.n_chunks; the comment itself flags it as an "approximation," because the usage chunk never arrives.

If it hangs up midway, the chunk carrying usage never gets sent at all. That is exactly why it falls back to approximating from chunk count.

The code does not do that. It uses the number of delta chunks received.

4. After injection, when the whole prefix is resent, where does the main cost fall?

Correct. prompt = prompt_head + raw; that segment was just computed and is still in the KV pool, so prefix caching picks it up directly (Lesson 2).

It does not recompute the whole segment. Prefix caching is on by default, and the segment just computed gets reused directly.

It has nothing to do with temperature. What decides it is whether the prefix is in the KV pool.

5. How should the text discarded after the cut point be accounted for?

Correct. The code records it in discard (live_appworld.py:297-298). Having been generated means it was spent, it just didn't make it into the final text.

That is padding results with what got thrown away. These tokens really were generated.

What the resend makes up is new content, not this discarded text. Its compute cost does not come back.

Three things to do before touching streaming code next time

  1. Confirm whether your usage is complete or estimated. On any path that might hang up midway, the final usage chunk will not arrive, and the books must flag which values are approximations.
  2. To see with your own eyes whether abort happens, add --enable-log-requests when starting the service, then: 
    grep -c "aborted" <log>
    Without that flag turned on, a zero-hit grep does not mean anything.
  3. Keep discarded generated content in its own column; don't fold it into "tokens saved." The two numbers represent opposite things in the report.
