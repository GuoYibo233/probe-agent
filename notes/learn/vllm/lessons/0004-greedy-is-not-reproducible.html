Lesson 0004 · vLLM 0.26.0

temperature=0 does not mean verbatim reproducibility

Set temperature to 0, and the sampling step really does lose its randomness. But running the same prompt twice can still produce different text, because the requests batched alongside it changed. This lesson digs the fact out of the source code, then looks at the rules our repo already wrote for it.

What temperature=0 actually does

Below 1e-5, the temperature switches everything to greedy mode, and the other three sampling parameters get overwritten to "no filtering" along with it. Greedy mode itself is one line:

Take the max, no draw. So seed has no effect on this path, the random number generator is only used on the random-sampling branch (sampler.py:288). Our client code has in fact never passed a seed.

So where does the nondeterminism come from

Not in the sampling step, in the step before it: the forward pass that computes the logits. 0.26.0 admits this itself, in the environment variable table:

Read that comment backwards: without turning it on, the result is not "independent of batch composition." The default value is "0", meaning off. We have never set this variable.

What batch composition is. At every step vLLM gathers whichever requests are currently running into one batch and runs the forward pass on them together. Which requests get pulled in, and how long they are in total, decides the shape of the matrix multiplication; when the shape changes, the order floating-point numbers get summed in changes, and the last digit drifts a little. Most of the time the difference gets swallowed by argmax, but where two candidate tokens' scores are nearly tied, that last-digit difference is enough to flip argmax. Flip it once, and the rest of the sequence branches off from there.

And what decides batch composition? How much concurrency you open, what else is running on this server at the same time, when requests arrive. None of that is in your request parameters.

Two rules our repo already wrote for this

1. The nofill arm is a health-check line only, not the primary control pipeline/inject/replay_inject.py

2. Every point on one curve must use the same concurrency pipeline/inject/sweep_theta.py

So sweep_theta uses the same --concurrency for all six θ points. This is not fastidiousness: for two points at different concurrency, the difference between them has jitter mixed in that has nothing to do with θ.

Do not cite the two together. The measured number in sweep_theta.py:39–48 — that running the same batch twice produced different calls in 14/1061 cases (1.3%) — measures the probe's 0.6B-parameter pipeline, which uses HF batch inference, where the mechanism is that left-padding length varies with batch size. It is the same class of phenomenon as the vLLM case, not the same measurement. We have not run a controlled measurement on the vLLM side.

So what actually is reproducible

Breaking "reproducible" apart, we already have an example on hand (the same sweep_theta.py comment, from the 2026-08-01 two-run comparison):

This layerResult across the two runs
Set of events the probe fires onZero difference
Position of the triggering sentenceZero difference
DepthZero difference
Tool-level predictionZero difference
Confidence value446/1061 differ at the 7th decimal place
The full call as written out14/1061 differ

From pipeline/inject/sweep_theta.py:39–48. The comment explaining the confidence-value row says: the reduction order of CPU softmax varies with thread count; it does not change any firing decision.

The pattern is clear: the discrete decision layer holds up under reproduction, continuous numeric values and long-range generation do not. Reporting numbers along this split is more honest than a blanket statement like "it uses greedy so it's reproducible."

Practice

No scrolling back up. A wrong answer gets feedback immediately, and each question locks once answered.

1. When temperature=0, what effect does seed have?

Correct. Greedy mode is just logits.argmax (sampler.py:240-241); the random number generator is only used on the random branch.

Temperature 0 goes through argmax; there is no draw step at all (sampler.py:240-241).

How the batch is formed is decided by the scheduler and concurrency, not seed.

2. Running the same prompt twice gives different results. Where does that originate?

Correct. Batch composition changes, the matrix shape changes, the accumulation order changes, and the last-digit difference flips argmax where scores are tied.

Temperature 0 has no random sampling. The branch happens at the step that computes logits (see the comment at envs.py:600-602).

Decoding is deterministic. The problem is in the earlier forward computation.

3. What is the default value of VLLM_BATCH_INVARIANT in 0.26.0?

Correct. The default string at envs.py:602 is "0". Reading its comment backwards is the whole point of this lesson.

The default is "0" (envs.py:602). Getting that guarantee requires setting it yourself, and requires compute capability ≥ 9.0.

It is not automatic. It just reads an environment variable, defaulting to "0".

4. Why must all six points on a θ curve use the same concurrency?

Correct. sweep_theta.py:19-22 hardcodes this rule: once batch composition changes, greedy continuations get numerical jitter, and mixed into the curve that becomes a heterogeneous point.

GPU memory is not the reason for this rule. The reason is that a changed batch composition introduces jitter that has nothing to do with θ.

The context limit is set by the server, and has nothing to do with client-side concurrency.

5. Which pipeline does that measured 14/1061 divergence measure?

Correct. 0.6B, HF batch inference, left padding varies with the batch (sweep_theta.py:39-48). Same class of phenomenon, not a measurement of vLLM.

No. We have not run a controlled measurement on the vLLM side; do not carry this number over to use there.

Environment replay has been checked step by step; that pipeline has its own fidelity check.

Three things to do before reporting "reproducible" next time

  1. Say clearly which layer is reproducible. The discrete decision layer (firing events, trigger position, tool-level prediction) and the long-range generation layer reach different conclusions; mixing them into one sentence is a false report.
  2. Write concurrency into the report, alongside temperature and max_tokens. It is a hidden variable right now, but it does change the result.
  3. If you actually need a verbatim-reproducible control, first confirm whether the card's compute capability is enough, then consider turning on that switch: 
    nvidia-smi --query-gpu=name,compute_cap --format=csv
    envs.py:601 requires ≥ 9.0. Once that is satisfied, then talk about VLLM_BATCH_INVARIANT=1 — it has a performance cost, and whether it is worth it depends on what you need it for.
