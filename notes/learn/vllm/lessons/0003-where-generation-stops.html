Which character it stops on is decided by two mechanisms

One works at the token layer, one works at the text layer. The two trigger under different conditions, and the text-layer one gets quietly disabled by another flag. Our collection line has exactly this kind of stop string, and it has never once taken effect.

The last row on the right is the whole point of this lesson. Broken apart below.

A stop string compares against "the decoded text"

It compares against self.output_text, a string accumulated token by token. So how does this string get built up:

The decode stream is built carrying skip_special_tokens. This value defaults to True, stated in two places: the engine side sampling_params.py:295, and the HTTP interface side entrypoints/openai/completion/protocol.py:82.

Consequence: under the default setting, special tokens never enter output_text at all. So a stop string made up of special tokens, things like <|im_end|> or <|return|>, can never match. It does not raise an error, it is simply a no-op. Making it work requires also giving skip_special_tokens=False.

Our two lines: one gave it, one did not

Inject line: gave it pipeline/inject/replay_inject.py

This one gave everything it needed, so the stop string can match. As a side note, <|return|> also happens to be gpt-oss's EOS (tokenizer_config.json's eos_token is exactly this, id 200002), so here both mechanisms are managing it at once.

Collection line, raw mode: did not give it envs/collect/common.py

No skip_special_tokens=False, so following the consequence above, this stop string is a no-op on the server side.

So why didn't collection break? Because there is another mechanism backstopping it: the engine automatically adds the model's EOS token id into the set of stop tokens.

One thing I cannot verify. This backstop only holds if <|im_end|> really was that batch of Qwen models' EOS. Those weights are no longer under /net/…/models/ (only gpt-oss-120b and Qwen3-0.6B-Base remain now, and the latter's eos_token is <|endoftext|>). So I can only say "the stop string is a no-op," I cannot determine for you that "generation definitely stopped in the right place." Next time you start a Qwen service, verify this yourself; the method is in the last section.

Whether the stop string ends up in the output

Not included by default. When a stop string is hit, output_text gets truncated to just before the stop string (detokenizer.py:138–140). So the text you get back does not show that string, not because the model didn't write it, but because the server cut it out.

finish_reason has only five values

ValueMeaningWhere we use it
stopHit a stop token or a stop stringNormal completion
lengthmax_tokens ran out, or hit the context limitreplay_inject.py:1050 counts truncated cases with it
abortClient aborted (covered in Lesson 5)When the live-run driver interrupts and resends
error / repetitionEngine error / repetition detection triggeredNot handled currently

The value stop by itself does not tell you which one was hit. To know which, look at the response's stop_reason, when a stop string is hit it is that string, when a stop token is hit it is that id (outputs.py:46–47).

Three things to do before changing a stop condition next time

  1. Ask yourself: does my stop string contain a special token wrapped in angle brackets? If so, you must also give skip_special_tokens=false, otherwise it is a no-op.
  2. Verify what the model's EOS actually is, do not rely on memory: 
    python3 -c "import json;print(json.load(open('<weights dir>/tokenizer_config.json'))['eos_token'])"
    That is exactly what the backstop relies on. If the EOS does not match and the stop string is also a no-op, generation really will run all the way to max_tokens.
  3. Store finish_reason in the output. It is the only after-the-fact basis for judging "did this one finish normally or get cut off," and it cannot be recovered afterward.

Read this one first: vLLM SamplingParams, look only at stop, stop_token_ids, skip_special_tokens, and include_stop_str_in_output. ⚠️ Defaults are as given by the local envs/vllm-env/…/vllm/sampling_params.py.
