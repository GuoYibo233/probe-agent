Lesson 0001 · vLLM 0.26.0

A service's real settings live only in the startup log

The command line records what you intended. The log records what actually happened. The two often disagree, and when they disagree nothing raises an error. This lesson teaches you to read five things out of a startup log, then practice on the real numbers from our own four services.

Why learn this first

Your four goals, judging whether a configuration is correct, picking the right features for the next batch, stating settings clearly in the paper, and understanding the existing code, all start with the same first step: being able to state a service's real settings right now. That does not come from the command line. It comes from the startup log.

The command line falls short for three specific reasons. First, any flag you did not write still has a default value, and that default changes across versions. Second, vLLM decides some things for you automatically (which parser to attach, how long the context is), and none of that shows up on the command line. Third, some flags you do write get ignored, the fifth log line below is one example.

Five log lines, five things

Everything below comes from the same file: new1_diag_srv_a.log, the startup at 2026-08-02 17:08, gpt-oss-120b running on tokyo108 GPU 0. The number on the left is its line number in that file.

1. What I actually passed in

vLLM only prints arguments that differ from the default. This service's command line clearly has --gpu-memory-utilization 0.92, yet this line does not show it, because 0.26.0's default already is 0.92, so writing it changes nothing. This line is the fastest way to check for "I thought I changed this, but I didn't."

2. What the context limit ends up being

This service was not given --max-model-len, so vLLM took 131072 automatically from the model config. That was deliberate: that batch of experiments needed to reproduce the exact configuration used during the w0 collection run, and the reason is written at the top of envs/serve_logs/launch_vllm_awdiag.py. Another batch of services from the same period was given 65536 instead. Same model, two different settings, and the data they produce cannot be compared directly.

3. How the GPU memory got split up

The whole card is 93.1 GiB. At 0.92 it claims 85.65 GiB, of which the weights take 61.43 GiB, leaving 20.45 GiB as the KV cache pool. The "KV cache pool" is the GPU memory the service uses to store context it has already computed, it decides how many requests this service can hold at once.

4. How much the pool holds, and how many it can hold at once

These two lines are the most important ones in the whole log. The first line is the pool's total capacity, counted in tokens. The second line is its direct consequence:

Concurrency limit = KV pool capacity ÷ per-request context limit

528,934 ÷ 131,072 = 4.04

The log prints exactly 4.04x. This is one division, and you can verify it yourself. It means: if every request used the full 131072-token context, this service could only serve four of them at once.

So the number in line 2 is not arbitrary. Double the context limit, and concurrency is cut in half.

5. Some flags you give are given for nothing

vLLM states plainly that it ignores this flag. Line 14 of the same log also shows it automatically attached reasoning_parser='openai_gptoss', neither of these two facts appears anywhere on the command line.

The one thing to do next time you start a service

  1. Once the service is up, pull these three lines from the log and paste them into your experiment record: 
    grep -E "Using max model len|GPU KV cache size|Maximum concurrency" <log>
  2. Work it out by hand: KV pool ÷ context limit, and check whether it equals the concurrency multiplier the log prints. If it matches, you read the right lines.
  3. Compare that concurrency multiplier against the number of client shards you actually launched. If the shard count exceeds it, the extra requests queue instead of running in parallel.
