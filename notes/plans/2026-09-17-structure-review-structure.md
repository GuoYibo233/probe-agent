## (1) Verdict

The tree is a real improvement on today's: it collapses eleven batch configs (pipeline/configs/), four collection manifests, twenty-two placement JSONs (ops/*_placement.json), seventeen vLLM launchers (envs/serve_logs/launch_*.py), thirty-three shell launchers (ops/ro1_launch/) and the two cell tables in run.py into settings YAML plus one launcher, and it puts the AppWorld import behind one object instead of the two files that hold it today (live_appworld.py, exec_calls.py). Its weakest point is that it reintroduces, under new names, the two files that have cost the most since 08-20: the 1,293-line shared trainer (16 commits, the most-edited code file) becomes train/utils/trainer.py with more duties (resume, the prediction run) and an alignment gate whose reference implementation the fourth draft deleted, and the cgen/cparam pair becomes four near-identical files after the packing module they share today (share_data.py) was removed. Three of the eight code directories hold two kinds of thing (data/ holds live benchmark adapters beside on-disk formats; jobs/ holds a launcher, a ledger writer, four subcommands and the git-tracked ledger; models/ holds two sides that share only a table), and the two files the plan itself expects to outgrow their name (schema.py, registry.py) have their split lines already visible in today's code. Principle 7 (eval reads disk only) is applied without settling who chooses the row at which cgen and cparam generate, which is either a large GPU cost or a missing edge in the stage table. None of this needs a fifth draft of the whole tree; the fixes below are file moves, four splits, one merge, a few renames and five lines the tree forgot to write.

Today's pain points, in one block. Fixed by the plan: two isomorphic tables drifting (run.py CELLS imported by ops/launch_probe.py; LEDGER_PATHS copied in run.py, ops/record.py, ops/runmeta.py; the call regex in pipeline/inject/parse_call.py duplicating pipeline/annotate/rules.py AW_CALL; the harmony system message hand-assembled in envs/collect/common.py beside pipeline/inject/harmony_render.py); configuration spread over six places; the appworld import confined to two files with a jsonl hand-off between venvs; per-batch launch scripts; the mbert/cprobe two-venv rule; two cut rules (offline thinned to 64, live unthinned); the copied-verbatim spines of eval_causal_call.py / eval_causal_param.py and train_causal_tool.py / train_causal_share.py. Carried over under a new name: the shared trainer as the largest and most-edited file; the "heavy imports inside functions" device for crossing venv boundaries (today share_data._lazy_imports, lora_util's peft note, readonly_map; in the plan both service.py files and gptoss.py); the cgen/cparam duplication. Forgotten (no line in the tree): the sampler and its verdicts, the offline replay line, the dirty-tree gate, CONTEXT.md, the 34 existing test files, and where RESULTS.md sits relative to the other three ledgers.

## (2) Problems, ranked by six-month cost

1. `train/utils/trainer.py` — a god file with an alignment gate that has nothing to compare against.
   Why it hurts: the plan lists eleven duties on one line (settings to arguments, seed, backbone, tuning, checkpoints, metrics, heartbeat, resume, the alignment gate, the prediction run over val and test, the continue-from-checkpoint rule). This is /home/y-guo/reproduce/new1/pipeline/train/train_causal_share.py renamed and enlarged; that file already has 30 top-level functions and took 16 commits in four weeks. Worse: the fourth draft says the gate "compares" but dropped `reference.py` ("the row-by-row loss lives in the deferred test") while `tests/` is "empty for now", so the gate in the tree has no reference to compare the packed loss against, and the "alignment test, run per method" that is supposed to catch a fix missed in one method file does not exist either. Today the reference is the 600-line old row-wise trainer (train_causal_callgen.py), which is exactly what the plan is deleting.
   Alternative: split at the seams today's code already has. `train/trainer.py` (optimizer, schedule, steps, metrics.jsonl, heartbeat, best/ and last/, resume at the same commit), `train/tuning.py` (full vs LoRA wrap and merge-on-save: today's stable /home/y-guo/reproduce/new1/pipeline/train/lora_util.py, 156 lines, 2 commits), `train/predict.py` (the last step: load the probe still on the card, write one prediction row per val/test example; it is a program with its own resume point, so it deserves its own name), and `train/reference.py` back (the plain one-example-per-sequence loss, no loop, about 100 lines) as the thing the gate and the future test both compare against. reference.py is the one place where "shared before the third repetition" is as justified as the plan already grants probe_models/base.py.

2. `train/methods/cgen.py`, `train/methods/cparam.py`, `eval/methods/cgen.py`, `eval/methods/cparam.py` — the principle-5 versus principle-6 trade is decided the wrong way for this pair.
   Why it hurts: today cgen and cparam are one trainer (`--mode`) over one packing module, /home/y-guo/reproduce/new1/pipeline/train/share_data.py (611 lines, 6 commits since 08-20, its rules frozen in .scratch/kvshare-train/spec.md). The plan un-shares it into two copies and says so: "a fix in one is repeated in the other and the alignment test ... catches the one that was missed" — a test that does not exist. Principle 5 ("share on the third repetition, and only when it has stopped changing") is a rule against extracting code that is still moving; here the shared code exists, has stopped changing, and is being split into two 600-line copies whose only difference is the instance string and the target. The eval side is the same: "exact match of the generated call" and "exact match of the generated arguments" are one function with a column name. Two near-copies with a nonexistent guard is the copy-paste disease the plan was written to end.
   Alternative: bring back `train/packing.py` (examples sharing a prefix packed into one sequence with the block mask, batches by token budget; the third draft's file). Then `train/cgen.py` and `train/cparam.py` each hold what actually differs: instance strings, target, loss positions, validation. On the eval side, one `eval/exact_match.py` with the target column chosen by the method (or two 30-line files if gyb wants the name pair; the cost is then small). If gyb prefers no shared packing at any price, the honest alternative is one method file `cgen.py` with a `probe.target: call | arguments` axis in schema.py, which removes cparam as a separate method rather than duplicating it.

3. The stage table (`experimental_settings/schema.py`) and `train/utils/trainer.py`'s prediction run — principle 7 leaves the fired row unchosen.
   Why it hurts: the tree says eval/methods/cgen.py reports "exact match of the generated call at the frozen theta", and theta is fitted by eval/methods/ctool.py on a ctool run, on the CPU, after training. Today /home/y-guo/reproduce/new1/pipeline/eval/eval_causal_call.py generates once per event, at the first row crossing ctool's theta. In the plan the prediction run inside train does not know theta, so either it generates greedily at every row (rules.py caps rows at 64 per event, so the bound is 64 times today's generation count), or the cgen train stage must name the ctool eval run whose theta picks the row — and the stage table has no such edge (the third draft's table gives eval only "the train key" as upstream; inject is the only stage that names two probe runs). This is both a GPU-hours decision and a hole in the key chain (principle 2): a cgen number depends on a ctool run that is not in its key.
   Alternative: make the dependency explicit the way inject already does. A cgen/cparam setting in train_probe.yaml carries `probe_score: train_probe/ctool_on_qwen06`; the stage table gives train(cgen) that upstream and folds its key in; predict.py generates at the fired row (plus a fixed small set of fractions if the curve is wanted) and writes the ctool score beside the generated text. If instead gyb wants generation at every row so that any theta can be scored later, the plan should say so and state the cost.

4. `experimental_settings/schema.py` — three edit triggers in one file, and it is the file every extension touches.
   Why it hurts: the plan's own test for each entry is "what operation edits this file", and schema.py answers with three: a new field or axis value (every new hyperparameter, environment, method, format, tuning), a stage-table change (a stage's inputs, program, venv, what enters the key), and a loader change (merge order, debug overlay, overrides, references, sweep expansion, diff, key). With two agent sessions working in worktrees (the 2026-08-28 precedent in memory), this is the file that conflicts. run.py has the same shape in miniature: "edited when a subcommand is added or the stage walk changes" is two triggers, and the stage walk is what /home/y-guo/reproduce/new1/pipeline/driver.py (1,615 lines) is today.
   Alternative: `experimental_settings/schema.py` (sections, fields, defaults, axes: what a setting is), `experimental_settings/stages.py` (the stage table and the per-stage key rule: what a stage consumes), `experimental_settings/load.py` (file to setting: merge order, debug overlay, overrides, references, sweep expansion, diff). For run.py, keep it a CLI and put the walk (each stage's directory, its status, the next action) in `jobs/walk.py` the moment it passes about 150 lines; better to name that file now than to add a "the day it grows" clause.

5. `jobs/registry.py` — the plan admits the split and postpones it; the split is needed on day one.
   Why it hurts: "the day ls or kill needs more, the subcommand half becomes registry_cli.py". ls already needs more today: /home/y-guo/reproduce/new1/ops/gpu_jobs.py probes tmux liveness over ssh per host (live_sessions) and reads the sampler's latest.json; that is 529 lines beside record.py's 339. Putting both in one file means the file every stage imports changes at the reader's frequency.
   Alternative: `jobs/ledger.py` (stdlib, the writer: rows, lock, meta.json, heartbeat) and `jobs/status.py` (ls/where/find/kill, tmux and server probing, the RESULTS.md render). Two files, two importers (stages import ledger.py, run.py imports status.py).

7. `models/table.yaml` — serving facts and identity in one row, both keyed; this is why the hook question is open.
   Why it hurts: "how it is served" (today's preset server block: host, port, gpu_memory_utilization, env LD_LIBRARY_PATH, extra_flags) enters the key, so moving a server to another host or changing the memory fraction gives every downstream stage a new key and forfeits every finished directory. Yet max_model_len does change results, so the row cannot simply be exempted. The row conflates two kinds of value, and constants/'s own definition ("nothing here enters a key") already has the right home for one of them. The open question ("does the read-only hook cover table.yaml") exists only because the table holds result-changing values outside experimental_settings/, contradicting that directory's definition ("everything in here changes a result").
   Alternative: the model table moves to `experimental_settings/models.yaml` (role, family or backbone, weights alias, context length, dtype: the fields that change a result, written by gyb, covered by the existing hook, keyed); serving location moves to `constants/models.yaml` (host, port, memory fraction, env vars per alias; never keyed) which absorbs path_models.yaml. models/ then holds only code, and the open question closes itself.

8. `data/environments/` — the wrong layer, and the prompt text is code with a hand-bumped VERSION.
   Why it hurts: data/'s own line says "Nothing else is added here; a new environment goes under environments/", which is the admission that environments is its own layer. Its callers are agent/loop.py, agent/inject.py and data/build_dataset.py; it holds the developer message, the no-code message, the call regex and the call syntax, none of which is an on-disk format. ## (3) What the plan gets right and must not be "improved" away

- The environment object owns the call regex, the call syntax, `speculate` with its snapshot/restore/clock guard, and `judge`; the loop calls eight methods and nothing else (today split across live_appworld.py and exec_calls.py).
- One generation path for sample and inject (the streamed completion with a seed); the chat endpoint survives only inside the render-equals-server check.
- `data/probe_input.py`: one cut rule and one assembly, used offline by build and live by inject (today two rules).
- Three on-disk formats defined once with a VERSION, read into Polars; consumers keyed on the manifest of what they consume, so a VERSION bump that changes no bytes stops there instead of cascading through days of training.
- eval/ reads prediction rows only, no torch: the direction is right even though item 3 must be settled.
- Output directories named by key, owners in meta.json; settings YAML written by gyb only and hook-enforced; sweep as a keyword instead of three sweep tools.
- constants/ holds nothing that enters a key (keep that definition exactly; item 7 moves things to honour it, not to loosen it).
- inject.step replaces generate.step instead of a switch inside it; inject_format.py stays a small table with the splice logic beside it.
- debug.yaml is sizes only, laid over any setting, applied before command-line overrides.
- Deleting the placement JSONs, the vLLM launcher scripts, pipeline/configs/, the collection manifests and the presets in favour of settings plus free-card picking.
- `run.py` as the single entry with no task registry and no recipe engine; the dirty gate as one function (once restored, item 10).
