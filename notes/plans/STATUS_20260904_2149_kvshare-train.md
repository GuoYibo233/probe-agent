First, pin down every name the whole document uses.

- The model being probed is gpt-oss-120b, and the task is AppWorld (a test environment where the model operates a phone app on the user's behalf). The collected trajectory batch is called the nyapass batch, directory name `nyapass_aw_v1`. An earlier batch is called the p1 batch: data directory `aw_p1_v1`, plus the probe directories trained from that batch's data (names starting with p1); none of these are in use any more.
- The probe is a separately trained, much smaller model that reads the part of the thinking text the probed model has already written and guesses the next tool call ahead of time. There are three kinds of probe: the one that only judges the tool type and decides whether to fire is called ctool; the one that generates the whole call string is called cgen (the training script's file name writes callgen, and eval run names write ccall; all three spellings refer to the same probe); the one that fills in only the parameters given the tool name is called cparam. The project calls these three cells.
- The probe's base model is from the Qwen3-Base family. The code names of the four base-model configurations (called configurations below): b06 is 0.6B full-parameter fine-tuning, b17 is 1.7B full-parameter fine-tuning, l17 is 1.7B LoRA, l4 is 4B LoRA. Full-parameter fine-tuning trains every weight in the base model; LoRA leaves the base weights untouched and trains only the small matrices attached beside the linear layers; full-parameter fine-tuning and LoRA together are called the two training methods. The p1 batch also has an l06 (0.6B LoRA), not used this week.
- Training data is split into three splits: the train split, the val split, and the test split, each a jsonl file. One line is one jsonl record: the probed model's thinking text truncated at some sentence boundary as a prefix, plus the ground truth (the `label_call` field, the call string the probed model actually issued next). The cut point is that sentence boundary. An event is the group of lines before the same tool call; an event's full text is the text of the longest line in that group (the line with the largest `sent_idx` field, `sent_idx` being the line's index within the event). A task instance is one AppWorld task, under which there are multiple events. After a line's text plus the separator string `\n[CALL] ` is tokenized, the leading part that matches the event's full-text tokenization is called the common prefix, and the few tokens from after the common prefix to the end of the line are called the tail; the target string is the ground-truth call string plus the end token; the target segment is the tail plus the target string. A loss position is a position in the packed sequence where cross-entropy is computed, that is, every token in the target segment; an event's number of loss positions equals its number of target tokens.
- This week's main subject is the cache-reuse trainer (file `train_causal_share.py`, shared by cgen and cparam; the data and tokenization parts are in `share_data.py`): an event's full text passes through the base model only once, and each cut point's target segment is appended after the common prefix to compute loss. The design document calls this "pack the prefix plus every target segment into one sequence for a single forward pass" shape A; shape B passes the prefix through once to get a cache, then has each row continue from that cache to compute its own target segment; shape B was only used for comparison, never put into training. The comparison point is the row-by-row trainer (`train_causal_callgen.py` and `train_causal_param.py`), where each row separately passes through the base model from scratch. ctool has its own trainer `train_causal_tool.py`, which is not the cache-reuse trainer, and it was also changed this week.
- A convention refers to one fixed set of training settings or generation settings. The new convention is the set decided on August 28: an event's full-text token cap is 8192 (called the cap below), and an event that exceeds it is dropped whole; 8 events per update; cgen and cparam each run 1 epoch. The old convention is the one np821's batch used: cap 4096, with anything over it left-truncated; 32 rows per update (the row-by-row trainer counts by row) or 32 events per update (the ctool trainer counts by event); 3 epochs. np821 is the twelve-cell probe (four configurations times three cells) launched on August 21 and wrapped up on August 26 (wrap-up means training and evaluation are both done and the books are closed). ks828 is the prefix that starts every run name this week (the batch prefix set in `TIMELINE.md` on August 28). A tier refers to one fixed set of run settings: the smoke tier, the speed tier, and the memory-probe tier are each one such set, with specifics given in each experiment's "How it was done."
- Quantities inside training: a logical mini-batch is the group of events fed into the trainer at once; "N events per batch" below means the logical mini-batch, which defaults to 4 for the cache-reuse trainer; accumulating M times means running M logical mini-batches in a row before updating parameters once, and the logical mini-batches accumulated into one update are called an update group; one update equals the optimizer updating parameters once, called one step in the logs, and `gstep` is the cumulative update count; a physical block is a segment of packed sequence cut from the logical mini-batch according to the token budget, and the number of events in one block is denoted B; the token budget (`--tok-budget`, default 16384) is the token cap after padding within one block, where padding means padding every event in a block with empty tokens out to the same length; the memory probe (`--mem-probe`) is a routine that, before training starts, picks a few of the physical blocks that use the most memory and runs a forward-plus-backward pass on each, recording the peak; there are three ways to pick blocks, tokens, cost, and loop (explained in experiment 5); the whole-run peak is the maximum of torch's allocated-memory peak across the step logs for the entire training run; the alignment check is a check done before training starts that feeds 6 short val events into both the cache-reuse trainer and the row-by-row trainer at the same time and compares loss row by row in fp32; the alignment gap is the row-by-row maximum absolute difference measured by this check, with a tolerance of 2e-5 (decision 18, origin in experiment 2); the alignment rule is the rule for whether the alignment check passes: abs looks at the absolute difference (the alignment gap must not exceed the tolerance), rel looks at the relative difference, and both requires both to pass; the gradient checkpoint (`--grad-ckpt`) is a switch that recomputes forward activations during the backward pass to save memory; validation cross-entropy is the cross-entropy computed on the val split (or a subset of it), log field `val_ce`; generative evaluation is an evaluation done during training that runs greedy generation on 200 rows of the val split and compares the call strings, with the whole-string exact-match rate being the ratio generative evaluation reports; saving the best version means saving a copy of the weights to `best/` whenever an evaluation's validation cross-entropy hits a new low.
- GPUs and machines: the cluster has four machines, tokyo105 through tokyo108; only two were used this week. tokyo108 has three H100 NVL and three H200 cards, tokyo107 has four RTX 6000 Ada cards (called Ada below). Launch commands are issued from the login machine shiga. NFS is the cluster's shared network drive, with paths starting with `/net/`; data and output both live there. `DATA.md` is the file in the repo that records data settings, and it has several data-integrity gate checks. Active means currently in use. Card capacity has two numbers: nvidia-smi reports H100 95,830 MiB, H200 143,771 MiB, Ada 49,140 MiB; torch reports H100 93.10 GiB, H200 140.4 GiB, and Ada's torch reading was not recorded, so the design document computes with nvidia-smi's 49,140 MiB. Both the trainer and the design document compute headroom using torch's numbers; headroom is the proportion of card capacity left after subtracting some peak (the whole-run peak, or the peak measured for a single block) from card capacity; card type refers to the GPU model; nvidia-smi is the memory-usage-viewing command that ships with the GPU driver. Memory numbers use two units: GB is decimal, used by the trainer log's `peak_mem_gb` field; GiB is binary, used by nvidia-smi, card capacity, du, and experiment 1's script's `peak_alloc_GiB` field.

### Experiment 1 · Attention kernel verification

What this experiment asks: which attention kernel shape A's packed forward pass uses on a real GPU, how much memory the longest event needs, and how much the row-by-row loss differs from the row-by-row trainer's. Kernel refers to one of the four implementations behind torch's `scaled_dot_product_attention` interface (called sdpa below): flash, mem-efficient, math, cuDNN.

How it was done: a verification script ran on one H100 on tokyo108, using Qwen3-0.6B-Base as the base model (script constant `MODEL`); the script picked out the longest event in the val split whose full text does not exceed 8192 tokens (the result JSON's `longest_event` key: `n_rows` 64 rows, prefix `P` 8,167 tokens, packed `L` 9,381 tokens), and ran nine steps in order (the script's `steps_done` field, a list recording which steps completed): step 1 asks each of torch's four kernels whether it accepts a mask of the real shape; step 2 forces the memory-saving mem-efficient kernel to do one forward-plus-backward pass, recording the peak and the kernel name; step 3 does it again without specifying a kernel, to see which one gets picked by default; step 4 measures the math kernel's peak on a short event, where a short event is built by taking only rows whose prefix does not exceed 2,048 tokens, truncating the prefix to 2,048 tokens, and packing rows one by one until the concatenated length would exceed 2,560, actually packing 42 rows for a concatenated length of 2,552 tokens (the `math_at_short_L` key's `n_rows` and `L`); step 5 records the peak for each of four mask formulations (a boolean mask is a true/false table, an additive mask is a table of 0s and added negative infinities; whether the length is padded to a multiple of 16, 16 being the multiple mem-efficient requires between mask dimensions in memory, design document 2.4); step 6, on another batch of 5 short events totaling 34 rows, subtracts the packed forward pass's row-by-row loss from the row-by-row trainer's, in bf16; step 7 does the same on the same batch of 5 events in fp32 (steps 6 and 7 are the prototype of what later became the trainer's alignment check: the trainer draws 6 events with a tolerance of 2e-5 decided later in decision 18, while here the verification script draws 5 events, 34 rows, with acceptance criteria of 1e-5 and 1e-4); step 8 turns on the gradient checkpoint and measures the longest event again; step 9 attaches LoRA and measures again. The row-by-row trainer has two ways of running: feeding one row at a time with no padding (called "single-row unpadded" below), or padding several rows in a batch to equal length on the right (called "batch-padded" below); steps 6 and 7 ran both ways. What is registered on the books is one run (start 09:16, finish 09:36); the launcher ran the script three times within the same tmux session (three logs, `.log`, `.r1.log`, `.r2.log`), and the ledger registers only once: the first time ran out of memory truncating the prefix at step 4, the second time reported "no available kernel" at step 6, and after the script was fixed, the third time all nine steps passed (the finish record's `conclusion` field is a one-sentence conclusion the launcher wrote, in the original words "three launches (step 4 prefix truncation OOM, step 6 GQA rejected, third launch all nine steps passed)"; GQA is grouped-query attention).

Why this design counts: only the forward pass's shape and kernel change; the model weights, the event, and the precision settings are all identical, so any difference in loss can only come from shape and kernel. The acceptance criterion decided before the run (design document section 5, written the morning of August 28) was that the row-by-row loss's maximum difference in fp32 must not exceed 1e-5, and the per-token difference must not exceed 1e-4; exceeding either would mean the mask or the position index (the position subscript each token gets in the packed sequence, letting each target segment follow its own common prefix) is wrong. The memory criterion was that the longest event's peak must leave at least 10% headroom on H100. What this design cannot control is the memory used when multiple events share one block, which had to wait for experiments 2 and 3.

One real sample: the raw record for step 2 (key `forced_efficient`) in the result file `pipeline/runs/smoke/kvshare_gpu_kernel_check/gpu_result.json` (NFS) is

```
"forced_efficient": {"L": 9381, "mask": "bool", "backends": ["EFFICIENT_ATTENTION"],
  "peak_alloc_GiB": 31.08, "delta_GiB": 28.86, "seconds": 2.96,
  "kernels": [..., "fmha_cutlassB_bf16_aligned_128x128_k128_sm80(...)", "fmha_cutlassF_bf16_...", ...]}
```

`L` is the packed sequence length, `mask` is the mask formulation, `backends` is the kernel this step restricted to (`EFFICIENT_ATTENTION` is mem-efficient), `peak_alloc_GiB` is torch's allocated-memory peak, `delta_GiB` is the peak minus the starting value right after the model is loaded, `seconds` is the number of seconds for this forward-plus-backward pass, and `kernels` is the kernel name the profiler recorded (cutlass is NVIDIA's template library, fmha is the fused attention kernel inside it, the F in the name is forward and B is backward, and the string after that is the kernel's shape parameters and GPU architecture code). In the same file, step 7's raw record is `"row_new_vs_old_batched": {"n": 34, "max_abs": 4.410743713378906e-06, "mean_abs": 1.65e-06, "p90_abs": 3.06e-06, "max_rel": 3.10e-06}`: `n` is the row count, `max_abs` is the row-by-row maximum absolute difference, `mean_abs` is the average, `p90_abs` is the 90th percentile, and `max_rel` is the maximum relative difference; `new` refers to the packed forward pass, `old_batched` refers to the row-by-row trainer's "batch-padded" run. The same step also has `tok_new_vs_old_batched` (the same four numbers per token) and `row_old_single_vs_old_batched`, `tok_old_single_vs_old_batched` (the row-by-row trainer's own difference between "single-row unpadded" and "batch-padded," called the baseline gap below). This run's commit is 024b34f, the machine is tokyo108 gpu0, torch 2.11.0+cu128, recorded in the same JSON's `torch` and `gpu` fields (torch version, GPU model) and in the directory's `RUNMETA.json` (launch command, commit, whether the working tree was dirty).

Experiment results (all numbers come from `gpu_result.json`; the finish record in `ops/runs.jsonl` copies the same figures):

- Kernel eligibility (step 1): with a mask present, the flash kernel refuses while mem-efficient and cuDNN both accept; cuDNN refuses when an fp32 query is paired with an fp32 mask; mem-efficient refuses when there is no mask and K/V has only 8 heads (Qwen3-0.6B has 28 layers, 8 K/V heads per layer).
- Forcing mem-efficient (step 2): the longest event's peak is 31.08 GiB, kernel name is cutlass's fmha forward and backward. Not specifying a kernel (step 3): peak 31.11 GiB, kernel name is cuDNN's sdpa forward and backward, the 64-row average loss is 3.2500 against mem-efficient's 3.2452.
- The math kernel (step 4) peaks at 22.55 GiB on a 2,552-token sequence, versus 10.37 GiB for mem-efficient on the same input.
- Among the four mask formulations (step 5), the bf16 additive one padded to a multiple of 16 peaks at 26.65 GiB, the other three at 31.11 to 31.20 GiB; all four give the same 64-row average loss of 3.2452.
- bf16 alignment (step 6, 5 events, 34 rows, 505 target tokens): row-by-row average difference 9.31e-3, maximum 3.07e-2.
- fp32 alignment (step 7, same batch): the packed forward pass's row-by-row maximum difference against the row-by-row trainer's batch-padded run is 4.41e-6, per-token maximum difference is 3.05e-5 (`tok_new_vs_old_batched`'s `max_abs`); the baseline gap is 5.01e-6 row-by-row, 6.91e-5 per-token.
- The gradient checkpoint (step 8) brought the longest event's peak down to 6.34 GiB; attaching LoRA (step 9) gives 31.18 GiB.

Configuration details: on the second launch, step 6 reported "no available kernel"; the design document section 7's readout is that the row-by-row trainer's "single-row unpadded" batch has no mask, so HF (HuggingFace's transformers library) keeps K/V at 8 heads using grouped-query attention, which the mem-efficient kernel does not support; the fix was to restrict only the packed-forward-pass path to the mem-efficient kernel (using torch's `sdpa_kernel` context manager, called the kernel context below), while the row-by-row trainer's path uses the default kernel. Design document section 7 goes on to infer, from step 1's kernel-eligibility result, that the "single-row unpadded" batch used the math kernel, not the same kernel as "batch-padded"'s mem-efficient, and that this is why the baseline gap is larger than the new-versus-old difference; this inference was not verified with the profiler. Also, this script has no optimizer state; training needs to add AdamW's two states on top.

Index: run_id `kvshare_gpu_kernel_check`; script `.scratch/kvshare-train/verify/gpu_kernel_check.py`; readout in design document section 7; decisions 17, 18 in the decision ledger.

### Experiment 2 · The first smoke test of the three cells plus a supplementary memory test for ctool

What this experiment asks: whether the cache-reuse trainer (the cgen and cparam cells) and the ctool trainer, changed in three places (overlong events switched from left-truncation to whole-event drop, the cap changed from 4096 to 8192, and the read position changed to the rule in spec 11.3: the read position is the token position ctool takes its hidden state from; the new rule takes the last token whose start position is before the cut point, and if that token crosses the cut point and the part it crosses is not whitespace, it backs off one and reads the token before it; "no read position found" means no token's start position is before the cut point, or backing off one would already be before position 0) run start-to-finish on a small sample of real data, and whether the alignment check passes for all three cells; and whether H100 has enough memory for ctool once truncation is removed and the cap doubles to 8192.

How it was done: each of the three cells ran one smoke tier (the cache-reuse trainer's smoke tier takes the 40 training events and 16 evaluation events with the shortest full-text token counts and runs 1 epoch; 40 events at 8 per update is 5 updates, with evaluation every quarter epoch for 4 total; ctool's smoke tier takes 200 training events and 80 evaluation events, and 200 at 8 per update is 25 updates), running in parallel on three H200 cards on tokyo108. Before the smoke tier, an alignment check runs first: the cache-reuse trainer draws 6 val events whose full text does not exceed 2,048 tokens, feeds the same temporary file to both the cache-reuse trainer and the row-by-row trainer at once, and compares loss row by row in fp32 with TF32 (a matrix-multiply speedup that reduces precision) turned off; ctool's alignment check compares a single forward pass over the whole sequence against an incremental per-token forward pass (feeding one new token at a time, with a cache), comparing the maximum absolute difference in the final hidden state and the classification head's logits. ctool's memory supplement was launched twice more on a separate H100, wrapped in a script that records one nvidia-smi sample every 2 seconds: the first run used the then-current default of 4 events per batch accumulated 2 times, the second changed to 2 events per batch accumulated 4 times.

Why this design counts: the smoke tier only checks "does it run, does it save, are the logs complete, does the alignment check pass," not whether the numbers are good; the alignment check's tolerance was set before the run (decision 18): 2e-5 row-by-row, derived from experiment 1's 4.41e-6 multiplied by 1.3, about 6e-6, then multiplied by 3 to round up to 2e-5; the 1.3 multiplier was estimated from how, on CPU, the maximum difference rose from 2.15e-6 to 2.62e-6 (a 1.2x rise) as the sample grew from 34 rows to 151 rows; decision 18 estimated the formal check would be about 380 rows and 7,000 target tokens, while in practice cgen came out to 154 rows and 2,877 tokens, cparam to 154 rows and 1,916 tokens; the per-token tolerance of 3e-4 comes from experiment 1's baseline gap of 6.91e-5 already being close to 1e-4, and since the maximum is likely to cross 1e-4 as the sample grows, 3e-4 still leaves a 30x margin from the gap seen when the mask is genuinely wrong (on the order of 1e-2). Spec section 9 states that the alignment check's purpose is to confirm that the loss computed by the packed forward pass and by the row-by-row trainer are the same function. ctool's two memory supplements differ in only one variable, events per batch; both use 8 events per update, so any difference in peak can only be attributed to events per batch. What this design cannot control is that the smoke tier only takes the shortest events, so neither the memory nor the speed numbers represent the full dataset.

### Experiment 3 · The speed tier

What this experiment asks: how many rows per second the cache-reuse trainer processes on H100, how much faster that is than the row-by-row trainer running the same number of rows on the same machine; whether a token budget of 16384 or 24576 is better; and whether PyTorch memory allocator's `expandable_segments` switch (letting the allocator extend an existing memory segment instead of opening a new one, to reduce fragmentation, fragmentation being scattered free memory that cannot be reused) helps. The speed tier is this set of settings: 450 events, one step log recorded every 3 updates, evaluation only at epoch end.

How it was done: all three runs are b06's cgen cell, randomly drawing 450 events from the train split with seed 42 (20,641 rows, 57 updates at 8 events per update), with the memory probe on; the three runs differ only in token budget (16384 or 24576) and the allocator switch, running in parallel on three H100 cards on tokyo108. Speed is looked at two ways in rows per second: cumulative rows per second is the cumulative row count from the start of the epoch to some row divided by the cumulative training seconds; window rows per second is the row count of some 1,600-row span divided by that span's seconds. The six comparison points are set by decision 9 and spec section 1: the cumulative rows per second at 1,600 / 9,600 / 19,200 rows, plus the window rows per second for three windows (0 to 1,600, 8,000 to 9,600, 17,600 to 19,200 rows); these three row counts are positions the row-by-row trainer's log has recorded, and 450 events was chosen to cover the 19,200-row point. The comparison numbers are the row-by-row trainer's figures at these six points, taken from np821b06's (np821 batch's b06 configuration) cgen log on the same machine (tokyo108) and same card type (H100): 2.76 / 3.26 / 3.97 and 2.77 / 3.94 / 6.24. The cache-reuse trainer only logs once every 3 updates, so its number at a comparison row count is obtained, per spec section 11's algorithm, by linearly interpolating in time between the two step-log entries whose cumulative row counts straddle the comparison row count.

Why this design counts: comparing at the same cumulative row count rather than the same update count is because every run of the row-by-row trainer on tokyo108 is slower at the start than later on (`plans/2026-08-28-plan.md` section 12.10: np821b06 cgen's window speed rises from 2.77 at update 50 to 10.4 at update 2,050); comparing only at update 50 would credit the cache-reuse trainer with speedup that is really just the row-by-row trainer's slow start (decision 9). The three runs share the same seed and the same event order, so the rows in each window are identical one by one, and any difference can only be attributed to the budget and the switch. The acceptance criterion set before the run (spec section 1) was that all six comparison numbers must exceed the row-by-row trainer's, and the whole-run peak must leave at least 10% headroom against card capacity. What this design cannot control is that 450 events are only 11% of the train split's 4,127 events (`DATA.md`), so the speed at the tail window is affected by the length of events in that stretch.

### Experiment 7 · Learning-rate sweep

What this experiment asks: after training switches to the new convention (cache-reuse trainer, 8 events per update, 1 epoch), which learning rate gives the four configurations the lowest validation cross-entropy on the cgen cell; and how many times apart the best rates for full-parameter fine-tuning and LoRA are.

How it was done: each of the four configurations swept three rates: full-parameter {1e-5, 5e-5, 2e-4}, LoRA scaled up 10x pointwise {1e-4, 5e-4, 2e-3}; the grid was set once per training method, not adjusted per base model (decision 29 settled two things: how to pick the grid, and the extension rule below); the grid is the set of three learning rates, and a grid edge is whichever of the three is highest or lowest. Each run is the cgen cell on the full train set (4,127 events, the figure from `DATA.md`; 4,126 events, 186,415 rows after dropping 1 overlong event), 1 epoch, 516 updates, computing a validation cross-entropy on the full val set (2,556 events, the figure from `DATA.md`; 2,553 events, 115,019 rows after dropping 3) every quarter epoch, plus greedy generation on 200 rows at epoch end reporting the whole-string exact-match rate, token budget 16384, memory-probe block-picking method cost. The learning-rate schedule is the curve the learning rate follows against update count: the new convention warms up over 25 updates to `--lr`'s value (the peak learning rate) and then decays linearly to 0 over the full 516 updates; the old convention warms up over 874 updates over a full run of 17,484 (design document 9.7). Card assignment followed decision 30: l4 with the gradient checkpoint on, on three H100 cards; b17 with the gradient checkpoint off, on three H200 cards, and once b17's three runs finished, l17 (gradient checkpoint off) followed on the same three H200 cards; b06 with the gradient checkpoint on, on three Ada cards. The first stage's 9 runs launched between 00:26 and 00:31 on August 29; l17's three runs launched between 01:32 and 01:33. Once all 12 finished, per the rule decision 29 had already written, "if the best point lands on a grid edge, sweep one more rate further in that direction" (sweeping further means running one more rate outside the grid), b06 and b17 each got an additional 2e-6 run (decision 40), launched between 02:49 and 02:50; b06's extra run ran on tokyo107 Ada gpu0, b17's on tokyo108 H200 gpu3.

Why this design counts: all 12 runs share the same seed, the same tokenizer, and the same budget, so the sequence of physical blocks in the first epoch is identical across all 12 runs (helper 2 enumerated this on CPU with `verify/enum_blocks.py`, `enum_blocks.json` recording 1,577 physical blocks), leaving no variable besides base model and learning rate; within the same configuration, the three rates are the only difference. How the three rates were chosen (design document 9.7): 1e-5 is the code's existing default for full-parameter fine-tuning (the old value decision 31 refers to), used as a control; 2e-4 comes from requiring "the new schedule's integral of learning rate over update count for one epoch to equal the old schedule's integral over its first epoch" (integral meaning summing the learning rate at every update); design document 9.7 computes the old schedule's integral at 4,653 times the peak learning rate and the new schedule's at 258 times, a ratio of 18; 1e-5 times 18 is 1.8e-4, rounded up to the whole tier 2e-4; 5e-5 is the two rates' logarithmic midpoint (geometric mean 4.47e-5, rounded). LoRA's code default of 2e-4 is not on the grid, falling between 1e-4 and 5e-4. The criterion, set before the run, is whichever tier gives the lowest validation cross-entropy at epoch end; the extension rule was also set before the run. What this design cannot control is two things: only 1 epoch was swept with the learning rate decaying linearly to 0, and whether the ranking would change with a different epoch count is not something there is data for; and only the cgen cell was swept, with cparam and ctool not swept (decision 31).

## Section 6 · My judgment

There is exactly one conclusion this week that holds up: the cache-reuse trainer can replace the row-by-row trainer. The reason is section 3's alignment table and speed table: the row-by-row loss difference is between 5.007e-6 and 1.5378e-5, rises monotonically with base-model size, and is bit-identical within the same configuration and card type; speed on the same machine's H100 is 23.3 to 67.8 times the row-by-row trainer's (section 3's speed table's multiple column, lowest 23.3 at the window 17,600 to 19,200 rows, highest 67.8 at cumulative 1,600 rows). This conclusion's scope is b06's cgen cell and a sample of 450 events; cparam has only smoke-tier numbers, ctool runs on a separate code path, and neither has a single number on the full train set.

The learning-rate sweep answers the question it was designed to answer, but only answers half of "whether to change the code default." Both full-parameter configurations' lowest point is 1e-5, matching the default, with both neighbors, 2e-6 and 5e-5, higher (b06 0.2157 / 0.1730 / 0.1857, b17 0.2046 / 0.1636 / 0.1750); both LoRA configurations' lowest point is 5e-4, 2.5 times the default of 2e-4, with both neighbors, 1e-4 and 2e-3, higher. So the decision "whether to change the default" really only concerns LoRA: for full-parameter, changing it or not gives the same result. This is the first of the nine items in 5.5, and until it is settled, every launch of formal training can only pass the learning rate explicitly (the second of those three options). l4's loss at 2e-3 rises to 4.2674 by update 70, is 1.0461 by update 250, and comes back to 0.5433 at the last entry, with 9 entries exceeding 5 times the median gradient norm; my judgment is that 4B LoRA's grid edge (the highest tier, 2e-3) is already at the edge of divergence, and there is no need to try higher than this tier.

I consider the memory-probe question already solved: the cost block-picking method's memory probe reads only 0.001 to 0.422 GB below the whole-run peak across the four configurations, while the 1.1x multiplier used for card assignment sets aside an extra 2.20 to 10.23 GB for each configuration (section 3's memory table, the "memory probe times 0.1" column); that extra amount is 5.2 times (b06) to 8,165 times (l17) the gap, with b17 at 222 times and l4 at 26.6 times (section 3's memory table, second-to-last column).
