# nyanpasu-probtest821 plan: build the pipeline program first, then use it to run the first temperature-1 batch

The plan splits into two blocks, construction and execution, done separately and accepted separately; if the construction block doesn't pass acceptance, the execution block doesn't start a single step. The ruling process and where convention changes came from are recorded in TIMELINE; this file only writes down how to do it.

## 0. Goal

On new data at temperature 1, 4 trajectories per task, equal weight per step, train three cells each for four backbone-x-training-method combinations and compare them side by side: 0.6B full-parameter, 1.7B full-parameter, 1.7B LoRA, 4B LoRA, with the cells being ctool, cgen, cparam. Temperature-1 numbers are not comparable to any historical temperature-0 numbers.

## 2. The pipeline program's shape: a resumable-from-checkpoint driver

One command, for example `python3 run.py pipeline --config <batch config>`. Every time it's run, it reads the state file on disk, decides which stage can move forward right now, advances one step, and exits: a stage that needs to launch a GPU task exits once launched (reusing the whole `launch` chain, probing the card, verifying it's alive, all three ledger entries, nothing skipped); running the same command again first probes whether the last-launched task is alive and whether it's finished, and once finished it passes the gate and moves into the next segment. State isn't lost when interrupted; if any step in the middle fails, fix it and run the command again to keep going.

The correspondence between the five stages and their gates: collection (G2 card probe, G3 service health, G4 one-task smoke, G6 completeness, G7 VRAM back to zero), annotation and dataset building (the cut-distribution stop point, G9 row count, gates A/B/D, G11 spot check, byte-for-byte reconstruction comparison), training (G1 hard-blocks a dirty tree, smoke per cell, G16 registration), evaluation (dependency order: ctool first, then cgen/cparam, dual-level risk), the matrix. If a gate doesn't pass, the driver stops right there and writes the reason into the state file.

The stop point is made an explicit state, `awaiting_decision`: the reason and the item awaiting a ruling are written into the state file; once a person rules on it, the decision is written into the batch config and the command is run again to continue.

## 5. Wall-clock and risk (projected, updated once measured)

Collection: p1 measured about 104 tasks per hour (two H200 instances), working out to about 52 tasks per hour per instance; four instances running 1260 tasks takes about 6 hours, and temperature 1's longer thinking can only make it slower. Sample size: if cut density is unchanged, the train split would be about 4 times p1's (p1's train split had 46438 samples).

Training: 12 training tasks against 10 cards, placement follows shortest wall-clock overall: ctool is cheap (p1's LoRA ctool wrapped up in 1.5 to 3.5 hours on an A6000), it finishes first and frees a card first; cgen and cparam are the long poles, given priority on H200 and H100. Full-parameter per cell runs from a few hours to about a day on big cards (scaling up proportionally once data multiplies by 4). LoRA speed has only been measured on A6000 (0.92 and 0.41 samples per second, projecting to 170 and 380 hours per cell once data multiplies by 4; running at that scale isn't viable), there is no measurement on big cards, ETA is re-scheduled after the smoke test, and if it's still not viable, stop and go to gyb.

Evaluation: about 0.5 GPU-hours for p1's one batch, on the order of 2 hours per batch once test events multiply by 4.

Four risks: the four trajectories of the same task might land two that are exactly identical, they are only counted, not deduplicated; the risk 0.05 level might come up unsolvable more often on the temperature-1 distribution than it did for p1 (p1b17 already fell back to the 0.10 level), the dual-level fallback is an established convention, not an incident; a free card is whatever a real G2 probe finds at launch time; tokyo107's driver only goes up to CUDA 12.2, but the cu128 wheel has been measured to run (`ops/gpu_state.md`'s pitfall 1 exception entry), and a real driver error will be dealt with if and when it's reported.

### 6.2 Implementation conventions newly settled during construction (not fixed in the plan's main text, worth focusing on when verifying)

- The multi-sample filename is `appworld_<tid>_r<k>.jsonl`, with k from 0
  to K-1; when `--traj-per-task 1` is given without `--seeds`, the
  filename and all behavior are byte-for-byte identical to the old
  version. AppWorld's experiment_name also carries a `_r<k>` suffix per
  sample: reading the appworld package's source
  (`environment.py`'s `_prepare_directories` does an rmtree on the
  same-named task directory when reopened), reopening the same
  (experiment, task) leaves no environment state but does overwrite the
  output directory, so isolation is required.
- ANNOTATE_REPORT's four new statistics are gated on whether the config
  has a `trajs_per_unit` key: the old config used by the two acceptance
  lines has no such key, which is exactly why its set of report lines
  matches the old version entirely; np821's config has `trajs_per_unit:
  4`, so its real report carries all four statistics. The
  step-count-cap statistic looks itself up per environment (appworld 30
  / alfworld 50), and prints "not applicable" for an environment not in
  the table.
- The G8 reproduction convention goes through build's CLI flags, not a
  new config file: the report embeds path strings for `config=` and
  `out=`, and moving to a config file would make those two lines not
  match, so byte-for-byte reproduction can only be run in place.
- Alongside loosening gate B, two more criteria were added: the K trajs
  of the same unit are all distinct from each other, and the sampling
  indices `_r0..r{K-1}` are all present. Missing even one (some
  trajectory produced not a single usable event) also hard-stops.
- Driver exit codes: 3 only means this run actually launched something;
  running the command again on an already-launched, not-yet-finished
  batch returns 0 (waiting, no relaunch); 4 is the a1 cut-cap stop point
  awaiting a ruling; 1 is a gate failure. The state file
  `logs/pipeline/<run_family>/state.json` carries a `launched` launch
  marker (if a batch is confirmed dead and needs relaunching, delete the
  corresponding marker first) and `manifest_sha1` (if the manifest is
  edited again after generation, it blocks c2/c5; `gen-launch --force`
  regenerates and updates the field).
- The actual reach of the seed switch: the SEED constant in `rules.py`
  and the three causal training scripts switches to 42 (training's
  torch.manual_seed and smoke sampling switch along with it, and the
  temperature-1 batch was never comparable to historical smoke anyway);
  `run_tau2.py`'s `--seed` default imports from `rules.SEED`, so it also
  becomes 42, and old tau2 runs that explicitly recorded their seed are
  unaffected. Eight places are left untouched (eval_tool, two mbert
  training scripts, four split generators, the old line's
  `envs/collect/build_dataset.py`), all recorded in the WORKPLAN
  write-back list; the construction-time inventory wrote it as seven
  places, missing build_dataset.py, corrected at the 2026-08-22
  acceptance check.

### 6.3 Three deviations from the plan text (all with justification)

- Change-list item 2 asked for `common.py`'s merge layer to accept seed:
  in fact only an explanatory comment was added, the code was not
  touched. The reason is that `run_tau2.py`'s `--seed` default is not
  None, and once the merge layer accepts seed, tau2's old command line
  would stuff the environment seed into the sampling request body,
  effectively changing an old path's convention. Per-trajectory seed
  dispatch is implemented on the collector side with a per-trajectory
  Chat instance, so nothing is missing functionally.
- The driver's t1_smoke only verifies the criteria, it doesn't launch:
  `launch-probe`'s smoke tier cannot pass `--base qwen17`/`--lora`/
  `--grad-ckpt`, so three of the four batches can't get a correct smoke
  command issued; it's better to be blocked and hand over a command
  skeleton than to issue one that silently runs wrong. When the
  execution block reaches this step, launch manually from the skeleton
  (or extend launch-probe first, a separate matter).
- §2 said the launch stage "reuses the whole launch chain: card probe,
  liveness check, all three ledger entries, nothing skipped." In fact
  the driver never calls `run.py launch`; launching is handed off to
  launch-probe / launch-eval and the batch's own launch_servers.py /
  launch_clients.sh, the card probe reuses launch's own probe_free, and
  the collection stage's three ledger entries are filled in by the
  driver's own register_collect; the run.py registry's stance on
  pipeline is exactly "an orchestrator, not a launcher." Card probing
  and the three ledger entries are both fully present, but launch's
  semantics of "don't register if the liveness check fails" doesn't hold
  on the training and evaluation launch paths: launch-probe /
  launch-eval register first and check liveness after, a liveness-check
  failure only prints, it doesn't block registration, and the exit code
  doesn't change; so after launching training and evaluation, the
  execution block has to confirm the process is alive via monitoring, it
  cannot trust the driver's exit code alone. The collection stage is
  unaffected, c3_health checks the startup marker plus an HTTP liveness
  probe, which checks more than launch's 30-second liveness window.
  (added at the 2026-08-22 acceptance check)
