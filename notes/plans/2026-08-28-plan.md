Mechanisms confirmed one by one in the discussion, one sentence each; all line numbers are in `train_causal_callgen.py`:

- Training data `train.jsonl` is grouped by event within the file, with the same event's rows kept together; for example, lines 1 through 19 are the 19 rows of event `appworld_07b42fd_1_r0|s0`, all sharing the same label, with each row's text a prefix of the next.
- Lines 433 through 436, `DataLoader(..., shuffle=True)`, draws a new random permutation every epoch, with the permutation's seed coming from line 224's `torch.manual_seed(42)`. The reason for shuffling is that file order would make one update's 32 samples come from the same one or two events, skewing the update direction; reshuffling every epoch keeps the batch-composition noise independent across epochs.
- Line 496 averages the per-sample cross-entropy of a batch of 4 samples into one number `loss`, weighted by `w`; in np821, `w` is always 1. Differentiation is linear, so the gradient obtained by backpropagating from the average equals the average of the per-sample gradients; averaging loses none of the information a parameter update needs.
- Line 243, `F.cross_entropy(lg[m].float(), tg[m], reduction="none")`, computes, for every answer-token position, the negative log of the probability assigned to the correct token; `reduction="none"` keeps the per-position values, and lines 245 through 248 then average per sample to get `ice`. The vocabulary size, 151,936, comes from the base model's `Qwen3-0.6B-Base/config.json`'s `vocab_size`.
- Line 505 calls `backward()` once per batch, accumulating the gradient into `.grad`; line 507 only executes lines 508 through 512's gradient clipping (norm capped at 1.0), `AdamW` update, scheduler step, and gradient zeroing once every 8 batches have accumulated. One update combines 4 x 8 = 32 samples.
- As long as the product of batch size and accumulation count stays the same (4 x 8, 8 x 4, 2 x 16), every sample's coefficient in the accumulated gradient is 1/32, the k-th update always covers samples 32k through 32k+31 in the random permutation, and the update rule is identical under exact arithmetic; the only differences are the coefficient of the last, underfull batch at the end of each pass, and floating-point rounding.

## VI. Proposal and interpretation

What follows is interpretation; the facts in the first five sections do not depend on this section.

gyb's proposal: the new version of training no longer truncates; set a token cap, max, and drop any sample whose total length exceeds max whole, counting it. This way every sample entering the model is complete, and the task instructions are never cut off the way left-truncation does now (the start of text is the `Task: …` line). This change also has the row-by-row cgen version and the event-packed version see exactly the same set of samples, clearing away the obstacle of inconsistent truncation semantics for the artifact's chapter 6 "proposal two: prefix-shared packing."

The pros and cons of the three cap candidates:

- 4096, whole-sample drop for overlong. By row, train drops 2.66%, test drops 5.07%; by event, train drops 8.85%, test drops 12.27%. Memory is unchanged, the smallest change. The cost is that everything dropped comes from the longest-thinking end, and test's drop ratio is twice train's.
- 6144, whole-sample drop for overlong (the number gyb first proposed). By row, train drops 0.29%, test drops 0.86%; by event, train drops 1.99%, test drops 3.50%. The batch on H100 has to drop to 2 with accumulation rising to 16; Ada 48G needs a fresh smoke test.
- 8192, whole-sample drop for overlong. By row, train drops 4 rows, test drops 218 rows (0.06%); by event, train drops 1 event, 64 rows, test drops 16 events, 1,024 rows. With so little dropped, the "drop by row or by event" disagreement nearly disappears. With batch-of-2 accumulated 16 times, the projected memory peak on H100 matches the current setup, and compute accounting shows 20% less than the current setup, with the utilization item needing smoke testing. Claude marks this "recommended," on the grounds that the dropped-sample count is an order of magnitude smaller and H100's memory peak does not need to change.

When the batch size changes from 4 to 2, the accumulation count must change to 16 at the same time; one update still combines 32 samples, one epoch is still 5,827 updates, and the learning-rate schedule does not need to change; if the accumulation count is not changed, one update would only have 16 samples, and that would really mean "less goes into a batch."

An independent fact noticed in passing: currently 43.3% of the compute is spent on pad positions, and grouping batches into length buckets could push this down; this has nothing to do with the cap and is a separate proposal, noted here only in passing.

### 8.3 Labels are extracted from the calls the model itself issues, with no human annotation

`build.py` lines 52 through 106's `jsonl_events` scans a trajectory file step by step. A trajectory file has one JSON line per step; a `type=gen` line carries `reasoning` (that step's thinking), and a `type=env` line carries `action` (the code block the model wrote) and `result` (the environment's return). In the AppWorld environment, a step becomes an "event" only when two conditions both hold: the regex `AW_CALL = apis\.(\w+)\.(\w+)\(` (`rules.py` line 60) can find a first call in this step's `action`, with the label being the string `apis.<app>.<api>` (`build.py` lines 76 through 81); and this step's `reasoning` length is at least `MIN_THINK = 40` characters (`rules.py` line 16). A step missing an env line stops the whole trajectory's scan at this step, and a step with an empty `action` is skipped. Each event also extracts the first call's parameters (`rules.first_call_named`), assembling two fields, `label_call = tool(k=v, …)` and `args_named`; these two fields are cgen's and cparam's targets, and ctool does not read them.

The vocabulary `tool_vocab.json` (`build.py` lines 386 through 388) is a count of tool names across all events, sorted descending by frequency. np821's vocabulary has 150 entries; the top three are `apis.api_docs.show_api_doc` at 5,994, `apis.supervisor.show_profile` at 2,554, `apis.api_docs.show_api_descriptions` at 2,416; 92 entries appear fewer than 5 times (`DATA.md` line 49). The vocabulary is computed from all events, including test-split events.

### 8.4 One event is cut into at most 64 samples, and every sample shares the same label

`build.py` lines 194 through 217's `make_samples` takes cut points on each event's full thinking text. The cut-point rule is in `rules.py` lines 22 through 40: at a newline, or at a position where `.!?` is followed by whitespace, plus the end of the full text; a cut point whose prefix, after stripping, is under 20 characters (`MIN_THINK // 2`) is dropped; when an event has more cut points than `max_bounds` (64 in np821's config), it is thinned by near-even spacing, always keeping the final cut point. `DATA.md` lines 42 through 43 record the untruncated distribution as p50 60, p90 246, max 842, with 47.8% of events having more than 64 cut points.

Each cut point produces one sample. A sample's `text` is assembled by `rules.assemble` (lines 48 through 55): the format is `Task: <task instruction>`, a `[HISTORY]` line, the last 3 rounds of `<action> -> <result, truncated to 400 characters>` (writing `(start)` when there is no history), a `[THINKING]` line, and then the full thinking text cut to this cut point as a prefix. `hist` stores only `(action, result)` pairs (`build.py` line 106); the thinking from earlier steps never enters text. A sample's `label` is this event's tool name; every sample from the same event shares the same label. Sample weight `w` is 1 in np821 (`weight_mode: uniform`). The remaining fields are `depth` (cut-point position divided by the full thinking length), `sent_idx`, `n_sents`, `event` (`<traj>|s<step>`), `traj`, `unit`, `step`. The split assigns task instances to the train, val (the official dev), and test splits according to the official task-list files, without shuffling; the program exits when a unit is not in any task list (`build.py` lines 347 through 354). np821's numbers are 1260 trajectories, 15,216 events, 693,583 samples; the train split has 90 instances, 4,127 events, 186,479 samples (`DATA.md` line 32 and lines 47 through 49).

### 8.5 The trainer folds samples back by event, and one event's full text passes forward only once

`train_causal_tool.py` lines 82 through 121's `load_events` groups samples back into events by the `event` field: the full text takes the `text` of the sample with the largest `sent_idx`, `y` takes that sample's label's index in `label2id`, and `bounds` is each sample's `(len(text), w, whether it is the final boundary)`. Randomly drawn samples from 50 events were asserted to have prefix-of-each-other text. A sample whose label is not in `label2id` is skipped (line 88); np821's vocabulary comes from all events, so no sample was skipped.

Lines 135 through 159's `collate` tokenizes a batch of events' full texts all at once, with `truncation_side` set to left and `padding_side` to right (`build()` lines 189 through 190), carrying `offset_mapping`. For each boundary, it finds the largest token index j whose character end position is less than or equal to the cut-point position, and records `(the event's index in the batch, j)`; a boundary that cannot be found after left truncation is skipped and counted, with the count written into the log's `n_bound_dropped`.

Lines 164 through 181's `CausalProbe` is the base model plus a linear head. `hidden()` calls `self.backbone(input_ids=…, attention_mask=…, use_cache=False).last_hidden_state`, returning a tensor of shape `[batch size, sequence length, hidden]`, with every token position in the sequence having a final-layer hidden state; the notation `h = self.backbone(**enc).last_hidden_state` cited in discussion corresponds to this function. `forward()` uses `h[rows, cols]` to pull out the vector at each boundary position, giving `[total boundaries, hidden]`, then passes it through `self.head`.

"One forward pass" means an event's full text runs through the base model exactly once, and from that pass you get the hidden state at every sentence-end position in the event. The base model is causal, with attention looking only leftward, so in the whole-segment forward pass, the j-th token's hidden state depends only on tokens 0 through j, the same number as the final-position hidden state obtained by feeding only the prefix 0 through j on its own. Lines 201 through 240's `align_check` verifies exactly this equality: it takes the val split's longest event's full text truncated to `--max-len`, and compares, element by element, the whole-segment single-pass final-position hidden state and logits (lines 213 through 215) against the result of pushing token by token to the last position incrementally with `past_key_values` (lines 217 through 224); training is only allowed to start if the maximum absolute difference is below tol, otherwise it exits with code 2. np821b06_gptoss_ctool's `ALIGN_CHECK.json` records PASS as true, tol 0.0003, `n_tokens` 4096, `maxdiff_hidden` 9.78e-5, `maxdiff_logits` 1.34e-5, `reldiff_hidden` 1.40e-6. Training and evaluation only use the whole-segment single forward pass; incremental forward passes appear only in this check.

### 8.6 The classification head is a linear layer, with the class count equal to the number of tools in the vocabulary

The classification head is `torch.nn.Linear(hidden, n_labels)` (line 171), one matrix plus one bias. hidden is the base model's `config.json`'s `hidden_size`: 1024 for Qwen3-0.6B-Base, 2048 for Qwen3-1.7B-Base, 2560 for Qwen3-4B-Base. n_labels is decided by lines 318 through 327: reading the data directory's `tool_vocab.json`, numbering `label2id = {tool name: index}` in json order, and building the head with `build(args.base, len(label2id), dev)`. np821's n_labels is 150, and `train_log.jsonl`'s start record's `n_labels` field is also 150. `label2id` is saved in `best/label_map.json` (lines 443 through 444), which the eval side uses to translate an argmax index back to a tool name. The `--readonly-env` switch at lines 296 through 299 folds the vocabulary down to that environment's read-only tools plus one abstain class; none of np821's four batches' ctool card-placement tables pass this flag, so `readonly_env` is null in the start record.

The head's output is one 150-length logits vector per boundary. During training (line 413), `CrossEntropyLoss(reduction="none")` computes one cross-entropy per boundary, with the target being the index of the tool this event actually called. During evaluation (line 252), argmax is taken as the prediction and compared against y.

### 8.7 What gets updated is the base model plus the classification head; the three cells each train separately

The base model and the head are updated together: one loss, one optimizer, one `backward()` call, with the gradient flowing back into both the head and the base model at the same time (lines 411 through 420). In full-parameter mode (np821b06, np821b17), `model.parameters()` goes into AdamW as-is, learning rate 1e-5 (`FULL_LR`, line 75). In LoRA mode (np821l17, np821l4), `lora_util.opt_params` (lines 120 through 127) only takes parameters where `requires_grad` is true, that is, the LoRA adapters on the base model plus the classification head, learning rate 2e-4; the base model's original weights are frozen. In both modes, the classification head is freshly initialized and fully trained.

ctool, cgen, cparam, the three cells, do not train jointly. Each of the three scripts loads its own copy of the base model with `from_pretrained`, trains separately, and saves its own `best/`; `launch_probe.py` runs one cell per card in one process, producing three directories, `<batch>_gptoss_ctool`, `_cgen`, `_cparam`. During evaluation, `eval_causal_call.py` reads the temperature and `chosen_theta` from `REPLAY_REPORT.json` via `--ctool-run`, reads `logits_test.pt` to replay each event's firing row, the first row to cross θ (file header lines 8 through 9), then loads the cgen model from `--cgen-run/best` (lines 587 through 593) to generate the call string at the firing row. ctool's classification head only decides which sentence to fire on; the call string is generated by a separate model, cgen or cparam.

### 8.8 One forward pass's unit is one event; only text is reused between consecutive steps

One forward pass's unit is one event, that is, one step in the trajectory, not the whole trajectory. np821's 1,260 trajectories produced 15,216 events, about 12 events per trajectory on average. During training, events are shuffled and batched 4 at a time per `--bs 4` (line 275, lines 365 through 368). The text one event feeds into the base model carries only the task instructions, the last 3 rounds of (action, return), and the current step's full thinking text; actions before those 3 rounds and thinking from earlier steps are not included. When the text exceeds `--max-len 4096` tokens, it is left-truncated, cutting off the beginning.

Step k and step k+1 are two independent events, each tokenized from scratch and forward-passed from scratch; the trainer's line 176 and the evaluator `eval_tool.py`'s line 139 both explicitly pass `use_cache=False`. There is no KV cache carried across events and no hidden state carried across events. The m sentence-ends within the same event share the attention computation over the common prefix, and that sharing happens inside one single call. The eval side's reuse is a different kind: `score_causal` computes logits once per row for val and test, saving them as `logits_val.pt` and `logits_test.pt`; fitting temperature, sweeping 20 θ tiers, choosing θ by risk tier, and `replay` simulating each event's first sentence-end to cross θ are all CPU post-processing that reads these two tensors, with the `--cached-logits` flag skipping model inference.

### 8.9 One update combines every sentence-end kept across 32 events

The training loop is at lines 404 through 429. Each mini-batch has 4 events, `loss = Σ(CE_i · w_i) / Σ w_i` (line 413); when w is always 1, this is the average cross-entropy over all sentence-ends in these 4 events. `(loss / 8).backward()` accumulates, and when `(i + 1) % 8 == 0`, `clip_grad_norm_(1.0)`, `opt.step()`, `sch.step()`, `opt.zero_grad()` run (lines 416 through 420). So one update's gradient is the average of 8 mini-batches' own "average sentence-end cross-entropy": sentence-ends are weighted equally within a mini-batch, mini-batches are weighted equally against each other, and an event with more sentence-ends takes up a larger share within its own mini-batch. The log writes one `event=step` every 50 updates, with the `loss` field being the average of these 50 x 8 mini-batches' losses.

The sentence-ends that enter the loss pass through two filters: the annotation-time cut-point rule (section 8.4's 20-character floor and 64-event cap) and training-time left-truncation (section 8.5's `n_bound_dropped`). np821b06_gptoss_ctool's start record writes `n_train` 4127, `steps` 387: 4,127 events at 4 per batch is 1,032 batches, and 1,032 divided by 8 is exactly 129 updates, 387 total across three epochs, matching `steps` exactly; this cell has no remainder of an underfull final batch like cgen did in section 2. cgen's and ctool's "32 per update" units differ: cgen counts by sample row, 32 rows per update; ctool counts by event, 32 events per update, with the number of sentence-ends per event not fixed.

### 9.5 The algorithm behind `group_by_length` (grouping batches by length) in transformers 5.14.1, and accounting simulated with the train set

`group_by_length` corresponds to `transformers.trainer_pt_utils.LengthGroupedSampler`, with the algorithm in the same file's `get_length_grouped_indices`; the original comment reads:

> Return a list of indices so that each slice of `batch_size` consecutive indices correspond to elements of similar lengths. To do this, the indices are: randomly permuted / grouped in mega-batches of size `mega_batch_mult * batch_size` / sorted by length in each mega-batch. The result is the concatenation of all mega-batches, with the batch of `batch_size` containing the element of maximum length placed first, so that an OOM happens sooner rather than later.

In other words: all rows are randomly shuffled first, then cut into large blocks of `mega_batch_mult x batch_size` rows each (`mega_batch_mult` defaults to 50, so at batch-of-4 one block is 200 rows); each block is sorted internally from longest to shortest, then cut into batches of 4 rows in order; the batch containing the single longest row is moved to the very front of the whole epoch. ## X. Round 3 interpretation, and four performance ideas (proposals)

What follows is interpretation and proposals; section 9's facts do not depend on this section.

### 10.1 Interpreting the smoke tests

There is no speed difference between the two card types: A is 2.75 versus 2.80, B is 1.45 versus 1.45; this 0.6B model computes equally fast on both card types, and the only difference is memory capacity (95 GB versus 143 GB).

What is slow is batch-of-2 itself, not the 8192 cap. On H200, with the same 8192 cap and the same 1,600 samples, batch-of-2 is 1.45 samples per second and batch-of-4 is 2.50, batch-of-2 being 42% slower; raising the cap from 4096 to 8192 while keeping batch-of-4 throughout is only 11% slower (2.80 to 2.50). Section 5's compute accounting said B computes 21% fewer positions than the current setup, the opposite direction: the padded position count cannot predict wall-clock time, and starving the card with small batches is the main cost (this mechanism has not been confirmed with a performance profile; the only number measured is this 42%). Converted to whole-run terms: np821b06's cgen took 24.4 hours with the current configuration; by the 1.45-to-2.75 ratio, batch-of-2 would take about 46 hours, and by the 2.50-to-2.75 ratio, batch-of-4 at cap 8192 would take about 27 hours; the absolute hour counts are only order-of-magnitude.

Memory does not grow linearly with per-batch token count. B's largest batch, 15,360 tokens, is fewer than A's 16,384, yet its peak is 90.9 GB versus 80.0 GB; a single sequence getting longer itself eats more memory. B leaves only 5.0 GB (5.2%) on H100, and the full-dataset worst-case batch needs 6.7% more tokens still; by the gpu-run methodology's rule that "under 10% headroom at smoke-test peak counts as not fitting," B cannot be counted as fitting on H100; C leaves 9.6 GB (6.7%) on H200, also below 10%. So of the three configurations measured, not one can run comfortably on H100 under the 8192 cap.

### 10.2 Idea one: reuse the KV cache for prefix sharing (proposed by gyb, no change to the attention implementation)

ctool currently runs one forward pass per event: the event's full text is fed into the model once, and the final-layer hidden state is read at each cut point for the classification head. Numerically this is identical to running each prefix separately, because of causal attention: position k's hidden state is determined only by tokens 0 through k. cgen needs one more step than ctool: each cut point k's target segment (median 20 tokens) must sit after prefix k, seeing only prefix k and its own preceding target tokens, never sentences after sentence k, so the 45 target segments cannot simply be appended after the event's full text and computed together.

The KV cache is the two sets of vectors, key and value, that each attention layer stores for tokens already computed; later tokens look these two sets up directly when computing attention. The approach: run the event's full text through one forward pass, keeping every layer's key and value; for each cut point k, feed only the target segment's roughly twenty tokens into the model, letting these tokens look up the cached key and value at positions 0 through p_k (p_k being prefix k's token length), with position indices continuing to count up from p_k. What the target segment sees is identical to running "prefix k plus target segment" on its own, giving the same loss position for position. Gradients can also flow back: the key and value in the cache are intermediate results of the event's forward pass, and that forward pass does not turn off gradients; summing the loss over all cut points and doing one backward pass sends the gradient flowing back through the cache to the shared prefix, so the prefix's backward pass is also computed only once.

The accounting (section 9.6): currently cgen computes 263 million real tokens per epoch, 456 to 474 million positions after padding; after switching to prefix sharing, the prefix part is 7 million plus the target segments' roughly 3.5 million, about 10.5 million total, 25 times fewer real tokens. The attention cost of target-segment tokens looking up the cache is linear in p_k, not counted in this accounting, and is much smaller than recomputing the whole prefix as is done now.

Implementation points: the attention implementation does not need to change, since sdpa already supports a forward pass with a cache; transformers 5.14's cache object `DynamicCache` is obtained from the event's forward-pass output, sliced by cut point into a view of the first p_k positions for the target segment to use, with the slice not copying the tensor and the gradient chain preserved; each cut point's target segment runs at batch size 1 in sequence, or the cache is trimmed shorter in order from largest p_k to smallest; the event's forward pass cannot be inside `no_grad`; one event's target-segment losses are summed and backpropagated only once (backpropagating each target segment separately would recompute the prefix's backward pass 45 times). Memory: at batch size 1 for one event, with a full text up to 8,192 tokens, the computation graph for 45 target segments has to be kept until the backward pass; the peak for a single 8,192-token event on H100 was not measured this time and needs smoke testing; short events (median 1,271) can put several events into one batch by token budget. This is exactly the artifact's chapter 6, "proposal two: prefix-shared packing"; the two rulings, 8192 and by-event drop, have already laid the groundwork it needs (the row-by-row version and the by-event version seeing the same batch of samples).

A convention change that needs gyb's decision: currently one update is 32 rows from the random permutation, coming from about 32 different events; once switched to counting by event, one update's unit is the event, and one event averages 45 highly correlated rows. To keep diversity within an update, several events must go into one update (for example, 8 events, about 360 rows), and both the effective batch size and the learning-rate schedule's total step count change accordingly. Each row's weight within an update can still be made equal (loss divided by the total row count in this update), but "32 rows from 32 events" cannot be preserved. The acceptance standard copies ctool's alignment-check line: randomly draw some events, compare the row-by-row version's loss against the cache-reuse version's loss row by row, and only allow it into training if the difference is within tolerance.

### 10.3 Idea two: `group_by_length`, grouping batches by length

This can be used directly: swap the trainer's lines 433 through 436's `shuffle=True` for `sampler=LengthGroupedSampler(bs, lengths=…, generator=…)`, with each row's length computed at dataset-construction time (currently the prefix is tokenized only inside collate, and that spot needs to move). By section 9.5's simulation, batch-of-4's pad drops from 44.4% to 3.4%, and the position count computed drops 42%; but the worst-case batch is still 4 times 8192, 32,768 tokens, exactly the same as random batching, because with a fixed batch size, the four longest rows eventually end up in one batch. So after grouping, batch-of-4 still OOMs on H100 the same as before, just moving from OOMing at a random moment to OOMing on the very first step; on H200 the headroom is thin. Grouping changes the average speed and memory, not the peak.

Convention change: one update's 32 rows now come from length-adjacent positions within the same large block, similar in length and mostly from later cut points of long events, no longer 32 random events; HF's fine-tuning default allows this, but it is a different convention from np821's. This does not conflict with idea one: if both are adopted, the object of grouping becomes the event (grouped by event full-text length).

### 10.4 Idea three: batch by token budget

gyb's principle is "pack as many into each batch as possible, but without blowing up memory." `group_by_length` only does half the job: same-length rows go together, but the row count per batch is fixed, so a batch of short rows still only holds 4. Batching by token budget sorts rows by length and then packs a batch until it hits a budget (say 16,384 tokens): a batch of short rows can hold a dozen or more, a batch of long rows only two. With the worst-case batch pinned by the budget, H100's memory peak becomes controllable; batches of short rows grow bigger, keeping the card fed. transformers has nothing ready-made for this; a batch sampler of a few dozen lines has to be written (`batch_sampler=`). Once batch size can vary, "32 rows per update" has to become accumulating by row count (updating once 32 rows have accumulated), with each row's weight normalized by the total row count within the update. This idea also applies once idea one lands, with the object of the budget becoming the token count of the event's full text plus target segments.

### 10.5 Idea four: the gradient checkpoint

`--grad-ckpt` is a switch the trainer already has: it does not store intermediate activations during the forward pass and recomputes them during the backward pass, trading compute for memory. np821's batch experience (`plans/archive/2026-08-22-np821-exec-worklog.md`) is that 1.7B full-parameter relies on it to fit on a 48G card, while 0.6B full-parameter without the checkpoint blows up all three cells on 48G. The time cost of the checkpoint under the 8192 cap has not been measured; if the cost is less than batch-of-2's 42%, then "batch-of-4 with the checkpoint" would be more worthwhile than "batch-of-2" on H100. Getting the numbers means two more smoke tests (C with the checkpoint, B with the checkpoint, both on H100, each to update 50, about 15 minutes).

### 10.6 One point not expanded in discussion: computing logits only at target positions

Section 9.4 recorded that `inst_ce` has the model compute vocabulary logits for every position across the whole batch (batch x sequence length x 151,936), then takes only the target positions. Each row has at most 160 target positions, and the logits at all other positions are computed and thrown away. Running only the target positions through the output layer could save this tensor and its backward pass, though how much needs to be measured. This point was not discussed with gyb in round 3, only noted here in passing.

### 12.2 How many events go into one update

cgen and cparam batch by row: `train.jsonl`'s 186,479 rows are randomly shuffled as a whole every epoch (`train_causal_callgen.py` lines 433 through 436, `shuffle=True`), 4 rows per mini-batch, 8 mini-batches accumulated for one parameter update, 32 rows per update. The train set has 4,127 events, averaging 45.2 rows per event, so 32 rows almost certainly come from 32 different events (computed from the distribution of rows per event, the expected count of two rows from the same event appearing in one update is 0.12). One epoch is 5,827 updates, and each event's 45 rows are scattered across roughly 45 of them.

ctool batches by event: one event's full text goes through one forward pass, with all cut-point positions in the event supervised together (`train_causal_tool.py` lines 135 through 159), 4 events per mini-batch, 8 mini-batches accumulated per update, 32 events per update. One epoch is 129 updates, 387 total across three epochs.

### 12.3 How each row's weight is normalized

Weight normalization has three layers, all inside `train_causal_callgen.py`.

The first layer is within a row. Lines 243 through 248 compute cross-entropy token by token over each row's target segment (the call string plus eos), then divide by that row's target-token count, giving one number, `ice`, per row. So a row's loss is "average per target token": in a row with a long target string (a call with many parameters), each token gets a smaller share of the gradient, while in a row with a short target string (a parameterless call, `apis.x.y()` plus eos), each token gets a larger share. Target-string length, per section 9.6's statistics: median 20, average 18.7, maximum 74 tokens (that statistic includes the `[CALL]` separator string).

The second layer is across rows. Line 496, `loss = Σ(ice_i · w_i) / Σ w_i`, and np821's `w` is always 1 (`configs/np821_gptoss.json`'s `weight_mode: uniform`, set as the long-term convention in TIMELINE 2026-08-21), so the 4 rows in a mini-batch are weighted equally.

The third layer is across mini-batches. Line 505, `(loss / accum).backward()`, weights the 8 mini-batches equally. Put together, each of the 32 rows in one update has a coefficient of 1/32.

What row-equal-weighting means at the event level: an event has as many rows as it has cut points, and 1,930 of train's 4,127 events (46.8%) hit the 64-row cap, while 227 events have 8 rows or fewer. So an event at the cap takes more than 8 times the share in the loss of an 8-row event. This is the direct consequence of the 08-21 ruling of "equal weight per step," and the trade-off made at the time is written in TIMELINE.

ctool's normalization is the same setup: one cross-entropy per cut-point position, averaged within a mini-batch and across mini-batches by `w` (always 1). An event with more cut points takes a larger share within its own mini-batch.

### 12.4 How many steps the learning-rate schedule is planned over

All three trainers use `get_linear_schedule_with_warmup(opt, int(steps * 0.05), steps)`, with `steps = ceil(number of mini-batches / accum) × epochs` (cgen lines 457 through 461, ctool lines 380 through 383). cgen's and cparam's `steps` is 17,484 (3 epochs), warming up over 874 steps and then decaying linearly to 0; the actual update count is 17,481 (already computed in section 2). ctool's `steps` is 387, warming up over 19 steps.

The learning rate's value at the best-checkpoint weights: all 8 cgen and cparam runs save their best at the end of epoch 0 (section 12.7), that is, at step 5,827, when the linear schedule's coefficient is (17,484 − 5,827) / (17,484 − 874) = 0.702, giving a full-parameter learning rate of 7.0e-6 and a LoRA rate of 1.4e-4. In other words, the weights used for evaluation were saved while the learning rate still had seven tenths of its peak, and the cool-down segment over the remaining 11,657 planned steps never acted on it. All four ctool runs' best are at the end of epoch 2, where the schedule has finished.

The learning rate is not written into the step event (a step event has only `ep`, `gstep`, `loss`, `ips`, with ctool adding `n_bound_dropped`); knowing the learning rate at a given step can only be done by computing from the formula.

### 12.5 How cut points land on tokens

Cut points are set at the character level: `rules.py` line 22, `SENT_RE = (?<=[.!?])\s+|\n`, with the cut point being `m.end()`, the end of the whitespace span after sentence-ending punctuation; a sample's `text` is `assemble(task, hist, think[:cut])`, carrying this whitespace at the end. Among train's 186,479 rows, the whitespace at the cut point is one space in 91,439 rows (49.0%), two newlines in 53,572 rows (28.7%), one newline in 35,316 rows (18.9%), no whitespace in 4,127 rows (2.2%, exactly one per event, the cut point at the very end of the thinking text), and three newlines in 1,368 rows (0.7%).

cgen hands `text + "\n[CALL] "` to the tokenizer. The actual tokenization (600 rows sampled from val) shows the seam as follows: for a row whose whitespace is one space, the sentence end splits into six tokens, `.`, `Ġ\n`, `[`, `CALL`, `]`, `Ġ`; for a row whose whitespace is two newlines, the text's two newlines merge with the separator string's newline into one token, `.\n\n\n`; a one-newline row merges into `.\n\n`; a no-whitespace row is `.\n`. In other words, the token right before `[CALL]` encodes which kind of whitespace sits at the cut point, with four whitespace kinds mapping to four different tokens, and the no-whitespace kind (`.\n`) appears in the training set only at an event's final cut point. The separator string's own trailing space is always a separate `Ġ` token, with the target string's first token following right after it.

ctool's read position: `collate` lines 144 through 149 take, for each cut point, "the largest token index whose character end position is ≤ the cut-point position." Actually tokenizing 400 cut points sampled from val, the tokens read are `.` 131 times, `.\n\n` 101 times, `".` 22 times, `?` 16 times, `).` 16 times, `.\n` 11 times, with the rest being a mix like `:\n`, `` `\n\n ``. The distance between the token's end position and the cut-point position is 0 characters 187 times (whitespace merged into the punctuation token) and 1 character 188 times (one space belongs to the next token). So what ctool reads is the sentence-ending punctuation token; when the punctuation is followed by a newline, the newline is inside this same token, and when it is followed by a space, the space is not. The eval side's `eval_tool.py`'s `score_causal` uses the same mapping (section 3), so training and offline evaluation agree.

## XIII. Round 4 interpretation and proposals

What follows is interpretation and proposals; section 12's facts do not depend on this section. Proposals are ordered by strength of evidence and benefit, each carrying a time cost, with costs computed on b06's one cell.

### 13.1 cgen and cparam train only 1 epoch, the schedule is planned for 1 epoch, and evaluation points are added within the epoch

The evidence is that all 8 runs in section 12.7 save best at epoch 0, plus section 12.10's 64%. This proposal, training only 1 epoch, is exactly the artifact "Training Step Machine"'s chapter 6, proposal one, marked as still awaiting ruling in section 7 item 7; now there are numbers from all 8 runs.

The change is three things done together. First, `--epochs 1`; `steps` automatically becomes 5,827, warming up over 291 steps, and the cool-down segment decaying linearly to 0 now lands on the weights used for evaluation (currently those weights are saved when the learning rate still has seven tenths of its value, section 12.4). Second, evaluate once every quarter epoch; otherwise training only 1 epoch would leave just one evaluation at the very end, and choosing best would degenerate into "save the last version," while training loss is already down to just 0.035 by 30% through epoch 0 (section 12.7), and there is currently no data on where within the epoch val_ce's lowest point falls. Third, switch evaluation to a fixed-seed subsample of val (say, 23,000 rows, one fifth) with a larger evaluation batch (evaluation stores no gradients, and `--bs 4` is training's memory constraint, unneeded for evaluation), compressing one evaluation from 34 minutes to a few minutes; keep one full-dataset val_ce at epoch end so the number stays comparable to np821's.

Time: b06's one cell goes from 17.5 hours to about 7 hours (epoch 0 includes the ramp-up segment); l17 on Ada goes from 98.7 hours to 33 hours; the 4 batches' 8 cells together go from 425 hours to about 150 hours.

Risk: val_ce's lowest point may fall earlier within the epoch than expected; evaluating every quarter can bracket it to within a quarter epoch; for finer resolution, the evaluation subsample can simply be shrunk further.

### 13.2 First pin down the ramp-up segment over the first 2,000 steps on tokyo108

Section 12.10's ramp-up segment appears both in training and in the first evaluation, only on tokyo108, with epoch 1 running at full speed from the start and the second evaluation also at full speed. The same batch of sequence shapes being fast the second time it appears fits the mechanism of "a one-time cost the first time a tensor shape is seen"; the most likely candidate is the CUDA caching allocator repeatedly defragmenting when memory is close to full (b06 full-parameter peaks at 80 GB on a 95 GB card, section 9.2; l17 peaks at 34.7 GB on a 48 GB Ada card, with plenty of headroom and no ramp-up). This is a hypothesis, without profiling data.

The verification method is a 30-minute smoke test: the same b06 cgen command plus the environment variable `PYTORCH_CUDA_ALLOC_CONF=expandable_segments:True`, run to step 300, comparing the six window speeds against np821b06_gptoss_cgen's log values of 2.77, 2.89, 3.22, 3.41, 3.65, 3.94. If the speeds match, it is not the allocator; if the speed is already close to 11 from the start, it is. Ruling 6 did not run this experiment at the time (`plans/archive/2026-08-22-np821-exec-worklog.md`), on the grounds that the time saved didn't match the 30-hour scale of the OOM scenario; the scenario now is different: once training is only 1 epoch, the ramp-up segment takes up three tenths of a run.

Benefit: about 2 hours saved per cell for b06, about 2.5 hours for b17, about 2.6 hours for l4, plus another 40 to 45 minutes saved on the first evaluation.

### 13.3 Add epochs for ctool

Section 12.8's 4 runs are still rising at epoch 2, and one ctool run only takes 1 to 3 hours. Changing to `--epochs 6`, b06's one cell takes about 2 hours, and the four batches' ctool total about 15 hours, enough to see at which epoch accuracy flattens out. ctool's schedule is planned over 6 epochs, warming up over 39 steps.

### 13.4 Sample only part of an event's cut points each epoch, and put more events into one update

Section 12.7's training loss already falls to 0.0085 within epoch 0, while each row is only seen once within epoch 0; the only explanation for this is that the same event's 45 rows share exactly the same target string (section 12.9): once the model has seen a few rows of an event, the same event's remaining dozens of rows have the same target string, so their loss naturally approaches zero; section 12.9's 525 target strings against 186,479 rows, and 90 task instances against 30 scenarios, amplify this repetition. I have no direct evidence that repetition is the main cause (confirming it would require separately logging the loss for rows that are "the first time this event is seen this epoch" versus "already seen"), but all 8 runs point the same direction.

If repetition is the main cause, then the current feeding method, "equal weight per step, all 64 cut points in," is trading 45x repetition for one epoch's worth of coverage. The fix is a training-time sampler: each epoch, randomly draw K cut points (say, 8) from each event, swapping to a different batch the next epoch, with the data file untouched. One epoch goes from 186,479 rows to about 33,000; training 5 epochs sees 40 different cut points per event, bringing repetition down from 45x to 8x. This fix also answers "how many events go into one update": once K is smaller, one update's 32 rows still come from about 32 events, the event count unchanged, with what changes being the cap on each event's share within one epoch (K rows). The 08-21 ruling's per-step equal weighting, in terms of the weight ratio between events (an event at the cap versus an 8-row event, 8x), gets flattened by K to 1x; this is a convention change and needs gyb's decision.

Time: b06 cgen's one epoch is about 5.17 x 8 / 45 ≈ 0.9 hours, and 5 epochs plus evaluation is about 6 hours, comparable to 13.1's one cell. This cut-point subsampling idea does not conflict with section 10.2's idea one (prefix sharing): once idea one changes the forward-pass unit to the event, K simply becomes the number of target segments fed into the loss per event.

### 13.5 Change within-row normalization to per-token

Section 12.3's first layer: each row first averages over target tokens, so a call with more parameters gets a smaller gradient share per token. cgen's and cparam's errors concentrate on parameters (the results report, section 3.2: b06 cgen tool_ok 0.9057 versus params_all_ok 0.8702, cparam pred_tool 0.9529 versus 0.9026). Switching to summing all target tokens within one update and dividing by the total token count is a one-line change (`inst_ce` returns sum and count, and line 496 changes to divide by the summed count). The direction cannot be predicted in advance; OLMo 2's table 17 shows sum beating mean by 0.1 to 1.5 points on SFT (literature survey section 2.1), so it would take one cell's experiment to find out. Time: b06 cgen's 1 epoch is about 7 hours.

### 13.6 A three-point learning-rate sweep

The literature survey's section 4 concludes that no source has swept the SFT learning rate on Qwen3-Base, and LoRA's 2e-4 against full-parameter's 1e-5, a 20x gap, is higher than the literature's 10x rule of thumb. The relevant facts visible in np821 are: 1.7B full-parameter's val_ce (0.512) is higher than 0.6B full-parameter's (0.479), and 1.7B LoRA's (0.381) is lower than 1.7B full-parameter's (0.512). Both the 0.512-versus-0.479 gap and the 0.381-versus-0.512 gap could come from the learning rate, or from LoRA's capacity limit, and these cannot currently be told apart. Once 13.1 lands, one cell only takes 7 hours; sweeping {5e-6, 1e-5, 2e-5} on b06 cgen is 21 GPU hours, and sweeping the same three points on b17 is 36 hours; both groups fit within a single day on tokyo108's six cards as they are now.

### 13.7 Two log corrections and one field

Section 12.6's `run` accumulator has its denominator misaligned at epoch boundaries; the root-cause fix is to move `run`'s zeroing from the start of the epoch to right after the log is written (that is, zeroing only after `gstep % 50 == 0`). Add an `lr` field to the step event. Neither the accumulator's zeroing position nor the lr field changes any numeric value; both only change the log.

### 13.8 Whitespace at cut points: training and offline evaluation agree, but live runs need to align

Section 12.5: the token right before cgen's `[CALL]` encodes the whitespace kind, and the shape `.\n` appears in training only at an event's final cut point (2.2%); the punctuation token ctool reads merges in the newline when one follows. Training and offline evaluation go through the same character cut-point-plus-retokenization process, so this batch's numbers have no problem. In the future, when a live run has the probe fire at gpt-oss's sentence-end token and hands the prefix text to the Qwen tokenizer, whether the prefix is cut right at the punctuation or after the whitespace will decide whether the seam token is `.\n` or `.\n\n\n`; 49% of cut points are a space and 29% are two newlines, and the two correspond to different tokens in training. The prefix-truncation method does not need to change now, but when the live-run code fixes its prefix-truncation method, it must align with the distribution in section 12.5.
