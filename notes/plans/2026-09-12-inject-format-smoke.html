Four Ways to Hand Back a Result

When the probe predicts the agent's next tool call, the system runs it early and pushes the result into the agent's token stream. This page shows the four formats that were tried, what the model actually wrote after each one, and what to change next.

The loop, step by step

The agent (gpt-oss-120b on AppWorld) thinks in sentences before writing code.

At every sentence end, the probe reads the thinking so far. When it is confident about the next call, it fires.

The predicted call runs in a saved copy of the world; the world is then restored. The result is captured, errors included.

The call and its result are inserted into the token stream at that sentence end. Text the model had already generated past that point is thrown away.

The model keeps generating from the inserted text. What it does next is the whole question.

The step in which the model is asked to keep going, and the result never became a tool call it had to wait for, is where tokens and a round trip can be saved.

Two places the result can go

P1, inside the thinking. The result is appended right after the model's last sentence, and the model continues the same thought.

…We need to gather all songs in the libraries. [Prefetch: … result …] (model continues thinking)

P2, after the thinking is closed. The thinking is ended with the model's own end marker, a message from a sender named prefetch is appended, and the model is handed the turn again. It chooses whether to think more or to act.

…We need to gather all songs in the libraries. <|end|> <|start|>prefetch to=assistant … result … <|end|> <|start|>assistant (model chooses: think again, or code)

Crossed with two ways of explaining the mechanism to the model: E1, one sentence inline every time; E2, one paragraph in the system prompt, and only a marker inline.

What this smoke cannot tell you

  • No performance number exists yet. "Works" means task success no lower than the chat baseline and fewer billed tokens than the no-probe control, over many tasks. Neither control ran here.
  • The trigger was fake. Every arm fired at the third sentence of every step, whatever the probe's confidence. So the inserted call was often not the call the model was about to make, which is why "re-issued" is low everywhere for a trivial reason.
  • Two tasks. Enough to see mechanism, not enough to see rates.

What it can tell you: nothing broke in any arm; every arm let the model read and use the result; one arm, the bare marker inside the thinking, gets imitated.

Advice: three changes before the real run

Decision 1 · which formats go forward

Scenario. The formal run compares formats on 168 tasks with controls. Every extra arm costs a full pass.

Problem. The bare marker inside the thinking (p1_e2) taught the model to write its own prefetch lines, including invented results. That defect does not depend on the trigger or the task count.

Recommended: drop p1_e2. Keep p1_e1 (inline, explained), p2_e1 (after the thinking, explained), and p2_e2 (after the thinking, marker) — the two p2 arms showed no imitation because the model cannot write the sender header itself.

Decision 2 · skip what the model already knows

Scenario. The probe fires and predicts a call. In this smoke, in most tasks half or more of the insertions repeated a call that had already been run for real earlier in the same task, or had already been inserted.

Problem. Re-inserting a known result costs tokens on every step and cannot save a round trip, because the model was not going to make that call again. It also inflates the fire count that the token account is charged for.

Recommended: before inserting, check whether the predicted call already appears in this task's executed code or in an earlier insertion; if it does, do not fire at that cut. One switch in the driver, off by default, measured as its own arm. This is a change to when to insert, not to the format, so it composes with every format.

Decision 3 · measure before changing anything else

Scenario. Both services are up. A real θ makes the probe decide when to fire, which changes both how often it fires and how relevant the inserted call is.

Problem. Every other idea (shorter results, a read-only filter, letting the model continue its thought after a p2 message instead of choosing) is a guess until there is one measured comparison against the controls.

Recommended: run the three kept formats plus chat baseline and no-probe on ten dev tasks with the real probe. The two θ values on record for the served probe are 0.975 (risk 0.05) and 0.9 (risk 0.1); θ is always chosen by a person. Read the success and token numbers against the controls, then decide the next change.

Ideas held back until that measurement exists

  • Shorter results. A single inserted API doc reached 1,595 tokens. Capping the result at the length the probe was trained on would cut cost but may hide the field the model needed.
  • Read-only calls only. Every insertion runs in a rolled-back world, so a write call the model then skips never happens for real. A per-API read/write tag would let the system refuse to prefetch writes.
  • Continue instead of choose, for p2. After the prefetch message the model always restarts its reasoning. Handing it an already-open thinking block might make it continue rather than re-derive its plan. Worth one arm once the base numbers exist.
