## 1. Verdict

The fourth draft's tree names the files that a reproducible lifecycle needs (a keyed loader in schema.py, one registry, one launcher, formats in data/), but the mechanism that connects them was in the Part 2 that gyb deleted, and the tree lines do not restate it: the draft never says what enters a key, whether a key is per setting or per stage, what a stage process is told on its command line, what the output directory is called, or which check decides "finished". Walking one train_probe setting through sample -> build -> train -> eval, the only reuse/continue rule that survives on the page is trainer.py's "checkpoint and no predictions is continued", and that rule cannot tell a finished training that died in prediction from a training that died at step 40. The "edit one value, reuse upstream" promise depends on per-stage keys computed over the fields each stage reads (the third draft's stage table), while the fourth draft's own wording ("the name then points at a new key") reads as one key per setting; under that reading an lr edit resamples the agent. Version numbers now exist only on appworld.py and schema defaults, so a cut-rule edit in probe_input.py or a metric edit in eval/methods/ leaves every existing output looking finished and reused, which contradicts principle 7. Against today's ops/ the draft silently drops the dirty-tree gate, commit capture and dirty patch, RUNMETA.json, the sampler's six-way verdict with the incident agent and the one-refire quota, service pieces with port checks, and the deregistration gate; registry.py/launch.py as described cover none of them beyond "meta.json" and "refire" as bare words.

## 2. Gaps, ranked (A = mechanism cannot work as described; B = silence that will be filled inconsistently; C = naming)

A1. Key granularity is contradictory. experimental_settings/ text: "a tuning is an edited value (the name then points at a new key)", singular. Scenario 3a needs a key per stage over only the fields that stage reads, or an lr edit gives sample and build new directories too. schema.py says "the stage table" exists but its content (which sections each stage reads, which upstream, which VERSIONs, which venv, how many pieces) was deleted with Part 2. Proposal: experimental_settings/schema.py owns STAGES = {stage: sections read, upstream stage(s), versioned modules, venv, piece rule} and key(cfg, stage) hashes exactly that plus the upstream key; the draft states it in the schema.py line.

A2. What a stage process receives is unspecified, so identity can drift between launch and run. If a piece command is "run.py train_probe X --stage train" and recomputes the key from the YAML, a YAML edit after launch (or before a refire days later) sends the process to a different directory than the one registered; "refire with its original command" then starts a fresh directory instead of continuing. Exposed in scenario 2 (refire) and 7. Proposal: jobs/launch.py freezes the resolved setting as settings.yaml inside the run directory and every piece command names the run directory, never the setting name; the registry row carries the directory; refire reuses it (the third draft had `run.py <run dir>/settings.yaml`, dropped).

A3. Two writers of the start row, no owner of the finish row. launch.py: "the record's start"; registry.py: "every stage imports it to write its start and finish rows". Both write starts. A six-piece sample has no designated finisher (a piece cannot know it is last without the claim state), and a piece that dies before importing anything (venv broken, OOM at model load) leaves no row, so `ls` cannot show it failed. Today launch_common.register_all writes start after the alive check, exactly once. Proposal: jobs/launch.py writes the one start row with the piece list after the alive check; the stage writes progress into its run directory; jobs/registry.py writes finish when the last piece reports the pool empty (or run.py on the next walk when all task files are done).

A4. No "running" state, so shared keys double-launch. Scenarios 2, 4, 7: sweep children, several names on one run.py call, or two sessions all find the shared sample key "missing" and launch it; tmux refuses a duplicate session name on one host only; on two hosts two runs write one directory. launch.py's "alive check" is post-launch. Proposal: jobs/registry.py gives a row the status running with heartbeat age and session liveness; run.py refuses to launch a key whose last row is running with a fresh heartbeat and reports the session; --retry is the only way past failed.

A5. Records "appended one task at a time by many pieces" to jsonl (data/__init__.py) plus "claim tasks across pieces" (loop.py) with no claim home. A piece killed mid-write leaves a partial line that breaks every Polars read of the file; a dead piece's claimed-but-unfinished tasks are neither redone by the refired piece nor by live pieces. Today run_appworld.py shards statically and resumes by a per-task file's final record. Proposal: data/task_record.py: one file per (task, seed); claim = O_EXCL create of that file with the piece's session name as its first line; done = final record with no abort; refire in launch.py releases files whose owner session is gone.

A6. Train continuation rule is undecidable as written. "A directory with the checkpoint and no predictions is continued from that step": best/ exists both after a finished training that died during prediction and after a training that died at step 40. Today's trainer saves only best/ and refuses a second run in the same --out without --force (train_causal_share.py:1017); there is no resume path to reuse. Proposal: train/utils/trainer.py writes last/ with the step count and a train_done marker; continue rule: train_done present -> predictions only; last/ present -> resume from its step at the same commit; neither -> fresh; commit mismatch -> refuse without --retry.

A7. Eval reuse contradicts principle 7. No VERSION on eval/methods/*.py or score_run.py, so a change to how numbers are computed leaves the eval key unchanged, the finished eval is reused, and the new computation never runs. Proposal: eval/utils/probe_eval.py and eval/score_run.py always recompute (seconds by the draft's own claim) and write the git commit into report; reuse applies to GPU stages only.

B1. Version numbers cover only schema defaults and appworld.py. Scenario 3c: editing the cut rule in data/probe_input.py changes nothing; build, eval and inject outputs are stale and no file says so. The third draft folded VERSIONs of probe_input, call_syntax, build_dataset, task_record, trainer, methods, score_run into stage keys; the fourth draft's lines for those files carry none. Proposal: each of data/probe_input.py, data/build_dataset.py, data/task_record.py, agent/inject.py, train/utils/trainer.py, train/methods/*.py, eval/score_run.py carries VERSION; the STAGES table in schema.py lists which fold into which stage key; `run.py ls` flags directories whose folded VERSIONs are behind the code.

B2. The prediction run's sizing has no section. debug.yaml's "100 eval examples" and the split choice govern trainer.py's last step, which is in train. If they are `eval.*` fields, either eval fields enter the train key (scenario 3b: a risk-target edit reruns training on GPU) or one section splits across two keys. Proposal: schema.py puts them under `train.predict` (splits, cap), states that cgen/cparam prediction rows cover every example so the theta filter is CPU-side, and `eval.*` never enters train's key.

B3. Cross-setting references have no syntax and no staleness rule. eval/methods/cgen.py needs ctool's frozen theta from another setting's eval; inject.yaml must name two probe runs and a baseline; the draft's inject.yaml line says only "workflow inject, score". Nothing says what happens when the referenced training setting is edited (the name resolves to a key with no run) or how the baseline is found and checked for the same-setup rule. Proposal: schema.py: `ref: <workflow>/<setting>` or a bare key, resolved at load, the resolved key enters the referencing stage's key and meta.json; run.py refuses when the referenced run is not done; eval/score_run.py refuses a baseline whose data/models.agent/generation sections differ.

B4. Debug placement is unspecified. Whether debug.yaml is laid over before or after keying decides everything: after keying, a debug sample writes into the real sample directory and its tmux session name (stage+key) collides with a real run; before keying it is a separate directory but then "outputs/debug/, not registered" from the third draft is gone and `ls` shows debug rows beside real ones. Proposal: schema.py applies debug before keying and adds `debug: true` to the key; registry.py writes debug rows with a debug flag under `<outputs>/debug/<stage>/<key>`; a non-debug walk never considers them for reuse.

B5. Sweep expansion has no home and no addressing. Where `sweep:` expands, how children are named and keyed, how one child is named on run.py for `where`/refire, and how --debug's list replacement (`seeds: [42]`) interacts with a sweep over a list field (children collapse to one key) are all unsaid; method_table.py "groups sweep children" from registry rows whose fields are unspecified. Proposal: schema.py expands at load into children named `<setting>/<field>=<value>`, accepted by run.py as a setting name, the parent name and swept fields written into the row by registry.py; debug is applied per child and refused when it touches a swept field.

B6. Dirty-tree gate, commit capture, dirty patch, RUNMETA.json, the LEDGER_PATHS exemption: dropped without a sentence. "commit" appears only in the task record line. CLAUDE.md still makes commit-before-launch a hard rule and record.py/runmeta.py/run.py each capture commit+dirty list today. Proposal: jobs/launch.py owns the gate (one function, --allow-dirty); jobs/registry.py writes commit, dirty count, dirty file list and dirty.patch into meta.json and the start row; the gate exempts jobs/runs.jsonl, jobs/RESULTS.md, *.lock.

B7. Verdicts and escalation are dropped without saying. CONTEXT.md defines the sampler as the verdict authority ("computed by the program, never guessed by an agent"), the incident agent, the one-refire quota and the incident record; the third draft said "no monitor process and no web page" and the fourth draft keeps only "the heartbeat" and "refire" as words. Who decides dead versus suspected stall now is unstated, and the quota is gone. Proposal: jobs/registry.py `ls` computes the six-way verdict from heartbeat age and session liveness with verdicts.py's pure functions folded in, launch.py enforces one automatic refire per piece, and the sampler/incident-agent entries in CONTEXT.md are retired in the same commit; or keep a sampler and say so.

B8. Server pieces are unowned. agent_models/service.py "start or attach to the vLLM server"; who starts it, whether it is a piece with a row and a port check (today kind=service, --port required, probe_port in the sampler), and how attach verifies the same model row and generation settings are unsaid; `free` shows a busy card with no row. Proposal: launch.py registers server pieces with kind=service and port in the start row; attach only to a server whose row is running with the same table row and generation settings.

B9. Build completeness. Manifests vanished (0 mentions). A build over a half-finished sample silently yields a smaller dataset; the draft's build_dataset "gates" are unnamed. Proposal: data/build_dataset.py refuses unless every requested (task, seed) has a done record and writes the consumed file list with hashes beside the parquet; that list enters the build key in place of the manifest.

B10. Venv handoff. run.py's own interpreter and the stage-to-venv map are unsaid (sample: loop in the AppWorld venv plus service in the vLLM venv; train: probe venv; build/eval/score: any). Proposal: the STAGES table in schema.py names the venv per stage module; run.py runs under the probe venv and builds `external/<venv>/bin/python -m <module> <run dir>`.

B11. The runs.jsonl lock moves from one host to many. Today only the login-machine launcher takes jobs.json.lock; the draft has every stage process on a compute node take an fcntl lock on a file inside the git checkout over NFS. Proposal: only jobs/launch.py and run.py (login machine) append to runs.jsonl; stage processes write status into their run directory's meta.json, which `ls` folds in.

C1. The output directory rule (`<root>/<stage>/<key>`) exists only in the third draft. Proposal: constants/path_outputs.yaml holds the root and jobs/registry.py `run_dir(stage, key)` is the one function.

C2. "record" means both the task record (data/task_record.py) and the registry row ("the record's start" in launch.py). Proposal: call the registry row "row" everywhere.

C3. The human fields of today's wrap-up (`record finish --conclusion`, `gpu-jobs finish` with its alive-session refusal) have no successor; the draft should say the conclusion moves to notes/TIMELINE.md and that a finish row for a stage with a live session is refused.
