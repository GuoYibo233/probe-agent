### 1.2 Annotation stage (trajectories → dataset, pure CPU)

| Program | What it does | How to use it |
|---|---|---|
| `pipeline/annotate/rules.py` | The single source of truth for cut rules (constants + pure functions): SEED=42 (since np821; the old 20260729 only takes effect through an explicit seed field in old configs), MAX_BOUNDS=64 (the default cap on boundaries, overridable by argument since 2026-08-22), MIN_THINK=40 characters, keep 3 rounds of history, environment returns truncated to 400 characters, sentence boundary = newline or `.!?` + whitespace | Only imported, cannot run standalone |
| `pipeline/annotate/build.py` | The main builder: cuts trajectories into "thinking prefix → tool name" samples, one set per model per environment; samples carry `label_call` (the normalized full call string) and `args_named`. A unit that is in no task list → exits with code 1. Since 2026-08-22, two knobs: `weight_mode` (default uniform = w=1 per step; the old convention per_event = w=1/m only applies when given explicitly) and `max_bounds` (default 64), set via config field or CLI `--weight-mode/--max-bounds` (CLI overrides config); when the config carries `trajs_per_unit`, the report adds four extra statistics (cut-point distribution / hit-the-cap count / identical trajectories / hit at 30 steps) | `python3 run.py ann-build --config pipeline/configs/<env>_<model>.json [--weight-mode per_event --max-bounds 64]` (with the flags this is the G8 reproduction convention) |
| `pipeline/annotate/param_label.py` | Extraction-head labels: locates the character span of each argument value in the sample text via `rfind`, records found=false when not found | `python3 run.py ann-params --config <same as above>`; produces the `params/` three splits + PARAM_LABEL_REPORT.md + CHECK_50.md |
| `pipeline/annotate/check_callstr.py` | The post-hoc gate: whether the evaluation side's parse_call can cut the ground-truth call string back out unchanged, plus five hard structural checks (model filtering / primary key uniqueness / task-list membership, etc.). Since 2026-08-22, gate B's unit→traj criterion follows the config's `trajs_per_unit` (default 1 = the old criterion verbatim; when K>1, exactly K entries are required with sampling indices `_r0..r{K-1}` all present) | `python3 run.py ann-check-callstr --config <same as above>`; ⚠️ its main() imports torch (moved out of module level since 2026-08-22, the import itself no longer needs torch), running main still requires the `cprobe-env` interpreter, and `CUDA_VISIBLE_DEVICES` must be cleared, both of which the registry already handles for you |
| `pipeline/annotate/accept_v3diff.py` | The G8 reproduction acceptance checker: feeds the new code the old input, compares nine fields one by one against the old data | `python3 run.py ann-accept-v3diff` (no parameters, paths are hardcoded; ⚠️ the hardcoded old data was deleted in the clear-out, this acceptance check is only meaningful for the old phase) |
| `pipeline/configs/*.json` | Annotation configs (one per environment × model: trajectory source, task-list mode, output location; since np821 can also carry `weight_mode`/`max_bounds`/`trajs_per_unit` and the driver's `collect`/`train` sections) | passed in via `--config`; for a new batch, copy one and edit the fields |
| `pipeline/driver.py` | The resumable pipeline driver since np821: reads the batch config and `logs/pipeline/<run_family>/state.json`, advances one step per invocation (collect → annotate → train → eval → matrix, 15 steps each with its own gate), hard-blocks a launch step on a dirty tree, and turns the cut-point-cap decision into an awaiting_decision stop point. Exit codes: 0 = advanced one step / waiting on an already-launched batch / everything complete, 3 = actually launched this time, 4 = waiting on a decision, 1 = gate failed (the reason is written to the state file; the state file also records the `launched` marker and `manifest_sha1`, relaunching a dead batch requires deleting that marker first) | `python3 run.py pipeline --config pipeline/configs/np821_gptoss.json`; status only `… --status`; the state file lives in logs/ (a git-ignored area) |

### 1.3 Training stage (four cells; the launch shells live in ops/, see §3)

The four cells = backbone × head. mtool/mext use `mbert-env` (transformers 4.57.6),
ctool/cgen use `cprobe-env` (5.14.1); neither is upgraded to match the other.

| Cell | Program | What it learns | Key settings and pitfalls |
|---|---|---|---|
| mtool | `pipeline/train/train_mbert_tool.py` | ModernBERT-base + classification head: prefix → tool name | `--data <dataset> --out pipeline/runs/<batch>_<model>_mtool [--smoke] [--input-mode full/no-think/no-hist]`; weighted CE (w=1/m_i), left-truncated at 4096 keeping the tail of the thinking; produces `best/` (an HF directory) + train_log.jsonl (⚠️ append mode, rerunning the same --out appends to it); ⚠️ **a second training run on the same out is refused by default**, an existing `train_log.jsonl` under `--out` triggers a SystemExit and training does not start, `--force` is the only escape hatch, all four cells share this semantics |
| mext | `pipeline/train/train_mbert_extract.py` | ModernBERT + start/end pointer head + answerable head: which character span an argument value falls in | one instance = (sample × argument), the query string `\n[FIND] tool.argument` is appended at the end; ⚠️ the weights are a bare `best/model.pt` (a state_dict), not an HF directory |
| ctool | `pipeline/train/train_causal_tool.py` | Qwen3 backbone + linear classification head: one forward pass over the whole segment, supervision placed at every sentence boundary | `--base` is required, three tiers qwen(0.6B)/qwen17(1.7B)/qwen4(4B); **the pre-training alignment check is a hard rule** (whole-segment vs token-by-token incremental, maxdiff<tol, FAIL exits with code 2; default `--align-tol 3e-4`); 48G cards OOM often → `--grad-ckpt`; `--lora` only swaps the backbone to LoRA training (the classification head is still trained in full, see the lora_util row); the cap `--max-len` defaults to 8192 (an event whose full text exceeds the token limit is dropped whole, no longer truncated, counted into `dropped_events_train`/`dropped_events_val`); the read-position rule uses `share_data.read_position`, when a cut falls on a whitespace character between two tokens, reading crosses the cut and is assigned to the previous token; `--bs 2 --accum 4`, one update per 8 events (since 2026-08-28, decision 15: 8192 × bs 4 OOM'd on the first H100 training batch, backed off to bs 2) |
| cgen | `pipeline/train/train_causal_share.py --mode cgen` | Qwen3 backbone fine-tuning: continues writing the whole call directly (`\n[CALL] ` separator) | one forward pass per event, shared prefix; an event over the 8192 cap is dropped whole; one update per 8 events; within 1 epoch, val_ce is evaluated every quarter; `--tok-budget` controls memory usage; since 2026-08-28, optional `--gen-eval`/`--gen-eval-at` (does an extra generation pass at evaluation time, defaults to 200 rows, only at the end of the epoch), `--align-rule` (the alignment criterion abs/rel/both), `--mem-probe-pick` (how the memory probe picks blocks, tokens/cost/loop, default cost) |
| cparam | `pipeline/train/train_causal_share.py --mode cparam` | Qwen3 backbone fine-tuning: given the tool name, writes only the argument segment, input runs up to `…[CALL] tool_name(`, the target is the arguments inside the parentheses plus the closing parenthesis (stripped from `label_call` by prefix, a mismatch drops the whole entry and is counted as `assembly_mismatch`) | one forward pass per event, shared prefix; an event over the 8192 cap is dropped whole; one update per 8 events; within 1 epoch, val_ce is evaluated every quarter; `--tok-budget` controls memory usage; since 2026-08-28, optional `--gen-eval`/`--gen-eval-at` (does an extra generation pass at evaluation time, defaults to 200 rows, only at the end of the epoch), `--align-rule` (the alignment criterion abs/rel/both), `--mem-probe-pick` (how the memory probe picks blocks, tokens/cost/loop, default cost) |
| (sweep) | `pipeline/train/sweep_lr.py` | Driver and report for the learning-rate sweep: `plan` produces 12 train-cgen commands and launch lines from the GRID constant (four configs b06/b17/l17/l4, three learning-rate anchors each), `--write` saves plan.json; `report` collects train_log.jsonl from a batch of run directories into SWEEP_REPORT.json/.md | pure CPU, registered in `run.py` as `sweep-lr`; GPU launches still go through gpu-run; output in `pipeline/runs/sweep/`, does not enter the matrix, does not enter `summarize_matrix.py` (spec 16.6, ticket 11) |
| (reference) | `pipeline/train/train_causal_callgen.py`, `pipeline/train/train_causal_param.py` | Line-by-line reference implementations, used only for alignment checks and comparison, output does not enter the matrix | launched via `train-cgen-rows`/`train-cparam-rows` (the old convention of 4096, left-truncation, 3 epochs is frozen unchanged, not a word altered); `best/meta.json` has no `trainer` field, its run_id shape is the same as the active version, evaluating it would mix indistinguishably into the matrix (extending §5 #26) |
| (shared) | `pipeline/train/input_modes.py` | The single source of truth for the ablation cutters full/no-think/no-hist, training and evaluation import the same copy | eyeball check: `python3 … --data … --env … --split test` |
| (shared) | `pipeline/train/lora_util.py` | The single source of truth for the `--lora` flag family shared by the three causal cells (ctool/cgen/cparam), the seven target modules, and merge-and-save | `--lora [--lora-rank 16 --lora-alpha 32 --lora-dropout 0.05 --lora-lr 2e-4]`; the target modules are Qwen3's seven q/k/v/o/gate/up/down_proj; ⚠️ **the save contract does not change**, before saving best a deep copy is made first, then `merge_and_unload` merges the adapter back into the backbone, `best/` has the same item-for-item structure as a full-parameter save, zero changes needed in the three evaluation scripts; the deep copy is required (`merge_and_unload` strips the adapter in place, the original still needs to continue training the next round); meta.json gets one extra `"lora"` block recording the hyperparameters, absent when not enabled; peft is fully lazy-loaded (`import peft` is written only inside the function body of the `--lora` branch). ⚠️ But "not passing --lora means the process has no peft" does not hold: when peft is installed in the environment, transformers 5.14.1's `trainer_utils.py` does its own `from peft import PeftModel`, and the `get_linear_schedule_with_warmup` the three scripts import happens to go down that chain, that is transformers's own behavior and changes no numbers |
| (shared) | `pipeline/train/share_data.py` | The pure-CPU data and tokenization module shared between the new cgen/cparam trainer (`train_causal_share.py`, ticket 03) and ctool/`eval_tool.py` (ticket 02): `load_events` groups by event, computes the shared prefix `p`, assembles the target segments `seg_ids`/`seg_lab`; `pack_event`/`allowed_mask`/`batch_mask` build form A's concatenated sequence and attention mask; `chunk_by_budget`/`worst_blocks` greedily pack blocks under a token budget; `read_position` is the single source of truth for the cut-read-position rule shared by ctool/`eval_tool.py`; since 2026-08-28 adds `full_token_ids`/`n_full_tokens` (the single source of truth for tokenizing and counting an event's full text, called by the `drop-event` criterion in all three evaluation scripts), `event_full_texts` (the evaluation side takes the full text at the largest `sent_idx`, used by `--overlong drop-event`), `select_keys` (filters a batch of events by `--overlong` and the ctool exclusion rows, producing kept_keys and four counts), `epoch_minibatches` (the event ordering and logical-minibatch splitting for one epoch, the single source shared by the training loop and the `cost`/`loop` memory probes) | The module top level has only stdlib+torch, imports of `train_causal_callgen`/`train_causal_param`/`rules.MAX_BOUNDS` are all deferred inside the `load_events` function body (mbert-env's transformers 4.57.6 cannot pass the version gate at the top level of the old training scripts, while `eval_tool.py` needs to import this module under mbert-env to get `read_position`); `mbert-env/bin/python -c "import sys; sys.path.insert(0,'pipeline/train'); import share_data"` is a hard gate, must exit with code 0 |
| (demo) | `demo/prepare.py` | Builds the fixtures for the debugger demo: synthesizes small AppWorld-style data `demo/data/{train,val}.jsonl` (cuts, task text, and call strings each call the annotation stage's `rules.boundaries` / `rules.assemble` / `build.make_call`, fields match the real data field by field) + a randomly initialized two-layer Qwen3 with a real tokenizer, `demo/tiny_qwen3/`; first turns `demo/tiny_qwen3` and `demo/runs` into symlinks pointing at mirrored directories on the net drive (the hard rule: big outputs go to net, same as `pipeline/runs`); after running, loads the fixtures once itself with `build(path=)` / `share_data.load_events` / `chunk_by_budget`, printing each event's length and the block count of each logical minibatch in epoch 0 | `python3 run.py demo-prep` (pure CPU, ten seconds, tokenizer copied from NFS); to enter the debugger use the two training configs in `.vscode/launch.json` (what is being debugged is the real trainer `train_causal_share.py`, not a single word changed, relying on the two ready-made doors `--base demo/tiny_qwen3 --device cpu`); without the debugger use `demo-train --mode cgen --out demo/runs/cgen`; output `demo/runs/` goes to the net drive via symlink, does not enter the repo or the matrix; where to set breakpoints is in `demo/README.md`, reading through the trainer step by step in execution order is in `demo/WALKTHROUGH.md` |

### 1.4 Evaluation stage

| Program | What it does | How to use it |
|---|---|---|
| `pipeline/eval/eval_tool.py` | Tool-cell replay: calibrates a temperature on val, then across 20 θ points (0.5-0.975, step 0.025), picks the θ with "the largest trigger ratio subject to the precision constraint" per risk tier (0.10/0.05), and freezes the numbers on test; since 2026-08-28 `--overlong {left,skip,drop-event}` (default left, only takes effect for `--head causal`, the mbert head raises a SystemExit for anything other than left) | mbert head: `python3 run.py eval-tool-mbert --env <e> --run <run> --data <d>`; causal head: `python3 run.py eval-tool-causal …` (`--head` and the interpreter are both pinned by the registry). Both are launch-class; run.py only prints the command, launching goes through gpu-run; `--cached-logits` recomputes on pure CPU (changing θ never touches the GPU). ⚠️ logits are always written into `--run`, `--report-dir` only changes where the report goes. Smoke test `--limit N` truncates each split to the first N rows, only allowed for a `--run` whose name contains smoke (to keep truncated output from contaminating anything, the report carries a `limit` stamp; added 2026-08-21) |
| `pipeline/eval/eval_mbert_call.py` | mext trigger-time evaluation: consumes mtool's temperature and θ, extracts arguments on the trigger prefix, reports in three tiers, no-argument/choice/free-form | `python3 run.py eval-mcall --env <e> --run <mtool run> --extractor <mext run> --data <d> --risk 0.05` (launch-class); ⚠️ the report is written into `--extractor`; a null θ hard-exits with code 1 |
| `pipeline/eval/eval_causal_call.py` | cgen trigger-time evaluation: at ctool's trigger points, writes the whole call greedily, judges tool_ok/arguments/full_call_ok; since 2026-08-28 `--overlong {left,skip,drop-event}` (default left) | `python3 run.py eval-ccall --env <e> --ctool-run … --cgen-run … --data …` (launch-class); ⚠️ the report is written into `--cgen-run` |
| `pipeline/eval/eval_causal_param.py` | cparam trigger-time evaluation: at the same batch of ctool trigger points, runs two conventions, gt_tool feeds the ground-truth tool name (pure argument-filling ability), pred_tool feeds the classification head's argmax (system B's real numbers), reassembles `tool_name+"("+generated_string` and scores it with the same parse/scoring as cgen; the matrix reads only pred_tool; since 2026-08-28 `--overlong {left,skip,drop-event}` (default left) | `python3 run.py eval-cparam --env <e> --ctool-run … --cparam-run … --data …` (launch-class); ⚠️ the PARAM_REPORT is written into `--cparam-run`; meta without `param_only` is refused outright (guards against accidentally feeding it a cgen run) |
| `pipeline/eval/summarize_matrix.py` | Matrix summary: collects a table from multiple runs, a missing report is marked PENDING | `python3 run.py matrix --runs-dir pipeline/runs --out …/MATRIX_REPORT.md [--prefix …] [--models …] [--risk 0.05]`; ⚠️ N/A is displayed as PENDING, reads a single fixed risk tier, any citation must come with explanatory text |

Evaluation dependency order: the tool cell first (produces temperature and θ) → then
the argument cell. If neither tier has a solution, record N/A; never relax the
constraint or borrow another cell's trigger points.

### 1.5 Injection stage (offline injection measurement + θ sweep)

| Program | What it does | How to use it |
|---|---|---|

### 1.6 Live-run injection line (task-level evaluation)

The evaluation never judges whether a prediction is right or wrong throughout: firing
means getting the real return on the genuine world through "save state → execute →
roll back → refreeze the clock" (errors included as-is), injecting
`[SYSTEM NOTE: prefetched {call} = {result}]` (no authorization sentence),
discarding whatever overflows past the cut, and continuing generation in segments.
The design document was deleted in the clear-out; to see it, go to the git snapshot
`b1f5b9c`'s `plans/2026-08-01-live-inject-design.md`.

| Program | What it does | How to use it |
|---|---|---|
| `pipeline/inject/inject_format.py` | Injection format table (2026-09-12, METHOD.md axis 5): five named formats as plain strings — `note` (the pre-existing text, default), `p1_e1` / `p1_e2` (inside the thinking; explanation inline / once in the system prompt), `p2_e1` / `p2_e2` (close the thinking with `<|end|>`, append a message from sender `prefetch` on the analysis channel, then `<|start|>assistant`). `splice_text` gives the exact appended text, `system_extra` the system-prompt paragraph, `needs_special` whether the text carries control markers. Edit the strings here to change an arm |
| `pipeline/inject/live_appworld.py` | The driver: a full live run of a task (three arms: with probe / no probe / probe-but-nofill). `--format {note,p1_e1,p1_e2,p2_e1,p2_e2}` picks the injection format (2026-09-12; meta records `format`; `--no-probe --format <e2 arm>` = the control for that arm, same system paragraph, no injection). | `pipeline/inject/ident3_gate.py` | The ident3 pre-launch gate (stdlib): for the same set of messages, the `prompt_token_ids` the chat endpoint returns must equal `/render`'s prefix_ids id-for-id (pins down the vLLM date pin and confirms return_token_ids is in effect), a mismatch exits non-zero and `ident3_job.sh` refuses to run on that basis | `python3 run.py ident3-gate --base-url <vLLM /v1> --probe-url <render service>` |

Known convention gaps (must accompany the report): the probe's per-prefix forward pass
vs. the training side's whole-segment forward pass (tokenization boundary effects);
only the first 64 real cuts are checked; the injected content is "a single call's
return" vs. the replay line's "the whole stdout block"; the harmony date line is the
day of the live run, not the same as the control batch's collection day.
